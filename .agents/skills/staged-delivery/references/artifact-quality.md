# 产物质量标准

门禁只能检查结构与字面值，不能替你判断内容是否靠谱。以下标准用于填写产物和做评审。所有结论都应有可复核的依据。

## 通用证据要求

- 引用真实文件、命令、测试名和结果，而不是“已测试”“没问题”。
- 证据至少包含：做了什么、如何验证、结果、时间或位置。
- 不复制大段日志；保留关键失败行、命令与定位信息。
- 不把未运行的检查写成通过；不把计划写成已完成。

## 方案（plan.md）

必须：

- 用代码、配置、文档或数据说明现状，指出问题根因。
- 信息不足时先调查；需求意图、优先级、验收口径或外部约束仍不明确时，提 1-3 个高影响问题并记录答复、假设与影响。不要用提问替代可自行完成的调查。
- 区分目标与非目标，避免范围悄悄膨胀。
- 给出至少两个方案及取舍；推荐方案要回应约束。
- 验收标准可观察、可判定，能映射到测试。
- 明确通用性与扩展点：为什么不是临时补丁，未来变化在哪里接入。
- 写出失败模式、兼容性、数据/权限影响、回滚方式。
- 测试策略覆盖主路径、边界与错误路径。

反模式：只有实现步骤没有取舍；验收标准是“功能正常”；范围写成“相关优化”；把“加一个 if 特判”当方案；没有回滚。

验收标准示例：

- 弱：搜索功能正常工作。
- 强：查询包含大小写混合的关键词时返回匹配项；空查询返回 400 且不触发数据库查询；无匹配时返回空列表而不是 null。

## 方案评审（reviews/plan-review.md，独立子代理）

必须：

- 由独立子代理执行：主代理只提供产物路径、代码基线与评审清单，不提供自己的结论或倾向。
- 子代理逐项检查：目标可观察、现状与根因有据、取舍充分、设计覆盖失败与边界、通用性与扩展点明确、测试策略能先失败后通过、风险与回滚可执行。
- 验收标准逐条判定“可观察/可判定”，给出判定方式；判定不了的 AC 要回方案修改，不能靠评审放水。
- 记录子代理标识、评审范围与检查依据；结论来自子代理返回，不是主代理代写。
- 有阻塞问题时先修方案再复评，复评仍由子代理执行。

反模式：主代理自己填 PASS；把方案摘要复述一遍当评审；验收标准“看起来合理”就放行；子代理指出问题后主代理自行判断“不影响”并改写结论。

## 验收标准确认（acceptance.md，用户审批）

必须：

- 逐条列出全部验收标准，附判定方式或验证命令；用用户不需要读代码就能判断的语言。
- 提审记录写明时间、方式与用户原话或选择；用户提出修改时回到方案阶段，改完重新子代理评审、再次提审，并留变更记录。
- `确认结论: 通过` 只能在用户明确确认后填写；`advance --approve` 的审批人就是用户。
- 用户未答复时不得用假设代替确认；确需继续时按方案阶段的假设规则处理并如实标注。

反模式：把验收标准翻译成实现描述（“新增 XxxService 类”）；用户只说“嗯”就记“确认通过”；自行 `--approve`；用户提了修改意见仍按原 AC 继续。

## 任务清单（tasks.md）

必须：

- 每个任务是一个可独立交付和验证的行为单元，不是“改 A 文件”。
- 任务包含依赖、验收标准、验证方式；验收来自方案 AC。
- 依赖图无环，顺序能实际执行。
- 任务粒度适中；一个任务过大时拆分，过小时合并。
- 任务状态与证据及时更新；范围变化通过新增、取消或回退处理。

反模式：任务之间没有依赖却声称可并行；所有任务都写“跑测试”；实现任务与测试任务脱节；用取消任务隐藏未完成工作而不写原因。

## 任务评审（reviews/task-review.md）

必须：

- 建立“验收标准 → 任务 → 验证方式”的追溯关系。
- 检查粒度、依赖、顺序、可测试性与风险处理。
- 检查是否混入范围外改动、硬编码、特判或过度设计。
- 发现的问题有严重度、处理方式和状态；修复后重新检查。
- 结论来自检查过程，不是模板默认值。

反模式：未读任务就填 PASS；问题栏写“无”但没有评审依据；把“测试会覆盖”当唯一验证；忽略回滚与兼容性。

## 测试计划（test-plan.md）

必须：

- 说明测试层级与选择理由，覆盖验收、边界、错误路径和回归风险。
- 用例与任务/验收对应；输入、步骤、预期明确。
- 记录预期失败的命令、实际失败内容，以及为什么这是正确的失败。
- 说明如何运行全量与新增测试。
- 无法先写失败测试时，写明替代验证与残余风险。

反模式：测试只验证实现细节；断言过弱；为使套件变绿删测试或改断言；测试依赖执行顺序；只测快乐路径；把环境错误当红测。

## 施工记录（build-log.md）

必须：

- 任务事件由 CLI 自动追加；你补充关键决定、偏差、问题与修复。
- 每个关键决定写清背景、选择与代价。
- 偏差必须说明原因、影响范围和补偿措施。
- 问题记录症状、根因、修复与验证。
- 验证结果与证据路径可追溯；交付摘要能独立说明结果。
- 文件清单覆盖实际修改；未决事项不得隐藏。

反模式：流水账；只记录成功不记录失败；偏差写“无”但实现与方案明显不同；验证结果与证据矛盾；交付摘要只写“完成”。

## 代码评审（reviews/code-review.md，独立子代理）

必须：

- 由独立子代理执行：给子代理代码基线（提交号、`git diff --stat`、未跟踪文件）与评审清单，不给主代理的结论；主代理按子代理返回落盘。
- 基于实际 diff 与文件内容，先理解改动再下结论。
- 检查变更是否完整实现任务与验收，是否有范围外改动。
- 检查主路径、边界、异常、并发、资源释放与回归。
- 检查测试是否验证行为，是否覆盖失败路径，是否被削弱。
- 检查通用性：根因是否解决；是否有调用方特判、魔法常量、重复逻辑；抽象是否有当前需求支撑。
- 检查扩展性：同类场景的接入路径、需要改动的模块、接口稳定性与回归影响；是否存在过度抽象。
- 单独给出“通用性”和“扩展性”结论；二者任一 FAIL 即阻塞，不能用总 PASS 覆盖。
- 检查安全：输入校验、注入、权限、敏感信息、路径与命令执行。
- 记录问题严重度、位置、修复与状态；修复后复测并更新证据。
- 修复阻塞问题后重新开子代理复评修复项与回归面，并在复测记录写明复评子代理；`wf verify` 重新运行。
- 控制评审轮次：默认最多 3 轮（首轮 + 复评）；超过 3 轮仅当每一轮都发现 blocker/major 级重大问题，并在复测记录逐轮留痕；某轮只剩 minor 时修复、复测后直接收口。
- 最后才写结论；阻塞问题必须为 0；`评审方式: 独立子代理` 留痕。

严重度建议：

- `blocker`：错误结果、安全漏洞、数据损坏、核心验收未满足、测试虚假通过。
- `major`：明显边界缺陷、兼容性风险、维护性严重问题，发布前应修。
- `minor`：命名、局部可读性、非关键优化。

反模式：只写“LGTM”；主代理自评并写 `评审方式: 独立子代理`；复述 diff 而不判断；忽略测试质量；把已知阻塞问题留在“后续处理”；未复测或未复评就把结论改为 PASS；为 minor 问题反复开复评轮次。

## 通用性与扩展性（代码评审清单）

必须回答：

- 根因：本次改动解决的是共享根因，还是只让当前样例通过？
- 复用边界：哪些调用方或场景会共享这条路径？是否存在只对当前调用方生效的分支？
- 扩展路径：新增一个同类场景时，需要改几处？是否通过既有扩展点接入？
- 稳定性：接口、数据结构、配置与错误语义能否继续演进？是否引入破坏性耦合？
- 反例验证：是否用至少一个相邻输入或扩展场景验证过通用性，而不只是目标用例？

优先：

- 找到共享根因，在合适的边界修复。
- 用数据、配置或现有扩展点表达差异。
- 让新行为在多个合法输入下成立，而不是只让当前样例通过。
- 保持改动最小；抽象只有在当前需求明确需要时才引入。

避免：

- 为每个调用方增加特判分支。
- 硬编码日期、路径、ID、环境名或测试数据来绕过逻辑。
- 复制粘贴逻辑并留下不一致副本。
- 用 catch-all 异常或静默 fallback 掩盖失败。
- 为假想未来构建复杂框架。

## 评审后的动作

- 有阻塞问题：修复代码/测试，重新运行验证，更新评审与施工记录。
- 任务验收或方案需要变化：不要偷偷在代码里改语义；回退到相应阶段，更新产物并重新评审。
- 只影响记录的问题：更新文档或任务证据，保持结论与事实一致。
