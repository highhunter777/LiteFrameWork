## 检查项

1. **粒度**：每个任务对应一个"可独立验证的结构变化"（框架入口 / 段迁移 / 适配器上收 / 域垂直化 / 冒烟 / 端口 / 组合根 / 外边界 / 文档），不是"改某个文件"。通过。
2. **依赖顺序**：T1（框架 Create）→ T2（迁移，依赖 T1 的入口存在）→ T3（适配器上收，依赖 T2 的段位置）→ T4（垂直化，依赖 T3 的能力端口）→ T5（冒烟，依赖 T4 的 Battle 程序集）→ T6（端口，依赖 T5 的装配稳定）→ T7（组合根，依赖 T1–T6）→ T8（外边界，依赖 T7 的段序）→ T9（文档）。与方案批次顺序一致；无环。
3. **可测试性**：每任务都有 `--verify`（编译 0 error / 定向 L1 / `wf verify` / PlayMode 用例 / 手测记录）。守卫类任务（T2 CompositionBudget、T4 DomainBoundary）显式要求"先取红"。
4. **风险处理**：批 2 的 asmdef 合并风险由 T4 单列并含"允许表 + 硬边 case + friend 三件同批"；`.meta` 迁移风险由 T2/T4 的 `AssetDatabase.MoveAsset` 约束与 `git status` 成对核对兜住；`ComposeRoot` 时序风险由 T7 的三路径用例兜住。
5. **禁止项**：任务描述内无"加特判/临时开关/绕过守卫"；`Modules.*→App` 反向边被明确禁止（T3）。
6. **验证与验收对照**：T1–T9 的 `--verify` 与方案"测试策略"一致；T5/T8 的 `commands` 变更与"config 变更先于取红/取绿"纪律一致。
