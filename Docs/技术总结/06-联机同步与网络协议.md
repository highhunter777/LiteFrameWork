# 06 · 联机同步与网络协议

> **本章回答**：客户端与服务端之间到底传什么、为什么这样分可靠/不可靠、快照如何差分与裁剪、输入如何抗丢包、BuildHash 如何保证两端判定代码一致、重连如何恢复。
> **上游权威**：[状态同步专项设计](../设计文档/网络/状态同步专项设计.md)（协议/快照/和解）、[联机同步残差收敛专项设计](../设计文档/网络/联机同步残差收敛专项设计.md)（残差与背压）。字段全表见 [12-联机全栈参考](../项目说明/12-联机全栈参考.md)。
> **口径**：2026-10-22 工作区；协议单源 `Assets/LiteNet/Core/Proto/battle.proto`，生成物 `Proto/Generated/Battle.cs`。

## 1. 分层：协议、打包、传输各司其职

```text
battle.proto（单源）
   └─ Proto/Generated/Battle.cs（生成物，勿手改）
        └─ Protocol/：PacketCodec（信封）、InputPacker（输入位打包）、
             SnapshotDiffer/Codec/Reassembler（差分/编解码/重组）、
             AoiFilter、CombatEventCodec、WireBudget（载荷预算）
                └─ Transport/：IClientTransport / IRoomTransport 窄端口
                     └─ KcpTransportClient/Server + Vendor/kcp2k
```

- **信封**：`[1B PacketType][protobuf 载荷]`，`PacketCodec` 是纯函数、零 IO；坏包/未知类型/截断返回 false，不抛异常。
- **协议单源**：服务端不可能另写一套消息结构——它引用 `LiteNet` 同一个 csproj/asmdef。
- **BuildHash 覆盖**：`Proto`、`Protocol`、`Transport/Security` 均在闭包内；改线格式必然改哈希，Join 握手会拒绝两端不一致的组合。

## 2. `PacketType` 全表与可靠/不可靠分工

| 值 | 类型 | 方向 | 通道 |
|---|---|---|---|
| 0 | `None` | —— | 过滤随机噪声（不响应 0x00） |
| 1 / 2 | `Join` / `JoinAck` | C→S / S→C | Reliable |
| 3 | `StartGame` | S→C | Reliable |
| 4 | `Input` | C→S | **Unreliable** |
| 5 | `StateSnapshot` | S→C | **Unreliable** |
| 6 | `MismatchReport` | C→S | **Unreliable** |
| 8 | `Leave` | C→S | Reliable |
| 9 / 10 | `ReconnectRequest` / `ReconnectResponse` | C↔S | Reliable |
| 11 | `RestoreComplete` | C→S | Reliable |
| 12 | `MatchEnded` | S→C | Reliable |
| 13 / 14 | `StartMatchRequest` / `StartMatchResponse` | C→S / S→C | Reliable |
| 15 | `OwnerChanged` | S→C | Reliable |
| 16 | `Heartbeat` | 双向 | **Unreliable**（应用层 RTT/丢包观测，不参与保活） |
| 17 | `RoomSeats` | S→C | Reliable（房间页玩家列表） |
| 18 | `CombatEvents` | S→C | **Unreliable**（公共战斗事件独立包） |

> 7 号已退役、保号不重用。**信令走可靠、状态与事件走不可靠**是硬分工：可靠通道上的重传会放大延迟，状态面宁可丢一帧也不能排队。

**为什么 `CombatEvents` 要独立成包**：历史上命中/击杀/开火三个窗口塞在 `StateSnapshot.match` 里随每份快照全量携带，实测把快照顶到 **1531B**，超过 KCP 不可靠上限 **1194B**，整份快照被 kcp2k 静默丢弃——表现是"打一会儿双方不同步"。独立后状态面尺寸只随实体数变，事件面有自己的预算与降级阶梯，互不挤占。

## 3. 上行输入：16 帧冗余 + 快照锚

客户端不是"每帧发一个输入包"，而是发送**未确认段的冗余窗口**：

- `MaxRedundancy = 16`：包内 `frames[0]` 是当前帧，往回连续历史；
- **窗口下界 = `LastSnapshotFrame + 1`**：只重发服务端可能还没见过的帧，不浪费带宽；
- **上界 = 环内连续可用帧数**：一旦跳帧就断开，不用陈旧帧冒充连续；
- `ack_snapshot` = 客户端收到的最新快照帧；
- 服务端据此知道"客户端已经确认到哪一帧"，输入闸门按帧预存、去重、校验边界。

**viewFrame 的口径**：`viewFrame = SimView.RenderFrame`（jitter buffer 正在渲染的那一帧），不是"最新快照帧 + 插值"的近似值。服务端以它作为回溯补偿的目标帧，并 clamp `[当前-16, 当前]`。这样"玩家看到的过去"就是命中裁判，而不是客户端自称的延迟。

客户端每个渲染帧的驱动次序固定为：**网络泵 → 输入上行 → 本地服步进（若启用）→ 预测推进 → 追帧补发 → 视图**；上行提前 `InputLeadFrames=3` 帧，追帧时多出的逻辑帧逐帧各发一包。

## 4. 快照链：30Hz、差分、AOI、背压、预算

### 4.1 节拍与差分

- 30Hz 下发（`stride = TickRate/SnapshotHz = 2`）；广播序号先自增再取模，**首帧不广播**。
- 差分基线是轻量摘要 `EntitySnapshotEntry`（公共字段 + 开火窗 + 尸体期 + 主动作摘要 + 帧号/Rng/位图），不含私有面/Globals/CustomData；float 按位比较。
- **全量帧触发**：`forceFull` ∪ 活体位图变化 ∪ 60 帧到期 ∪ ack 落后 30 帧 ∪ Globals/CustomData/Rng 脏。关键状态（如死亡/复活）在 60 帧内粘滞重复下发，抗丢包。
- **全量帧不裁 AOI**——"缺席判死"的语义（全量帧里没有的槽位视为死亡）以此为前提下发。

### 4.2 AOI：只裁增量

- `radius <= 0` 关闭；默认格边 10m、半径 30m、栅格覆盖 ±640m。
- 邻域取视点格 ±`ceil(r/cell)` 整格——**可以多发半格，永不漏发**。
- 网格外按 XZ 距离兜底，并计 `OutsideCount`；结果升序（确定性）。
- **只裁增量帧**：全量帧是权威全貌，不能被 AOI 裁剪，否则客户端会误判缺席实体死亡（历史事故）。

### 4.3 重组

`SnapshotReassembler` 是**持久镜像**语义：全量帧清位图与全部运行态数组（缺席 = 死），增量只覆盖指到的槽位；帧头与分配器版本先于私有面应用；未和解时仍刷新 Match 与私有面；只接受严格新帧。

### 4.4 背压三档

| 档 | 动作 | 触发 |
|---|---|---|
| 1 | 抽帧（stride 2） | 发送队列积压 |
| 2 | AOI 半径收到 15m | 继续积压 |
| 3 | 只保留最近 50% 实体 | 严重积压 |

队列上限 4096B；回落到 40% 以下且持稳 2000ms 才升档（防抖动）。背压的目标是**降级而不是拖垮房间**。

### 4.5 载荷预算：1158B 的由来

不可靠上限 = `KcpPeer.UnreliableMaxMessageSize(MTU)`；proto 预算 = `1194 − 35 − 1 = 1158B`（`WireBudget` 单源）。发送前判预算：

1. 超预算先裁最远一半实体；
2. 仍超则**诚实放弃**并计 `SnapshotDropped`（宁可丢一帧，不冒险让 KCP 静默丢整包）。

事件批按预算**留新弃旧**。这套预算是"快照 1531B 事故"的直接产物。

## 5. 和解锚点：全量走全图，增量走部分

`RollbackSim` 收到快照时按全量/增量走不同锚点：

| 快照 | 比较 | 不一致时 |
|---|---|---|
| 全量 | 公共 checksum（整帧） | 权威整帧覆盖 + 重放本地历史 |
| 增量 | `visible + match` checksum 短路 | 逐槽 `SlotDelta.checksum` 定位差异，只写差异槽 |
| 超前/环外 | —— | 权威整帧覆盖续跑 |

这正是 AOI 不会制造"每快照误和解"的原因：增量快照本来就不含全图，不能用全图 checksum 比较。重放终点截到 `MaxPredictionLead=6`，保证本地帧号不会越过输入冗余窗口。

## 6. KCP 与安全信封

- **KCP 全默认**：`config ?? new KcpConfig()`，生产装配不覆盖；默认 `NoDelay=true`、`Interval=10ms`、`FastResend=0`、拥塞窗口关闭、收发缓冲 7MiB、`DualMode=true`。项目没有自定义 KCP 参数——这是"先稳定、后调优"的选择。
- **安全信封**：magic `"LSE1"` + `Version=1` + kind 的 6B 头；ClientHello 38B / ServerHello 102B / ClientFinish 38B；数据帧 = 19B 头 + 密文 + 16B tag；序号从 1 起，19B 头进 AAD。
- **密钥**：PSK 强制 32B（AES-256-GCM）；信封载荷上限缺省 64KiB（1B..1MiB 可配）；信封源集在 BuildHash 闭包内——改密文帧形状/握手版本即两端 wire 不兼容。
- **重连**：一次性票据，TTL 300s、容量 256、16B 熵；客户端 10s 超时；`JoinAck.reconnect_token` / `reconnect_window_seconds`；`RestoreComplete` 后才回 `Connected`（避免"恢复了但状态没对齐"）。

## 7. BuildHash：两端判定代码的同一性

| 项 | 内容 |
|---|---|
| 覆盖 | `LiteSim/{Scripts,Systems}`、`LiteNet/{Proto,Protocol,Transport/Security}`、`GameData/Generated`（Luban 读码面）、源链接共编件（`SimConfigMapper.cs`/`TableLayout.cs`） |
| 算法 | 相对路径 Ordinal 排序 → `路径\0内容`（CRLF/CR→LF 归一）→ SHA-256 → 前 16 个十六进制字符 |
| 当前值 | `459a3145904693b7`（`Assets/LiteNet/Core/Protocol/BuildHash.g.cs`） |
| 生成 | `python scripts/codegen/gen-build-hash.py`（一次写共享源集 + Meta 构建身份两个常量） |
| 守卫 | 出包门禁 `--check-shared`；Meta 发布前 `--check` |
| 握手 | `JoinRequest.build_hash` 不等则拒绝进房 |

**表数值已移出闭包**：`Assets/GameData/Config/*.bytes` 的数值改动不触发 BuildHash，而由运行期摘要 `CombatConfigDigest` 守——客户端装载后复算 `StartGame.ConfigHash`，不等拒局。这样表值可以两端热更不出包。

## 8. 重连与会话状态

客户端 `RoomClient` 状态机：`Idle → Connected → SuspectedLost → Reconnecting → Restoring → Connected`，失败进 `Failed`。重连时：

1. 用票据发 `ReconnectRequest`；
2. 收到 `ReconnectResponse` 后进入 `Restoring`；
3. 服务端补发全量快照/座位/比赛状态；
4. 客户端对齐后发 `RestoreComplete`，服务端放行 `Restoring → Active`。

版本确认会比较 `seed/configHash/buildHash`；快照只收严格新帧，避免重连后旧包把状态拉回去。

## 9. 边界、坑与文档冲突

1. **KCP 全默认**：没有针对弱网/移动端调参；`FastResend=0`、拥塞窗口关闭意味着丢包恢复主要靠冗余与快照全量，弱网表现仍是待验证面。
2. **预算只记账不裁决**：实体很多或全量帧超预算时，`SnapshotDropped` 会计数，但不会自动改变房间容量/策略。
3. **`InputMessage.frames` 注释写 ≤4 帧，实际冗余 16**（proto 注释滞后，以 `InputPacker.MaxRedundancy=16` 为准）。
4. **文档字段滞后**：`12-联机全栈参考` 仍列 `recent_kills/fires/hits` 与旧 checksum 常量 `3dc63e3e05b792b8`；实际已由 `CombatEvents` 独立包 + `visible/match_checksum` 取代，当前哈希为 `459a3145904693b7`。
5. **`battle.proto` 的 `AimX/AimZ` 已 reserved**（4/5/10），瞄准改为 `aim_point`（11-13 浮点）；`状态同步专项设计` 仍列旧字段。
6. **票据注释漂移**：`JoinTicketFormat` 类注释仍写 v3/15 段，实际 v4/16 段。
7. **无自定义 MTU/分片策略**：MTU 走 kcp2k 默认，分片/重组由 KCP 负责；大快照靠差分与预算规避。

## 10. 本章要点

- 联机层的核心不是"发得快"，而是**把不可靠的东西做得可恢复**：输入冗余、快照差分、全量兜底、AOI 只裁增量、预算超限诚实丢弃。
- 两条锚点必须分清：**全量快照用全图 checksum，增量快照用 visible/match + 逐槽 checksum**；混用会造成每帧误和解。
- 事件面独立成包是血泪教训：状态面与事件面必须解耦预算，否则一次字段膨胀就能让整条状态流静默中断。
- BuildHash 是"两端同一份判定代码"的硬约束；表数值走运行期摘要，两者分工不要混。
