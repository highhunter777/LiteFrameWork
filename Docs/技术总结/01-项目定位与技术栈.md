# 01 · 项目定位与技术栈

> **本章回答**：这个仓库到底是什么、为什么长成"框架 + 游戏"两副面孔、由哪几块组成、用了什么技术、规模与现状如何。
> **上游权威**：组成与边界细节见 [项目说明/01-项目总览](../项目说明/01-项目总览.md)；关口状态见 [待办总览](../待办总览.md)；本章只做技术总结视角的收敛。
> **口径**：2026-10-22 工作区代码；规模数字为当日统计快照。

## 1. 一句话定位

这是一个 **Unity 2022.3 客户端 + .NET 8 服务端**的自研游戏工程，同时承担两个身份：

1. **商业级通用框架**：客户端 C0～C5、服务端 R0～R4，解决 Host 生命周期、依赖注入、作用域与租约、内容事务、UI 运行时、热更、测试门禁等"与玩法无关"的能力；
2. **确定性联机射击 Demo**：以 G0～G6 关口推进的第一个真实业务，用来证明框架"跑得动、验得过"，而不是"接口齐全"。

这两副面孔不是拼盘：**框架的能力边界由 Demo 的真实需求倒逼**（例如回滚和解逼出确定性数学与双端共编，热更逼出租约与激活事务），**Demo 的每个机制又必须通过框架提供的装配、时钟、内容与门禁落地**。理解这一点，才能理解仓库里大量"看起来过度设计"的结构。

## 3. 技术栈

### 3.1 运行时与引擎

| 项 | 版本 / 选择 | 用途与说明 |
|---|---|---|
| Unity | **2022.3.55f1c1**（中国版，含 revision `06b99830297d`） | 客户端编辑器与 Player |
| 渲染 | **URP 14.0.11** + ShaderGraph 14.0.11 + PostProcessing 3.4.0 | 固定斜视角/TPS 越肩画面 |
| 动画/相机 | Cinemachine 2.10.7、Timeline 1.7.6、Animator + Playable | 相机档位、过场、层次动画机 |
| UI | uGUI 1.0.0 + TextMeshPro 3.0.7 | 页面/控件模板 + 代码生成绑定 |
| 输入 | Input System 1.11.2 | 设备源统一键鼠/触屏 |
| 序列化 | Newtonsoft.Json 3.2.1（UPM） | 配置/存档/Meta 投影 |
| 脚本 | **XLua**（vendored） | UI 页面逻辑与热更脚本 |
| 资源 | **YooAsset 3.0.5**（内嵌 UPM） | 资源包、内置/候选包、租约底层 |
| 配置 | **Luban 1.2.0**（内嵌 UPM） | 表源 → 双端二进制 + 读取代码 |
| 测试 | Unity Test Framework 1.1.33 + ext.nunit 1.0.6；xUnit 2.9.2 / Test.Sdk 17.11.1（net8.0） | EditMode/PlayMode 与 dotnet 双轨 |
| 编辑器通道 | `com.unity.pipeline` 0.7.0-exp.1 | Unity ↔ CLI，L2 门禁/自动化 |

### 3.2 服务端与基础设施

| 项 | 版本 / 选择 | 说明 |
|---|---|---|
| 运行时 | **.NET 8**（net8.0） | RoomServer / MetaServer 自包含发布（win-x64） |
| 传输 | **kcp2k V1.41**（vendored） | 可靠有序 + 不可靠通道，UDP 之上 |
| 协议 | **Google.Protobuf 3.36.1** + `battle.proto` 单源 | 生成 C#，两端共用 |
| Meta 宿主 | ASP.NET Core（FrameworkReference，零 Web NuGet） | `/live` `/ready` `/metrics` + HTTP 端点 |
| 持久化 | **MongoDB.Driver 3.12.0**，副本集 rs0 | 结算账本、Outbox、迁移（唯一真 NuGet） |
| 云侧网络 | WireGuard 隧道（`10.8.0.1`） | 运维 SSH、Meta/Room/GM 只绑隧道地址 |
| 工具脚本 | Python 3（`scripts/` 全量 Python，2026-10-21 起） | 门禁、生成、构建、部署、内容候选 |

### 3.3 关键第三方与"为什么是它"

- **UniTask**：框架唯一的异步底座，`LiteFramework.Async` 因此单独成程序集，保证 `Core` 零第三方、零引擎依赖。
- **YooAsset**：提供"内置包 / 离线包 / 联机候选包"三态与引用计数；项目在其上再包一层 `AssetLease` 与代次校验，避免直接暴露第三方 API。
- **Luban**：表源（xlsx）一次生成两端读取代码与 `.bytes`，是"双端同读一份数据"的基础。
- **kcp2k + Protobuf**：快照走不可靠、信令走可靠；协议单源在 `battle.proto`，服务端不可能另写一套消息结构。
- **XLua**：UI 页面逻辑热更；但通过 `LuaBehaviourAdapter` 与白名单门面收窄，不允许脚本触碰判定与网络底层。

## 5. 工程化的四个特征

1. **双轨共编**：`LiteFramework.Core/Async`、`LiteSim.Core`、`LiteNet`、`RoomServer.Runtime/Application.Runtime`、`LiteTesting.Core`、`DisciplineScanner` 同时被 Unity asmdef 与 dotnet csproj 编译。收益是"同一份判定代码在客户端、服务端、dotnet 单测里逐位一致"；代价是必须维护 asmdef/csproj 两套引用与产物重定向（`.dotnet/`）。
2. **生成物单源**：协议来自 `.proto`，表来自 Luban，BuildHash 来自源集摘要，UI 绑定来自 prefab 扫描。生成器统一收在 `scripts/codegen/toolbox.py`，改源不重生成会被门禁或运行时摘要拦下。
3. **规范门禁化**：确定性（禁超越函数/FMA/float 等值）、纯化（房间内核禁 IO/时钟/proto）、适配器边界、UI 视觉单一来源等，都不靠评审记忆，而由 `DisciplineScanner`（R1～R13）与专项扫描器在 L1/L2 打红。
4. **文档即基础设施**：设计文档裁决目标、施工进度保存证据、待办总览管关口、代码地图管定位；文档本身也有门禁（索引孤儿、链接/锚失效、设计与进度混写）。

## 6. 现在做到哪（只给结论，证据见第 11 章）

- **框架先行准入已达成**（2026-10-04，桌面先行口径）：五样例成链、内容事务/热更/持久化接缝/Meta 票据等前置件清零；Android 热更真机矩阵因无设备挂起，随 G4 登记。
- **当前主关口是 G2 正式联机业务切片**：从"能联机"走向"有完整玩法与产品入口"（登录/大厅/结算、HUD、8 人基线、动作余部）。
- **明确未闭合**：L4 真机/性能基线、真云 CDN 与 Android 真机、断点续传/写盘中断矩阵、部分"已实现未接线"件（详见第 11 章）。

## 7. 本章要点

- 项目本质是**用 Demo 反证框架**：所有"通用能力"都能在一条真实对局链上找到消费者。
- 技术选型围绕**确定性、双端一致、可回滚**三个约束展开，而不是追求最新版本。
- 规模不大（约 8 万行自研代码），但**机制密度高**：52 个程序集、13 条纪律规则、5 层验证、4 类生成器，理解成本主要在机制之间的关系。
