# 08 · 内容、热更与资源管线

> **本章回答**：配置表与资源如何从源变成运行时可用的内容、热更如何做到"可验证、可回滚"、签名与摘要各守什么、资源收集目录如何组织、候选包如何产出与发布。
> **上游权威**：[热更与内容发布专项设计](../设计文档/客户端/内容/热更与内容发布专项设计.md)、[资源收集目录专项设计](../设计文档/客户端/内容/资源收集目录专项设计.md)。本章按代码事实重写。
> **口径**：2026-10-22 工作区；工作区有在途改动（样例①标记素材退役、`BundleCollectorSetting` 删 `ShareResource` 组、入口探针改真实实体 prefab）。

## 1. 三条独立的事实链

内容正确性不是一个开关，而是三条互不替代的链：

```text
代码一致性  → BuildHash（共享源集摘要）→ Join 握手
数据一致性  → CombatConfigDigest（判定面表字节 + 本局规则）→ StartGame.ConfigHash
内容可信性  → 清单签名（描述）+ 逐文件摘要（字节）→ 候选校验 + 激活事务
```

- **代码**：改 Sim/协议/内核/生成读码面 ⇒ 必须重跑 `gen-build-hash.py`，否则两端判定代码不同。
- **数据**：表**数值**可以两端热更、不出包；客户端装载后复算 `ConfigHash`，不等拒局。
- **内容**：签名只保"清单描述没被篡改"，摘要只保"文件字节与清单一致"；两者都过才允许激活。

把三者混为一谈，就会出现"签名过了就以为内容对"或"哈希没变就以为表没改"的误判。

## 2. 内容访问模型：租约 + 代次 + 共享加载

### 2.1 端口与租约

`IContentService`（`LiteFramework.Async`）是内容访问唯一入口：

- `AcquireAsync(location, type)` 返回 `AssetLease<T>`（带引用计数）；
- 租约 `Dispose` 幂等、只首次回调；计数归 Host，末位释放才允许卸载底层；
- 取消必须贯穿，且不留半截状态。

`AssetLease<T>` 落在 `Core`（零引擎依赖），因此 L1 可以直接测租约语义。

### 2.2 代次是缓存键的一部分

`ContentGeneration`＝`(ReleaseId, 单调 Value)`，默认 `("builtin", 0)`。加载/缓存键包含代次，所以：

- 旧代次的租约继续有效，不会被热更"抽走"；
- 新获取走新代次，自然命中新内容；
- 不需要"全局卸载再重载"这种会打断对局的操作。

### 2.3 共享加载的三条边界

`SharedLoadCoordinator` 处理"同一 location 并发请求"：

| 场景 | 行为 |
|---|---|
| 同键并发 | 只加载一次，等待者共享结果 |
| 等待者取消 | 只退本人；全员退出才弃置并尽力取消底层 |
| **迟到结果** | 就地卸载，**不发出租约**（避免"没人要的资产泄漏"） |
| 引用归零 | 卸载恰好一次 |

### 2.4 YooAsset 适配

`YooAssetContentService` 把 `(代次, location, Type)` 映射为 YooAsset 句柄；类型不符先归还句柄再抛（不留半截引用）；`Advise` 推进代次，已持有租约不受影响。

`PrefabLeaseCache` 是另一种语义：同 location 共享一份租约、常驻到 `ReleaseAll`，按 location 归零卸载尚未实现——它适合"页面级复用"，不适合"临时对象"。

## 3. 配置表：从 xlsx 到两端同一份字节

```text
Luban/Data/#*.xlsx + Map/*.json
  → Luban/gen.bat → scripts/codegen/gen_luban.py
      ├─ Assets/GameData/Generated/*.cs      （读码面，进 BuildHash）
      ├─ Assets/GameData/Config/{域}/*.bytes （表数据，两端同读）
      └─ Lua Cfg + LuaKeys                   （脚本侧常量）
```

- **布局单源**：`TableLayout.Files` 决定表→域目录映射；`JudgmentDomains`（Combat/Movement/Entity/Item）整表进运行期摘要，UI/Content/Strategy/Animation 属单端热更面。
- **实测规模**：12 张表、9 个域（Combat×2、Movement、Entity、Item、Map、UI×3、Content、Strategy、Animation）。
- **装载**：`ConfigService.LoadAsync` 预取字节 → `new Tables` → `Publish` → `GameplayDigestBase` → 回填 Combat/Movement/Weapon/Animation → 对外可见；校验闸门在发布前跑（含 `tbweapon`/`tbcrosshair`/`tbanimationprofile` 行校验）。
- **原子发布**：`ConfigSnapshotService` 先 validate 再 lock 替换，版本单调 +1；失败抛且 `Current` 不动——不会出现"半张新表"。
- **两端共读**：客户端经租约取字节，服务端直读同一份 `.bytes`（`ServerTableLoader`），`TableLayout`/`SimConfigMapper` 源链接共编。

## 4. 资源组织：三层目录 + 10 个收集组

### 4.1 三层目录模型

| 层 | 位置 | 规则 |
|---|---|---|
| L1 原始资源层 | `Assets/` 顶层（如 `Assets/Synty`） | 只作来源，不被产品直接引用 |
| L2 模块资源层 | 模块目录内（如 `Assets/LiteGame/Lua`） | 模块聚合，可带收集 tag |
| L3 共享资源层 | `Assets/ShareResource/{类别}` | 跨模块共享的进包资源 |

产品资产必须引用"复制进收集目录后的那份"，不能直接引用第三方原始库；第三方付费资源的复制件同样不入库（随打包机本地还原）。

### 4.2 收集组（当前 10 组）

`Assets/BundleCollectorSetting.asset`：`Scenes`、`Config`、`Lua`、`UIScreens`、`UIWidgets`、`Fonts`、`Characters`、`FX`、`Sound`、`UIHud`。

- AddressRule 全 `AddressByFileName`；PackRule 多为 `PackDirectory`（`UIScreens`、`UIHud` 为 `PackSeparately`）；`UniqueBundleName=1`。
- `Config` 按域成包：改一域只重发该域，不必整包重打。
- tag 只有 `lua`/`ui`；唯一生产消费是 `ListAssetPathsByTag("lua")`（Lua 预载）。
- 工作区已删除 `ShareResource` 组与 `SampleContent`（样例①退役的一部分），与设计文档的"9 组"记载不一致。

## 5. 热更事务：薄编排 + 阶段状态机 + 激活记录

### 5.1 分工

| 件 | 角色 |
|---|---|
| `ProcedurePatch` | 主链：调编排、失败进 Error、无候选退化、资源包初始化、入口探针 |
| `PatchRunner` | **薄编排**：取候选 → 无候选也走一次恢复 → 信任门 → 生效窗口 → 交给协调器 |
| `PatchCoordinator` | **真正的阶段状态机**：10 个 `PatchPhase` |
| `ActivationTransactionStore` | 激活记录：三态、事务 ID、恢复、完整性盖章 |

### 5.2 10 个阶段

```text
Idle → Recovering → PrecheckingSpace → Fetching → Verifying
     → PendingActivation → Activating → HealthChecking → Confirmed
                                   └──────────────→ Failed
```

关键顺序不变量：

1. **`BeginCandidate` 先于下载**：先把事务写盘，再开始拉文件；中途崩溃可识别"有一个未完成候选"。
2. **`MarkPendingActivation` 先于激活**：激活前落盘，崩溃后可判断"是否已切过"。
3. **`Confirm + Advise` 最后**：健康检查通过才推进代次、清理 Pending。

### 5.3 失败与恢复

- 失败收尾：先留档再重建；只有 **HealthChecking 失败** 才 `RebuildConfirmedAsync`（Shutdown + Initialize），其它阶段失败保留 Confirmed。
- `ActivationTransactionStore`：`MaxRecoveryAttempts=3`；启动时 `RecoverOnStartup` 发现在途即回退 Confirmed，超限放弃并留档；每次写盘 `RecordSequence++` + 完整性盖章，用于识别旧记录/回填。
- 恢复语义是**放弃在途、以 Confirmed 继续**（远程重取尚未接线）。

### 5.4 记录 IO

`FileActivationRecordIO`：缺文件/解析失败/结构版本≠1/完整性不符 → 返回 null（回 builtin）；Save 走 `FileSystem.WriteJson`。注意 `ActivationRecord.ConfirmedRevision` **未并入完整性摘要**——反回退只提高门槛，不是安全边界。

## 6. 信任与签名：两门分离

| 门 | 时机 | 保什么 | 失败 |
|---|---|---|---|
| **签名**（RSA-2048 + PKCS#1 v1.5 + SHA-256） | 下载**前**验清单 | 清单描述（版本、条目、摘要、平台） | `UnknownOrRevokedKey`/签名不符 → 拒候选 |
| **摘要**（逐文件 SHA-256） | 下载**后** | 文件字节与清单一致 | 长度/摘要/多余文件/重复路径 → 拒候选 |

- 公钥来源：编入应用本体的锚表 `ContentTrustAnchors`（1 条 `release-key-2026-09-26`，e=65537）；`TrustedKeyStore` 未登记/已撤销 → null → fail-closed。
- 私钥：签名机用户目录 `~/.unitylib-content-signing/...xml`，仓库外、绝不入包；签发后用内置锚点 modulus 自校验。
- 反回退：`Revision < confirmedRevision` 拒，基线取 `ActivationRecord.ConfirmedRevision`。
- 校验顺序：结构 → releaseId → 路径/预算 → 条目 → 过期 → 撤销 → **签名 → 反回退** → 平台 → 兼容。
- 生效窗口：仅 `NextLaunch` 可用（`ValidateEffectWindow`）；`SafeWindow`/`NextMatch` 与 LiveRefresh 未实现。

**Lua 候选沙箱**：独立 `LuaEnv` + 每脚本新建 fenv，回收 `CS/io/os/debug/load*`，白名单 SafeGlobals；受限 `require` 只认本批集合、遇环即拒。边界自述：无 debug 加固、无指令计数/超时——沙箱防误用，不防恶意脚本。

## 7. 候选包工具链

| 脚本 | 输入 | 输出 |
|---|---|---|
| `gen-candidate.py` | `--content-dir`（只收 `config/**`、`lua/**.lua`、`bundle/**`）+ 私钥 + 锚表 | 紧凑 JSON 清单 + RSA 签名信封（`{"manifest":…,"signature":base64}`） |
| `publish-candidate.py` | 内容目录 + `--cdn-root`（缺省读 `local-cdn.json`）+ 可选 `--bundle-source` | `{cdn}/{releaseId}/**`、bundle 段镜像、`{cdn}/candidate.json` |
| `serve-cdn.py` | 同一配置 | 本地 HTTP 服务（Ctrl+C/130 视为正常停止） |
| `_local_cdn.py` | `LocalCDN/local-cdn.json` | 配置装载（`127.0.0.1:18090`） |

**内置包**：`build-player.py` → `BuiltinBundleBuildInvoker` → SBP 构建 DefaultPackage → `ClearAndCopyAll` 到 `StreamingAssets/yoo`，版本 `1.0-yyyyMMddHHmmss`。

**候选包**：编辑器工具 `content.bundle-candidate`（`RunForCandidate`，不覆盖内置）→ 反射补生成 `BuiltinCatalog.bytes` → 再经 `publish-candidate --bundle-source` 打成 `bundle/`。

**运行时包根二选一**：空 = `StreamingAssets/yoo` 内置包；非空 = 已确认候选的 `content/candidate/bundle` 绝对路径。判定要两条同时成立（ReleaseId≠builtin 且 `<包根>/<包名>.version` 存在），缺一退回内置（fail-safe）。

## 8. 现状：已兑现、未接线、未验证

**已兑现（有证据）**：

- 候选校验内核、编排、主链、Lua 沙箱、反回退、真实 HTTP 下载、CDN 双通道、两版本对照。
- 真实资产包段（2026-10-03 Windows Player：候选包根初始化 + `entry-assets checked=1`）。
- 样例①失败矩阵（2026-10-04）。

**健康确认实际装配**：编排内挂 `candidate-config` + `lua-scripts`；`entry-assets` 由 `ProcedurePatch` 在包初始化后单独执行（不是"只挂了 AssetsHealthProbe"）。

**未接线**：

- `CandidateEntryFilesHealthProbe`：仅定义无实例化。
- `BridgeCapabilityHealthProbe`：无装配点。
- `BuiltinBundleBuildInvoker.RunCandidateAsync`：无脚本调用者。

**未实现/未验证**：

- **断点续传**：`HttpCandidateFetcher` 失败仍从 0 重下（无 Range 续取）。
- **真云 CDN**、移动端磁盘余量、Android IL2CPP 密码学后端。
- **掉电/杀进程矩阵**：`File.Replace` 的 fsync 行为未覆盖；`HttpCandidateFetcher` 的"原子提交"实际是 temp 写完→读回→再写 target，不是 rename。
- 运行态重发布/Release 归属/对局固定快照；`SafeWindow`/`NextMatch` 激活。

## 9. 文档与代码的已知冲突

| 文档 | 说法 | 代码事实 |

| 热更专项 / 框架先行记录 | `scripts/content/*.ps1` | 只有 `.py`（2026-10-21 全量 Python 迁移） |
| 热更专项 | 健康确认只挂 `AssetsHealthProbe` | 协调器挂 `candidate-config` + `lua-scripts`，`entry-assets` 二期单独执行 |

这些差异不影响机制理解，但做热更/资源改动时必须以代码与 `TableLayout`/`BundleCollectorSetting` 为准。

## 10. 本章要点

- 热更的可靠性来自**顺序不变量 + 每步持久化 + 有界恢复**，而不是"下载成功就切换"。
- 签名与摘要必须分开看：签名保描述、摘要保字节；任何一门缺失都不可激活。
- 代次让"旧租约不失效、新获取走新代次"成立，是热更不能打断对局的关键。
- 当前最大的未验证面不是"能不能更"，而是**断点/掉电/移动端/真云 CDN** 这些真实故障面。
