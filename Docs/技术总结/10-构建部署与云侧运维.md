# 10 · 构建、部署与云侧运维

> **本章回答**：客户端怎么从源码变成一个可启动的 Player、服务端怎么发布到 Windows 云主机、云上如何托管与观测、联机测试如何从"改完代码"走到"打完一局"。
> **上游手册**：[10-Windows云主机部署](../项目说明/10-Windows云主机部署.md)（现行形态）、[11-联机测试流程](../项目说明/11-联机测试流程.md)（主线）、[云侧速查](../开发导航/云侧速查.md)（命令）。本章按技术总结口径收敛，不复制全部命令。
> **口径**：2026-10-22；`Server/`、`scripts/deploy/`、`deploy/`、`BuildProfiles/` 当时无未提交改动，事实与 HEAD 一致。

## 1. 客户端构建：一条带判据的流水线

`scripts/build/build-player.py` 不是"调一次 BuildPipeline"，而是**一串可核对的步骤**：

```text
restore-check（环境/版本/依赖）
  → l0-dep-scan（依赖与秘密）
  → gen-build-hash.py --check-shared（共享源集常量）
  → profile 同步（target / backend / scenes）
  → 内置内容包（仅 StandaloneWindows64，异步构建 + 轮询）
  → dry-run（先验一次）
  → build --confirm（真构建）
  → build_status 轮询（45 min 超时）
  → 产物校验（artifactGlob 至少一个 + mtime 新鲜度）
```

| 步骤 | 关键判据 | 失败含义 |
|---|---|---|
| 环境 | `restore-check.py` 的 BLOCKING 项 | Unity 版本/依赖/表工具不齐，先修环境 |
| 依赖 | `l0-dep-scan.py` 无个人路径/密钥/未固定依赖 | 不可复现或泄密风险 |
| BuildHash | `--check-shared` 复算共享源集常量 | 判定代码改了未重生成，出包必被拦 |
| 平台/后端 | `activeBuildTarget` 不符则切换；后端不符则 `SetScriptingBackend(IL2CPP)` 后**复读校验** | 切了没生效（编辑器状态未持久），直接抛 |
| 场景集 | profile 与工程 Build Settings 双向补齐/移除 | 出包场景与档位不一致 |
| 内置包 | 只支持 Windows；10s 轮询、总上限 1200s | 内置资源包未产出，离线启动不可用 |
| 构建 | `dry-run` 先验，`--confirm` 真跑；状态轮询 | 构建失败/取消/超时 |
| 产物 | `artifactGlob` + 输出目录内 `mtime ≥ build_start-60s` | "构建成功但什么都没产出"（历史假绿） |

**档位**（`BuildProfiles/`）：

| 文件 | 用途 | 关键项 |
|---|---|---|
| `windows-x64.json` | 开发档（默认） | IL2CPP、`channel=development`、场景 `Boot.unity`、输出 `Builds/StandaloneWindows64` |
| `windows-x64-release.json` | 发布基包 | `channel=release`、`environment=test`、输出 `...-release`；**committed 版 endpoints 为空**（部署参数由机器本地档或包内 `deploy.args` 注入） |
| `windows-x64-release.local.json` / `windows-x64-closedtest.local.json` | 机器本地注入 | `meta.url=http://10.8.0.1:5000` + `envelope.key`；不入库 |
| `android-il2cpp.json` | Android 档 | ARM64、debug keystore、`*.apk`；真机矩阵尚未闭合 |

`deploy.args` 的处理值得单独说：profile 的 `endpoints` 会逐条烙成 `-k=v`，**值含空白直接拒烙**；`endpoints` 为空则删除该文件。这防止"把带空格/引号的密钥写进启动参数"这类难查故障。

**冒烟**（`scripts/build/player-smoke.py`）：启动 exe → 超时内命中定义态标记之一即通过——`[Asset] ready`（离线包就绪）或 `BootstrapError`（预载失败但内建错误 UI 已显示）；`--mem-loop` 则改判 `[MemLoop] done/fail`，并断言 30 次循环后驻留增长 ≤ 8 MB。**裸标识符不算标记**（历史教训：拿 `AssetService` 当标记，命中的是启动栈帧）。

## 2. 服务端发布：两个自包含产物

| 产物 | 发布方式 | 体积（实测） | 配置 |
|---|---|---|---|
| `RoomServer` | `dotnet publish -c Release -r win-x64 --self-contained true -o Builds/win-server/room`，`tar` 成 `room.tgz`；玩法表另打 `GameData-Config.tgz` | 约 73 MB | `--config C:\litegame\room\roomserver.json`；表目录 `--combat-table C:\litegame\GameData\Config` |
| `MetaServer` | 同形态手工发布到 `Builds/win-server/meta` | 约 105 MB | `appsettings.json` → `META_` 环境变量 → 命令行覆盖，后者优先 |

- 云主机**不装 .NET SDK**：自包含发布把运行时打进产物，避免"服务器装什么版本"的漂移。
- 密钥**只走环境变量**，名字就是部署契约：`LITENET_SECURE_ENVELOPE_KEY`、`LITENET_LOBBY_INSTANCE_KEY`、`LITENET_SETTLEMENT_INSTANCE_KEY`、`LITENET_TICKET_KEY`、`LITENET_GM_KEY`。配了 `lobby.url`/`settlement.submit_url` 却缺对应密钥即拒启（fail-closed）。
- 配置是**启动期快照**：改 `roomserver.json` 后必须重启任务才生效；只重启任务不重新 publish，则配置生效而 exe 仍旧（常见误判）。

## 3. 云主机形态：Server Core + 隧道

现行形态是 **Windows Server 2025 Datacenter Server Core（无桌面，build 26100）**，2 vCPU / 3.9 GB / 40 GB 系统盘，时区 CST、服务内 UTC。选它而不是 Docker/WSL2 的原因在手册里：Windows 容器/UDP 端口转发在 Server Core 上缺口明显，原生进程 + 任务计划更可靠。

```text
C:\litegame\
├─ meta\        MetaServer 产物 + 配置
├─ room\        RoomServer 产物 + roomserver.json
├─ GameData\Config\   两端同读的 Luban .bytes
├─ mongo\       MongoDB 8.0.34（rs0，仅 127.0.0.1:27017）
├─ wg\          WireGuard 服务端配置
└─ python\      云上运维 payload（Python 3.12.9）
```

| 面 | 端口 / 形态 | 说明 |
|---|---|---|
| 运维 SSH | `10.8.0.1:22`（WireGuard 隧道） | 公网 `22/tcp` 已从安全组撤掉，只留 `51820/udp` |
| Meta | TCP `5000` | `BindAddress` 缺省 `127.0.0.1:5000`；实机以 `META_Meta__*` 环境变量为准 |
| Room | UDP `17777` | 配置里**没有对局 bind 字段**；实测监听 `0.0.0.0:17777`（与"只绑隧道"的表述不一致，属已登记差异） |
| GM | TCP `9101`（仅隧道地址） | 只 POST + `X-GM-Key`；本机转发端口用 19101（9101 落在 Windows 排除区间） |
| Metrics | TCP `9100` | `roomserver_*` 约 32 项；本机转发用 19100 |
| MongoDB | `127.0.0.1:27017`，副本集 `rs0` | 事务依赖副本集；`rs.initiate` 后校验 `1 PRIMARY` |

**托管**：任务计划 `LiteGame-Meta` / `LiteGame-Room`，`SYSTEM` + `AtStartup`；Action 必须 `cmd.exe /c "…run.cmd"`（直接把 `.cmd` 当 action 会得到 `LastTaskResult=0x1` 且日志零字节）。**禁止在 SSH 会话里 `Start-Process` 起常驻进程**——会话回收会带走进程。

**隧道**：WireGuard 服务端 `10.8.0.1/24`、`ListenPort=51820`，peer 按 `10.8.0.x/32` 分配。换机/换公网 IP 时，已发出的测试者 `.conf` 全部作废（只需重生成 `Endpoint` 与 `PublicKey` 两处，客户端与游戏包不用动）。

## 4. 部署脚本：幂等、fail-fast、无自动回滚

| 脚本 | 作用 | 幂等 / 安全边界 |
|---|---|---|
| `bootstrap-cloud-python.py` | 云上装 pin 版本 Python（SHA256 校验）并补传 runner | 已装且 ≥3.10 且未 `--force` 则只补传；`--dry-run`；装后复验 |
| `deploy-room.py` | publish → 打包 → 停服 → scp → 解压 → 起服 → 回读 | 云端 Python 缺失在**停服前** fail；`--skip-publish/--with-config/--skip-tables` |
| `gm.py` | 本地起 SSH 隧道转发 GM，调动作 | 端口固定 19101；`finally` 关隧道；密钥从 env 或 `LocalNotes/cloud-host.md` 解析 |
| `wg-peer.py` | 生成 peer 密钥、追加 `[Peer]`、重装隧道服务 | 同名已存在即 `DUPLICATE` 拒；地址自动 `next_ip`；`--dry-run` 只生成 conf |
| `_remote.py` / `_ssh_host.py` | 云上 runner 协议 / 目的地解析 | 隧道不可达即 fail-fast，不回退公网 |

**没有自动回滚**：覆盖 `roomserver.json` 前留 `.bak`，但二进制/表/Mongo 都没有快照回滚；Mongo 无定时备份，数据随机器盘。这是当前形态的明确边界，不是遗漏。

**判据**：起服后回读 `task=Running` + `buildHash=...`；只看到进程在跑不算成功。

## 5. 联机测试主线：从改完代码到打完一局

### 5.1 发版矩阵（改什么发什么）

| 改动面 | 云侧 | 客户端 | 备注 |
|---|---|---|---|
| 纯表现 / Lua / prefab / 美术 | 不动 | 重打包 exe | 资源走内容包时另论 |
| `Server/{RoomServer,MetaServer}` `.cs` | 重新 publish + 上传 | 不动 | 两端 BuildHash 不变 |
| 共享源集（Sim/协议/生成读码面） | 重新 publish + 上传 | **必须重打包** | 先跑 `gen-build-hash.py` |
| `Assets/RoomServer/{Runtime,Application}` | 重新 publish | **不改 BuildHash** | 房间内核不在 BuildHash 闭包内，但服务端必须重发布 |
| 表源（Luban） | 重新生成 + 重发布 | 重编译重打包 | 生成读码面在闭包内，仍需重跑哈希 |
| 仅 `roomserver.json` | 传配置 + 重启任务 | 不动 | 配置是启动期快照 |

判据永远是**两端 `buildHash` 同值**；不符的典型表现是 Meta 签票 `409 version-mismatch`。

### 5.2 测试者接入与开测

- **基包只发一次**（release 通道，约 491 MB 级）；每个测试者一份 WireGuard `.conf`（`wg-peer.py` 生成，落 `Dist/out/<name>.conf`），不入库、不回显。
- 开测形态：编辑器 Play（读 `Assets/StreamingAssets/deploy.args`）、exe 零参数（读包内 `deploy.args`）、同机第二客户端 `-device.id ed-b`。
- 前提：本机隧道已起（Meta `/live` 返回 `live`）。
- 测试房 `sandbox` 模板：`match_duration_frames=0` + `kill_limit=0` + 复活 60 帧——**不限时、不按击杀结束，因此不会自然产出结算**。"打了半天没战绩"通常不是故障。

### 5.3 观测与收尾

- `C:\litegame\room\out.log`：`[GM]` 审计、Lobby 注册横幅、`Settle` 行、启动横幅（`rooms=[...] default=sandbox`）。
- `/metrics`：`roomserver_*` 32 项；启动失败只告警降级（服务照跑、无 metrics），绑 `+` 还需 `netsh http urlacl`。
- 收尾验结算：`default_template` 切回 `standard` → `deploy-room.py --skip-publish --with-config` → 打完一局看结算页/战绩；或 `gm.py --action settle-flush` 立即回灌 Outbox。

## 6. GM 通道：把外部动作收回权威线程

客户端 GM 面板在"真 KCP 独立进程"形态下够不到权威侧，因此房间服内置一条 HTTP 写面：

- **端点**：`http://10.8.0.1:9101/gm/*`，仅 POST，头 `X-GM-Key`；默认关闭，启用条件＝`gm_port>0` 且 `LITENET_GM_KEY` 非空；`gm_bind` 为通配地址在配置装载期即拒。
- **门禁**：密钥长度先比 + `CryptographicOperations.FixedTimeEquals`；非 POST 一律 404；body ≤ 4096 B。
- **动作**（契约单源 `Server/RoomServer/gm-contract.json`）：`rooms`、`start`、`abort`、`kick`、`rules`、`settle-flush`、`diag-list`、`diag-fetch`。
- **关键设计**：HTTP 线程只做"鉴权 → 解析 → 入队"，动作在权威循环 `FlushGmActions` 执行；`start` 取真实 owner 代发，不旁路 owner 校验；`abort` 走完整 Finishing/Settling。
- **审计**：`[GM] 入队/拒绝/执行/跳过` 目前走裸 `Console.WriteLine`、未经 `HostLog`——已登记的偏差，不是设计意图。

## 7. 边界与已知坑

1. **封闭测试环境**：不得公开宣传，**不得作为"可发布"判据**；公网只有 `51820/udp`，Meta/Room/GM 均无公网入方向。
2. **只重启任务不 publish**：配置生效而 exe 仍旧；`RoomServerConfig` 是启动期快照。
3. **运行中解压**：DLL 被占用会报 `Can't unlink already-existing object`；必须先停服。
4. **只换 Room 二进制不传表**：`StartGame` 以"玩法数据身份不符（ConfigHash）"拒整局。
5. **GM 本机端口用 9101**：Windows 排除区间会 `Permission denied`；脚本已固定 19101。
6. **手拼 curl 不带 body**：`HttpListener` 回 411。
7. **中文脚本走 SSH stdin**：PS 5.1 按 GBK 误解，静默失败；须 scp 文件 + `-File` 执行。
8. **单机单房限制**：Meta 多实例不支持（注册表/出号保留集驻内存）；`max_rooms=8`；席位上限 32；`Running` 后不可中途加入；观战/回放无实现。

## 8. 本章要点

- 构建/部署的设计哲学是**把"成功"变成可回读的判据**：出包前哈希、产物 freshness、起服后的 `buildHash` 与表基摘要、冒烟的定义态标记——都不依赖"看起来跑起来了"。
- 隧道单通道让"换机只重生成两处 conf、客户端与游戏包零改动"成立，代价是所有脚本必须对隧道 fail-fast。
- GM 写面的四重门禁 + 权威循环入队，是"外部运维动作不得绕过确定性线程"的具体实现。
