# 09 · 测试、门禁与工程质量

> **本章回答**：这个项目如何证明"改对了"——L0～L4 各守什么、L2 如何避免假绿、纪律扫描如何把规范变成红绿、工具链清单如何防止工具/文档/注册面漂移、CI 覆盖到哪一步。
> **上游权威**：[测试开发框架总设计](../设计文档/测试与性能/测试开发框架总设计.md) 定义分层与完成标准；[修改指南 §2.3](../修改指南.md) 定义"改什么跑什么"。本章给机制与现状。
> **口径**：2026-10-22 工作区；命令/阈值以 `scripts/gate/*.py` 为准。

## 1. 五层验证：每层只回答一个问题

| 层 | 回答的问题 | 入口 | 平台 | CI |
|---|---|---|---|---|
| **L0** 静态门禁 | 依赖可复现吗？有没有密钥/个人路径？工具注册面漂移吗？ | `scripts/gate/l0-dep-scan.py` | 任意（不需 Unity/.NET） | ✅（仅 windows step） |
| **L1** 纯逻辑 | 判定/协议/房间内核/框架语义对不对？ | `test.py --lane L1 --profile PullRequest` | win + ubuntu | ✅ |
| **L2** Unity | 工程能编译吗？EditMode/PlayMode 真跑了吗？资源/meta 合法吗？ | `scripts/gate/l2-unity-gate.py` | 仅 Windows（需编辑器或 batchmode） | 条件式（自托管 + `L2_ENABLED`） |
| **L3** 集成/端到端 | 真 IO/真网络/真进程内服务端能跑通吗？ | `test.py --lane L3 --profile PullRequest` | win + ubuntu | ✅ |
| **L4** 真机/性能 | 目标设备上的帧率/内存/生命周期达标吗？ | **无脚本、无 lane** | 真机 | ❌ |

> `test.py --lane` 的合法值是 **L1 / L2 / L3 / All / Doc**；L0 是独立脚本，L4 尚未纳入。`All` 会顺序跑 L1→L3→L2，因此也要求 Windows。

## 2. 统一入口：`test.py` 的确定性来自"契约"

`scripts/gate/test.py` 不是简单循环，而是把"跑哪些、怎么判、产物在哪"固定成契约：

- **工程发现**：只认 `Tests/**/*.Tests.csproj`；出现其他命名的 csproj 直接抛错，避免"新增测试工程但没被跑"。
- **执行顺序**：逐工程 `restore --disable-parallel -m:1` → `build Tests/Tests.slnx --no-restore -m:1` → 逐工程 `dotnet test --no-build --no-restore --blame-hang-timeout 5m --filter …`。
- **过滤**：
  - L1：`Category!=Integration&Category!=EndToEnd&Category!=Performance&Category!=Quarantine&Duration!=LongRunning`；
  - L3：`(Category=Integration|Category=EndToEnd)&Category!=Quarantine`，PR 档再加 `&Duration!=LongRunning`。
- **判红**：任一工程失败仍继续跑完其余工程再汇总；**`Total=0` 判红**（防"测试程序集没编进来"静默通过）。
- **产物**：每工程一份 TRX（`TestResults/{lane}-{工程}-{runId}.trx`）+ 一份 `summary-<lane>.json`；导出 `LITETEST_RUN_ID` / `LITETEST_ARTIFACTS` / `DOTNET_PROCESSOR_COUNT=4`。
- **summary schema v1**：`schemaVersion / lane / profile / status(pass|fail) / runId / total / passed / failed / skipped / artifacts[]`，失败附 `error`；CI、夜间日志、人读输出消费同一份，不再各自解析控制台。

**超时**：L1 5m；L3 PR 档 5m、非 PR 12m 并设 `M10_LONGRUN=1`（长跑用例开关）。**Doc lane** 只跑文档门禁（`doc-lint.py` + `toolchain.py docs --check`），不碰 dotnet。

## 3. L2：两条路径与三道反假绿

### 3.1 路径判定

```text
存在 Library/Pipeline/.unity-pipeline-port 且未强制 batchmode？
  ├─ 是 → A. 编辑器在跑（Pipeline，不用关编辑器）
  └─ 否 → B. batchmode（要求没有 Unity 进程占用同一工程）
```

### 3.2 路径 A 的关键步骤

1. `set_autotick --enable true`：保证后台编译/测试期间编辑器继续 tick；
2. **新鲜度守卫**：写临时 `.cs`，执行 `AssetDatabase.Refresh(ForceSynchronousImport)` + `CompilationPipeline.RequestScriptCompilation()`，轮询 `isCompiling` 至收敛（上限 90s）；
3. `recompile_status` 判编译失败；Console 只对 `error CS####` 判红（其它 error 级条目降级为提示）；
4. `run_tests --mode editor|playmode --async_tests true`，5s 轮询 `test_status`；**两模式各自判红**，`Total<=0` 判红。

**为什么需要新鲜度守卫**：外部改 `.cs` 后 Unity 不会自动导入，`recompile_status` 会误报 `up_to_date`，用例跑的是**旧程序集**——这是最隐蔽的 L2 假绿。mtime 比较（源码最新 vs `Library/ScriptAssemblies/*.dll` 最新）是第二道辅助判据。

### 3.3 路径 B

先 `tasklist` 确认没有 Unity.exe 占用同一工程，再 `unity test <工程> -e <UnityExe> --mode EditMode|PlayMode --timeout 1800`；两段独立判定，不因前一段失败短路。

### 3.4 meta GUID 扫描（两模式共有）

扫 `Assets` + `Packages` 全部 `.meta`，`guid` 必须是 32 位 hex。历史事故：非法 GUID 的 `.meta` 被 Unity 拒收 → 资源/类型静默消失，而 L1 全绿。

## 4. 纪律扫描：规范的可执行面

`Assets/Tools/DisciplineScanner` 是唯一引擎，规则集 R1～R13：

| 规则 | 拦什么 | 为什么 |
|---|---|---|
| R1 | 超越函数（Sin/Cos/Tan/Atan2/Exp/Log/Pow） | 跨平台 libm 结果可能不同，判定层走 `SimTrig` 查表 |
| R2 | 显式 FMA | 融合乘加在不同 CPU/编译器下结果可能不同 |
| R3 | float `==`/`!=`（0/null/default 字面量豁免） | 浮点等值比较不可靠 |
| R4 | LINQ / 不稳定遍历（判定层） | 顺序不确定 = 结果不确定 |
| R5 | 裸 `UNITY_EDITOR` | 应走开发三宏或适配器，避免 release 残留 |
| R6 | 原生协程（`IEnumerator`/`StartCoroutine`/`yield return`） | 统一 UniTask，生命周期可控 |
| R7 | 非法 `.meta` GUID | 资源静默消失 |
| R8 | `Resources.Load/LoadAsync` | 资源必须走内容服务/租约 |
| R9 | Mod 类型进入 Sim | 判定面不得被模组污染 |
| R10 | UI 服务装配直接发业务包 | 分层：UI 不认识网络业务 |
| R11 | 运行时纯化（Console/墙钟/Stopwatch/Sleep/Socket/Kcp/文件 IO/proto/LiteNet/`new Random()`） | 房间内核必须可确定性测试 |
| R12 | 适配器边界（YooAsset/XLua/DOTween/InputSystem/Cinemachine 只在登记目录 import；`LiteClient.*` 禁引 `LiteGame.*`） | 防止第三方 API 泄漏进框架 |
| R13 | 机制面禁读静态数值读口（常量面豁免） | 技术债 #1 防复辟：值必须经实例传递 |

**作用域不是全仓一把扫**：`ScanTargets.Default` 14 个目标，每个目标只启用相关规则子集（如 `LiteNet`/`LiteFramework.Core` 只扫 R5，`LiteSim` 扫 R1-R5+R9，`RoomServer/Runtime` 扫 R11+R13）。**豁免三层**：路径级（`/Editor/`、`/Vendor/`、规则表自身）、目标级（`ExcludeRoots`、配置读口定义文件）、行级（`lint-allow`，可只豁免某条规则）。

另有 **7 条结构守卫**（同为 L1 红）：LiteGame 顶层目录白名单、注释卫生（禁日期戳/批次号）、S1/S2 asmdef `noEngineReferences`、S2 零第三方依赖、Assets 下禁 `bin/obj`、服务端宿主/调试宿主的依赖方向、`LiteClient` 框架侧禁引 `LiteGame`。

**视觉单一来源**由独立扫描器把守（`VisualConstructionScanner`）：用户可见视觉必须来自 `ShareResource/UI/Screens|Widgets` 模板；命中 `typeof(T)` 参数或 `AddComponent<T>` 即违规（23 个视觉/交互类型名），例外按**文件名**登记（仅 `ProcedureError.cs`/`UiInput.cs`）。正/负例由 EditMode 用例执行，且被 `ui.validate` 工具复用。

## 5. 测试基础设施：双轨、可重复、可诊断

| 件 | 机制 |
|---|---|
| Trait 单源 | `Category/Duration/Priority/Owner` 四个键，NUnit 与 dotnet filter 共用同一批字符串 |
| 分类 | `Unit`/`Contract`/`Integration`/`Asset`/`Smoke`/`EndToEnd`/`Performance`/`Quarantine`；`Duration=Fast/Medium/LongRunning`；`Priority=P0–P3` |
| 双轨 | `Assets/LiteTesting/Core/**` 一份源码：Unity asmdef + `netstandard2.1` csproj；dotnet 测试与 Unity 测试共享断言/等待工具 |
| `Eventually` | 有界轮询（timeout/pollInterval 必填且 >0），超时抛 `TimeoutException` 并附 `Last state` |
| `DeterministicRandom` | SplitMix64 定序，种子来自 `LITETEST_SEED`（默认固定值）按测试 ID 做 FNV-1a 派生 |
| 逐位基线 | `Tests/LiteSim.Core.Tests/Baselines/{IeeeBaseline.txt,SimChecksum.txt}`；跨平台 L1 矩阵 + 基线比对 |

**Quarantine 的现状**：文档要求"必须关联缺陷 + 责任团队 + ≤7 天到期，禁止用重试掩盖不稳定"；代码侧只有常量与各 lane 过滤（排除），**没有到期日/缺陷关联的机械校验，当前 0 个 Quarantine 用例**。这是"制度存在、执行面未机械化"的典型。

## 6. 工具链平台：单清单驱动四个面

`scripts/gate/toolchain.json`（schema v6）是工具的唯一清单：**60 个 tools、9 个 category、5 个 surface**，每个工具声明 `kind`（action/cli/gate/page/docs/content/window/build/hud）、`plane`（external/editor/runtime/none）、`purpose`（dev/delivery/debug）、`requires`（play/player/unity-batch）与是否 `destructive`。

```text
toolchain.json
   ├─ 编辑器 Hub（唯一菜单 LiteGame/工具链）→ 按 kind 选适配器
   ├─ CLI（python scripts/toolchain.py list/check/docs/open/run/generate/verify/build/doctor）
   ├─ 生成索引 Docs/工具链/工具索引.md（docs --check 逐字节比对，stale 即失败）
   └─ 外部注册面（CI workflow / hook / 计划任务引用的脚本是否存在）
```

`check` 校验：清单结构与路径、surfaces 引用、索引新鲜度、**孤儿可执行脚本**（无 `main` 且未豁免）、编码/EOL（`scripts/**/*.ps1` 禁止新增、`*.py` 禁 BOM、全禁 CRLF；这条默认是 warning，`--strict` 才升 error）、域形态三规则（同义参数同名 / 文档权威唯一 / 一域一个输出前缀；同样默认 warning）。`doctor` = `check` + `restore-check` + Pipeline 端口状态。

**这套清单解决的是"工具/文档/注册面三处漂移"**：新增工具只改清单，Hub/索引/CI 检查同步；改脚本路径会立刻被 surface 校验发现。

## 7. CI：覆盖到哪、没覆盖到哪

| Job | 触发 | 做什么 | 备注 |
|---|---|---|---|
| `l1-dotnet-test` | push（`LiteGame`/`main`）/ PR | win+ubuntu 矩阵：基线防篡改 + L0（仅 win）+ L1 | **定时/手动不触发** |
| `l3-network-test` | 同上 | 同矩阵：L3 | 25 min 超时 |
| `l2-unity-gate` | schedule/dispatch 且 `L2_ENABLED=='true'` | 自托管 Windows：L2 + 构建 + 冒烟 | 与本地夜间任务二选一 |
| `nightly-longrun` | schedule/dispatch | L1/L3 `--profile Nightly`（含长跑） | cron `0 19 * * *` UTC |

**基线防篡改**：diff `BASE..HEAD` 的 `Tests/**/Baselines/**`，有变更须在 PR 标题/正文或提交信息声明 `[baseline]`，否则失败；BASE 取不到时**跳过**（浅历史可绕过）。

## 8. 现状缺口（按影响排序）

1. **L4 完全缺失**：无 lane、无脚本、无设备/性能基线；真机与内存证据只能靠手工。
2. **L2 只能在自托管 Windows 跑**：需要完整工程 + 中国版编辑器授权 + `L2_ENABLED`；GitHub-hosted 不可用，与本机夜间任务目的重叠。
3. **L2 存在"绿而未跑"分支**：Pipeline 路径找不到 `unity` CLI 时只 note 后 return，最终仍 `pass`，且不经过 `Total<=0` 判红——需要人工确认输出。
4. **Doc 门禁未进 CI**：4 个 job 都没有 Doc lane，文档索引/链接/命名只在本地或手动跑。
5. **Quarantine 未机械化**：无到期/缺陷校验，容易变成"永久豁免"。
6. **文档与代码的已知不一致**（本卷按代码写，此处登记以便回写）：CI 触发条件、L3 超时、`--lane` 参数、视觉类型数（23 vs 24）、`.ps1` 检查是 warning 还是 error 等。

## 9. 本章要点

- 这套体系的重点不是"测试多"，而是**每个门禁都针对一种历史假绿**：旧程序集、测试没编进来、构建没产物、部署没换二进制、基线被改。
- 纪律扫描的价值在于**把架构约束变成编译/测试期错误**；没有扫描的约束最终都会退化成注释。
- 仍缺的三块很清楚：真机/性能（L4）、文档 CI、Quarantine 生命周期——它们也是下一阶段质量建设的优先级。
