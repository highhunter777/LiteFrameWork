# 09 分层与命名

> **定位**：裁决产品侧**契约层级**（core / module / module-core / submodule）的落点与准入判据，以及单元入口类型的命名后缀。
> **权威边界**：框架侧（`LiteFramework`）内部分层归[《商业级通用客户端框架总设计》](../设计文档/架构/商业级通用客户端框架总设计.md)；批次与迁移证据归[施工进度](../施工进度/README.md)；本文件只裁"放哪、叫什么、凭什么判"。
> **关联**：[02 代码与修改规范](02-代码与修改规范.md) · [04 术语与用词](04-术语与用词.md) · [02 架构总览与程序集分层](../说明/02-架构总览与程序集分层.md) · [18 域间引用矩阵](../说明/18-域间引用矩阵.md)

## 1. 契约层级

```text
Assets/LiteGame/Core/                 ① core —— 产品纯契约/纯计算（零引擎）
Modules/<模块>/
    Abstractions/                     ② 模块契约（独立 asmdef，零引擎）
    <实现件>
    Core/                             ③ 模块 core —— 按需
    <子模块>/
        Abstractions/                 ④ 子模块契约 —— 按需
        <实现件>
```

| 位置 | 放什么 | 准入判据 |
|---|---|---|
| `Assets/LiteGame/Core/` | 跨域纯契约、纯计算 | 被 **2+ 模块**消费；零引擎、零第三方、零状态 |
| `Modules/<模块>/Abstractions/` | 模块端口与行契约（含 DTO） | 被**其他模块**或**适配器**消费；实现件单向依赖它 |
| `Modules/<模块>/Core/` | 模块内纯类型、纯计算 | 被本模块 **2+ 子模块**共享；零引擎、零第三方、无状态、不引 `Abstractions/`、不引实现件 |
| `Modules/<模块>/<子模块>/Abstractions/` | 子模块端口 | 被同模块其他子模块或跨程序集消费 |
| `Modules/<模块>/<子模块>/` | 其余一切 | **默认落点** |

**判据一句话：有没有"外部"消费者。** 有 → 上提；没有 → 就地。

切分轴是**依赖许可**，不是技术层。只有"这一层能不能引上一层不能引的东西"答得出"不能"时，才分层；接口/逻辑/数据三层在同一个程序集里许可完全相同，不构成层级。

边界细则：

- `Abstractions/` 放**跨边界的契约**（端口 + 行契约/DTO）；`Core/` 放**不跨边界但被多个子模块复用的纯计算**。分不清时，答案就是"就地"。
- 除 `Abstractions/`、`Core/` 两个保留技术名外，业务域子目录一律按**职责**命名，禁 `View`/`Presentation`/`Domain`/`Logic`。
- `Modules/Composition/`（组装件）与 `LiteGame.Shared`（共享常量面）不适用本节的 `Abstractions/` 要求。
- **不拆 asmdef**：模块 core 与模块实现同编，零引擎与反向依赖由目录扫描守（见 §4）。
- `LiteGame/Core` 与 `Modules/<模块>/Core` 是**不同作用域的同名概念**，文档、评审与提交说明中一律写全路径。

### 1.1 模块内子包：一条轴 + 三档定位

模块需要切子包时才切（[04 §6.7](04-术语与用词.md) 触发线：文件 >20 或顶层类型 >30；被第二个模块直引先评估提模块）；未到线就平铺 + `Abstractions/`，不预先切包。

**一个子包只属一条轴**，同一个词不得在不同模块指不同轴：

| 轴 | 判据 | 现行例 |
|---|---|---|
| 契约 | 被外部程序集消费的端口/行契约，或命令载荷 | `Abstractions/`、`SubModules/CommandsSubModule/` |
| 阶段 | 只在某个生命周期相位存在 | `SubModules/SessionSubModule/`、`SubModules/SettlementSubModule/`、`SubModules/StagesSubModule/`、`SubModules/LaunchSubModule/` |
| 物件 | 世界里的一类空间/实体载体 | `SubModules/ArenaSubModule/`、`SubModules/CharactersSubModule/` |
| 通道 | 消费一类事件或驱动一条输出 | `SubModules/CombatSubModule/`、`SubModules/HudSubModule/`、`SubModules/AimSubModule/`、`SubModules/TransportSubModule/` |
| 装配 | 只做组合、可全向依赖 | `SubModules/SetupSubModule/`（`Setup` 只留给装配轴；启动/对局步骤件按阶段命名 `LaunchSubModule`/`MatchSubModule`） |
| 共享 | 被 ≥2 个子包依赖的数据/件 | 域根共享件、`Shared/` |

**定位三档**（按依赖方向判，不按概念归属）：

- **共享子包**：被 ≥2 个子包依赖 → 只依赖域根与 `Abstractions/`；
- **叶子子包**：只依赖域根、`Abstractions/` 与共享子包；
- **装配子包**：唯一可全向依赖。

**域根的三类合法住客**：共享件、装配件（`<模块>Segment.cs`，装配根，可引用各包以登记产物与时序）、单消费者件（应下沉到消费子包，不属合法住客）。除装配件外，域根文件不得依赖叶子；共享件需要叶子类型时把访问口契约化到 `Abstractions/`，或承认它是取件域并登记为例外。

**三条硬规则**：

1. 一个子包一条轴；同名目录跨轴即违规（`Setup` 在 Battle 是装配包、在 Procedure/Session 是启动步骤，必须按轴改名或按轴归属）。
2. 只有一个消费包的具体件必须住消费子包（`WeaponMounts` 仅 `CombatSubModule/` 使用，已从域根归位该子包）。
3. 共享件不得依赖叶子；装配件可引用各包，但只做"登记 + 时序"，细节构造下沉装配子包。

**模块的物理形态**（五项，缺一不成型）：目录 `Modules/<模块>/` + 装配件 `<模块>Segment.cs`（就地）+ 端口 `Abstractions/`（被外部消费时独立 asmdef）+ 子包 + 测试归属。测试可经目录映射与模型登记（§4），不强制物理同目录——模块内建 `Tests/` 必须挂独立 Editor-only asmdef（否则进包），按规模另议。

**子模块容器**：子模块＝二级职责目录，目录名一律 `<职责>SubModule`（装配子包同样带后缀：`SetupSubModule`）；**≥2 个时归 `SubModules/`**，仅 1 个时直接放模块根（不建单元素容器）。四个保留技术名（`Abstractions/`、`Core/`、`Generated/`、`Shared/`）**不进** `SubModules/`——它们表达契约/生成物/共享层，不是职责件。容器目录**不参与命名空间**：子模块命名空间仍是 `<根>.Modules.<模块>.<子模块>`（容器是分类，不是层；本批只搬目录，命名空间随收敛批处理）。

## 2. 命名后缀

| 后缀 | 角色 | 判定 |
|---|---|---|
| `XxxSegment` | 装配段 | 实现 `IClientSegment`、进 `ClientEntry.RegisterSegments` 的段；住 `Modules/<模块>/<模块>Segment.cs`（组装件段用 `<能力>Segment.cs`，见 `Modules/Composition/`） |
| `XxxUnit` | 内聚单元 | 模块内聚单元入口，**不**参与启动装配；`Module` 后缀不得用于新类型（见 §5） |
| `XxxSubModule` | 子模块单元 | 子模块需要独立装配点或对外暴露时（按需；**目录名 = `<职责>SubModule`，与入口类型同后缀**） |
| `IXxxService` / `XxxService` | 服务本体 | 能力端口与实现 |
| `XxxServiceModule` | 服务模块 | 把服务及其依赖装起来的单元，**不**是启动装配段 |

**判定树**（一个单元只取一个后缀）：

1. 进 `RegisterSegments` → `XxxSegment`
2. 是能力本体（端口 + 实现）→ `IXxxService` / `XxxService`
3. 是该服务的装配单元、但不是启动段 → `XxxServiceModule`
4. 是模块内子单元 → `XxxSubModule`
5. 其余模块内聚单元 → `XxxUnit`

**一单元一入口**：同一单元不得同时拥有两个入口类型。角色不同才可并存——例如某域已有 `XxxSegment`（域装配段），其服务仍可另有 `XxxServiceModule`（服务装配单元）。

**框架契约族**（Host 侧，同一词根 `Segment`，不留 `Module`/`Composition` 混用）：

| 现名 | 目标 | 角色 |
|---|---|---|
| `IClientSegment` | `IClientSegment` | 装配段契约 |
| `IClientSegmentGraph` | `IClientSegmentGraph` | 依赖名声明 |
| `IClientSegmentHandle` / `ModuleHandle` | `IClientSegmentHandle` / `SegmentHandle` | 关闭句柄 |
| `SegmentContext` | `SegmentContext` | 装配窗口 |
| `ModuleScope` / `IModuleScope` | `SegmentScope` / `ISegmentScope` | 段资源作用域 |
| `ModuleGraphValidator` | `SegmentGraphValidator` | 重名/缺依赖/环校验 |
| `ModuleTrace` | `SegmentTrace` | 装配期追踪 |
| `AddSegment` / `ModuleCount` | `AddSegment` / `SegmentCount` | Host 注册面 |

命名细则：

- 后缀是**类型**约定；目录名与程序集名不变（`Modules/<域>/`、`LiteGame.Modules.<域>`）。
- 文件名与类名一致：`XxxSubModule.cs` 放 `XxxSubModule`；装配段 `<域>Segment.cs` 放 `<域>Segment`。
- 服务一律 `XxxService`，接口 `IXxxService`；禁用 `Manager`/`Helper`/`Util`/`Impl` 作后缀（`IVFXService` 式全大写属[术语与用词](04-术语与用词.md)管辖，不在本条）。
- 命名空间跟目录（`LiteGame.Modules.<域>`），共享域由 `DomainBoundaryTests` 钉住。

## 3. 装配段

**定义**：实现 `IClientSegment` 的类，在 `InitializeAsync(SegmentContext)` 里把本域产物登记进容器、声明依赖；由 `ClientEntry.RegisterSegments` 链式注册，**注册序即依赖序**。

**Host 保证的生命周期**（段自己不重复实现）：

| 步 | 行为 | 失败处理 |
|---|---|---|
| 1 | `ModuleGraphValidator.Validate`：重名 / 缺失依赖 / 依赖环 | fail-fast，早于任何副作用 |
| 2 | 按注册序 `InitializeAsync`；`Put` 只在本段窗口内合法 | 任一失败 → 只关闭已成功段（逆序）→ 终态 |
| 3 | 全部成功后 `AppComposition.ComposeAfter` 跨域装订 | 同上 |
| 4 | `Seal`：装配面密封，运行期不再接受登记 | —— |
| 5 | 关闭：逆序 `ShutdownAsync`，最后释放根 Scope | 单段失败不阻断其余 |

**够格判据**（四条全中才建段）：

| # | 判据 | 不满足时 |
|---|---|---|
| 1 | 有独立生命周期：建的东西要在关闭时逆序释放 | 不是段 |
| 2 | 有产物且被**其他段**消费（`Put` → 别的段 `Require`） | 并进消费方 |
| 3 | 有独立失败面：失败应中止启动，不降级 | 不是段，做降级件 |
| 4 | 只装配：不判定、不渲染、不跑帧循环 | 业务实现，住域内 |

**不该建段**：

- 只被一个段消费 → 并进那个段。
- 没有 `Put` → 内部件。
- 需要跨域连线 → 归 `AppComposition.ComposeAfter`（装配点不是业务段，段内不许跨域连线）。
- 需要 new 适配器 → 适配器只在 `AppComposition` new（`Modules` 不引 `Adapters`）。

**段间规则**：

- 依赖用 `IClientSegmentGraph.DependsOn` 声明**模块名**，不用 `typeof`——用类型会把域程序集连成环。
- 段之间不直接引用；跨段协作只经容器端口。
- 段只 `Put` 本域产物；同类型重复登记即装配错误。
- `Name` 唯一，依赖按名寻址。

**命名与就地**：文件 `<域>Segment.cs`（硬约束）、类 `<域>Segment`、就地住 `Modules/<域>/`。

**可见性**：

- 新增实现件默认 `internal`；确需跨程序集时，要么经 `InternalsVisibleTo` 白名单显式开放，要么把类型提升为 `Abstractions/` 契约件。
- 子模块入口（`XxxSubModule`）只在**需要装配序或对外暴露**时建立；纯目录子模块不建入口类型。

## 4. 守卫

| 规则 | 承担者 |
|---|---|
| 业务域子目录按职责命名、禁四个技术分层名 | `DomainBoundaryTests.业务域子目录必须按职责命名` |
| 保留技术名只有 `Abstractions/`、`Core/` | `DomainBoundaryTests`（现行只禁四名，需扩为白名单） |
| 子目录守卫递归到子模块层 | `DomainBoundaryTests`（现行只遍历模块第一层） |
| `Modules/*/Core/` 零 `UnityEngine`、零第三方 `using` | 目录扫描，口径同 `ClientAsmdefAllowlistTests.框架Core与SimCore不得依赖Unity` |
| `Modules/*/Core/` 不出现本模块实现件类型名 | 类型名反向扫描，手法同 `DomainBoundaryTests.战斗叶子子模块不得引用装配包` |
| 子模块间直引可读 | 子目录矩阵，口径同 `scripts/gate/domain-matrix.py` 下沉一层 |
| 跨模块引用只指向被引模块的 `Abstractions/` 类型 | 新增"类型定义位置"守卫（按 `domain-matrix` 的类型名反查定义文件） |
| 装配段就地与计数 | `SegmentBudgetTests` |
| 装配段的依赖声明、产物与消费面可解析 | `SegmentDependencyDeclTests` |
| 装配段必须建 Scope | `SegmentScopeAdoptionTests` |
| 重名 / 缺失依赖 / 依赖环 | `ModuleGraphValidator`（`ClientHost.InitializeAsync` 启动前） |

新增规则时先落门禁再落文档；只写在文档里的层级约定视为未生效。

## 5. 存量与例外

**装配段统一 `XxxSegment`**：18 段类名与文件名一致（`Modules/<单位>/<单位>Segment.cs`），框架契约族同词根（§2 表）。`Module`/`Composition` 后缀不再用于新类型。

**两个例外**（不是装配段，保持现名）：

- `Modules/Composition/` 目录与 `LiteGame.Modules.Composition` 程序集——**组装件域**；改名会牵 asmdef、csproj、`Tests.slnx`、`ClientAsmdefAllowlistTests`、18 矩阵。
- `AppComposition`——**组合根**（适配器唯一 new 点 + `ComposeAfter`），不实现 `IClientSegment`。

**其他存量**：

- `Modules/Battle/SubModules/CombatSubModule/Abstractions/`、`Modules/Battle/SubModules/CharactersSubModule/Abstractions/`——子模块契约的既有样本。
- `Modules/*/Core/` 尚无实例；模块 core 只在 §1 判据成立时新增，不预先铺开。
- `IModuleStats`（`LiteFramework/Runtime/Core/Module/`）是 HUD 统计面，与装配段无关，不改名。

**守卫**：`SegmentBudgetTests` 钉 `Modules/**` 的 `*Segment.cs` 计数与"不得再有 `*Composition.cs` / `*Module.cs`"；`SegmentDependencyDeclTests`、`SegmentScopeAdoptionTests` 按 `*Segment.cs` 解析。

## 6. 程序集分层与命名

> **定位**：裁"单元落到哪个程序集、哪个命名空间、什么时候才允许为它新开程序集"。
> **权威边界**：命名范式（根白名单、禁用项、三名一致）归 [04 §6.11](04-术语与用词.md)，本节不复制；结构单元的词义归 [04 §6.7](04-术语与用词.md)；程序集清单的目标形态归[总设计 §5.1](../设计文档/架构/商业级通用客户端框架总设计.md)；迁移批次归[路线图 §5.1](../设计文档/架构/客户端架构重构演进路线图.md)。

### 6.1 三条原则

1. **程序集名表达部署/依赖边界，命名空间表达领域**（04 §6.5）。拆程序集不改命名空间；改命名空间不顺带拆程序集。
2. **Unity 侧切分必须目录对齐**：asmdef 只覆盖所在目录及其子目录，所以 dotnet 侧"按文件集合"的切分（如 `LiteFramework.Async.csproj`）无法照搬进 Unity——Unity 侧按目录切，两侧程序集不要求一一对应。
3. **一个目录段一个意思**：目录名、程序集名、单元名同源；历史路径名（`Modules/`）按 04 §6.7 登记为准，不再造新例外。

| 常量包 | `Modules/Shared` | `LiteGame.Shared` | `LiteGame.Shared` | 非模块件 |
| 产品适配 | `Assets/LiteGame/Adapters/<适配器>` | `LiteGame.Adapters.<适配器>` | `LiteGame.Adapters.<适配器>` | `<适配器>` 用**被适配物**命名（Unity/YooAsset/XLua/Luban），不用环境命名 |
| 组合根 | `Assets/LiteGame/App` | `LiteGame.App` | `LiteGame` | `ClientEntry` + `AppComposition` |
| 产品编辑器 | `Assets/LiteGame/Editor[/Core\|/UITools]` | `LiteGame.Editor[.Core\|.UITools]` | 同名 | 编辑器工具 |

### 6.3 契约包独立成程序集的三个条件

`Modules/<模块>/Abstractions/` 默认与实现同编。**三条全中**才提为独立程序集（`LiteGame.<模块>.Abstractions`）：

1. 被 **≥2 个外部程序集**消费；
2. 消费者不得因引用而拖入实现件依赖（内容/Lua/引擎后端）；
3. 契约件零引擎（`noEngineReferences: true`，引 `LiteSim`/`LiteNet`/`LiteSync` 除外）。

现役只有 `Modules/Battle/Abstractions` 独立成程序集；其余模块的 `Abstractions/` 保持目录形态，跨模块引用由"类型定义位置"守卫约束（§4 守卫表新增一行）。是否独立，按三条件逐项评估并登记，不按模块数量批量铺开。

### 6.4 三个 `Core` 的消歧

| 写法 | 指什么 |
|---|---|
| `LiteFramework.Core` | 框架内核程序集（零引用、零引擎） |
| `LiteGame.Core` | 产品内核程序集（跨模块纯契约 + 纯计算） |
| `Modules/<模块>/Core/` | 模块内纯计算目录（不独立成程序集） |

裸写"Core"在文档与提交说明中视为歧义，必须带前缀或路径。代码内 `using LiteFramework;` 与 `using LiteGame;` 由命名空间区分，不适用本条。

### 6.5 `.Runtime` 后缀

`.Runtime` 只表示**双轨库的运行时半边**：与 `.Editor` 成对，或服务端/工具侧的运行时库（`RoomServer.Runtime`、`LiteCodeGen.Runtime`）。框架实现件不使用该后缀——框架四件按角色命名（`Core`/`Services`/`Adapters`/`Hosting`）。

### 6.6 新增程序集的准入

新开程序集必须同时满足：① 04 §6.11 B 表有对应范式；② 有独立依赖边界（能说出"这一件不能引什么"）；③ 有编译期收益（反向边/部署拆分/零引擎可测三选一）。只有目录整洁收益的拆分不立项——目录扫描能守的，不付程序集代价。

### 6.7 已裁决的四个命名问题

| # | 问题 | 裁决 | 理由 |
|---|---|---|---|
| N1 | 宿主件程序集叫 `Hosting`，`Runtime/Framework` 目录是否跟改 | **已跟改**为 `Runtime/Hosting`（B1，2026-11-04） | 目录名、程序集名、单元名同源（§6.1-3）；不改会出现"程序集叫 Hosting、目录叫 Framework"的新歧义 |
| N2 | `LiteGame.Shared` 是否并入 `LiteGame.Core` | **保留独立** | 常量面与契约面分开；常量包零引用，便于被任意层引用而不牵连内核 |
| N3 | `LiteGame.Adapters.Dev` 是否改为 `LiteGame.Dev` | **保留不改** | `<适配器>` 用被适配物命名，`Dev` 是**登记的环境例外**；改名会动 9k 行开发工具链、三宏门禁与允许表路径，收益低于风险 |
| N4 | `LiteFramework.Async`（dotnet 侧）是否改名对齐 Unity 侧 | **保留不改** | 它按文件集合切分（Hosting + Identity + 零引擎服务），Unity 侧受 asmdef 目录约束无法镜像；名字说明的是"带 UniTask"这一共享档位事实，不是角色 |
