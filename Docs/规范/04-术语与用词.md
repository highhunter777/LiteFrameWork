**违规判据**：新写仍用 A 档旧词；未登记的新自造词进入文档、注释或标识符；把 B 档词或结构名当 A 档词替换；引用术语表却与本文档位相反。

## 5. 一词多义消解

### 5.1 Lane——测试档位 vs UI 角色分层

**两义**：①测试门禁档位：`scripts/gate/test.py --suite` 参数（`L1`/`L2`/`L3`/`All`/`Doc`，默认 `L1`）；②UI 工作台角色分层：`UiLanePolicy`/`UiWorkbenchLane`，定义为「UX 分层与默认动作集，不是权限系统」（[UI 编辑器工具链专项设计](../设计文档/客户端/UI系统/UI编辑器工具链专项设计.md) §2.3）。两义互不相关，检索与沟通会串线。

**业界对应**：①测试语境＝Test Suite / Tier（`--profile` 是正交的运行档参数，不与测试层混义）；②角色语境＝Role Mode / Persona——工作台已有的「透视（Perspective）」表达窗口布局，与角色分层是两个概念，不得混用。

**规则**：

1. **禁止单写「Lane」**，必须写全称（「测试档位」「角色分层」）。
2. **新写用词**：测试面用**套件/档位（Suite/Tier）**；UI 面用**角色模式（Role Mode）**。只有泳道式视觉布局才回归 Lane 本义（swimlane）。
3. **CLI 与摘要契约**：门禁测试层参数名为 `--suite`（`L1`/`L2`/`L3`/`All`/`Doc`，默认 `L1`）；`--profile`（`PullRequest`/`Nightly`/`Release`，默认 `PullRequest`）正交，二者不合并。摘要文件 `TestResults/summary-<suite 小写>.json`，schema v2 键为 `suite`/`suites`（v1 曾用 `lane`/`lanes`，v2 改名即为此项消解）。
4. **类名收敛**：`UiLanePolicy`/`UiWorkbenchLane` 随自然重构改名为角色语义；专项改名须挂批次并走目录搬动同步。

**违规判据**：单写「Lane」；把 `--profile` 当测试层旋钮；新代码/新脚本写 `--lane` 或输出 `lane`/`lanes` 摘要键。

### 5.2 登记——注册表行 vs 债登记 vs 索引登记

**三义**：①UI 工具链把页面写入 `Luban/Data/#uiform.xlsx` 表行（`tbuiform`，入口 `ui.page-register`）；②把债记入质量登记表（`审计/**`）；③把新文档补进 README 索引。

**规则**：「登记」保留为泛动词，靠**限定搭配**消歧；无上下文的单写「登记」默认按②理解。

1. 页面/控件/服务写入表或容器 → **注册（Register）**；
2. 债/事实记入登记表 → **登记**（表本身＝债务登记表，Debt Register）；
3. 文档补进索引 → **索引登记**。

**违规判据**：用「登记」指表写入而不加限定；把索引登记写成「登记文档」；把债条目说成「注册」。

### 5.3 允许的同形复用

同一概念族的两个用法不算双义，不消解：

- **快照**：网络同步快照 / 批次 checkpoint——同为 Snapshot；
- **摘要（Digest）**：BuildHash 源集摘要 / `CombatConfigDigest` 运行期摘要——同为 Message Digest。

### 5.4 服务端同形 lane（登记待消解）

服务端还有一组与测试套件无关的 lane 同形词：传输/限流的 `Control lane`/`Outbound lane`（队列语义，业界对应 queue / channel）与限流 lane（限流键维度，业界对应 dimension / scope）。它们与 §5.1 无关，消解随服务端工作另行裁决；本文先行登记，禁止与此处两义串用。

## 6. 代码标识符用词规约

> 本节按四类问题组织：**缩写不统一**（6.1 / 6.9）、**同名异域与异名同物**（6.10）、**前缀混用**（6.11）、**改名流程**（6.12）。6.1–6.4 裁用词，6.5–6.8 裁结构与边界。

### 6.1 大小写（.NET 设计准则）

- **两字母缩写全大写**：`UI`（如 `UIFocusCoordinator`）、`GM`、`IO`；**`Id` 例外**——.NET 指南用 `Id` 而非 `ID`（`EntityId`/`PlayerId`）。
- **三字母及以上帕斯卡**：`Hud`（如 `DevHudFilter`）、`Kcp`、`Aoi`、`Tps`、`Vfx`。
- **存量现状**：类名前缀 `Gm` 与 `GM` 并存，属历史不一致（UI 域已随 2026-11-03 批 1 迁 `UI`；客户端 GM 工具类型已随批 2 迁 `GM`；协议/框架成员 `GmFlags`/`GmKey`/`GmOnly`/`GmBlocked` 与服务端 GM 通道仍为存量，改名须同步 proto/JSON）。**2026-10-29 裁决：`UI`/`GM` 是唯一目标拼法**；`Ui`/`Gm`/`HUD` 只作存量债，新增标识符一律按本节，存量按批次收敛（不按层分裂；逐项落定见 §6.9）。
- **只裁标识符**：文档行文里的全大写缩写（UI/API/JSON）不受本节约束；标识符内的缩写才按本节。
- **测试方法命名例外（2026-10-29 裁决）**：测试方法名允许中文；统一用 `_` 分段的语义短语（如 `场景_行为_预期`，段数不限），禁止空格/标点；测试名中的既有领域缩写（`HUD`/`UI` 等）保持原词，不做 Pascal 改写。生产标识符仍按本节 ASCII/PascalCase，不因测试例外放宽。
- **违规判据**：新增类型名出现与本节相悖的第二拼法（如新 `UIButton` 与既有 `UiButton`、`GMSceneCommands` 与 `GmSceneCommands` 并存）；把三字母及以上缩写写成全大写（`HUD`）；测试方法名含空格/标点。

### 6.2 动词语义

| 动词 | 语义 | 业界对应 |
| --- | --- | --- |
| `Take*` | 消费性获取：读即清或接管所有权，不可重复取 | `BlockingCollection<T>.Take`、channel receive |
| `Get*` / `Resolve*` | 幂等纯读，不改变状态 | DI Resolve / accessor |

二者禁止对同一资源混用。`GameEntry.TakeContainer`、`TakeSnapshot`、`TakeExitRequest` 均为消费语义，属正确用法；反之不得用 `Get` 命名读清语义的方法。

**违规判据**：同一资源同时存在 `Take*` 与 `Get*` 两个入口；新增读清方法命名为 `Get*`。

### 6.5 程序集名与命名空间（解耦约定）

- **程序集名表达部署/依赖边界，命名空间表达领域**；两者不要求同名。
- **现行约定（细则与例外见 §6.11）**：框架侧根命名空间 `LiteFramework`——`Core` / `Adapters` 基础设施平铺，模块按 `<根>.<模块>` 给子命名空间（`LiteFramework.UI` / `Animation` / `Diagnostics` 已存在）；共享内核各自保留根 `LiteSim` / `LiteNet` / `LiteSync`；服务端 `RoomServer.*` / `MetaServer.*`；产品侧壳件用 `LiteGame`，域程序集用 `LiteGame.Modules.<域>`。
- **例**：`LiteFramework.Runtime` 的 UI 模块 → `namespace LiteFramework.UI`（实测 `Assets/LiteFramework/Runtime/Services/UI/Widgets/VirtualList.cs`）；`LiteGame.Modules.Battle` 的目标命名空间 → `LiteGame.Modules.Battle`（现状平铺属存量，见 §6.11-E）；`LiteGame.Core` 的契约件 → `namespace LiteGame`（过渡）；`LiteGame.Editor.UITools` → `namespace LiteGame.Editor.UITools.*`（编辑器工具按子域）。
- **后果**：`using LiteFramework;` 同时覆盖 `LiteFramework.Core` 与 `LiteFramework.Runtime`（同根命名空间，`using` 不区分程序集）；Runtime 内部的依赖调查以**目录与命名空间**为准（Core / Modules / Adapters 三层由纪律扫描守），跨程序集依赖仍以 asmdef 为准。
- **新程序集**：只有拆出**独立领域**才允许新领域命名空间；仅按部署边界拆分时不改命名空间（避免全仓 `using` 漂移）。
- **违规判据**：领域未变却为新程序集另起命名空间根；同一程序集内出现两套命名空间根；以 asmdef 名反推命名空间。

### 6.6 作弊/调试能力分类词

- **DevCheat（开发作弊）**：本机开发面的免死/无限弹/传送/bot/调试绘制等；只住 `LiteGame.Adapters.Dev`，经 `IDevSession` 暴露给产品。
- **MatchSandbox（测试沙盒）**：本地测试房的每局规则与宿主钩子（`MatchTestRules`/`ILocalTestHooks`）；只随测试房生效。
- **OpsGm（运维 GM）**：云端运维动作（开房/中止/踢人/结算/诊断）；服务端端点＋审计，不进客户端运行时。
- **AntiCheat（反作弊）**：服务端判定/夹取/校验（`InputGate`/`LagCompensator`/checksum/身份摘要）；不是可开关模块。
- **用词纪律**：文档与代码禁止用裸「作弊」混指四类；必须按 `DevCheat`/`MatchSandbox`/`OpsGm`/`AntiCheat` 之一命名。新增能力先归类，再决定落点。
- **违规判据**：新增能力用裸「作弊」「GM」混指；把 OpsGm 端点放进客户端运行时。

### 6.7 结构单元：模块 / 子模块 / 装配件 / 系统 / 服务 / 适配器 / 组件

同一个"模块"在旧文档里指过四种东西（目录、程序集、装配段、功能集合），导致拆分决策尺度失真
（2026-11-02 评审实锤：`12 个域` 被当成 `12 个模块` 去切程序集）。2026-11-03 起统一为七个词，
每个只有一个含义；旧词（域/能力/段/包）只作历史名词，不再用于新写。

- **模块（Module）**：一个**变化原因 + 一个所有权**的单位。物理形态＝`Assets/LiteGame/Modules/<模块>/`
  ＋ 程序集 `LiteGame.Modules.<模块>`；只有模块出现在 [18-域间引用矩阵](../说明/18-域间引用矩阵.md) 的列上，
  跨模块直引必须登记。**两类**：
  - **业务模块**：有运行时状态与独立生命周期（会话/连接/阶段），**可以依赖其他业务模块**。
    现行 4 个：Battle、Meta、Session、Procedure。
  - **服务模块**：只有只读或缓存状态，随宿主存活，**不得依赖任何业务模块**（叶子）。
    现行 6 个：Camera、Config、Input、Map、Settings、Ui。
  - `Modules/Composition`（组装件）、`Modules/Dev`（开发契约包）、`Modules/Shared`（常量包）、
    `Modules/Battle/Abstractions`（`LiteGame.Battle.Abstractions`，战斗契约包）**不是模块**——
    有目录和程序集，但没有独立变化原因，一律按"件"称呼。
- **子模块（Submodule）**：模块内的二级职责目录，目录名一律 `<职责>SubModule`（`Modules/Battle/SubModules/{ArenaSubModule,HudSubModule,CombatSubModule,...}`），**无 asmdef**，靠目录＋命名空间＋引用纪律约束。**≥2 个子模块时归 `SubModules/` 容器，仅 1 个时直接放模块根**；`Abstractions/`/`Core/`/`Generated/`/`Shared/` 是保留技术名，不进容器。**三档**：
  - **共享子模块**：被 ≥2 个子模块依赖（现役 `ArenaSubModule/`，被 Aim/Characters/Combat/Hud/Setup 消费）；
    只许依赖域根与 `Abstractions/`，**不得依赖任何叶子**。
  - **叶子子模块**：只许依赖域根、`Abstractions/` 与共享子模块。
  - **装配子模块**（`SetupSubModule/`）：唯一可全向依赖。
  子模块间允许直引，但方向必须构成 DAG（`DomainBoundaryTests` 钉住"叶子不得引装配包""共享不得引叶子"）。
  子模块名必须是职责名 + `SubModule` 后缀（`View/Presentation/Domain/Logic` 被钉死）。
- **装配件（Segment）**：`Modules/<模块>/<模块>Segment.cs` 里的一个 `IClientSegment` 实现＝一个
  **生命周期单元**（初始化/关闭时机 + 它 `Put` 的产物集）。一个装配件可产多个服务（实测 1～14 个，均值 4.4），
  **装配件数 ≠ 模块数**："18 个装配件"是装配序刻度，不是功能划分刻度。存量类名 `*Composition`/`*Module`
  与接口 `IClientSegment` 随批改名，见 [09 分层与命名 §5](09-分层与命名.md)。
- **系统（System）**：`Packages/com.litegame.sim/Systems/*System.cs`，`public static class` ＋ `Run(...)`，
  只能在 `SimStep.Step` 的固定序里被调用一次；不持状态、不被表现层调用。判据＝"在固定步进序里有一个确定槽位"，
  与行数无关（21 行的 `CleanupSystem` 与 272 行的 `WeaponSystem` 同为合法粒度）。
- **服务（Service）**：**类型角色，不是目录**——实现端口的无状态对象，注册进容器且有生产消费者。
  可住业务模块、服务模块、适配器或框架 `Services/`。判据＝"能报出类名 + 实现哪个端口 + 注册在哪"。
  不得用"服务"命名目录（服务与模块是两个维度：模块答"住哪"，服务答"是什么"）。
- **适配器（Adapter）**：`Assets/LiteGame/Adapters/<第三方>/` 与 `Assets/LiteFramework/Runtime/Adapters/<第三方>/`，
  实现模块自持端口，只由组合根装配；模块不得反向引用适配器。
- **驱动（Driver）**：表现层事件消费者（`*Driver`），一个事件族一个驱动，驱动之间不互调，
  只读事件/端口、不回写 `Sim`。**现存两义待拆**：事件消费（13 个，如 `BattleAudioDriver`）与逐帧推进
  （3 个，如 `CharacterLocomotionDriver`）并存，本节与 §6.10 的"逐帧驱动"定义冲突；目标拆分——
  事件消费改 `*Consumer`，逐帧推进保留 `*Driver`，随批收敛。
- **组件（Component）**：只指 Unity 引擎载体（`UnityEngine.Component`、`UIWidget`），**不是架构单元**；
  Sim 明确不上 ECS（[Sim组织专项设计](../设计文档/游戏玩法/Sim组织专项设计.md) §2），状态用同槽位平行数组。

**业务模块 vs 服务模块的四条判据**（均可实测）：

| 判据 | 业务模块 | 服务模块 |
|---|---|---|
| 状态 | 有运行时状态（会话/连接/阶段/大厅） | 只读或缓存 |
| 生命周期 | 自己初始化/关闭 | 随宿主 |
| 依赖方向 | **可依赖其他业务模块** | **不得依赖任何业务模块**（18 矩阵行可验） |
| 对外端口 | 编排端口（`IBattleRun`/`IMatchJoin`/`IAppFlow`） | 能力端口（`ICameraService`/`IInputService`） |

服务模块之间允许依赖（登记边，如 `Map → Config`、`Ui → Config`）；服务模块 → 业务模块禁止。

**新增模块的判据**（五问，全过才建）：有可变状态 → 有唯一写者 → 被 ≥2 个模块消费（否则做子模块）→
有业务语义（否则进框架 `Services/`）→ 依赖只指向下层。**新增服务模块的成本与业务模块同级**（都要 asmdef、
程序集、矩阵列、装配件），能并进现有模块就别新建。

**子模块拆分的触发线**（任一触发即评估）：文件数 > 20、顶层类型 > 30、被第二个模块直接引用。
触发后先走"提取成模块"（需端口 + 外部消费者 + 无回边）；不满足则维持子模块，并靠守卫测试把包轴纪律机械化
（而不是为它加 asmdef——9 个子模块各加 asmdef 的成本远大于收益）。

**用词纪律**：说"模块"时必须能判定是业务模块还是服务模块；说"子模块"时不得简称"模块"；
不得用"系统"指客户端模块（`System` 专指 Sim 槽位）；"服务"必须能报出端口与注册点；
不得让"模块"同时覆盖目录/程序集/装配件。

**违规判据**：文档出现"XX 模块"而无法判定业务/服务；把 `Composition`/`Dev`/`Shared` 称作模块；
新增 `*System` 却不在 `SimStep` 里被调用；服务模块引用业务模块；子模块名用技术分层词；
把 Unity 组件当架构单元；用"服务"给目录命名。

### 6.8 拆分语义：一条主问题 + 四条规则

§6.7 的七个单元用**三条件不同的轴**切（时间 / 所有权 / 通道），轴不统一——但**判据统一**。
任何结构单元都必须能回答同一句话：**这里有没有可变状态？写者是谁？**

- 答得出唯一写者 → **所有权单元**（域 / 能力）：状态与唯一写者同住，跨单元只经端口。
- 答"没有状态，只是顺序" → **时间单元**（系统 / 段）：只排序与装配，不持状态。
- 答"只读，从不写" → **通道单元**（驱动 / 表现装配）：单向消费事件。

四条规则（现有代码各自满足，此前只是没写成同一套话）：

- **R-A 时间单元不拥有状态**：`*System` 与 `*Composition` 里出现可变字段即偏离——状态住 `SimWorldState`
  或域内状态对象。理由：步进序与装配序是"调用序"，一旦持状态，顺序就变成隐式数据依赖。
- **R-B 所有权单元不依赖时序单元**：域/能力不得引用装配段（`Modules/*` 不引 `App`/`Adapters/*`，asmdef 已钉）。
  理由：时序在上、所有权在下，反引会把"何时初始化"泄进业务。
- **R-C 通道单元只读**：`*Driver` 消费事件/端口，不回写 `Sim`、驱动之间不互调（纪律扫描与目录惯例已钉）。
  理由：回写会制造第二写者，破坏判定的确定性与唯一性。
- **R-D 依赖方向优先于归属**：概念上"属于 A"的共用件若被 B 使用，放 A 与 B 都能依赖的下层
  （域根 / `Abstractions/`），不为归属造回边。反例：`WeaponMounts` 曾住装配子包（当时的 `Battle/Setup/`）却被 `Combat/` 使用，
  形成包级回边；下移域根后包图恢复 DAG。

**不统一的**：轴的数量（三轴并存不是缺陷——层级不同、回答的问题不同）；包内部的切法
（Battle 的包按 通道/阶段/物件/契约 四选一，见 [说明 14 §3.4](../说明/14-代码地图与根目录.md) 的包轴表）。

**违规判据**：`*System`/`*Composition` 出现可变字段；域引用装配段；驱动回写 `Sim`；为"概念归属"把共用件放在依赖上层。

### 6.12 改名迁移

- **一次一批、不许半改**：类型名、文件名、命名空间、asmdef 同批一致；半改比不改更贵。
- **顺序**：① 命名空间与类型名（纯 C#，先编译）→ ② 文件/目录（unity-pipeline，保 `.meta`/GUID）→ ③ asmdef 名与引用、allowlist/清单 → ④ 文档、测试、生成物。
- **Unity 序列化类**（MonoBehaviour / ScriptableObject / EditorWindow）：文件名必须等于类名，改名必须走 unity-pipeline；禁止只改类名。
- **禁区**：Lua 键（`Bridge.ui`）、Luban 表键（`tbuiform`/`tbltext`）、manifest 资源路径（`UiWidgetManifest.json`）、prefab 序列化字段名、`.meta` GUID。
- **共享源集**：改 `Packages/com.litegame.sim` / `com.litegame.net` 的标识符会改 BuildHash → 同批跑 `python scripts/codegen/toolbox.py build-hash`。
- **每批验证**：Unity 0 错、相关 EditMode/PlayMode、`python scripts/gate/test.py --suite L1`、`--suite Doc`。

**违规判据**：只改类型名不改文件名/命名空间；改 asmdef 名不更新引用；改共享源集不重跑 BuildHash；改 Lua 键/表键/序列化字段。
