## 0. 两条环：内环（本机）与外环（云）

| 环 | 形态 | 何时用 | 手册 |
|---|---|---|---|
| **内环** | 本机进程链：`local-chain.ps1 up`（Meta + Room + 本机 Mongo） | 日常迭代：改代码→重启即验；表现/手感/调参 | [07-本地联测](07-本地联测.md) |
| **外环** | 云主机 `docker compose`（Meta + Room + Mongo 三容器同机） | **跨网络真联机**、他人接入、容器形态验收（设计 §6 第 1–3 项） | 本文 |

云形态**不替代**内环：改玩法/表现仍在本机打转；上云只为"真实公网链路 + 非本人机器接入 + 容器编排验收"。两条环共用同一份密钥来源（`deploy/.env`，见 §2.2）。

## 1. 云主机供给（一次性）

- **规格**：2 vCPU / 4 GB / 40 GB SSD 起（三容器同机，Mongo 单节点副本集；容量不做承诺，同设计 §0 预算）。
- **系统**：Ubuntu 22.04/24.04 LTS（下方命令按 Debian 系写）。
- **装 Docker 与 compose 插件**：

```bash
curl -fsSL https://get.docker.com | sudo sh          # 或 sudo apt-get install -y docker.io docker-compose-v2
sudo systemctl enable --now docker
sudo usermod -aG docker $USER                        # 重新登录后免 sudo
```

- **端口与安全组**（白名单粒度按人手加 `/32`，同设计 §4 裁决点④）：

| 端口 | 协议 | 用途 | 开放给 |
|---|---|---|---|
| 22 | TCP | SSH 运维 | 运维 IP |
| 5000 | TCP | Meta（登录 / 大厅 / 战绩提交与查询） | 测试者白名单（或经 Caddy 走 443，§2.6） |
| **17777** | **UDP** | **RoomServer KCP 对局** | 测试者白名单 |
| 9100 | TCP | `/metrics`（Prometheus 文本） | **不对公网开**（本机 curl / SSH 隧道看） |
| 27017 | TCP | Mongo | **不开放**（compose 内网，不发布端口） |

- **SSH 加固（必做）**：云控制台新建实例的缺省安全组通常把 `22` 开给 `0.0.0.0/0`（厂商图你一键能连上），而公网扫描器会在**分钟级**内开始撞口令——按上表把 22 限到运维 IP。四件套一起做：① 只留密钥登录（`PasswordAuthentication no`、`PermitRootLogin prohibit-password`）；② 安全组限源 IP；③ 装 `fail2ban`；④（可选）换非标端口只减少日志噪声，**不替代** IP 白名单。注意"密钥登录"不等于"可以不限 IP"：扫描噪声、sshd 自身漏洞、密钥泄露都会因此缩小或放大——**SSH 没有第二道门**（对比：17777 还有信封 PSK 兜底且 fail-closed），所以 22 最该收紧。
- **防自锁（家宽 IP 会变）**：把 22 锁到 `/32` 后，家宽重拨换 IP 就 SSH 不进去。**先在云控制台确认 Web 终端 / VNC（不经 SSH）可用**，把它当破窗路径（IP 变了从控制台安全组补一条新 `/32` 即可）——别在"控制台也进不去"的前提下锁死 22。
- **落地顺序（照这个顺序做才不会把自己关在外面）**：
  1. **先备好破窗**：在控制台确认 Web 终端/VNC 能登进 OS——若实例只有密钥、没有 OS 密码，先在控制台**重置实例密码**（部分厂商重置后**需重启实例**，早点做）。SSH 这时还开着，正好用来收尾。
  2. **装公钥并当场验证**：`mkdir -p ~/.ssh && chmod 700 ~/.ssh` → 追加公钥到 `~/.ssh/authorized_keys` + `chmod 600` →**另开一个终端**用密钥登入成功（此时**不要**断开当前会话）。
  3. **硬 sshd**（写 drop-in，再验后重启）：

     ```bash
     sudo tee /etc/ssh/sshd_config.d/00-hardening.conf >/dev/null <<'EOF'
     PasswordAuthentication no
     KbdInteractiveAuthentication no
     PermitRootLogin prohibit-password
     PubkeyAuthentication yes
     EOF
     sudo sshd -T | grep -Ei 'passwordauthentication|permitrootlogin|pubkeyauthentication'   # 必须是三项都符合预期
     sudo systemctl restart ssh
     ```

     文件名用 `00-` 前缀是**有意的**：sshd 对多数选项取"**先出现者生效**"，而 Ubuntu 的 `sshd_config` 在**顶部** `Include /etc/ssh/sshd_config.d/*.conf`、cloud-init 又写了 `50-cloud-init.conf`（可能带 `PasswordAuthentication yes`）——按字母序，`00-` 才压得住它。第 2 条命令是权威复核（`sshd -T` 会把 include 展开后算总账），**别只看文件写了什么**。
  4. **`sudo apt-get install -y fail2ban`**（少量成本，补一层日志侧拦截）。
  5. **这步才动安全组**：把 `22` 的源从 `0.0.0.0/0` 收成你的 IP `/32`。取 IP **别用 `curl ifconfig.me`**（本机挂着代理时它给你的可能是代理出口 IP，加白了也没用）——用服务器视角的权威值：在还连着的会话里 `echo $SSH_CLIENT`（第一个字段就是安全组看到的源 IP）。
  6. **验证破窗**：断开 SSH → 从控制台 Web 终端登入成功 → 再从手机热点试 SSH（应超时）。这两条都过了，锁 22 才算收尾。

- **同一条推论适用于白名单本身**：`5000` / `17777` 也按 `/32` 加白，而测试者换网络（家宽/办公室/手机热点）就会连不上——把"谁来加白名单、多久复核一次"写进测试安排（设计 §4 裁决点④ 的口径）。
- **白名单不是"加一次管永久"**：规则本身**不过期**（加了就一直开，测完要撤掉，符合封闭测试最小暴露口径），但**源 IP 会变**——家宽重拨/路由重启、手机热点、办公室 NAT、以及本机代理（TUN/全局模式会把 SSH 出口换成代理节点 IP，与"直连时的 IP"不是同一个）。所以：① **给自己预先加 2–3 条**（家宽 + 办公室 + 手机热点），换网络不必现场找控制台；② 加之前用**服务器视角**确认（`echo $SSH_CLIENT`，别用 `curl ifconfig.me`——挂代理时会报代理出口 IP）；③ 别人（测试者）的 IP 只能**线下报给你**（被安全组挡掉的流量到不了服务器，日志里看不到）；④ 连不上时先怀疑"IP 变了"与"是否走了 IPv6"（只加了 v4 `/32` 而连接走 v6 同样不匹配）。
- **域名与 HTTPS（可选）**：要 HTTPS 就启用 `--profile tls`（Caddy + `DOMAIN`，DNS A 记录指向本机）；国内主机绑域名需备案，**封闭测试可先用 `http://<公网IP>:5000`**（Meta 侧 `AllowNonLoopbackHttp` 已由 compose 显式放行）。

### 1.1 自动化接入：让"非交互式的 ssh"能跑（部署与运维都靠它）

人和 Agent 的操作通道是同一条：**从开发机 SSH 出去**。所以目标不是"能手动登进去"，而是"`ssh <别名> <命令>` 能不开提示地跑通"——交互式提问（主机指纹确认、sudo 口令）会卡住任何自动化。四件事：

1. **专用密钥**，不复用别处的（如 git 服务器那把）：`ssh-keygen -t ed25519 -f ~/.ssh/id_ed25519_litegame -C "litegame-closed-test"`。
   - **无口令**（直接回车）＝ 任何自动化都能无人值守跑；代价是"拿到这个文件即可登录"。缓解：密钥专用、`chmod 600`、账号非 root、安全组限源 IP。
   - 想留口令：用 `ssh-agent`（`ssh-add` 输入一次，之后由 agent 代签）。注意 Git Bash 下 agent 与会话的联通性不稳，**先试通再用**；不通就退回"你敲命令、把输出贴回来"。
2. **本机 `~/.ssh/config` 加一段别名**（免去每次打一长串参数，也是自动化脚本引用的稳定入口）：

   ```sshconfig
   Host litegame-cloud
       HostName <云主机公网IP>
       User <登录用户名>
       IdentityFile ~/.ssh/id_ed25519_litegame
       IdentitiesOnly yes          # 只用这一把，不遍历其它密钥（避免"试错太多次被服务器拒"）
       StrictHostKeyChecking accept-new   # 首次连接自动记录指纹（不弹 yes/no）
       ServerAliveInterval 30
   ```

   `accept-new` 的含义是"**首次**连接无条件信任"——全新 VPS 可接受；要更严就先手动连一次，把控制台显示的指纹与 `ssh-keyscan` 结果对一下再写进 `known_hosts`。
3. **特权步骤别交给免密 sudo**：`apt install` / `systemctl` 这类由**你在控制台（或你自己的 ssh 会话）粘一次**（见 §1 的安装块），此后自动化只做"不需要 sudo"的事（预装 Docker 后普通用户进 `docker` 组即可跑 compose）。真要免密，也只给**具体的几条命令**写 `NOPASSWD`，不要整条 `ALL`。
4. **公钥怎么上服务器**（二选一）：创建实例时绑了密钥对 → 直接用那把私钥；没有 → 控制台 Web 终端 / VNC 登进去，把公钥追加到 `~/.ssh/authorized_keys`（`chmod 700 ~/.ssh && chmod 600 ~/.ssh/authorized_keys`），比"绑定密钥对"少一次重启。

**给自动化准备的三样信息**（**永远不要传私钥内容**）：`~/.ssh/config` 里的别名、登录用户名、私钥路径。另：确认 SSH 没被本机代理的 TUN/全局模式接管（那会让安全组看到的源 IP 变成代理出口，白名单加错人）。

### 1.2 访问模型：逐人白名单 / 云侧 VPN / 隧道（先选一个，别等开测再想）

三种模型都合规（设计 §4 裁决点④ 的默认与**备选**），差别只在"谁的活、什么时候干"：

| 模型 | 公网暴露 | 测试者要做什么 | 换网络要重加吗 | 适用 |
|---|---|---|---|---|
| **A 逐人 IP 白名单**（设计缺省） | `22` + `5000` + `17777` 各按 `/32` 加白 | 报一次出口 IP | **要**（家宽/热点一变就断） | 1–4 人、一周内测完 |
| **B 云侧 VPN**（设计 §4 裁决点④ 备选，原话"测试者多时改云侧 VPN/跳板"） | **只留 VPN 的口**（如 WireGuard `UDP 51820`）；`22`/`5000`/`17777` 对公网**全关** | 装一次客户端 + 导入你给的配置（你自己生成，一人约 2 分钟） | **不用**（IP 无关） | >5 人、或测试跨多周、或你自己常换网络 |
| **C 隧道反代**（只解决 Meta 的 TCP） | 不出站口（Cloudflare Tunnel 等），可选邮箱验证码门 | 拿到一个稳定域名 | 不用 | 想给 Meta 一个稳定 HTTPS 域名；**UDP 那条仍需 A 或 B** |

**选择规矩**：预计测试跨周、或测试者超过 5 人、或你自己要在多个网络间切换 → 直接上 B；否则 A 够用（把 churn 当已知成本：只招家里宽带的测试者，开测前顺口问一句"这周会不会换网络"）。

**选 B 时要动四处（别漏）**：

1. `deploy/roomserver.container.json` 的 `lobby.advertise_host` 填 **VPN 服务端地址**（如 `10.8.0.1`）——票据下发的就是这个地址，客户端才会走隧道（§2.3 机制）；
2. 客户端 `-meta.url` 也用 VPN 地址（`http://10.8.0.1:5000`），**且必须随包烙入**（`deploy.args`/本地 profile 的 endpoints，§3.3）；
3. `deploy/.env` 加 `LITEGAME_PUBLISH_HOST=10.8.0.1`——容器端口只发布到隧道地址 ⇒ **公网 IP 上压根没有 5000/17777**（安全组配错也够不着）；缺省 `0.0.0.0` = 模型 A 形态。绑隧道地址时注意开机次序：docker 若早于 `wg-quick@wg0` 起，绑定失败由 `restart: unless-stopped` 重试到 wg0 就位；
4. **你自己的开发机也要进隧道**（作为 0 号测试者）：不然编辑器连不上 `10.8.0.1`、`curl` 自检与日志排查也都没路——用 [Dist/](../../Dist/README.md) 那套给自己打一份包（`-SkipGameCopy`），跑一次装好隧道即可（此后开机自启）。

安全组随之收敛为：`51820/udp` 对 `0.0.0.0/0`（WireGuard 本身就是"密钥即门票"，端口公开是正常形态）、`22/tcp` 只给管理 IP（或稳定后也收进隧道）、`5000`/`17777`/`9100` **不对公网开**。

选 B 的溢价与坑：隧道终点就在同一台机上，多出的只是加解密（延迟代价约等于零）；但测试者网络若封 UDP，`51820` 多半也通不了（要 `udp2raw`/`wstunnel` 之类兜底，属额外工程量）；用托管方案（Tailscale/ZeroTier）配置更省事，但国内连通性看运气、且依赖第三方协调服务——自建 WireGuard 最稳。

选 B 后 §6 第 1 项的验收证据改写为："**公网上不存在游戏入口** + 未持配置者不可达"——比"白名单外不可达"等效且更强，记录时按此口径留证。

**B 模型里测试者到底要做什么**（如实，别粉饰）：装一次官方 WireGuard（Windows 约 2 MB，免注册免账号）→ "导入隧道（从文件）"选你发的 `.conf` → 点"激活"。**约 2 分钟、一次性**；此后换网络、开热点都不用再动。对比 A 模型每次换网都要重报 IP——对超过几天的测试，这一次性投入通常更划算。

**A 与 B 可以混用**：公司机装不了 VPN 客户端（无管理员权限 / 禁装网络驱动）的那一两个人，单独给他们的固定 IP 加白即可，两套并存无冲突。

**"不想让测试者装任何东西"的代价（如实）**：那只剩 A（人工、随 IP 漂）或自建**动态白名单门**——测试者点一个带密钥的公开链接，你的小程序读到来访源 IP、调云厂商 API 自动加一条带 TTL 的 `/32` 并在到期后撤掉。后者不要客户端安装、也不要你手工加白，但要写一个小服务、保管云 API 凭据、还多一个公网面——三五个人的封闭测试不值得，人多了（十几人、长期）再评估。

**选 B 的现成分发包**：[`Dist/`](../../Dist/README.md)（根目录下的分发组装目录）已备好测试者侧一键包（`加入联机环境.cmd` 双击入口 + `Join-LiteGameTest.ps1`：自动装 WireGuard → 把 `.conf` 装成隧道服务 → `GET /live` 连通自检）与**组装助手** `New-Package.ps1`（拼好待发包：游戏构建 + 该测试者的 `.conf` + `server.txt` + 接入脚本，可选 `-Zip`；详见 [Dist/README.md](../../Dist/README.md)）。**只有 `.conf` 因人而异**，游戏包所有人同一份（端点出包时就烙进 `StreamingAssets/deploy.args`，§3.3）。

**云侧一次性配置（Ubuntu）**：

```bash
sudo apt-get install -y wireguard
umask 077
wg genkey | sudo tee /etc/wireguard/server.key | wg pubkey | sudo tee /etc/wireguard/server.pub
printf '%s:51820\n' '<公网IP>' | sudo tee /etc/wireguard/litegame-endpoint >/dev/null   # 客户端 .conf 的 Endpoint
sudo tee /etc/wireguard/wg0.conf >/dev/null <<EOF
[Interface]
Address = 10.8.0.1/24
ListenPort = 51820
PrivateKey = $(sudo cat /etc/wireguard/server.key)
EOF
sudo systemctl enable --now wg-quick@wg0
sudo wg show
```

每个测试者一条命令（用 [`deploy/wg/wg-peers.sh`](../../deploy/wg/README.md)：生成密钥 → 追加 peer → 热加载 → 输出 TA 的 `.conf`）：

```bash
sudo install -m 755 deploy/wg/wg-peers.sh /usr/local/sbin/wg-peers.sh   # 一次性
sudo /usr/local/sbin/wg-peers.sh add alice        # → /tmp/alice.conf（600；拿回本机打包）
sudo /usr/local/sbin/wg-peers.sh list             # 谁开过、各自隧道内地址
sudo /usr/local/sbin/wg-peers.sh remove alice     # 人退出测试时撤回
```

> **想让我自己加人**（不必每次找你敲 sudo）：给它一条**窄免密**即可——`<部署用户> ALL=(root) NOPASSWD: /usr/local/sbin/wg-peers.sh`。**只放行这一个脚本，不要 `ALL`**：脚本本身不做内部 sudo（假定已是 root），特权面就是这一行 + 那个可审计的脚本。

手工做法（对照 / 脚本坏了时的兜底）：

```bash
N=2; T=alice
wg genkey | tee /tmp/$T.key | wg pubkey > /tmp/$T.pub
sudo tee -a /etc/wireguard/wg0.conf >/dev/null <<EOF

[Peer]
# $T
PublicKey = $(cat /tmp/$T.pub)
AllowedIPs = 10.8.0.$N/32
EOF
sudo wg syncconf wg0 <(wg-quick strip wg0)      # 热加载，不断已有连接

cat > /tmp/$T.conf <<EOF
[Interface]
PrivateKey = $(cat /tmp/$T.key)
Address = 10.8.0.$N/24
MTU = 1420

[Peer]
PublicKey = $(sudo cat /etc/wireguard/server.pub)
Endpoint = <云主机公网IP>:51820
AllowedIPs = 10.8.0.0/24        # split tunnel：只把服务器网段导进隧道
PersistentKeepalive = 25
EOF
rm -f /tmp/$T.key               # 私钥只存在于要发出去的那份 .conf 里
```

把 `rm -f` 之后剩下的 `/tmp/$T.conf` 与游戏、地址交给组装助手打包：`cp Dist/server.txt.example Dist/server.txt`（填 `http://10.8.0.1:5000`）→ `pwsh -NoProfile -File Dist/New-Package.ps1 -Tester $T -Conf <$T.conf> -Zip` → 发 `Dist/out/$T.zip`（结构见 [Dist/README.md](../../Dist/README.md)）。

**三个现场坑（发之前先知道）**：

1. **`AllowedIPs` 只写 `10.8.0.0/24`**：写成 `0.0.0.0/0` 会把测试者的**全部上网流量**也拽进隧道（他变慢、你成了他的出口，隐私面也不对）。
2. **脚本可能被 Windows 拦**：从网上/网盘下来的 `.cmd` 会带"来自互联网"标记，双击可能没反应或被 SmartScreen 拦——教他"右键 → 属性 → 勾选**解除锁定** → 再双击"（zip 分发同理）。
3. **装 VPN 客户端会被部分安全软件盯上**（驱动级操作）：脚本会在"装完是否真的到位"那步报出来（`装完仍找不到 wireguard.exe`）——那一两个人改走 A 模型（给他的固定 IP 加白）即可，不用为一个客户端折腾。

## 2. 服务端部署（compose）

编排、Dockerfile、配置模板都在 `deploy/`（《上云测试专项设计》批B 制品，本机容器级验收已完成 §6 第 4–7 项）。

### 2.1 取码与构建上下文

- 构建上下文 = **仓库根**（源链接件跨目录）。镜像所需内容**全部在 git 内**（`Server/**`、`Assets/{LiteNet,LiteSim,RoomServer,GameData}`、`Config/`）——云上 `git clone` 即可构建，**不需要**搬 `Library/`、美术、`StreamingAssets`。
- **基础镜像通道**：构建机要能拿到 `mcr.microsoft.com/dotnet/{sdk,runtime,aspnet}:8.0` 与 `mongo:8.0`。国内云直连 mcr 常慢或不通，两条现成路：
  - **本地导出再导入**（推荐，本机已有这四个镜像）：`docker save mongo:8.0 mcr.microsoft.com/dotnet/sdk:8.0 mcr.microsoft.com/dotnet/runtime:8.0 mcr.microsoft.com/dotnet/aspnet:8.0 | gzip > base.tgz` → `scp` → 云上 `docker load`；
  - 镜像源回打标签（daocloud 形态，命令见 `deploy/README.md`）。
- **NuGet 代理**：`DOCKER_BUILD_HTTP_PROXY` 在云上**必须留空**（直连 nuget.org）；只有本机经 Clash 构建时才填 `http://host.docker.internal:7897`。
- **分发形态选择**：云上 `git clone` + `up --build`（简单，但每次要拉 SDK 层与 NuGet）；或本地 `docker compose build` → `save` 两个应用镜像 → `scp`/`load`（国内网络通常更快，且构建环境与内环一致）。

### 2.2 密钥与 `deploy/.env`（**先读：已实测的坑**）

同一路径 `deploy/.env` 被**两个消费者**用**两套键名**读：

| 消费者 | 键名 |
|---|---|
| `scripts/local/local-chain.ps1`（内环） | `ENVELOPE_PSK` / `AUTH_SIGNING_KEY` / `LOBBY_INSTANCE_KEY` / `LOBBY_TICKET_KEY` / `SETTLEMENT_KEY` |
| `deploy/compose.yaml`（外环） | `${LITENET_SECURE_ENVELOPE_KEY}` / `${META_AUTH_SIGNING_KEY}` / `${LITENET_LOBBY_INSTANCE_KEY}` / `${LITENET_SETTLEMENT_INSTANCE_KEY}` / `${TICKET_KEY_BASE64}` |

**实测证据（2026-10-17，本机）**：在由内环脚本写的 `deploy/.env` 下执行 `docker compose config`，五个密钥**全部解析为空**，`LITENET_TICKET_KEY` 渲染为 `"l1:"` → 直接 `up` 是 fail-closed 拒启（Meta 缺签名密钥、Room 缺信封键）。这不是容器缺陷，是"一个文件两套命名互相踩"。

**现状：已消解（同一批，2026-10-17）**——compose 每处密钥改为**双名回退**（`${本编排名:-${内环名}}`），一份机器私有 `.env` 两个消费者都读（单源，且不必另存一份密钥）。自查：

```bash
cd deploy && docker compose config | grep -E "META_Meta__(Auth|Lobby|Settlement)|LITENET_"   # 五处应全是值，不应为空
```

| 键（容器本名） | 回退读的内环名 |
|---|---|
| `META_AUTH_SIGNING_KEY` | `AUTH_SIGNING_KEY` |
| `LITENET_LOBBY_INSTANCE_KEY` | `LOBBY_INSTANCE_KEY` |
| `TICKET_KEY_BASE64` | `LOBBY_TICKET_KEY` |
| `LITENET_SETTLEMENT_INSTANCE_KEY` | `SETTLEMENT_KEY` |
| `LITENET_SECURE_ENVELOPE_KEY` | `ENVELOPE_PSK` |

若你的 compose 版本不支持嵌套回退插值（上面自查渲染出空值），退回**两份 env 文件**：内环 `deploy/.env`、外环 `deploy/.env.compose`，容器链走 `docker compose --env-file .env.compose up -d`（代价：密钥存两份，易漂）。

密钥生成（32 字节 → base64，与 §1 生成命令同源）：

```bash
python -c "import os,base64;print(base64.b64encode(os.urandom(32)).decode())"
```

| 密钥 | 用途 | 客户端需要吗 |
|---|---|---|
| 信封 PSK（`ENVELOPE_PSK`/`LITENET_SECURE_ENVELOPE_KEY`） | KCP 安全信封，**两端必须同值** | **需要**（§3） |
| `AUTH_SIGNING_KEY` | 访问令牌 HMAC | 否 |
| `LOBBY_INSTANCE_KEY` | 房间服实例注册凭据（= Meta `LobbyInstanceKeyBase64`） | 否 |
| `LOBBY_TICKET_KEY` / `TICKET_KEY_BASE64` | Join 票据验签（单源：room 侧拼 `l1:<base64>`） | 否 |
| `SETTLEMENT_KEY` | 结算提交凭据 | 否 |

> 密钥红线：只落机器私有 `deploy/.env`（已 gitignore）；不进 compose 明文、不进命令行、不进文档、不截图。

### 2.3 房间服对外地址（**必改，否则每个客户端都连自己**）

`deploy/roomserver.container.json` 的 `lobby.advertise_host` 改成**公网 IP**：

```json
"lobby": { "url": "http://metaserver:5000/lobby/instances/register",
           "instance_id": "room-1", "advertise_host": "<公网IP>" }
```

机制（代码事实）：房间服心跳注册上报的地址 = `advertise_host + ":" + port`；Meta 签票时把它随票据下发（票据响应的 `Address`）；客户端据此连房。留 `127.0.0.1` = 客户端连自己的机器 → 对局永远进不去。
改完要 `docker compose up -d`（配置在**启动时快照**，运行中不重读）。

### 2.5 首次联机建议：用一个"快对局"模板

"rooms": { "fast": { "expected_players": 2, "kill_limit": 3, "match_duration_frames": 3600,

（房规模由客户端「创建房间」选的人数随票据盖章，`0` = 按模板；上界=内核席位容量。模板名只决定其余规则与缺省人数。）

## 3. 客户端接入（编辑器 + 打好的 exe）

### 3.1 客户端只需要三样输入（其中一样可选）

| 项 | 是否密 | 值 |
|---|---|---|
| `-meta.url` | 否 | `http://<公网IP>:5000`（基址末尾不带 `/`） |
| `-envelope.key` | **是** | 与服务端同一把信封 PSK（base64） |
| `-device.id`（可选） | 否 | 游客身份键。不注入＝用平台机器标识——**同一台机器上的编辑器与 exe 会落到同一账号**；同机要各自身份时各给一个不同值（如 `ed-a` / `ed-b`）。同值 = 服务端同账号，上限 128 字节 |

房间地址**不配**——由票据下发（§2.3）。其余服务端密钥与客户端无关。

> **明文 HTTP 的客户端开关（现场踩过）**：`-meta.url` 用 `http://` 时，客户端还得放开 Unity 的"允许 http 下载"（`PlayerSettings.insecureHttpOption`）——**默认 `NotAllowed` 会让登录直接失败**（`UnityWebRequest` 抛 `Insecure connection not allowed`，编辑器与 player 都拦）。本工程已设为 **`AlwaysAllowed`（值 2）**：隧道内本就加密、Meta 侧也显式放行非回环 HTTP（§2.2），两端口径一致。**注意**：本工程实测 `developmentBuild: false`（**不是** Development 构建），所以 `DevelopmentOnly`（值 1）覆盖不到 player；要收紧成"只在开发构建放行"，得先把构建设置真的打开 Development 再回到 1。**改这个开关要重出包**（构建期烙定）。

### 3.2 注入口与合并序（代码事实）

命令行参数 > **包内烙入** `Assets/StreamingAssets/deploy.args` > 环境变量（仅信封）/默认；编辑器与 player 同一装载路径（`MetaDeployConfig.Load`），四个键（`meta.url`/`meta.timeout`/`envelope.key`/`device.id`）共用这套合并序。
因此：**编辑器**读工程内 `Assets/StreamingAssets/deploy.args`；**exe** 读打包时拷进包的那一份（`StreamingAssets/` 整目录随包分发），运行期也可用命令行覆盖。
未配置 `-meta.url` 是 **fail-closed**：登录页显示"未配置服务器"、按钮禁用，不悄悄回落本地。

### 3.3 推荐配置法：本地 profile 烙入（一份配置，两边同时生效）

1. `.gitignore` 增一行（**防 PSK 入库**）：`BuildProfiles/*.local.json`
2. 复制 `BuildProfiles/windows-x64.json` 为 `BuildProfiles/windows-x64-closedtest.local.json`，改 `profileName`，填端点到 `endpoints`（**值不可含空格**）：

```json
"endpoints": { "meta.url": "http://<公网IP>:5000", "envelope.key": "<信封PSK>" }
```

  同机两个客户端要各自身份时，再加 `"device.id": "ed-a"`（§3.1；另一份用 `ed-b`，或给其中一个客户端用命令行覆盖）。

3. 出包：`pwsh -NoProfile -File scripts/build/build-player.ps1 -Profile BuildProfiles/windows-x64-closedtest.local.json`
   内置内容包已接进构建链（步骤 3c，自动执行并轮询状态）——此前漏跑＝把上一版表/场景打进包，exe 启动即 `BOOT FAILED 配置文件加载失败:…`。细节与判据见 [07 §4.1](07-本地联测.md)。
   脚本会把 `endpoints` 烙进 `Assets/StreamingAssets/deploy.args`——**编辑器读同一份**，于是 exe 双击即玩、编辑器直接 Play，两边零参数启动且配置同源。

### 3.4 不想动 profile 的最小法

- **编辑器**：手写 `Assets/StreamingAssets/deploy.args` 两行（`-meta.url=…` / `-envelope.key=…`，该目录已 gitignore）。
- **exe**：快捷方式带参 `"Builds\StandaloneWindows64\Test.exe" -meta.url http://<公网IP>:5000 -envelope.key <PSK>`。
- 或 PSK 只走环境变量 `LITENET_SECURE_ENVELOPE_KEY`（编辑器需**启动 Unity 前**设好；exe 同进程环境），烙入里只放非密的 `meta.url`。
- **同机两个客户端**（编辑器 + exe）各自加 `-device.id <不同值>`——否则两者是同一个游客账号（§3.1）。

### 3.5 **打包副作用（必读坑）**

`build-player.ps1` 会用 `BuildProfile.endpoints` **重写** `Assets/StreamingAssets/deploy.args`；**endpoints 为空时直接删除该文件**（防上一个渠道的密钥残留随包分发）。
后果：用默认 profile（`endpoints: {}`）跑一次打包，**编辑器那份手写部署参数会被清掉**——下次 Play 变成"未配置服务器"（是显性拒绝，不是"连不上"，别误判成网络问题）。
处置：走 §3.3（打包输出与编辑器输入同源），或每次打包后重新写 `deploy.args`。

### 3.6 编辑器侧启动验证点

Play 后：登录页 → 游客一键登录 → 跳大厅；大厅 `Txt_PlayerName` = 账号短号；设置页/登录页版本行 = 云上实例的 `buildHash`（§2.4 同值）。登录失败看页内提示 + Toast（`UI.Login.*` / `ListFailed` 一类稳定码，`Network` = 到不了 Meta）。

## 4. 联机测试用例：两人一局（编辑器 + exe）

**准备**：云服在跑且 §2.4 自检通过；客户端注入同一 `meta.url` + 同一 PSK（§3）；**同机**两台客户端再各给一个不同 `-device.id`（否则两者是同一个游客账号——能进同一局，但战绩/结算按账号归并成一人）。

| 步 | 谁 | 动作 | 期望 |
|---|---|---|---|
| 1 | A（编辑器） | Play → 登录页「游客一键登录」 | 跳大厅，账号短号显示 |
| 2 | A | 大厅选图 + 人数选 **2**（下拉第一档）→「创建房间」 | 跳房间页，显示房号；席位名单 1 人 |
| 3 | B（exe） | 双击启动 → 同样游客登录 | 跳大厅 |
| 4 | B | 大厅列表出现 `房号 · 地图名`（`1/2`）→ **点该行** | 跳房间页，房号同 A；**两边名单都 2 人、`2/2`** |
| 5 | A（房主） | 房间页「开始对局」（钮只对房主可见） | 两边进对局；服务端开局横幅 |
| 6 | 双方 | 打到击杀上限 / 时限 | 两边出现 MatchEnded → 结算页 |
| 7 | A / B | 结算页记分板 | 本局冻结结果（本机 kills/deaths + 结束原因） |
| 8 | 任一方 | 大厅「战绩」 | 最近战绩含本局（按账号查） |

**顺序提醒**：B 的大厅列表在**进页时刷一次**（页内无刷新钮）——先让 A 建好房，B 再登录；或 B 退房返回大厅（替换回大厅会重刷）后再找。房间明细上报随房间服心跳走（缺省 10 s，`lobby.heartbeat_interval_ms`），A 建房后可能要等一个心跳周期才在列表可见。

**成功标志（服务端侧）**：房间服日志出现进房/开局行、Ops 周期行 `players=2`；结算链 `POST /matches/result → 200`、`Outbox/settlements.journal` 落盘、Meta `GET /matches` 有行。

**两个已确认的"别踩"**：

- **不要**用大厅「开发 → 直连对局」入口：全链服带票据门禁后，测试身份会被票据拒（[07 §5](07-本地联测.md) 同款硬事实）。全链只走"登录 → 大厅 → 进房"。
- **「快速进入」的落点房已配**（`lobby-default`）：容器侧 `${LITEGAME_DEFAULT_ROOM_ID:-lobby-default}`、内环脚本 `LOBBY_DEFAULT_ROOM_ID`（缺省写 `lobby-default`）。双方都点它就落**同一间缺省房**——两人连通性测试的最快通路（代价：不带选图/选人数，房规模按模板）。若该键被置空，这个钮会被 Meta 字段校验拒 400（排障表有对应行）。
- 要选图/人数、或想让对方在大厅列表里"看到我的房再点进来"，走 §4 步 2/4 的「创建房间」+ 列表行进入。

## 6. 一致性地雷（跨网络放大版，逐条须过）

1. **buildHash 必须两端同值**：镜像与客户端同 commit；改共享源集后要 `gen-build-hash.py` → 重建镜像 → 客户端重编译/重打包。不符的直接表现是 Meta 签票 409 `lobby.version-mismatch`（不是"连不上"）。
2. **判定面表摘要（`CombatConfigDigest`）必须同源**：镜像里是构建时 `COPY Assets/GameData/Config`（表 `.bytes` 已入库）；改表源 → `Luban/gen.bat` → **重建镜像** + 客户端重打包，否则开局拒局。
3. **exe 内容是打包内置**（OfflineBundles）：表/场景/prefab/Lua 改动，exe 必须重打包才生效（编辑器即时生效 ≠ exe 生效）。
4. **别把密钥烙进入库文件**：`deploy/.env`、`Assets/StreamingAssets/deploy.args` 都已 gitignore；本地 profile 走 `*.local.json` 规则（§3.3 第 1 步）。
5. **同机两客户端默认是同一游客账号**（`deviceId` 缺省取 `SystemInfo.deviceUniqueIdentifier`，代码事实）：编辑器与 exe 在一台机器上会拿同一个 `accountId`。功能上**不阻断**（席位按连接分配，两席同账号可同局），但：战绩/结算按账号归并成同一人、账号维度限流共用一把桶。**要各自身份 → 各给一个 `-device.id`**（§3.1）；或把 exe 放到另一台机器。

## 7. 改动面 → 云端要不要动（速查）

| 改动面 | 云端 | 客户端 |
|---|---|---|
| 纯表现（`LiteGame` App/UI、`LiteView`、prefab/美术/Lua） | 不动 | 编辑器重编译；exe 重打包 |
| 共享源集（`LiteSim`、`LiteNet` 协议/信封、`Assets/RoomServer` 双端件、`GameData/Generated`） | `gen-build-hash.py` → `git pull` + `up -d --build` | 重编译 + **重打包**（旧包握手必拒） |
| 表源（`Luban/Data/*.xlsx`） | `Luban/gen.bat` → `gen-build-hash.py` → **重建镜像** | 重编译 + 重打包（摘要同源） |
| `.proto` | `gen_proto.py` → `gen-build-hash.py` → 重建镜像 | 重编译 + 重打包 |
| 服务端宿主（`Server/RoomServer`、`MetaServer` 的 .cs） | 重建镜像（不动共享源 → 哈希不变） | 不动 |
| `deploy/**`（编排/容器配置） | `docker compose up -d`（改 `advertise_host` 必须重启容器） | 换 IP 时改 `meta.url` |

## 8. 排障速查（云侧专有）

| 症状 | 大概率原因 | 处置 |
|---|---|---|
| `up` 后 Meta/Room 立刻退出 | **密钥解析成空**（§2.2 两套键名） | `docker compose config` 看密钥是否 EMPTY；按 §2.2 选一种处置 |
| 客户端连不上 Meta（登录报 Network） | TCP 5000 未加白 / 云防火墙 / `meta.url` 写错 | 安全组加白 /32；本机 `curl` 自检区分"服务没起"与"网络不可达" |
| 登录成功、**进房**卡住 | UDP 17777 未放行；**`advertise_host` 仍是 127.0.0.1** | §2.3 + 安全组 UDP 白名单；`§2.4` 自检看 `address` |
| 签票 409 `version-mismatch` | 镜像与客户端 buildHash 不同（不同 commit / 旧 exe） | 重建镜像 + 重编译/重打包（§6 第 1 条） |
| 开局即拒局 | 表摘要不同源（镜像内 `.bytes` 旧） | `Luban/gen.bat` → 重建镜像 + 重打包（§6 第 2 条） |
| 登录报 `Insecure connection not allowed` | 客户端 Unity 禁明文 HTTP（`insecureHttpOption` 默认 `NotAllowed`），而 `-meta.url` 是 `http://` | 设为 ≥ `DevelopmentOnly`（本工程用 `AlwaysAllowed`，见 §3.1）；**改完要重出包**；排障可先用一条 `UnityWebRequest` 探针复现/复验（改前抛异常、改后 200） |
| 编辑器"未配置服务器" | `deploy.args` 被一次空 endpoints 打包删掉了 | §3.5——重写 `deploy.args` 或改用 §3.3 |
| 「快速进入」失败 | Meta 的 `LobbyDefaultRoomId` 为空（默认已给 `lobby-default`——被 `.env` 置空或自建配置漏掉时复现） | 走「创建房间」；或补上 `LITEGAME_DEFAULT_ROOM_ID`（容器）/ `LOBBY_DEFAULT_ROOM_ID`（内环） |
| 房间列表看不到对方的房 | 列表只在进页刷新 + 心跳周期 | §4 顺序提醒：先建房、后登录/重进大厅 |
| 客户端声明的"两个玩家实际同一人" | 同机 deviceId 相同（§6 第 5 条） | 各给一个不同 `-device.id`，或换机器 |
| `/metrics` 从公网打不开 | 设计如此（9100 不对公网开） | SSH 隧道：`ssh -L 9100:127.0.0.1:9100 <host>` |

## 9. 已实施与仍待决

**本批已实施（2026-10-17，用户裁决"三处全按推荐"，证据见 [施工记录/上云联机前置补强](../施工进度/上云联机前置补强.md)）**：

- **`deploy/.env` 键名单源化**：compose 五处密钥双名回退（§2.2），一份机器私有 `.env` 内环/外环共用；`docker compose config` 实测五密钥由全空转为全有值。
- **「快速进入」落点房**：容器 `${LITEGAME_DEFAULT_ROOM_ID:-lobby-default}`、内环脚本写 `LOBBY_DEFAULT_ROOM_ID`（老 `.env` 走脚本兜底）、样例 `appsettings.json` 明示（§4）。
- **`-device.id` 注入口**：`MetaDeployConfig` 解析（`KeyDeviceId`/`MetaEntryConfig.DeviceId`）+ `ContainerModule` 提供者选择（非空优先，否则机器标识）；解析面 3 例 EditMode 用例覆盖（§3.1）。

**仍待决（本文范围内不擅自决定）**：

1. **Mongo 换托管**（如云厂商 MongoDB / Atlas）：`compose.yaml` 的 `MongoConnectionString` 目前是**硬编码** `mongodb://mongo:27017/?replicaSet=rs0`；要换成托管实例需把它参数化为 `${...}`（并按托管方要求补用户名/密码与 `authSource`）。**不改也能用**——Mongo 跑在同机 compose 里，数据卷 + 定时 dump 已满足封闭测试最小备份。
2. **云服与内环并存**：目前没有"一键切到云"的脚本（GM 面板「本地联测」页只管本机进程）。若要常态化，可加一个切端点的小工具；当前用 §3.3 的本地 profile 手工切换即可。
3. **「快速进入」的房满语义**：所有人落同一缺省房，满员后第三个人会被房间端拒（客户端显示失败），没有"等待空位/自动换房"。是否需要，等联机实测暴露真实诉求再定。
