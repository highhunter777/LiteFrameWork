# 04 · 技术细节：服务端

> 服务端程序由三个 net8.0 工程组成——**权威房间服** `Server/RoomServer`、**Meta 服务** `Server/MetaServer`、**重放对账 CLI** `Server/ReplayTool`——加两端共编的房间内核 `Assets/RoomServer/{Runtime,Application}`；协议与传输由 `Assets/LiteNet` 两端共用。
> 设计契约以 [服务端总设计](../设计文档/架构/商业级通用服务端框架总设计.md)、[Meta 服务专项设计](../设计文档/架构/Meta服务专项设计.md)、[状态同步专项设计](../设计文档/网络/状态同步专项设计.md)、[云端GM通道专项设计](../设计文档/架构/云端GM通道专项设计.md) 为准；本文只讲服务端程序怎么设计落地。
> **要查"每件在哪、字段号、配置项全表、已接线/未接线清点"→ [12-联机全栈参考](12-联机全栈参考.md)**；客户端侧机制（预测/回滚/和解）同样归 12 与状态同步专项设计，本文不展开。

## 1. 总体形态：三宿主与双编内核

| 工程 | 形态 | 职责 |
|---|---|---|
| `Server/RoomServer`（net8.0 控制台，唯一 NuGet＝Microsoft.Extensions.DependencyInjection） | 60Hz 权威节拍 + 多房间 | 连接/会话/房间表、权威仿真驱动、快照与事件广播、重连、结算入盒、`/metrics` 与 GM 运维端点 |
| `Server/MetaServer`（ASP.NET Core Minimal API + Kestrel，Web 面零 NuGet；`MongoDB.Driver` 为唯一外部包） | HTTP 服务 | 访客登录与访问令牌、实例注册心跳、Join 票据签发、战绩结算落库 |
| `Server/ReplayTool`（仅引用 RoomServer） | CLI | 回放权威输入流逐帧对账确定性（退出码 0=一致 / 2=首分歧 / 3=身份或格式 / 4=IO / 5=截断） |

### 1.1 程序集分层与纯度边界

内核与宿主分离——**纯逻辑不碰 IO，带 IO 的半边留在宿主**：

| 程序集 | 依赖上限 | 内容 |
|---|---|---|
| `Assets/RoomServer/Core`（`RoomServer.Runtime`） | 只依赖 `LiteSim.Core`；**R11 红线**：禁 Transport/Socket、系统时钟、Console、文件 IO、proto、LiteNet——时间只从 `RoomCommand.Tick.nowMs` 进入，发送出口归 App 层 | 权威状态唯一持有者 `RoomRuntime`、输入闸门、回溯补偿、比赛状态机 |
| `Assets/RoomServer/Modules`（`RoomServer.Application.Runtime`） | 可引用 `LiteNet`/proto；**仍禁 IO、墙钟、Console、kcp** | 快照流水线、事件流水线、会话与准入编排、票据线格式 |
| `Server/RoomServer`（宿主） | 全开（传输/HTTP/文件/进程外依赖） | `ServerLoop`/`ServerHost`、Worker 池与 Mailbox、结算 Outbox 与提交管道、HTTP 监听 |

Unity 侧 asmdef 与 dotnet 侧 csproj **成对双编**，LangVersion 锁死（Runtime/Application 为 9.0），防双轨编译漂移；Runtime 层纯化由 L1 纪律扫描打红兜底。

### 1.2 源链接共编件：两端一致性的机制基础

服务端不复制共享代码，而是 csproj `<Compile Include>` 直编客户端仓库内的源文件——**单源，漂移即 wire 不兼容**（BuildHash 守卫覆盖，改后必跑 `python scripts/codegen/gen-build-hash.py`）：

| 宿主 | 共编件 | 机制意义 |
|---|---|---|
| RoomServer | Luban Runtime、`Assets/GameData/Generated/**`（表读码面）、`Serialization.Luban/{SimConfigMapper,TableLayout,MapTableProjection}.cs` | 两端读同一份表字节、同一套列布局 |
| MetaServer | `Assets/RoomServer/Modules/{JoinTicketFormat,Base64Url}.cs`、`Assets/RoomServer/Core/MatchStateMachine.cs` | 票据线格式与比赛相位闸单源——签发方与验签方逐字节一致 |

### 1.3 拓扑一图

```text
MetaServer（HTTP，Mongo 持久化）                客户端
   ▲  │ 签票（HMAC）                            │ KCP ＋ 安全信封
   │  └───────── Join 票据 ────────────────────→ ▼
RoomServer ──验签/准入→ 房间 Mailbox → RoomRuntime（权威 Sim，单线程）
   │                                       ├─ SnapshotPipeline（30Hz 差分＋AOI＋背压）
   │                                       └─ LagCompensator（回溯判定）
   └─ SettlementOutbox ── POST /matches/result ──→ Meta 结算账本（matchId 幂等）
```

## 2. 房间服：进程与线程模型

线程有五类，**权威仿真单线程，其余只入队/只读**：

| 线程 | 驱动 | 纪律 |
|---|---|---|
| `RoomServer.Loop` | `ServerLoop`：60Hz 权威节拍。专用线程＋绝对锚点（`Anchor = start + n×freq/tickRate`）防漂移；落后有界追赶（至多 5 帧），超限丢时间债不雪崩；帧体异常吸收不杀线程 | 只跑 `ServerHost.Pump` |
| `RoomServer.Worker.N` | 固定 Worker 池：每线程一个有界 mailbox；按 roomId 哈希取模路由——**同一房间永远落同一 Worker**，房内工作项不并发 | 消费房间三 lane，驱动 Runtime 并广播 |
| GM / metrics 监听 | HTTP listener 线程 | **只入队/只读**；GM 动作只在权威循环内执行 |
| 后台 HTTP ×2 | Lobby 心跳、结算提交（`HttpSubmitWorker` 模板：专用线程、单在途、有界停止） | 失败只影响分配/落库，不影响对局 |
| 诊断 | `RoomDiagnosticsService` | 只读 |

房间与线程的交接面收敛在两处：

- **`RoomMailbox` 三 lane**（Input/Control/Outbound）：有界，满/关闭**显式返回不静默丢**；出队严格优先级 Control→Input→Outbound，lane 内 FIFO。
- **`RoomInstance`**：单房间全部宿主侧状态；宿主↔Worker 的跨线程同步收进 Interlocked 方法（调度/完成/待活标记），单线程约束由结构保证、不自我加锁。

生产装配为 **Worker 执行形态**（`workerExecution + mailboxRouting`）；宿主直驱形态保留作退化路径。优雅关闭：信号（Ctrl+C/SIGTERM）→ 停收新会话 → 逐房间排空（超期兜底投 `Shutdown` 命令）→ Outbox Flush → 退出。

## 3. 权威链路：一帧的生命周期

### 3.1 入站：从 UDP 到内核命令

```text
KCP 收包 → 安全信封解包（握手未建立期间的包被静默丢弃）→ proto 解码
  → JoinAdmissionGate 准入链（六步，顺序不可交换）：
      IP 频率 → 字段字节边界 → token 非空 → buildHash 版本 → 票据验签 → 账号频率
  → 会话映射 / RoomCommand 构造 → 房间 Mailbox
```

内核命令 `RoomCommand` 是 struct 判别联合（AuthenticatedJoin/ClientInput/Disconnect/Rebind/Tick/Shutdown/RestoreAck/StartEarly，零分配热路径）；**Runtime 信任 App 层已验证的命令**——校验只发生在闸门，不进内核。

### 3.2 一帧的顺序（`ServerHost.Pump`）

```text
TickIncoming（收包）→ 补投暂存断线 → FlushGmActions（GM 只在此执行）
→ 逐房间（插入序）：
    排空期超时兜底（到期未终态投一次 Shutdown）
    Worker 形态：Tick 入 Control lane → 应用 Worker 回传（输出/重绑/销毁终态房间）
    宿主形态：Control lane → Input lane → 投 RoomCommand.Tick → 快照 BroadcastIfDue
→ 周期清理（每 600 tick≈10s：会话 TTL / 重连票据 / 限流桶）
→ TickOutgoing（发送）→ Ops 周期行
```

权威 Sim 步进发生在房间 `Tick` 命令内部（`RoomRuntime.ExecuteTick`）：时限判定 → `StepFrame`（固定 13 步，见 [12 §4.2](12-联机全栈参考.md)）→ Sim 终局则 Finish 冻结结算。生产形态与 `SimStep` 缺省形态的差异：`advanceMatch=false` 把 `MatchSystem.Tick` 从 `Step` 内挪到回溯判定之后，同帧快照二次捕获覆盖最终计分/比赛状态。

### 3.3 输入闸门与快照广播

- **InputGate**：消息形状、帧号合法性（未来帧容忍窗）、同帧去重、EntityId 防伪覆写、按键白名单、action_seq 严格递增、数值边界等 14 项校验（清单见 [12 §4.3](12-联机全栈参考.md)）；过闸输入进 `PendingInputRing` 定容环预存。**不合法输入不进仿真**。
- **SnapshotPipeline**（App 层）：权威步进后从 `AuthSim` **拉取**构建（Runtime 不产快照输出）→ 30Hz 抽帧 → 两段差分 → AOI 裁剪 → 背压分档降级（跟不上的客户端降级，不拖垮房间）→ 全量兜底。
- **CombatEventPipeline**：事件面独立于状态面——仅当真广播了快照才同节拍 Publish，命中/击杀等事件不混进快照。
- **LagCompensator**：以客户端 `viewFrame` 对齐时间轴 → 暂存权威态 → 环回历史 → 目标取历史位、射手取当前权威位/武器 → 只跑 `ShootingSystem` → 结果落当前帧 → 还原；超窗或关闭走退化路径。**打到的判定以"玩家看到的过去"为准**。

### 3.4 内核与宿主的契约

内核对宿主只有两类数据交换：`RoomCommand` 进、`RoomOutput` 出（纯事件族：PlayerAdmitted/MatchStarted/JoinRejected/SettlementReady…，`TargetPlayerId=-1` 为全体）。proto 编码与发送归 App 层：握手/开局/终局信号经 `HandshakePacker`、输入解包经 `InputPacker`——真服宿主与离线本服共用同一映射单源。同一权威链路也可跑在**进程内本服**（`LocalServerTransport`），供无网开发与联测复用。

## 4. 会话、席位与重连

**身份事实在席位，连接只是载体**：

| 件 | 生命周期 | 内容 |
|---|---|---|
| `Session`（连接级） | 断线即弃 | ConnectionId/Epoch、路由缓存、票据身份；实现 `IBroadcastSeat` |
| `PlayerSession`（席位级） | 断线保留，重连复活 | PlayerId/EntityId、Phase（Active/Disconnected/Restoring）、IsOwner（首入座者）、输入去重水位 |

重连全链：断线 → `ReconnectService.Issue`（CSPRNG 128bit 不透明 token，TTL 5 分钟，容量 256 超限淘汰最老）→ 客户端持票重连 → 一次性消费（`TryConsume`）→ 绑定房间号校验 → 席位置 Restoring → 版本确认＋权威快照＋输入历史下发 → 恢复 ACK 前抑制该席位增量广播。Worker 形态下 Rebind 在 Worker 侧执行。

会话表构造期定容（默认 4×房间容量）；未进房静默 60s 回收；断线保留期＝重连票据 TTL。

## 5. 安全模型（服务端侧）

| 面 | 机制 | fail-closed 点 |
|---|---|---|
| 传输加密 | `SecureEnvelopeRoomTransport` 装饰传输层：三段握手（ClientHello/双 nonce/proof）→ `SecureEnvelopeSession`（AES-256-GCM ＋ HKDF-SHA256 ＋ 64 位重放窗口） | 无密钥且未 `--allow-insecure-local` 拒启 |
| 进房授权 | Join 票据：Meta 签发（HMAC-SHA256 盖章，nonce CSPRNG）→ 房间 `HmacJoinTicketValidator` 六步验签：kid 查表 → 常量时间比对 → 解字段 → 服务端时钟时效 → 绑定项（audience/roomId/buildHash/simVersion）→ nonce 一次性窗口 | 未知 kid/篡改/过期/重放/绑定不符全拒；nonce 窗口有界（4096） |
| 洪泛限流 | 分层限流：IP 连接/入场、账号入场、Session 包速率；桶容量上限＋周期清理 | 超额直接拒 |
| 运维通道 | GM 端点四件套：只绑运维网（云端只绑隧道地址）、仅 POST ＋ `X-GM-Key` 头、动作只在权威循环执行、全量审计；契约单源 `gm-contract.json` | 密钥不符即拒 |

票据线格式 `JoinTicketFormat`（v4 共 16 段，签名覆盖除 sig 外全部段）以源链接同时编进签发方与验签方（§1.2）。

## 6. Meta 服务

### 6.1 分层与条件装配

```text
Contracts/（端口＋DTO，零驱动依赖）
Modules/（用例：Auth / Lobby / Profile）
Host/（ASP.NET 宿主：端点、鉴权、限流、迁移 HostedService）
Infrastructure/Persistence/（Mongo 适配器 ＋ SchemaMigrationRunner）
```

装配是**条件式**的：密钥非空才注册对应模块，Mongo 连接串非空才注册持久化与迁移——缺配置＝功能降级不崩溃；唯一例外是**启动迁移 fail-closed**（配了 Mongo 而迁移失败，服务拒绝就绪）。配置链＝内联默认 → `appsettings.json` → `META_` 环境变量 → CLI 覆盖。

### 6.2 端点面与鉴权分权

| 端点 | 鉴权 |
|---|---|
| `GET /live` · `/metrics` | 无 |
| `GET /ready` | 无；draining=503；配了 Mongo 则 bounded ping，不可达=503 |
| `POST /auth/guest` | 无凭据，每 IP 限流 |
| `POST /lobby/instances/register` | **Lobby** 实例密钥 |
| `POST /lobby/join-ticket` · `create-room` · `GET /lobby/rooms*` | 访问令牌 Bearer（`rooms/public` 变体公开） |
| `POST /matches/result` | **结算**实例密钥——与 Lobby 分权：实例注册与提交结算用不同密钥 |
| `GET /matches` | 访问令牌（按令牌账号查询） |
| `POST /sample/settlement` | 默认不挂载（样例开关） |

### 6.3 持久化契约

端口三件：账号存储、**结算账本**（双维度幂等＋revision CAS 原子边界）、战绩归档；另有有界 Outbox 端口与 Mongo 实现（已备，暂无生产消费者）。Mongo 适配器以副本集事务保证原子性、唯一索引兜底幂等；`SchemaMigrationRunner` 显式版本化、失败回滚，启动迁移失败即拒服务，`/ready` 承担依赖检查。

## 7. 数据与结算

### 7.1 表与地图装载（fail-fast）

- `ServerTableLoader` 直读 `Assets/GameData/Config/*.bytes`——**与客户端同一份字节**，无服务端专属表；按 `TableLayout.Files` 清单装载 → `SimConfigMapper` 投影出 `CombatValues` 实例 → 经装配入参显式传入（缺表即拒装配）。
- 数据面守卫：`TableLayout.ComputeGameplayDigestBase` 计算判定面摘要 → 随 `StartGame.ConfigHash` 下发，客户端装载后复算比对，不等拒局——表数值可两端各自热更，不必同步出包。
- 地图：`ServerMapCatalog` 多图映射（行键→判定图），缺行 fail-closed。

### 7.2 结算链路（Outbox → Meta）

```text
对局终态 → SettlementOutbox（JSONL journal 逐条 write-through，幂等键=matchId，
          容量按待提交数计，连续完成标记达阈值自动压实）
  → SettlementSubmitService 后台线程 POST Meta /matches/result（结算实例密钥）
      → 2xx（含 duplicate）标记完成；可重试失败退避重投，载荷级 4xx 弃置
```

线程契约：入盒在权威循环、标记与取待提交在提交线程、Flush 在排空路径——全部经单一临界区。进程重启不丢账（journal 落盘），重复提交不重算（matchId 幂等）。

## 8. 边界与坑

- **改 Sim 源码 / proto / 表源 → 必跑 `python scripts/codegen/gen-build-hash.py`**：共享源集与共编件都在 BuildHash 闭包内，漏跑＝两端常量不同步、Join 握手全员拒进房；表**数值**改动走数据面摘要（§7.1），不进闭包。
- **R11**：`Assets/RoomServer/Core` 禁 Transport/系统时钟/文件 IO/Console/proto/LiteNet——时间只从 `Tick.nowMs` 进，L1 纪律扫描打红兜底。
- **监听线程不得动房间状态**：GM/metrics HTTP 线程只入队/只读；一切房间变更都发生在权威循环（或房间所属 Worker）内。
- **配置是启动期快照**：`roomserver.json` / `META_` 环境变量改后必须重启进程（云上＝重启任务计划）才生效。
- **密钥一律环境变量**（`LITENET_*` 五把），不落配置文件、不入库；开发本地无密钥必须显式 `--allow-insecure-local`。
