## R1：AOI 与公共校验口径（原文 §2）

### 2.1 目标

- 视野外实体的变化**不得**导致客户端每快照失配和解。
- 视野内可见实体的错误仍能被公共校验发现并纠正。
- 全量快照保留全图校验；重连/丢包兜底路径不变。
- 不泄漏视野外实体给客户端。

### 2.2 设计裁决

**采用“逐槽位公共校验 + 本次增量范围内的比对”，不再让全图 checksum 为 AOI 增量做和解裁判。**

1. `SlotDelta` 追加 `uint checksum`（只增字段号）：服务端按该槽位的公共面（`EntitySlot` 公共字段 + 主动作摘要，复用 `EntitySlot.MixPublic`/Action 摘要折叠）计算；客户端用**本地预测态在同一快照帧的回滚环探针**（`SnapshotRing` 恢复的 probe）按同一口径复算并比较——不一致即该槽位需要权威覆盖；镜像重建结果也做同口径自检（抓编解码漂移）。
2. `StateSnapshot` 追加 `uint match_checksum`（只增字段号）：覆盖本帧 `MatchStateDelta` 的公共字段（比赛状态每帧全量携带，客户端可复算）。
3. `StateSnapshot` 追加 `uint visible_checksum`（只增字段号）：覆盖**本次消息实际携带的槽位集合 + Match**，用于快速短路；全等则零和解，不等再逐槽位定位。它不能替代 `SlotDelta.checksum`（只知“有差异”不知“差在哪个槽”）。
4. `StateSnapshot.checksum` 语义收窄为**全量帧/全图校验**（保留现有 `ComputePublicChecksum`，只用于 `IsFull=true` 与重连/兜底）；增量帧不再用它做和解判定。
5. 增量和解判定：
   - 服务端在 `BuildFor` 时按发送给该客户端的 `Slots` 集合计算 `visible_checksum`；客户端按消息槽位集合 + Match 复算。
   - 不一致时逐槽位比对 `SlotDelta.checksum`：只把**差异槽位**写回快照帧探针（公共字段 + 主动作摘要），再重放本地历史（与现有和解同构，但覆盖面限定在消息槽位）；不整帧复制镜像，不触碰视野外槽位。
   - 若增量不含任何槽位（例如只带 Match/私有面），只比对 `match_checksum`。
6. 全量帧仍用全图 checksum 做完整和解；全量后清空“部分和解”状态。
7. 服务端 AOI 可见性判定与客户端的比对范围必须同源：使用服务端为该客户端构建快照时的 `viewPos/radius`（已有），并通过消息携带的槽位集合定义比对范围；**不要求客户端复算 AOI**——避免视点预测竞态。

### 2.3 拒绝的方案

- **全图 checksum + AOI 增量继续并存**：必然每快照失配（既有债务）。
- **客户端复算 AOI 后裁剪 checksum**：客户端预测视点与服务端视点存在竞态，可见集不一致会反复误判。
- **全量代替增量**：带宽不可接受，且不解决 AOI 语义。
- **仅按已发送槽位做 checksum 但不做部分和解**：失配后仍整帧复制，会把视野外本地预测拉回旧镜像，问题只从“误和解”变成“误回退”。

### 2.4 验收

- EditMode/L1：视野外实体移动 N 帧，客户端 `MismatchReport` 计数不随快照频率增长；视野内受击/死亡仍在一个快照内和解。
- 8 人房：30Hz 跑 60s，和解率相对现状显著下降；无“橡皮筋/事件静默”回归。
- 丢一包/乱序：部分和解只覆盖消息槽位，下一份快照继续收敛。
- 协议：`SlotDelta`/`StateSnapshot` 只增字段号；`SnapshotCodec/Reassembler/Differ`、公共 checksum、重连/单测同步更新；`BuildHash` 重生成。
- 反作弊：不得为校验向客户端发送视野外槽位内容。

## R2：远端换弹/动作公共面（原文 §3）

### 3.1 目标

- 远端玩家换弹可见，且换弹动画与权威弹药回国同节拍。
- 后续主动作（技能/受击/动作打断）有统一的公共进度载体，不再为每个动作加私有旁路。
- 不泄漏私有账本（弹药/备弹/背包）。

### 3.2 设计裁决

1. **主动作摘要即公共动作面**：`ActionRuntime` 主槽（slot 0）由 `WeaponSystem` 在换弹开始/结束时写入：
   - `ActionId = CharacterAnimationIds.Reload`（数值 Id 走表/常量单源，不硬编码字符串）；
   - `StartFrame = 换弹开始权威帧`；`Phase` 使用现有 `ActionPhase`（Windup/Active/Recovery 的映射由动作系统定稿；首版可只填 Start/Active 两态）；
   - 可选 `EndFrame`：若现有 `ActionRuntime` 没有结束帧字段，按“表 `ReloadFrames` + StartFrame”派生，不在协议里重复存第二份；若其他动作需要非表定长，再按只增字段号评估。
2. `SnapshotCodec.ToDelta/FromDelta` 已有 `action_id/action_phase/action_start_frame`，无需新增槽位字段；补齐 **服务端写入点** 与 **客户端读口**：
   - `SimView` 对远端读渲染帧快照的主动作摘要；
   - `CharacterLocomotionDriver` 对远端槽位以“ActionId=Reload ∧ 渲染帧在 [Start, Start+ReloadFrames)”提交 Overlay，和本地 `IsReloading` 走同一 `UpdateReloadUpper` 收口（不新增第二套叠加层逻辑）。
3. 换弹开始/结束的公共摘要必须进入**公共 checksum 与差分基线**（已有 Action 摘要字段；确认 `EntitySnapshotEntry`/`BitEqual`/`SimChecksum` 覆盖，不重复手抄）。
4. 远端动作状态取**渲染帧快照**，与位置/瞄准/开火窗同拍；快照丢包/迟到不按第 0 帧重播。
5. 私有面仍只发本人：`WeaponRuntime` 弹匣/备弹/节拍不进公共面。

### 3.3 边界

- 首版只接换弹；技能/受击等动作等其系统落地后复用同一主动作摘要，不预建空动作表。
- 远端换弹动画的播放倍率按 `ReloadFrames / TickRate` 与片段时长求商，沿用本地同款；不得让远端按墙钟自由播放。

### 3.4 验收

- 两台客户端：A 换弹，B 在 RTT+快照延迟内看到换弹动画，动画结束与 A 的弹匣回国同节拍（±1 快照）。
- 换弹被切枪打断：摘要清空/切换为切枪动作（按动作系统裁决），远端不回落到“永久换弹”。
- 重连/首份快照：远端换弹中进入视野，按 `StartFrame` 的剩余进度续播，不从头播。
- 公共 checksum/差分/重连用例覆盖新增写入路径；`BuildHash` 重生成。

## 附：原 §8 中属 R1/R2 的风险项

- **风险**：逐槽位/可见摘要增加协议字段与两端编解码面 → 必须同步 `SnapshotCodec/Differ/Reassembler`、`SimChecksum`、重连、测试与 BuildHash；字段只增不重编号。
- **风险**：主动作摘要若与私有换弹事实相位不一致，远端动画会抖动 → 以服务端权威 `StartFrame` 为唯一相位，客户端不按本地墙钟重播。
