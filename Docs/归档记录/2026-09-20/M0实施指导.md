### IMainThreadDispatcher / MainThreadDispatcher（Threading/，~50 行）

线程边界的唯一设施（§7.4 三档线程纪律）：后台线程结果的**唯一回归通道**。

```csharp
public interface IMainThreadDispatcher : ITickable {
    void Post(Action action);   // 任意线程可调；主线程帧首执行
}

public sealed class MainThreadDispatcher : IMainThreadDispatcher {
    private readonly ConcurrentQueue<Action> _queue = new();
    public void Post(Action action) => _queue.Enqueue(action ?? throw new ArgumentNullException(nameof(action)));
    public void Tick(float realDelta) {                       // 注册即发现自动驱动；**必须最先注册**（帧首泵）
        while (_queue.TryDequeue(out var a)) {
            try { a(); }
            catch (Exception ex) { Log.Error(ex, "MainThreadDispatcher"); }   // 单回调失败不炸队列（§7.8 同款语义）
        }
    }
}
```

- **Core 即可实现**（`ConcurrentQueue` 是纯 BCL），不需要 Unity 层；`ITickable` + 注册即发现自动驱动，GameEntry 装配时**第一个 RegisterInstance**
- **不做**：延迟调度（那是 `IScheduler` 的游戏时间域）、优先级、取消——`Post` 语义单一：扔到主线程帧首执行
- **自测**：子线程 Post 3 个 Action → Drain 后按序执行；回调抛异常 → 后续仍执行；主线程 Post → 同帧 Drain 即执行

## 2. 日志门面 Log（先写它，后面每件的测试都要打日志）

### API 契约（Logging/）

```csharp
public enum LogLevel { Info, Warning, Error, Fatal }

public interface ILogHelper { void Log(LogLevel level, string message); }

public static class Log {
    public static void SetHelper(ILogHelper helper);      // 默认 null → Unity 侧启动时注入
    public static void SetOutputLevel(LogLevel min);      // 运行时可再收紧（默认按构建分流，见下）
    // tag = 稳定的模块名常量（"FileSys"/"Event"）；动态信息（实例名/路径）进 msg 不进 tag——Recent 只有 32 条，tag 集合必须小而稳定。
    // helper 输出统一 "[tag] msg" 前缀（ILogHelper 接口不变）；Recent 存原始 msg + Tag 分离——HUD 可按 Tag 着色/分组，将来按 tag 过滤是一行事。
    public static void Info(string msg, string tag = null);   // 走 helper；helper 为 null 时静默丢弃
    public static void Warning(string msg, string tag = null);
    public static void Error(string msg, string tag = null);  // ErrorCount++
    public static void Error(Exception ex, string context = null, string tag = null);  // ex.Message + 堆栈进 Recent
    public static void Fatal(string msg, string tag = null);
    public static void Fatal(Exception ex, string context = null, string tag = null);
    public static int ErrorCount { get; }                 // HUD 读
    public static IReadOnlyList<LogEntry> Recent { get; } // 最近 32 条环形缓冲，HUD 读
}
public readonly struct LogEntry { public LogLevel Level; public long Time; public string Tag; public string Message; }
```

### 实现要点

1. **环形缓冲**：`LogEntry[32]` + 头指针，覆盖即写，不扩容
2. **发布分级——默认按构建分流，运行时可覆盖**：`#if UNITY_EDITOR || DEVELOPMENT_BUILD || LITEFRAMEWORK_DEBUG` 默认全放行（Info 起）；`#else` 默认收紧到 Warning——避免 release 忘记收紧就全量输出；`SetOutputLevel` 保留运行时覆盖能力。被过滤的级别在入口处直接丢弃，零成本。**Debug 判一律三宏并集**（`LITEFRAMEWORK_DEBUG` 供 .NET 测试侧注入，见《测试开发方案》§1.1），新代码禁用裸 `UNITY_EDITOR` 判 Debug 行为
3. 门面自己**不引用 UnityEngine**（Core）：输出全走 `ILogHelper`
4. 每条进缓冲的记录与 helper 输出同时发生，缓冲满覆盖最旧

### 自测

- Info 在 release 定义下不进 helper（可用假 helper 计数验证）
- 写 40 条 → Recent 恰好 32 条、最旧被覆盖
- ErrorCount 累计正确
- SetHelper 换实现后立即生效
- **tag**：`Info("msg", "FileSys")` → helper 收到 `"[FileSys] msg"`；`Recent` 条目 `Tag == "FileSys"` 且 `Message` **不含**前缀（分离由 HUD 格式化）；无 tag 调用 `Tag == null`

## 3. 事件中心（全部预算里最紧的一格，最认真写）

### API 契约（Event/）

```csharp
public interface IEventCenter {                    // 接口只留业务契约（ISP）；实现类 EventCenter 自行声明 ITickable/IModuleStats，GameEntry 用具体类型驱动
    Action Subscribe<T>(Action<T> handler) where T : class;   // 返回注销委托（§7.3 红线）；幂等可重复调用
    void Publish<T>(T e) where T : class;                     // FireNow：立即派发（热路径，稳态零 GC）——所有权语义见下
    void PublishQueued<T>(T e) where T : class;               // 入队，Tick 时统一派发（低频便利）；所有权语义同 Publish
    bool StrictMode { get; set; }                             // 默认按构建分流：编辑器/开发 true，release false
}
```

### 所有权规则（GF EventPool 同款语义——发布方的三条纪律）

1. **Acquire → 填充 → Publish**：事件对象从 `ReferencePool.Acquire`，填充字段后发布
2. **发布后不得触碰**：读/写/再发布皆违例——对象所有权已归中心，派发完成（含**无订阅者路径**）即 Release 回池，"发布出去没人听"不等于"对象丢了"
3. **订阅方要异步持有 → 自己复制**：回调结束后对象即回池；需要延后处理就拷贝需要的字段，或 Acquire 新对象深拷贝——订阅回调里把事件存进成员变量是最典型的踩坑点

为什么这样设计：事件参数发布前 Acquire、派发后统一回收，热路径全程零 GC 且没有泄漏窗口；`where T : class` 约束也由此而来（引用上转入队零装箱 + `RecycleIfPooled` 统一回收判断）。struct 事件的 GCOptimize 路径留待 M3 配 GenConfig 时再议。

### 实现要点（按 GF EventPool 的教训逐条落实）

1. **存储**：`Dictionary<Type, IEventChannel>`；`EventChannel<T>` 内部 `List<Action<T>>` + 版本号 `int _version`
2. **防派发中改集**（GF 用 cachedNodes 解决的问题）：**已落锤快照数组方案**——派发前拷订阅集到复用缓冲（增长式分配：稳态零 GC，只在订阅数超历史峰值时分配一次），嵌套派发各层独立缓冲（内层不复用外层，防互踩）；订阅/注销立即生效于下一次派发。版本号 + pending 列表方案作废
3. **队列派发**：`Queue<PendingEvent>`（存 Type + boxed 参数）；Tick 中逐个 FireNow。**装箱只发生在队列路径**——这是设计允许的取舍：热路径走 Publish（零 GC），PublishQueued 是低频便利
4. **严格模式**：派发时通道不存在或无订阅者 → `Log.Warning($"no subscriber: {typeof(T).Name}")`；release 构建跳过判断
5. **零 GC 派发**：Publish 路径全程无 new（查表、for 遍历、直接调用）；**闭包是分配大户**——订阅处传 `Action<T>` 方法组时注意别在热路径写 lambda 捕获局部变量
6. **跨流程切换时清空队列**：`PublishQueued` 入队的事件若在 `ChangeState` 后仍在队列里，基本都是设计错误（发方与订阅方生命周期不一致）。流程切换时 `Clear()`，Debug 下对非空队列告警——留着只会延后问题爆发并让现场更难还原

### 自测

- 订阅 → 派发 → 收到；注销 → 再派发不收到；**注销委托执行两次不抛**（幂等）
- 派发中订阅/注销（handler 里调 Subscribe/Unsubscribe）→ 本轮不崩、下轮生效
- PublishQueued → 当帧不触发、Tick 后触发
- StrictMode：未订阅事件派发 → Log.Recent 出现 Warning
- **零 GC 单列用例**：热身后再 Publish 1000 次，`Unity.Profiling.ProfilerMarker` 或 GC.GetAllocatedBytesForCurrentThread() 前后差值为 0

## 4. 引用池 ReferencePool（静态类）

### API 契约（Pool/）

```csharp
public interface IReference { void Clear(); }

public static class ReferencePool {
    public const int DefaultMaxSize = 64;                 // 每类型池容量上限默认值
    public static T Acquire<T>() where T : class, IReference, new();
    public static void Release(IReference reference);   // 严格校验：类型在池中 / 重复归还抛异常（Debug）；池满则丢弃
    public static void Add<T>(int count) where T : class, IReference, new();   // 预热（count 超上限时自动上调上限）
    public static void Remove<T>(int count) where T : class, IReference, new();// 裁剪池内存量
    public static void SetMaxSize<T>(int maxSize) where T : class, IReference, new();
    public static IReadOnlyList<ReferencePoolInfo> GetAllInfos();       // Debug：HUD 数据源
}
public readonly struct ReferencePoolInfo {
    public Type Type; public int Unused, Using, MaxSize, PeakUnused;
    public long AcquireCount, ReleaseCount, DroppedCount;
}
```

### 实现要点

- `Dictionary<Type, Queue<IReference>>`（Queue 天然 FIFO）
- **Acquire 后 Clear 责任在调用方**（GF 语义：Acquire 不帮你 Clear，取出来的对象要自己初始化）；Release 前 `reference.Clear()` 由池做
- 严格校验用三宏并集 `#if UNITY_EDITOR || DEVELOPMENT_BUILD || LITEFRAMEWORK_DEBUG` 包住（Debug 尽职、release 零开销、.NET 测试侧可注入，§14.6）
- **`MaxSize` 必须放在条件编译之外**：容量控制是运行期的内存保护，release 同样要生效。只有统计字段（`PeakUnused`/`DroppedCount`/`Using`）才归 Debug
- **容量上限的语义**：池的内存占用应与**活跃对象数**挂钩，而不是历史峰值。不设上限时，一次业务高峰（进战斗）取用的对象会全部永久驻留——这是池最常见的隐性膨胀
- **`SetMaxSize` 调小不裁剪存量**，只影响后续归还；要立即释放配 `Remove`（如退出战斗后）
- **`Add` 预热会自动上调上限**：`Add(200)` 是显式的"我需要 200 容量"声明，不该被默认上限截断
- `GetAllInfos` 是开发 HUD 的数据源——统计字段在 Acquire/Release 时维护

### 自测

- Acquire → 字段残留被 Clear 清掉；Release → 再 Acquire 是同一实例
- 重复 Release 抛异常（Debug）；未 Acquire 过的类型 Release 抛异常
- Add(10) 预热 → 前 10 次 Acquire 零分配
- **容量上限**：`SetMaxSize<T>(2)` → 归还 5 个只留 2 个，`DroppedCount` 为 3，池内数量不超 2
- **预热上调上限**：`Add<T>(100)` 后 `MaxSize` ≥ 100，且 100 个全部入池（不被默认上限截断）
- **裁剪**：`Add<T>(10)` 后 `Remove<T>(4)` → 池内剩 6

## 5. 对象池（直接使用 UnityEngine.Pool——不自研）

### 决策记录

`UnityEngine.Pool.ObjectPool` 与需求匹配度约九成（Get/Release、maxSize 容量上限、collectionCheck 防重复归还、actionOnGet/Release/Destroy 三回调全部现成）；缺的"优先级淘汰"经推演为**无消费者伪需求**（池满时销毁新归还对象/调大 maxSize 即行业常态策略，且官方池不暴露池内容无法实现）——不自研。引用池不受影响：它是纯 C# 计数池 + Clear 语义，Unity 无官方对应物。

### 接入方式

```csharp
using UnityEngine.Pool;

// 实体壳/特效壳按需创建，每类一个池
var pool = new ObjectPool<Bullet>(
    createFunc:      () => new Bullet(),
    actionOnGet:     b => b.OnSpawn(),      // 取出：Reset 生命周期钩子
    actionOnRelease: b => b.OnDespawn(),    // 归还：回收表现
    actionOnDestroy: b => b.TearDown(),     // 池满淘汰：真销毁（GameObject 池即 Destroy）
    collectionCheck: true,                  // Debug 防重复归还
    defaultCapacity: 16,
    maxSize: 16);

var b = pool.Get();
pool.Release(b);
```

stats 包装（~20 行，供 HUD，实现 IModuleStats）：

```csharp
public sealed class PoolStats : IModuleStats {
    private readonly ObjectPool<Bullet> _pool;
    public string StatsName => "ObjectPool(Bullet)";
    public void Snapshot(Dictionary<string, string> into) {
        into.Clear();
        into["池内"] = _pool.CountInactive.ToString();
        into["活跃"] = _pool.CountAll.ToString();
    }
}
```

### 使用要点

- **maxSize 就是容量上限**：满后 Release 直接 Destroy 新归还者（官方淘汰策略）——容量按业务峰值定，不为"可能有用"调大
- 三个回调分工：OnGet 生命周期开始 / OnRelease 生命周期结束 / OnDestroy 真销毁
- 与引用池分工不变：小参数/事件对象走引用池（IReference），重量对象走这里
- collectionCheck 只在 Debug 生效，防重复归还

### 自测

- Get/Release 往返 → 复用同一实例，OnGet/OnRelease 触发
- 超容量 → Destroy 回调触发（对 GameObject 池即对象被销毁）
- 重复 Release → collectionCheck 抛（Debug）

```csharp
    public float CurrentStateTime { get; }

    // 字符串键数据字典已删（零编译期检查 + 装箱 + 静默 cast 错误，§1.1）
```

### Procedure 的异步约定（Core 引不了 UniTask 逼出来的形态，必须守）

`ProcedureBase<TOwner>`（Core/Fsm/Procedure.cs；**泛型化：`where TOwner : IProcedureOwner`**，owner 实现由业务提供——2026-09-10 修订）把 `OnEnter/OnLeave` sealed 掉：进流程即 `new CancellationTokenSource` → 调 `RunAsync(fsm, ct)`；离场即 `Cancel + Dispose`。**`RunAsync` 是 `void` 签名**——Core asmdef 是 `references: []`，引不了 UniTask，这是零依赖的代价。

由此定死一条子类纪律：**`RunAsync` 必须是"一行转发"，禁止写成 `async void`**——`async void` 的异常调用方接不住，直接进 Unity 全局 log，`Fail()` 不知道、FSM 不知道、§3.4 的 fail-fast 也拦不住：

```csharp
protected override void RunAsync(Fsm<ProcedureOwner> fsm, CancellationToken ct)
    => RunAsyncCore(fsm, ct).Forget();          // 一行转发，仅此而已

private async UniTask RunAsyncCore(Fsm<ProcedureOwner> fsm, CancellationToken ct) {
    try { /* 流程主体 */ }
    catch (OperationCanceledException) { /* 正常取消，静默 */ }
    catch (Exception ex) { Fail(fsm, ex, nameof(RunAsyncCore)); }
}
```

try/catch 写在 **async 方法体内**——异常必有归宿，这是本约定唯一的要点。

两条配套认知：

- **取消是协作式的**：`OnLeave` 的 `Cancel` 不等异步真正停止——下一个流程 `OnEnter` 时上一个可能还在收尾。涉及互斥资源（如场景加载）时，ct 检查点必须足够密。
- **流程依赖不从 Owner 取**（那是局部服务定位器，与 §3.3"容器不静态暴露"同罪）：流程实例在装配点（注册进 FSM 的那处）构造，依赖走构造注入存为本类字段。

### 实现要点

1. **ChangeState 不立即切换**：记录 pending 状态（同帧多次请求 last-wins），**当前 OnUpdate 结束后**（Tick 末尾）才执行 OnLeave/OnEnter——防止在 OnEnter 里改状态引发不可预期的重入。**OnEnter 内请求 → 挂下帧末**（期间新状态收到一次 OnUpdate）；**OnLeave 内请求 → 直接抛**（离场中改道自相矛盾，代码用 `_inLeave` 窗口）
2. **重入直接抛**：`ChangeState<T>` 时若 `typeof(T) == CurrentState.GetType()` → `InvalidOperationException`（启动期就该暴露的问题不静默）
3. OnInit 在 Start 前对全部状态调一遍；Start 后才允许 ChangeState
4. `ProcedureBase<TOwner>` 即流程基类（owner 由业务给定，如 `ProcedureBase<ProcedureOwner>`）；流程的 Lua 回调转发是 M4 的事（§4.5），M0 只交付 C# 骨架

### 自测

- Start → OnEnter 触发；ChangeState → 旧态 OnLeave、新态 OnEnter、CurrentStateTime 归零
- ChangeState 到当前状态 → 抛；Tick 内 ChangeState → Tick 结束后才切换
- 流程间传参冒烟：业务 owner 的 `LastError` 由 `Fail` 经 `IProcedureOwner` 契约写入后可从 Owner 读回（具名，编译期可查）
- **Editor 一键 grep**：流程子类中出现 `async void` 即报错——约定防不住人，用 §7.5 白名单纪律同款手法兜底

## 7. 游戏时钟 IGameClock（三层：时钟语义 → 调度器 → 序列执行）

### API 契约（Clock/）

**三件拆开，不合成一个接口**——设计方案 §1.1 的排期本就是分离的（时钟语义进 M0，调度器与序列执行 M4 排位），接口跟着拆，避免 M0 先产出半截接口。三件都是 `ITickable`，由 GameEntry 按 `Clock → Scheduler → TimelineRunner` 顺序驱动（顺序显式，见 §12）。

```csharp
// —— M0 交付：时钟语义（唯一时间真相源）——
public interface IGameClock : ITickable, IModuleStats {
    float TimeScale { get; set; }        // 变速（0.2 慢动作 / 2 加速）
    bool Paused { get; set; }            // 暂停：全停（连 UI 时钟也停？否——分层见下）
    float Now { get; }                   // 游戏时间累计（受变速/暂停影响）
    float ScaledDelta { get; }           // 本帧游戏时间增量：供后两件消费，避免各自反算变速
}

// —— M4 排位：调度器 ——（构造注入 IGameClock，读 ScaledDelta）
public interface IScheduler : ITickable, IModuleStats {
    int Schedule(float delaySeconds, Action callback);   // 返回取消 id；delay 用"游戏秒"（受变速影响）
    void Cancel(int id);
}

// —— M4 排位：序列执行 ——
public interface ITimelineRunner : ITickable, IModuleStats {
    ITimeline CreateTimeline();
}

public interface ITimeline {
    ITimeline At(float seconds, Action action);   // 链式注册动作点
    void Start();
    void Stop();                                  // 可中断
    bool Finished { get; }
}
```

> **为什么加 `ScaledDelta`**：GameEntry 统一喂 `unscaledDeltaTime`（§12），变速由时钟内部处理。若后两件各自读 `TimeScale` 再乘一遍，同一份变速逻辑就有三处实现，改一处漏两处。让时钟**唯一**产出缩放后的增量，是"时钟是时间真相源"这条原则的落地。这也是 DI 在本框架里少有的真实用武之地——后两件构造注入 `IGameClock`。

**三个设计决策（M4 排位前定死，本指导给默认值）**：①固定步长（Tick 吃 GameEntry 喂的 elapse——v3 理由更新：联机后逻辑确定性由 Sim 的 FrameDriver 保证，GameClock 不承载逻辑正确性；保留固定步长是因与 Sim 的 `dt = 1/60` **同构**，战斗判定将来迁 Sim 阻力最小，见《状态同步实施方案》§3.9）；②时钟先于玩法更新（装配顺序 ITickable 列表中时钟排最前）；③世界/UI 时钟分层——**创建两个实例**：`WorldClock`（受时停影响）与 `UIClock`（只受 Paused 影响，不受 Frozen 影响）。**类型用空标记子接口区分**：

```csharp
public interface IWorldClock : IGameClock { }   // 空标记，仅用于 DI 区分
public interface IUIClock    : IGameClock { }
```

容器无 keyed registration、且重复注册抛异常（§10），同一接口注册两个实例必然冲突。子接口零 API 膨胀，且注入时类型安全——拿混即编译错误。**不要为此引入命名注册**（§1.1 硬验收：API 面不超清单）。"时停"= WorldClock.Paused，UI 转场动画走 UIClock 继续。

### 实现要点

1. **M0 只交时钟本体**：`Tick(elapse)` 中 `elapse *= TimeScale`（Paused 则 0）→ 先累加 `Now`，再算出 `ScaledDelta`。**调度器与序列执行不在本件内**（M4 独立件），它们各自 Tick 时读 `ScaledDelta`——时钟不再持有它们的内部列表
1b. **`MaxDelta` 尖峰钳制（实现回写）**：单帧增量上限 0.1s——加载/Hitch 的 deltaTime 尖峰被钳制，防调度器集体到期、动画跳变。已实现（`GameClock.MaxDelta`），回写设计文档
2. **调度器**：到期 callback 经 `SafeCall`？——M0 还没有 SafeCall（M3 才有 xLua 依赖），M0 阶段 callback 是纯 C# 委托，直接 try/catch + Log.Error 即可，M3 升级为统一 SafeCall
3. **UniTask 绑定（Unity 层，已实现两个扩展）**：

```csharp
// LiteFramework/Scripts/Unity/Clock/UniTaskClockExtensions.cs
// M4 后可用：调度器驱动 + UniTaskCompletionSource（等待语义服从调度器）
public static UniTask WaitAsync(this IScheduler scheduler, float seconds, CancellationToken ct = default) { ... }

// M0 可用：NextFrame 轮询扣减 ScaledDelta（IGameClock 无 Schedule 后的替代形态）
public static async UniTask WaitAsync(this IGameClock clock, float seconds, CancellationToken ct = default) {
    float remaining = seconds;
    while (remaining > 0f) {
        ct.ThrowIfCancellationRequested();
        await UniTask.NextFrame();
        remaining -= clock.ScaledDelta;   // 恢复时机与时钟 tick 的先后由 DefaultExecutionOrder 固定（装配步）
    }
}
```
**这是"底层封装 UniTask"的正确形态**：不是用 `UniTask.Delay`（它挂 PlayerLoop、不受你的暂停/时停控制），而是时钟驱动（轮询扣减或调度器回调）对外暴露 UniTask——业务拿到的是 UniTask 签名（§7.7），等待语义完全服从游戏时钟

4. 序列执行的 timeline（M4）：`List<(float at, Action a)>` 按 at 排序，Tick 中按 `ScaledDelta` 推进游标触发——**跳帧安全**（一帧跨过多个动作点时全部触发，顺序不跳）

#### 墙钟 IWallClock（第三时间域，~30 行，M0 顺手交付）

游戏时钟覆盖不了"真实时间"——`Now` 会被暂停、变速、时停，而网络超时 / 断线重试 / 每日刷新全都不吃这套。墙钟独立成件：

```csharp
public interface IWallClock {
    DateTime UtcNow { get; }     // 真实时间（UTC）
    long NowMs { get; }          // Unix 毫秒（跨端比对 / 持久化用）
}

public sealed class SystemWallClock : IWallClock {   // Core 默认实现，DateTime.UtcNow 直通
}
```

- **语义**：不可暂停、不可变速。这是它独立成件的理由——塞进 `IGameClock` 会逼出一个恒 1 的 `TimeScale` 和假的 `Paused`
- **联机演进**：换 `ServerWallClock`（服务器时间下发 → `offset = serverMs − localMs` → 读数即 `local + offset`，可周期校准），实现在 LiteNet/玩法层，M9+；接口不变
- **红线**：**禁止进入 Sim 层**——对局内判定用墙钟 = 确定性死亡；断线倒计时是 UI/流程层的事
- **`WaitAsync` 扩展（Unity 层，与 UniTaskClockExtensions 同文件）**：墙钟域内部用 `UniTask.Delay` 恰好语义正确——它就是"真实时间等待"的合法出口（《自研框架设计方案》§7.7 分域路由），从而 `UniTask.Delay` 从"被禁原语"变成"墙钟域的实现细节"

### 自测

- TimeScale=0.5 → Now 增速减半、`ScaledDelta` 同步减半；Paused → Now 不动、`ScaledDelta` 为 0，但 UIClock（若分层）继续
- **墙钟独立**：WorldClock 暂停、UIClock 冻结后，`IWallClock` 读数仍推进——三域互不干扰
- Schedule(1s) 在变速下按"游戏秒"触发（**M4 补测**——M0 不交付调度器）
- Timeline 一帧大步进跨多个动作点 → 全触发且有序（**M4 补测**）
- Cancel 后不再触发；WaitAsync 配合 ct 取消后任务 canceled（WaitAsync 扩展可 M0 交付，随 M4 用例补全）

### API 契约（IO/）

```csharp
public interface IPathProvider { string RootPath { get; } }   // Unity 侧：Application.persistentDataPath

public interface IJsonSerializer {                            // Core 只认接口；Newtonsoft 实现在 Unity 层（第三方不进 Core）

public static class FileSys {
    public static void Init(IPathProvider provider, IJsonSerializer serializer);   // GameEntry 装配时调用，未 Init 一切方法抛
    public static string PathOf(string first, string second);          // 热路径两段组合（零分配）
    public static string PathOf(params string[] parts);                // 低频多段
    public static void WriteAllText(string relPath, string content);   // 原子写
    public static string ReadAllText(string relPath);                  // 不存在返回 null

    // TryReadJson：显式层，不写日志——detail = "not_found"（首启正常）或 "parse: ..."（事故），版本迁移/坏档恢复用
    public static bool Exists(string relPath);
    public static void Delete(string relPath);

```

### 实现要点

1. **原子写是本件的灵魂**（§5.4-6）：tmp 写完 → `CommitAtomic`（`File.Replace` 分支 / 首写 `File.Move`）；`.tmp` 写一半被杀 → 目标仍是旧档。`EnsureDirFor` 补建目录——**首笔存档必炸的点**（`File.WriteAllText` 不建目录）
2. **ReadJson 双口径**：便捷层 `ReadJson`（不存在 → default 静默=首启正常；损坏 → default + Log.Error=事故可见）；显式层 `TryReadJson`（不写日志，detail 区分 not_found/parse，处置权在调用方——版本迁移/坏档恢复用）。**存档损坏不能炸启动**
3. **越界校验 release 也保留**（字符级零分配扫描）：禁 `..` 段（段边界判定，"a..b.json" 合法）、盘符、绝对开头——**越界路径可能来自配置/外部输入，属输入校验，不适用"信任 Debug"剥离模型**
4. **同步是主路径，异步是逃生口**：偏好/存档等小文件继续同步（主线程等微秒级 IO 可接受）；异步供大文件与归档（`MatchArchive`，§13）与"不能卡帧的写盘"。**Delete/Exists/GetFiles 不加异步**——元数据快操作，异步纯属噪音
5. **JSON 收口**：Core 只认 `IJsonSerializer` 接口，Newtonsoft 实现在 Unity 层（`Unity/IO/NewtonsoftJsonSerializer.cs`，GameEntry.Init 注入）——第三方零进 Core（第三方收口清单纪律）。**异步版序列化在线程池跑** → `IJsonSerializer` 实现必须线程安全（Newtonsoft：静态 `JsonConvert` 方法线程安全，实例 `JsonSerializer` 不保证——实现类用静态调用）
6. **不做**：归档打包、加密——回补口在 §1.2（异步已按本节增补）

### 异步实现要点（已实现，与文档对齐）

1. **形态（实现回写）**：文本读写用 **`FileStream(useAsync: true)` 真异步 IO**——不占线程池线程等待；**原子性保留**——tmp 异步写完，`CommitAtomic`（Replace）元数据级同步提交（微秒）。**JSON 序列化用 `Task.Run`**（CPU 工作，大文档不卡帧）+ 复用 `WriteAllTextAsync`
2. **原子写给了取消安全**：`ct` 在**步骤边界**检查（开始前/读完后），**不做写入中取消**——单文档单次写不可中断；中途取消/进程被杀只留 `.tmp`，旧档完好（原子写的附带红利）。**取消不是损坏**——`ReadJsonAsync` 里 `OperationCanceledException` 先放行，不进损坏分支
3. **同一文件并发防护（已实现）**：in-flight `HashSet<string>`（`StringComparer.Ordinal`）+ lock，重入 `Log.Error`——**Debug 与 release 都生效**（成本一次 lock+hash 可忽略，`.tmp` 冲突是静默损坏，可见性值得）；无锁防护——纪律仍是调用方对同一文件 `await` 串行
4. **UniTask 桥不写**：Core 只有 `Task`；业务侧直接 `await`（UniTask 支持 await Task）或 `.AsUniTask()`——不像 `INetworkService` 需要框架级 UniTask 包装（那边是持续事件流，这边是一次性等待）
5. **越界校验与同步同源**：relPath 防越界在异步入口同样检查（进后台线程**之前**）
6. **`GetFiles` 返回相对路径**（统一正斜杠，可回喂给本类任何 API）；`EnsureDirFor` 补建目录——`File.WriteAllText` 不建目录，首笔存档必炸的点

### 自测

- 原子写：写入 → 目标存在且 .tmp 消失；**模拟中断**：手工在 temp 位置放垃圾文件 → 下次写仍成功、目标完好
- JSON 往返（注入 fake serializer）；损坏 JSON → default + Log.Error
- 越界路径（`../`）Debug 下抛
- **异步**：`await WriteAllTextAsync` → 目标存在且 .tmp 消失；损坏 JSON 异步读 → default + Log.Error；**同一文件连发两次异步写 → Debug 告警重入**；ct 在开始前取消 → 任务取消、目标完好


### 实现要点

1. **构造注入**：Resolve 时反射取最长公共构造函数，参数递归 Resolve，结果缓存（仅单例）
2. **循环依赖**：解析栈（HashSet<Type>）检测，命中直接抛"循环依赖: A → B → A"——不做自动解
3. **解析时序（无运行时开关）**：容器不做 `AllowResolve` 门禁——它防不住真正的风险（`RegisterInstance` 之间的 Awake 顺序），防得住的场景即使发生也无害。防线是：装配完成前的解析命中未注册依赖直接抛、装配末尾 `Seal()` 封注册面、流程顺序契约（GameEntry `-1000` 最先执行）。组件 Awake"只注册不解析"是约定 + 流程层保证，不靠容器开关
4. ILuaRegistry：`Dictionary<string, T>`；Fill 重复名抛；Get 未命中抛（message 带"按 §4.4 路径约定应为 UI.<界面名>"）
5. **~~Validate() 构建期诊断~~（已作废）**：原设计的"遍历全部注册项模拟解析、四类问题一次报全"机制已于 2026-09-10 决策删除——诊断口径改为**解析时点当场抛**（未注册 / 循环依赖含 `A → B → C → A` 链 / 重复注册 / 构造抛真因），装配自检如需要走"流程内对关键服务各 Resolve 一次"的形态。见《M1实施指导》§1 决策记录。
6. **重复注册抛异常**：注册时就查重——现在静默覆盖，迟早踩。
7. **不做**：属性注入、自动扫描、AOP、线程安全、**Transient/Scoped 生命周期**（§2.1/§3.2 不做清单）。作用域需求为什么不成立，见《状态同步实施方案》§8.3——最需要作用域的战斗上下文被确定性纪律排除在容器外，剩下的全是活一辈子的单例。
8. **注册即发现 + Seal**：`RegisterInstance` 时与**工厂产物首次构造后**，检查 `is ITickable / is IModuleStats` 收进只读列表（漏收集 = 服务永不 Tick 的静默 bug，机制化后不可能再发生）；`Seal()` 后一切 Register* 抛、`Resolve` 不受限——由 ProcedureLaunch 装配末尾调用。**GameEntry 持有容器全程不置 null**（驱动要枚举 Tickables），密封靠标志。注册顺序即驱动顺序，显式写在装配处

### 自测

- A 依赖 B 依赖 C 的注入链全通；循环依赖抛且信息含环
- 单例：两次 Resolve 同实例；RegisterInstance 的实例与 Resolve 结果一致
- ILuaRegistry：Fill/Get/Has、重复 Fill 抛、未命中抛（信息含路径提示）
- **解析时点报错用例**：①未注册 ②循环依赖（信息含 `A → B → C → A` 依赖链）③重复注册 ④构造抛异常（解包报真因）
- RegisterFactory：工厂只在首次 Resolve 时调用一次，结果与 Register 一样按单例缓存
- **注册即发现**：按 Dispatcher → Clock → FSM 顺序 RegisterInstance（M0 实际集合，Scheduler/TimelineRunner 为 M4）→ `Tickables` 枚举顺序一致；RegisterFactory 产物实现 ITickable → 首次 Resolve 后补进列表
- **Seal**：Seal 后 Register / RegisterInstance / RegisterFactory 全抛、Resolve 正常

## 11. 网络服务契约 INetworkService（骨架预留挂点，无实现）

### 定位

**框架不实现网络，只定义挂点。** 沿用设计方案 §1.2「网络管理器砍掉，做联机时独立成插件，协议层不依赖框架」——框架认接口与生命周期，**不认协议**：不知道帧号、不知道 `InputFrame`、不知道房间概念。实现由 `LiteNet` 提供（联机场景见《状态同步实施方案》§7），装配期 `RegisterInstance` 进容器。

**落位：枚举在 Core，接口在 Unity 层**——`INetworkService` 含 `UniTask` 签名，而 Core 是 `references: []` 引不了 UniTask（§7.7 异步契约与 Core 零依赖在此撞车，Unity 层是唯一同时满足两者的位置）。`NetState`/`NetChannel` 是纯数据枚举，留 Core。**`LiteNet` 实现类不引用 LiteFramework（零依赖），桥接发生在 LiteGame**（它同时引用 Unity 层与 LiteNet）；且 LiteNet 必须禁 UniTask——`Server`（.NET 控制台）与客户端共用它，UniTask 依赖 PlayerLoop 在 .NET 下不可用。

**M0 只落契约文件（约 30 行），不写任何实现、不引入任何 socket 依赖。** 骨架保持零网络依赖，同时把"网络该怎么接"在动手之前定死——这是本件存在的全部理由。

### API 契约（Net/）

```csharp
public enum NetState { Disconnected, Connecting, Connected, Error }

public enum NetChannel { Reliable, Unreliable }   // 双通道：信令走可靠，逐帧输入走不可靠

public interface INetworkService : ITickable, IModuleStats {
    NetState State { get; }
    UniTask ConnectAsync(string host, int port, CancellationToken ct);
    void Send(ReadOnlySpan<byte> data, NetChannel channel);
    void Disconnect();
    event Action<NetState, string> OnStateChanged;   // 第二参数为错误原因，成功时 null
    event Action<byte[], NetChannel> OnReceive;      // 已按通道分流后回调
}
```

### 三点接法（决定了它为什么长这样）

| 关注点 | 归属 | 约束 |
| --- | --- | --- |
| **驱动** | 框架 | 实现 `ITickable`，由 `GameEntry` 统一轮询收发。**当前不开网络线程**（60Hz 小包轮询够用）；若按需引入收包线程，收包结果必须经 `IMainThreadDispatcher.Post` 回主线程（§7.4 边界规则） |
| **生命周期** | FSM/Procedure | `ProcedureLaunch` 注册实现；`ProcedureMatch` 调 `ConnectAsync`；退出战斗 `Disconnect`。**连接状态由流程响应，不由容器管理** |
| **诊断** | 框架 | `IModuleStats` → HUD 显示 RTT / 丢包 / 收发速率 |
| **协议语义** | `LiteNet`（框架外） | 帧号、输入打包、冗余、重连——框架一概不知 |

### 红线

1. 框架层**禁止**出现 `InputFrame` / `frameNo` / `RoomServer` 等协议概念。
2. UI 与薄壳**禁止**直引 `INetworkService` 发业务包，一律经玩法层封装（如 `IBattleService`）。
3. `OnReceive` 的 `byte[]` 所有权归网络实现，回调返回后即回收——订阅方要异步持有就自己拷贝（与 §3 事件中心所有权规则同款语义）。
4. **`NetChannel` 双通道不可省**：联机下输入走可靠通道会被 ARQ 队头阻塞，直接吃掉低延迟收益（《状态同步实施方案》§4.2）。

### 自测

M0 无实现，只验**契约可被装配**：写一个 `FakeNetworkService`（Send 存下来、可被手动喂 Receive），注册进容器 → 能被 `GameEntry` 排进 ITickable → Tick 被调用、stats 可读、`OnStateChanged` 能收到。契约面完整即可，不验任何真实网络行为。

## 12. 骨架装配 GameEntry（LiteGame 侧）

### 职责（唯一的装配点，替代 GF 的 GameFrameworkEntry）

```csharp
[DefaultExecutionOrder(-1000)]   // 见下方"执行顺序"说明
public sealed class GameEntry : MonoBehaviour {
    // 容器**不静态暴露 Resolve**：静态解析入口 = 服务定位器后门，会让"依赖从哪来"不可追踪。
    // 实例全程持有（驱动要枚举 Tickables）；密封靠标志不靠置 null——封的是注册面，不是容器生命周期。
    private static ServiceContainer s_container;

    /// <summary>组件 Awake 的唯一入口：**只许注册，不许解析**；装配密封后抛。</summary>
    public static void RegisterInstance<TInterface>(TInterface instance) {
        if (s_container == null || s_container.IsSealed)
            throw new InvalidOperationException("GameEntry 未装配或装配已密封");
        s_container.RegisterInstance(instance);
    }

    /// <summary>把装配权传给起始流程。ProcedureLaunch 是**唯一受信装配点**：
    /// 注册业务服务 → Seal。用 public：ProcedureLaunch 在 LiteGame.Runtime，跨程序集访问。</summary>
    public ServiceContainer TakeContainer() {
        if (s_container == null) throw new InvalidOperationException("未装配");
        return s_container;                              // 不置 null：Update 还要枚举 Tickables
    }

    private void Awake() {
        // 1. FileSys.Init(new UnityPathProvider(), new NewtonsoftJsonSerializer());  Log.SetHelper(new UnityLogHelper());
        // 2. 创建 SettingService 并 Load()——**先于容器与各壳注册**：UI/声音壳注册时就要读玩家偏好（音量/画质/语言）
        // 3. s_container = new ServiceContainer();
        // 4. 创建事件中心/时钟×(IWorldClock/IUIClock)/墙钟/FSM/各薄壳
        // 5. 各件 RegisterInstance 进 s_container（**注册即发现**：ITickable/IModuleStats 自动收集，
        //    注册顺序 = 驱动顺序：**MainThreadDispatcher 最先**（帧首泵，后台回调先于逻辑执行）
        //    → Clock → Scheduler → TimelineRunner（M4 交付后插入）→ FSM → 各壳——顺序就写在这里）
        // 6. 装配权传给起始流程：new ProcedureLaunch(TakeContainer(), ...)
        //    （M0 阶段 ProcedureLaunch 未交付——临时由占位流程持有容器，M2 接入）
        // 7. GetComponent<DebugTuner>()?.Inject(worldClock, uiClock, eventCenter);   // mono 调参组件（§12.5）
        //    GetComponent<DevHUD>()?.Inject(s_container.Stats);                      // 只读 HUD（§12.5）
        //    GetComponent<M0SelfTestRunner>()?.Inject(s_container.Tickables, s_container.Stats);  // 自测冒烟（§13）
        // 8. DontDestroyOnLoad(gameObject);
    }
    private void Update() {
        // 统一喂 unscaledDeltaTime：游戏变速由 IGameClock 内部缩放（勿用 Time.deltaTime 二次乘）
        foreach (var t in s_container.Tickables) t.Tick(Time.unscaledDeltaTime);
    }
}
```

> **为什么"静态持有但不静态解析"**：服务定位器的罪不在"有个静态对象"，在"任何地方都能随手 `Resolve`"。这里 `s_container` 私有，对外只有注册入口（密封后失效），解析一律构造注入——依赖图全部留在构造函数签名上。

- 场景上挂一个 GameEntry（首场景），DontDestroyOnLoad。**重复引导守卫（2026-09-10 实测补充）**：`s_container != null` → Warning + 销毁重复件（叠加加载的场景误含 GameEntry 时，否则二次引导会覆盖静态容器）
- **解析时序由流程层保证**：`ProcedureLaunch` 装配完成后 `Seal()`，此后才允许业务解析、注册面冻结（设计方案 §3.3）
- 骨架件**全部 RegisterInstance 进 DI**——M1 自测认领的接线动作；实现 `ITickable`/`IModuleStats` 的件**无需再手工收集**

**执行顺序（`[DefaultExecutionOrder(-1000)]` 不可省）**：启动顺序契约假设"其他 Component Awake（只注册）"全都在 `ProcedureLaunch` 之前完成，但 **Unity 跨 GameObject 的 Awake 顺序是未定义的**。若某组件晚于密封才 `RegisterInstance`，它的注册就会违例抛错——因此 FSM 启动（进而 Seal）放在 `GameEntry.Start()`，晚于全部组件 Awake。

因此：①`GameEntry` 用 `-1000` 强制最先执行 ②`Seal()` 封注册面——密封后一切注册当场抛（原 `Validate()` 的"已注册断言"随 Validate 删除，见《M1实施指导》§1）。

### DevHUD：IModuleStats 的消费端参考实现（M3 交付，消费端契约现在定死）

HUD 是 `Snapshot(Dictionary into)` 新契约的**直接受益者**：调用方复用容器、逐模块"填取渲染"，HUD 侧连 `Clear` 都不写（实现负责）。

```csharp
public sealed class DevHUD : MonoBehaviour {
    private IReadOnlyList<IModuleStats> _stats;
    private readonly Dictionary<string, string> _buffer = new(32);   // 全程复用，零容器分配
    private string _cache = "";                                      // 聚合成单串，OnGUI 只画一次
    private float _nextPoll;
    private bool _visible = true;

    private void Start() {
        var entry = FindAnyObjectByType<GameEntry>();
        if (entry != null) _stats = entry.Stats;    // 自拉取：LiteGame.DevHUD → Runtime 单向引用
    }

    private void Update() {
        if (!_visible || _stats == null || Time.unscaledTime < _nextPoll) return;   // 节流 4Hz
        var sb = new StringBuilder(256);
        if (Log.ErrorCount > 0) sb.AppendLine($"── ⚠ Errors: {Log.ErrorCount} ──");
        foreach (var s in _stats) {
            s.Snapshot(_buffer);            // 实现 Clear + 填（契约），HUD 不清
            sb.AppendLine($"── {s.StatsName} ──");
            foreach (var kv in _buffer) sb.AppendLine($"  {kv.Key}: {kv.Value}");
        }
        _cache = sb.ToString();
    }

    private void OnGUI() {
        if (!_visible) return;
        GUI.Label(new Rect(8, 8, 480, Screen.height - 16), _cache);   // Log.ErrorCount > 0 时标题行标红
    }

    private void LateUpdate() { if (Input.GetKeyDown(KeyCode.F1)) _visible = !_visible; }
}
```

四个设计决策：

1. **多模块共用一个 `_buffer`**：逐模块 `Snapshot → 渲染`，实现负责 Clear，前一个模块数据自动清掉——HUD 侧零 Clear 代码。
2. **自拉取而非注入（asmdef 方向修正）**：`LiteGame.DevHUD → LiteGame.Runtime` 单向引用，GameEntry 不能反向 `GetComponent<DevHUD>`（asmdef 禁循环）。HUD 在 Start 用 `FindAnyObjectByType<GameEntry>()` 拉 **`GameEntry.Stats` 只读访问器**——它是统计列表不是解析入口，不开服务定位器后门。
3. **节流是契约的组成部分，不是优化**：value 是插值串每次分配，4Hz 轮询摊薄到每秒几百小串（Gen0 无压力）；60Hz 全量轮询是每秒几千——不要做成每帧直读。
4. **聚合单串 + OnGUI 画一次**：OnGUI 本身昂贵，0.25s 生成一个串、每帧画一个 Label。F1 toggle；ErrorCount > 0 标题行标红。

### DebugTuner：mono 脚本调参组件（Development-only，M0 交付）

运行时旋钮的调参走 **MonoBehaviour + Inspector**（Unity 原生 UI，零 GUI 代码），不进 DevHUD 面板——`[Range]`/`[Header]`/`[Tooltip]` 开箱即用，Play 模式下 Inspector 改值实时生效。**不做通用调参抽象**：调参是 UI 手感活（滑条范围、bool 语义各不相同），字符串化通用接口会丢掉全部类型信息还逼实现方写解析器；M0 可调模块就 3 个，硬编码便宜得多——可调模块多了再议（YAGNI）。

```csharp
#if UNITY_EDITOR || DEVELOPMENT_BUILD
using UnityEngine;

namespace LiteFramework
{
    /// <summary>调试调参组件：Inspector 拖滑条实时调节运行时旋钮。
    /// GameEntry 装配期注入目标（step 7）；Update 同步字段 → 目标（每帧三次赋值，零成本）。
    /// 挂在 GameEntry 同 GameObject，随 DontDestroyOnLoad 常驻。</summary>
    public sealed class DebugTuner : MonoBehaviour
    {
        private IWorldClock _world;
        private IUIClock _ui;
        private EventCenter _events;

        [Header("世界时钟（时停/变速）")]
        [Range(0f, 2f)] public float WorldTimeScale = 1f;
        public bool WorldPaused;

        [Header("UI 时钟")]
        public bool UiPaused;

        [Header("事件中心")]
        public bool StrictMode = true;

        public void Inject(IWorldClock world, IUIClock ui, EventCenter events)
            { _world = world; _ui = ui; _events = events; }

        private void Update()
        {
            if (_world == null) return;
            _world.TimeScale = WorldTimeScale;
            _world.Paused   = WorldPaused;
            _ui.Paused      = UiPaused;
            _events.StrictMode = StrictMode;
        }
    }
}
#endif
```

要点：

1. **整个类包条件编译**——release 构建零残留（独立 Development-only asmdef 可以后置，条件编译先顶住）
2. **注入具体类型与接口混合**：时钟走 `IWorldClock`/`IUIClock` 接口（两实例类型安全），事件中心走具体类 `EventCenter`（StrictMode 是它的属性）——都是装配点拿得到的
3. **`Update` 每帧回写**：Inspector 改值 → 下一帧生效，实现 5 行；比 OnValidate 事件方案简单可靠
4. **与 DevHUD 的分工**：DevHUD = 只读快照展示（IModuleStats 读通道）；DebugTuner = 运行时旋钮（注入的具体引用写通道）——读写两条通道各自独立，都不碰容器
5. **自测联动**：调参改 `TimeScale`/`Paused` 后，DevHUD 上对应模块的快照值立即变化——**调参（写）与观测（读）在两个面板、一次 Play 里闭环**，这就是"mono 脚本调参测试"的完整形态

### 自测

- 进 Play 后：HUD（若已有）能看到各件 stats；Log.Recent 无 Error
- 手动在任意组件 Awake 里 Resolve → 编译期就该被拦（拿不到容器）；反射强取容器 Resolve 未注册项 → 抛
- **漏收集不可能**：新写一个实现 ITickable 的假件并 RegisterInstance → 不做任何额外登记，下一帧它被 Tick 到

## 13. M0SelfTestRunner（mono 自测入口，Play 模式）

`LiteGame/Scripts/Runtime/M0SelfTestRunner.cs`（Development-only 条件编译）——**从 Editor 菜单改为 mono 脚本**：挂 GameEntry 同 GameObject 的组件，`Start` 自动跑一轮 + `[ContextMenu]` 手动重跑。结果走 Log（tag `"SelfTest"`）：通过 `Info("M0 PASS")`，失败逐条 `Error`——DevHUD 的 ErrorCount 立即可见。
