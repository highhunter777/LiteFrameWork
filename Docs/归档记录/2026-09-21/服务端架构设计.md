# 服务端架构设计（精简主线）

> 本文是非战斗服务唯一总设计；战斗同步细节见《状态同步实施方案》，玩法六系统见《六大系统具体方案》。

## 1. 总体拓扑

```text
Client
 ├─ HTTPS/JSON + WebSocket → Gateway/JWT → Auth / Lobby / Profile / Chat / Guild
 └─ LiteNet KCP/UDP → RoomServer（权威 Sim）

RoomServer ──签名 RewardDelta──► ProfileService
Profile/Guild ──MatchStartSnapshot──► RoomServer
```

战斗 UDP 不经过 Gateway；非战斗请求和推送统一经过 Gateway。MVP 可以把 Auth/Lobby/Profile/Chat/Guild 托管在一个 .NET 进程，接口保持可拆分。

## 2. 服务职责

| 服务 | 职责 | 权威数据 |
|---|---|---|
| Gateway | TLS、JWT、HTTP/WS 路由和限流 | 无业务状态 |
| Auth | 游客登录、账号绑定、token | player/token |
| Lobby | 房间目录、创建/加入、匹配占位 | room_registry |
| Profile | 进度、局外背包、Loadout、结算 | Mongo player/inventory/ledger |
| Chat | 消息、频道、过滤、seq 补推 | Mongo chat + Redis online |
| Guild | 成员、角色、申请、公告、科技 | Mongo guild + guildLog |
| RoomServer | 60Hz AuthSim、输入、快照、回溯、重连、结算 | 本局战斗态 |

## 3. 协议矩阵

| 链路 | 协议 |
|---|---|
| 客户端 ↔ Auth/Lobby/Profile/Guild/Chat | HTTPS + JSON |
| 服务端 → 客户端社交推送 | WebSocket |
| 客户端 ↔ RoomServer | LiteNet：KCP 双通道 + protobuf |
| RoomServer → Profile | 内部 HTTPS/JSON + 服务凭证 |
| 服务间异步 | MVP 不引 MQ；需要削峰时再引入 |

所有错误使用 `code + messageKey + args`；时间统一 UTC；客户端不能提交 sender、奖励、库存数量或公会角色。

## 4. 账号、房间和进场

1. Client 调 Auth 获取自包含 token。
2. Lobby 创建/选择房间并返回 Room endpoint 和 join 参数。
3. Client 用 `(roomId, token, buildHash)` 走 LiteNet Join。
4. ProfileService 生成签名 `LoadoutSnapshot`；GuildService 可附加 `GuildBonusSnapshot`。
5. RoomServer 本地验 token/buildHash，锁定快照后启动本局；不在战斗中查询 Mongo。

## 5. 数据和结算

MongoDB（单节点副本集起步）保存：`player/playerProgress/inventory/loadout/progressLedger/guild/guildMember/guildLog/chatMessage/matchArchive`。

Redis 后置或按需用于：在线会话、room_registry、频道 presence、限流桶、邀请 TTL。

结算接口：

```text
POST /internal/profile/apply
{ operationId, settlementId, matchId, playerId,
  finalChecksum, resultHash, rewardDelta, consumptionDelta }
```

ProfileService 在 Mongo 事务中先写唯一 ledger，再更新进度/库存；重复 `operationId` 或 `(playerId, matchId)` 返回原结果，不重复发奖。

## 6. Chat 和 Guild 边界

- Chat 支持 World/Room/Team/Guild/Whisper/System；首版开放 Room/Team/Guild/System。
- Chat 消息由服务端生成 `messageId/serverSeq/sender/nickname/time`，UTF-8 限长、敏感词、禁言、黑名单、频道 ACL、限频均在服务端。
- Guild 的所有写操作带 `requestId + expectedVersion`，角色矩阵和 CAS 校验后写 `guildLog`。
- Chat 只依赖 Guild 成员权限缓存；Guild 不反向依赖 Chat。
- 公会科技只在下一局生成快照，不在战斗中动态改属性。

## 7. RoomServer 边界

- 每房间单线程 Sim，60Hz；30Hz 增量快照；AOI 只影响广播。
- KCP 输入不可靠冗余；信令、结算、重连可靠。
- 连接发送队列超限按降频、收缩 AOI、丢低优先级实体降级。
- RoomServer 不保存永久库存，不接受客户端直传奖励；只输出签名结算单和归档摘要。

## 8. 部署和排期

- MVP：Gateway + 一个 Meta .NET 进程 + N 个 RoomServer + Mongo；Redis 可后置。
- 达到房间/带宽/抗攻击阈值后再拆 Gate/Sim、Redis、MQ。
- 里程碑：Auth/Profile → Lobby → Guild/Chat → 匹配/运营化；战斗服按 M10–M12 主线推进。
