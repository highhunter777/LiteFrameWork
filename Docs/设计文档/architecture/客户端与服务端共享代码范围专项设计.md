## 1. 三个判据必须分开问

这是本文立论的基础。共享范围同时指三件不同的事，三者**互不相等**，必须分开问：

| 判据 | 问的是 | 决定 | 守不守得住 |
|---|---|---|---|
| **① 能编译吗** | 零引擎依赖？第三方依赖两端可对齐？ | 文件放哪、哪个程序集 | **编译器守** |
| **② 错了会被抓住吗** | 两端行为分叉时，多久暴露？ | 能不能改坏 | **握手守 / 用例守 / 没守** |
| **③ 谁可以依赖谁** | ProjectReference / asmdef references | 谁能认识谁 | **编译器守** |

判据 ①②③ 各自独立。当前仓库的事实是：

- 满足 ① 的集合（**177 个 .cs**）远大于满足 ② 中"硬守"的集合（**47 个 .cs + 玩法表**）——中间 130 个文件属**无守卫共享**（其中真会静默漂移的两类已由 G4 契约用例覆盖）；
- 判据 ③ 的守卫在编译期是硬的；方向本身由 §3 的 D1/D2 裁定。

**本文据此把"共享"拆成五档。**

## 2. 五档定义（S0–S4）

判据一句话：

> **S0 = 错了必须立刻被抓住**（硬握手）
> **S1 = 两端都要跑这套机制，但结果不需要逐位一致**（用例 + 纪律扫描）
> **S2 = 只有形状共享，两端各自实现**（G5 守零引擎 + 零第三方）
> **S3 = 只服务验证，不进任何运行时**
> **S4 = 客户端专属，服务端永不允许引用**

## 3. 方向规则

> **规则 D1（服务端产线）**：`RoomServer.exe` / `MetaServer.exe` **只准**依赖 S0 / S1 / S2。不得依赖 S3 / S4。
>
> **规则 D2（客户端）**：客户端**可以**依赖 S0–S3，但对 **S1** 的依赖必须在装配处分档声明——它是「**调试宿主**」关系，不是对等共享。
>
> **规则 D3（同源方向）**：S0 内**禁止**任何方向的分叉实现（"不引入第二套消息定义"已由《联机同步策略选型》§2 规定，此处承接）。

**D1 的实测依据**：`RoomServer.csproj` 与 `MetaServer.csproj` 均**零** `LiteFramework` / `LiteGame` 引用（grep 为空）——规则 D1 是**已被遵守的既成事实**，本文只是把它写成规则。

**D2 的实测依据**：`LocalServerTransport` 让客户端在**进程内**跑真 `RoomRuntime` + `SnapshotPipeline` 做离线开发——这是 S1 的正确用法。该依赖**只出现在具名程序集** `LiteGame.DevLocalServer`（D2 登记表唯一成员），由 L1 用例 `纪律_D2_…` 把守；业务程序集（`LiteClient.Runtime`/`LiteGame.App`）不引服务端程序集。

### 4.3 准入流程（新代码要划入共享范围时）

```
问 ① 零引擎依赖吗？
  ├─ 否 → S4（客户端专属），结束
  └─ 是 ↓
问 ② 错了会被握手抓住吗？（两端行为必须逐位一致）
  ├─ 是 → S0：进 gen-build-hash.py 的 TARGETS；改后必跑生成器
  └─ 否 ↓
问 ③ 两端都要"跑"这套机制吗？
  ├─ 是 → S1：asmdef noEngineReferences + 第三方两端同版本
  └─ 否 ↓
问 ④ 只有形状共享（接口/DTO），两端各自实现吗？
  ├─ 是 → S2：零第三方实现依赖；实现由组合根显式接线
  └─ 否 → S3（只服务验证）或 S4
```

**配套动作（三件，缺一不可）**：

1. **asmdef**：`noEngineReferences: true`（新增目录时）
2. **csproj**：`<Compile Include="新目录/**/*.cs" />`（`LiteNet.csproj` 是逐目录列举，不是整树 glob）
3. **`.gitignore` 白名单**：`!Assets/<模块>/<新目录>/*.csproj`（若新目录自带 csproj）
4. 若新目录有 dotnet 产物 → **同目录 `Directory.Build.props`**（重定向到 `.dotnet/`）

> **仓库无根级 `Directory.Build.props`**——重定向是**逐目录**的，新增共享目录必须自带，否则 `obj/` 里的生成 `.cs` 会被 Unity 当源码导入（CS1704/CS0579）。

## 5. 同源义务（共享不成立的两条路）

### 5.1 路径参与身份

多份产物的**路径**进哈希（Luban 表路径改动即 hash 变）。共享方向的路径挪动必须同步：`ScanTargets.cs`、YooAsset 收集组、`Tests.slnx`/csproj、`.gitignore` 白名单、构建器路径、`gen-build-hash.py`。

### 5.2 第三方依赖"同版本异构"

同一份源码，两端依赖来源不同——这是共享最脆的一环：

| 依赖 | Unity 侧 | dotnet 侧 | 对齐方式 |
|---|---|---|---|
| Google.Protobuf | `Assets/LiteNet/Vendor/Google.Protobuf`（DLL） | NuGet `3.36.1` | **人工对齐版本号**（注释明写"同一版本号"） |
| UniTask | `Assets/Plugins/UniTask` 2.5.11（源码） | NuGet `UniTask` 2.5.11 | 人工对齐 |
| kcp2k | `Vendor/kcp2k`（源码） | 同左（源码） | 无差异 |

**规则**：任一版本号变动，必须同批核对两端；**S0 的第三方依赖变动另须重跑 BuildHash**。

## 6. 口径边界（防止误用）

| 说法 | 边界 |
|---|---|
| "R 是共享的" | 指**能编译**（S1），**不**指结果必须逐位一致。`RoomServer.Runtime` 的改动**不**触发 BuildHash |
| "S0 以外都不保证同源" | 没错，但**不等于可以随意分叉**——S1/S2 仍受所属纯度红线与用例管辖（R11 等） |
| "S1 共编所以不会分叉" | **错**。两端依赖注入、线程模型、时钟来源都不同；S1 只保证**代码**相同 |
| "共编 = 同一个 DLL" | **错**。两端各编一份（Unity 侧 asmdef / dotnet 侧 csproj），**依赖解释不同**。BuildHash 常量的同值是"同目录双编"的副产品，证明的是源码相同，不是二进制相同 |
