## 1. 定位与分工

事件中心是框架级**机制件**：跨模块解耦通知的基座（UI 反馈、流程推进、Lua 桥、对局外事件）。与相邻机制的分工：

| 机制 | 分工 |
| --- | --- |
| `EventCenter`/`EventChannel<T>` | 委托订阅 + 快照派发（本专项） |
| `SubscriptionBag` | **订阅生命周期**：注销委托的栈式对称清理（`ClientScope`/`EntityHandle`/`UIForm.Subscriptions` 挂它）——事件中心不做 GC 魔法、不做弱引用，退订时机归调用方与 Bag |
| `ReferencePool`/`IReference` | **事件对象池化**：发布即移交、派发完中心统一回收（通道保持纯机制，不知道 IReference 存在） |
| `FrameEvent`（Sim 帧事件） | Sim 逻辑帧内瞬态事件（帧边界交付、重放静默）——与跨模块通知不同域，不经事件中心 |

红线：派发核心只有一套（快照式 `EventChannel<T>`）；新派发形态（优先级/延迟/有界）全部在既有核心上扩展，不做第二套派发器。

## 2. 继承基线（现状契约，本专项不改写）

- **快照派发**：本轮收到 = 派发开始时刻的订阅集；订阅/注销立即生效于下一次派发；嵌套派发各层独立快照（缓冲不复用外层）；稳态零 GC（快照缓冲增长式复用）。
- **异常隔离**：单订阅者异常只记 `Log.Error`，不炸派发链。
- **StrictMode**：未订阅事件告警——编辑器/开发构建默认 true，release 默认 false，运行时可覆盖。
- **所有权移交**：`Publish` 即移交事件对象，派发完成后 `IReference` 事件由中心统一回收；**无订阅者路径同样回收**（否则无订阅事件 = 泄漏）。
- **队列时序**：`PublishQueued` 当帧不触发、`Tick` 统一派发；派发快照量 = Tick 起点队列长度，派发期间新入队留到下轮（防同帧级联死循环）。
- **主线程 only**；事件类型 `where T : class`（引用上转零装箱）。
- **既有测试基线**：订阅派发/注销幂等/派发中改集/队列时序/StrictMode/零 GC/池化回收 七例（`EventCenterTests`）。

## 3. 高级化契约（新增能力）

### 3.1 优先级派发

`Subscribe<T>(handler, int priority = 0)`——**小值先派发**（与 `DownloadSource.Priority` 同约定）；同优先级保持注册序（稳定排序）。通道内订阅表按优先级有序维护，快照机制（含嵌套隔离、缓冲复用）不变。兼容：现有单参 `Subscribe<T>(handler)` = priority 0，调用方零改动。

### 3.2 有界队列与溢出防护

`MaxQueued`（默认 256，可配）：`PublishQueued` 入队超限时**丢弃并计数**（`QueuedDroppedCount`）+ `Log.Error`。被丢弃事件若实现 `IReference` **同样回收**——丢弃路径与"无订阅者路径同样回收"同纪律，不因溢出产生池泄漏。定位：`Tick` 驱动的队列在消费不及（卡顿/漏 Tick）时有界可诊断，不无界堆积。

### 3.3 延迟派发

`PublishQueued<T>(T e, int delayFrames = 1)`——延迟 `delayFrames` 帧后经**同一派发核心**（StrictMode/回收/异常隔离/优先级全适用）。中心维护帧计数，到期条目按入队序派发；延迟在途条目不受"当帧快照"级联防护语义约束（它们本就属于未来帧）。兼容：`PublishQueued<T>(e)` = delayFrames 1（现状语义保持）。定位：UI 反馈的"下一拍"时序（飘字错帧、结算延迟一拍）不必各自起计时器。

### 3.4 重复订阅告警

Debug 三宏下，同一通道重复 `Add` 同一 handler 委托 → `Log.Warning`（**不抛**——多实例订阅者复用同一静态方法是合法形态）；release 信任 Debug 全绿。与 `SubscriptionBag` 的"违例必炸"相反：重复订阅是可疑而非致命。

### 3.5 兼容红线

现有 `Publish`/`PublishQueued` 单参签名与语义逐位不变（`delayFrames` 默认参数即现状）；快照派发语义（含嵌套隔离、稳态零 GC）不变；StrictMode 默认分流不变；`SubscriptionBag`/池化回收分工不变。

### 3.6 明确不做（非目标登记）

- **跨线程发布**：主线程 only 是框架约定（服务端/客户端都是单线程泵），不加锁不加队列同步。
- **值类型事件**：`class` 约束的引用上转零装箱已声明，改造收益低。
- **事件拦截/过滤链、异步派发**：无场景，不做。
- **弱引用订阅者**：生命周期归 `SubscriptionBag`/`ClientScope`（§1 分工）。

## 4. 统计与诊断面

- **中心级**（`IModuleStats` 追加，键增量 HUD 兼容）：`QueuedPeak`（队列峰值）、`QueuedDropped`、`DispatchErrors`（派发异常累计）、`Recycled`（池化事件回收累计）、`StrictWarnings`、`DelayedCount`（延迟在途）。
- **通道级**（镜像 `ReferencePoolInfo` 形态）：`EventChannelInfo`（事件类型/订阅者数/累计派发/异常数）+ `GetChannelInfos()`——Debug 三宏（HUD asmdef 本身 Development-only），供"哪个事件被谁订阅了几次、有没有空转"的诊断。
- StrictMode 告警与异常计数是"事件系统健康度"的两个信号：前者抓没人听的事件，后者抓订阅者里的坏代码。

## 5. 验收口径

- **L1**：既有七例回归不翻红；新增——优先级序（含同优先级稳定序）、重复订阅告警、有界溢出（含池化事件丢弃路径回收断言）、延迟派发时序（当帧不触发/到期帧触发/与当帧队列的先后）、统计口径。
- **行为等价**：Lua 桥（唯一活跃消费者）与 `EntityService`/`UIForm` 注释范式零改动仍正确。
- 门禁：L1 全量 + Unity 编译；EditMode 随编辑器窗口期。
