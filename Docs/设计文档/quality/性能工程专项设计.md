# 性能工程专项设计

> 状态：草案（预算阈值为推导初稿，待基线回填）
> 版本：0.1
> 更新日期：2026-10-01
> 适用范围：LiteSim Core / View、LiteNet、LiteGame 战斗宿主的 CPU / GC / 带宽性能工程；UI 性能、真机发布性能不在本文范围。
> 维护责任：质量工程（性能方向）
> 关系：测试分层（L0～L4）、`Category=Performance` 元数据、统一执行入口 `scripts/gate/test.ps1` 以 [测试开发框架总设计](测试开发框架总设计.md) 为唯一权威；UI 性能预算与采样以 [UI 测试开发专项设计](UI测试开发专项设计.md) 为唯一权威。本文不复制第二份，只定义 Sim/网络/宿主侧独有的预算、度量与门禁。

## 1. 目标与原则

把性能从"凭纪律防慢"升级为"凭数据知快慢"：先量化目标，再建立度量，按证据优化，最后把阈值钉成门禁。

- **不测不优化**：没有基线数据的热点不允许动手；"感觉慢"不是优化理由。
- **先测后定**：预算阈值一律先占位，P1 基线产出后回填实测值加余量，禁止拍脑袋写死。
- **阈值即代码**：预算落 `PerfBudgets.cs` 常量表 + 测试钉住，与 `SimConfig` 同一纪律（一处定义，禁止散落魔数）。
- **度量不污染确定性**：墙钟、采样、Profiler 埋点永不进入 LiteSim Core 逻辑路径；Core 内维持 DisciplineScanner 现行纪律（禁 Stopwatch 等）。测量只能寄宿在 Unity 宿主层、Editor / DEVELOPMENT_BUILD 编译分支和测试工程里。
- **优化不改语义**：任何性能优化必须保持 checksum 逐位一致，以现有确定性测试（IeeeBaseline、重放等价性）为否决项。

## 2. 现状盘点

### 2.1 有利条件

LiteSim Core 为 net8.0 双轨（asmdef + csproj），可脱离 Unity 在 `dotnet` 侧跑微基准并接入 CI；Core 热路径已近零分配（`SimWorldState` 预分配定长数组、`SimStep` 零分配插入排序），确定性纪律由 DisciplineScanner（R1～R5、R9）守住；已有 `IModuleStats` 零分配统计契约与 DevHUD 展示通道可复用为性能计数器；测试框架已有 `Category=Performance` 分类与"夜间/发布执行、不进普通功能门禁"的执行契约（《测试开发框架总设计》§3），性能测试直接挂入，不另建体系。

### 2.2 缺口

全框架尚无 ProfilerMarker / FrameTiming 埋点、BenchmarkDotNet 与性能基线数据；View 层残留生产诊断分配（见 §5 表）且无静态规则拦截热路径分配模式；无性能回归门禁，慢代码合入没有环节会红。

## 3. 性能预算（P0）

### 3.1 最坏帧成本推导

由 `LiteSim/Core/Scripts/SimConfig.cs` 常量推导**单渲染帧逻辑侧最坏当量**：

```text
最坏当量 = MaxCatchUp + MaxRollbacksPerFrame × (1 + MaxRollbackFrames)
        = 5 + 2 × (1 + 8) = 23 个逻辑帧当量
```

（追帧 5 帧；每次回滚 = 1 次快照恢复 + 最多 8 帧重放；每逻辑帧成本含 `SnapshotRing.Capture`。）

若逻辑侧只占 60Hz 渲染帧（16.6ms）的 50%，则**单逻辑帧预算上限 ≈ 8.3ms / 23 ≈ 0.36ms**。该值是架构常量决定的硬约束，与实现快慢无关——实现超出它，最坏帧必然掉帧。

### 3.2 预算表（初稿，待基线回填）

| 编号 | 指标 | 场景口径 | 初稿阈值 | 状态 |
| --- | --- | --- | --- | --- |
| PERF-01 | 单逻辑帧 `Sim.Tick` | 256 实体满载、p95 | ≤ 0.36 ms | 推导值，待基线回填 |
| PERF-02 | 最坏渲染帧逻辑侧耗时 | 追帧 5 + 回滚 2×9 当量 | ≤ 8.3 ms | 推导值，待基线回填 |

| PERF-04 | GC 分配（View 热路径） | 每渲染帧 | 0 B | 诊断串改编译宏门控后生效 |

## 4. 度量基础设施（P1）

三层度量，各司其职，数据互相印证：

| 层 | 工具 | 覆盖对象 | 执行位置 |
| --- | --- | --- | --- |
| 微基准 | BenchmarkDotNet（net8.0 双轨工程，参照 `LiteTesting.Core.csproj` 双轨模式） | `SimStep` 全系统、`SimChecksum`、`SnapshotRing.Capture/Restore`、`InputHistory`、`SnapshotDiffer/Codec` | L1，`dotnet test` 旁路、夜间 |
| Unity 内埋点 | ProfilerMarker + FrameTimingManager；仅 `UNITY_EDITOR \|\| DEVELOPMENT_BUILD` 编译进来 | View 插值、动画后端、Vfx、宿主 `BattleContext.Tick` 各段 | Editor / Dev 构建 |
| 实时计数 | 扩展 `IModuleStats` 实现 + DevHUD 面板 | 逻辑帧耗时滑动窗、回滚次数、追帧次数、实体数 | 开发面日常观察 |

约束：

- ProfilerMarker 只许出现在 View / LiteGame / LiteNet 程序集；**LiteSim Core 零埋点**（守确定性纪律，测量靠宿主层包夹计时）。
- EditMode 性能断言用 `GC.GetAllocatedBytesForCurrentThread` 做零分配判定（PERF-03/04 的直接承载）；计时类断言只在固定场景定次计平均，且`Category=Performance`，不进 PR 功能门禁。
- 只引入 `Unity.PerformanceTesting` 包，或在 `LiteTesting` 上扩展性能采样夹具，二选一并保持单一实现，禁止两套并存。

## 5. 热点优化清单（P2）

按代码证据排序；**每一项的前置条件都是"基线确认该项确为热点"**，顺序随基线数据调整。

| 优先级 | 位置 | 问题 → 方向 |
| --- | --- | --- |
| 高 | `LiteSim/View/SimView.cs:412-423` | 远端插值每实体每帧 O(256) 线性扫 TryFind → 改槽位索引直查 |
| 高 | `LiteSim/Core/Scripts/SnapshotRing.Capture`（`SimWorldState.CopyTo` :203-222） | 每逻辑帧约 15 个数组全量 `Array.Copy`（CPU 热点非 GC）→ 先测；热则改连续块拷贝或脏段捕获 |
| 中 | `LiteSim/View/EntityViewMap.cs:86-87` | 视图回收路径 `$""` 插值 + LogWarning（生产残留诊断）→ 编译宏/日志级门控 |
| 中 | `LiteSim/View/Animation/Drivers/CharacterLocomotionDriver.cs:189,227-229`、`:192` | 首帧 `new SlotAnim` + 插值日志、`GetComponentInChildren` → 缓存与门控 |
| 中 | `LiteSim/View/Vfx/VfxService.cs:171,236-243` | `StopAll` 的 `ToArray()`、统计 `ToString×8` → 复用缓冲 |
| 中 | `LiteSim/View/SimView.cs:351` | 缺 AimPoint 时每帧 `transform.Find` → 缓存查找结果 |
| 低 | `LiteSim/Core/Scripts/SimChecksum.cs` | 校验和 SIMD 化（net8 `System.Numerics`）→ 必须通过确定性审查并登记 DisciplineScanner 白名单后才许动手 |

明确**不做**：

- Burst / Jobs / NativeContainer 进 LiteSim Core——破坏 net8.0 双轨与确定性纪律；仅当基线证明 View 侧确有瓶颈时，在 View 侧局部启用。
- 绕过 `IAnimationBackend.TryPlayBlend` 等既有契约做"性能捷径"——契约优先，优化在契约内部做。

## 6. 回归门禁（P3）

- **阈值门禁**：`PerfBudgets.cs` 常量表 + 性能测试断言钉住；基线回填前测试只记录不拦截（report-only），回填当批转为红绿门禁。
- **静态门禁**：DisciplineScanner 新增性能规则——Core 与 View 热路径禁 LINQ、字符串插值、装箱、`transform.Find`（规则编号与扫描目标沿用《测试开发框架总设计》L0 层既有模式，实施时在 `ScanTargets.cs` 登记）。
- **CI**：微基准结果 JSON 入产物库，按基线版本对比；性能报告口径（样本数、p50/p95/p99、设备/构建信息）沿用《UI 测试开发专项设计》§8.3 产物契约，不另定格式。
- **变更协议**：动 `SimConfig` 容量/回滚常量、动快照布局（`SimWorldState` 数组集）→ 必须重跑基线并在 PR 中附前后对比。

## 7. 阶段路线与退出条件

| 阶段 | 内容 | 退出条件 |
| --- | --- | --- |
| P0 预算定义 | `PerfBudgets.cs` 预算常量表与本文预算初稿入库，DevHUD 增加性能页签骨架 | 预算常量有唯一来源，测试引用该来源（占位不断言） |
| P1 度量基线 | BenchmarkDotNet 套件 + Unity 埋点 + 满载场景基线报告 | 产出首份基线数据；预算表回填实测值 + 余量 |
| P2 热点优化 | 按 §5 清单逐项：基线 → 优化 → 对比 → 确定性测试 | 每项有前后对比证据；checksum 相关测试全绿 |
| P3 回归门禁 | 阈值转门禁 + 扫描规则 + CI 对比 | 超阈值 PR 会被拦下；规则误报率为零 |

P3 之后回到 P1：门禁报警或 `SimConfig` 变更触发复测与预算校准，形成闭环。

## 8. 失败语义与边界

- 性能测试失败 = 超显式预算或样本缺失场景/设备/构建信息；失败报告必须含场景口径、样本数、p50/p95/p99 与基线版本，禁止只有"慢了"。
- 性能测试 `Category=Performance`，失败**不阻塞**普通功能 PR 的成功率统计，但阻塞夜间门禁与发布门禁。
- Editor 数字只用于趋势发现；涉及发布结论的口径（PERF-01/02 的定版）以 Player/目标设备为准——沿用《UI 测试开发专项设计》"Editor 不当真机结论"的同一立场。
- 肉眼观感、美术表现质量不进本文预算；UI 打开性能、列表滚动等归《UI 测试开发专项设计》§6。
