# 物品与容器系统专项设计

> 状态：草案
> 版本：0.1
> 更新日期：2026-11-02
> 适用范围：`ItemDef` / `ItemInstance` / `Container` 三层数据模型、二维容量规则、权威归属与写入分流、持久化与膨胀治理；联机对局与单人大世界共用同一套规则
> 维护责任：游戏业务架构 / 服务端
>
> **定位**：回答"物品怎么被表示、放进哪个容器、容量怎么算、谁说了算、怎么落库"。
> **不做的事**：不裁决玩法数值与表结构（归[《玩法数值与Luban配置专项设计》](玩法数值与Luban配置专项设计.md)）；不裁决进局/结算流程与首版玩法范围（归[《游戏业务系统总设计》§7](游戏业务系统总设计.md)）；不裁决客户端页面与性能判据（归[《局外背包客户端专项设计》](局外背包客户端专项设计.md)）；不定义世界模拟的运行时形态（见 §9 待裁决）。
> **冲突裁决**：数据结构与容量规则以本文为唯一权威；业务契约与流程以业务总设计 §7 为准；两者冲突时按"流程从总设计、结构从本文"处理，且不得在第三处复制本模型。

## 1. 既定口径

以下为已裁决的模型前提，后续章节全部由此推导。改任一条都必须重推容量规则与持久化模型。

| 编号 | 口径 | 影响面 |
| --- | --- | --- |
| D1 | **必须联网**，单人模式的数据同样由服务器权威 | 权威归属、断线恢复、写操作确认 |
| D2 | 容量为**格子 + 负重**双约束 | 容量算法、部分加入语义、UI 双指标 |
| D3 | 世界容器**全量持久化** | 落库模型、脏标记、膨胀治理 |
| D4 | 拾取**允许部分**，交易**不允许部分** | 容器策略位、反馈语义 |
| D5 | 堆叠判据 = **同 def + 未绑定 + 未过期** | 堆叠键、实例字段 |
| D6 | 负重**无二次影响**（不改变移速、耐力或任何判定量） | **负重不进 Sim、不进快照、不进投影、不产生 `SimCommand`** |

D6 是一条减法：它把背包从判定面彻底切开，代价是负重只作为拾取门槛存在。这条同时意味着**不许在后续批次把负重接进 `MovementSystem`**——那会重新引入跨端一致性风险，要接必须重新裁决。

## 2. 模型分层

```text
ItemDef        配置表，装载后只读，按 id 直接下标寻址
   │
ItemInstance   实例身份与可变状态（不定长）
   │
Container      容量、策略、归属、持久化级别
   │
Authority      服务器权威宿主：世界服务 / 对局服务
```

| 层 | 可变性 | 存放位置 | 谁写 |
| --- | --- | --- | --- |
| `ItemDef` | 只读（装载后） | Luban 表 → 两端内存 | 生成器 |
| `ItemInstance` | 可变（数量/耐久/过期） | 仅权威侧内存 + 库 | 权威事务 |
| `Container` | 可变（内容/状态） | 仅权威侧内存 + 库 | 权威事务 |
| 客户端视图 | 只读投影 | 客户端内存 | 读模型 |

**不定长字段（词条、来源记录、任务标记）只允许存在于 `ItemInstance`，永远不进 `SimWorldState`。** 对局内需要的战斗事实一律走定长投影（见 §7.2），这条是硬边界。

## 3. ItemDef

`tb_item` 建议列（已在业务总设计 §7.2 列出基础列，本文补足容量与持久化所需）：

| 列 | 用途 | 备注 |
| --- | --- | --- |
| `id` | 定义主键 | 热路径下标 |
| `type` | 分类（武器/消耗品/材料/任务/容器） | 决定可用动作 |
| `stack_max` | 单格堆叠上限 | `1` = 不可堆叠 |
| `unit_weight` | 单位负重 | 整数或定点，避免浮点累积 |
| `use_type` / `equip_slot` | 使用与装备槽语义 | 与 Sim 动作槽对齐 |
| `rarity` / `value` / `icon` | 展示与经济 | 不参与规则 |
| `max_durability` | 耐久上限（0 = 无耐久） | 参与堆叠键判定 |
| `bind_policy` | 绑定策略（拾取/装备/交易时绑定） | 参与堆叠键判定 |
| `container_kind` | 当 `type=容器` 时，开出的容器类型 | 见 §5 |

- 装载后不可变；运行期**禁止**按 def 改数值。
- 负重与堆叠上限一律从表读取，客户端与服务端不得各写一份默认值。

## 4. ItemInstance

```text
ItemInstance {
    itemUid      // 全局唯一，服务端生成（ULID 或号段），客户端不得构造
    defId
    qty
    durability   // 无耐久物为 0
    affixes[]    // 不定长；只活在权威侧
    bind         // 未绑定 / 已绑定 / 绑定中
    expireAt     // 0 = 不过期
    origin       // 产出溯源（审计用，见 §8.4）
}
```

规则：

- **`itemUid` 由服务端生成**，客户端只能回传；任何客户端生成的 id 一律拒绝（防刷的第一道闸）。
- `qty` 上限 = `stack_max`；跨堆叠的操作必须先拆分再合并，不允许实例数量越界。
- `expireAt` 用服务器时间（UTC），过期实例在下一次容器扫描时清理，不在读取时静默丢弃（否则 UI 与库不一致）。

## 5. Container

```text
Container {
    containerId
    kind          // PlayerBag / Equipment / MatchBag / WorldChest / Corpse / Shop / Quest / Warehouse
    slots[]       // { slot, itemUid }（实例内容见 ItemInstance）
    slotCapacity
    maxLoad
    policy        // 是否允许堆叠 / 是否允许部分加入 / 是否可被外部访问
    state         // 可刷新容器的状态机（见 §8.2）
    nextRefreshAt
}
```

| kind | 权威 | 持久化 | 生命周期 |
| --- | --- | --- | --- |
| `PlayerBag` | 世界服务 | 持久 | 账号级 |
| `Warehouse` | 世界服务 | 持久 | 账号级 |
| `Equipment` | 世界服务 | 持久 | 账号级，随 Loadout 锁定 |
| `Quest` | 世界服务 | 持久 | 账号级；不占背包格与负重 |
| `MatchBag` | 对局服务 | 会话 | 一局；12 格定长布局 |
| `WorldChest` | 世界服务 | 持久 | 世界级 |
| `Corpse` | 世界服务 | 持久（受 §8.3 收缩） | 世界级 |
| `Shop` | 世界服务 | 配置驱动 | 世界级；内容来自表，不落库 |

- **`Quest` 容器独立于背包**：任务物品不占格、不计重、不可丢弃，避免"背包满导致剧情卡死"这类不可恢复状态。
- `Shop` 不持久化内容，只持久化"该玩家已购买次数"；否则每开一次商店就写一次库。
- 容器的 `policy` 是规则层分支的唯一来源，禁止在业务代码里按 `kind` 散写 `if`。

## 6. 容量规则

### 6.1 二维判定

```text
CanAccept(container, defId, qty) -> acceptedQty
    // 槽位维度：先补现有堆，再开新格
    slotNeed   = max(0, ceil((qty - spaceInExistingStacks) / stackMax))
    slotOk     = usedSlots + slotNeed <= slotCapacity
    // 负重维度
    loadOk     = load + qty * unitWeight <= maxLoad

    acceptedBySlot   = 能放进槽位的最大数量
    acceptedByLoad   = floor((maxLoad - load) / unitWeight)
    return min(acceptedBySlot, acceptedByLoad)   // 两个维度取小
```

- 两维独立，不合并成"综合容量"；任一维满即限制。
- 负重比较用整数（或定点），**不用浮点累加**——浮点累加会让"刚好满"在不同端得出不同结果。

### 6.2 部分加入语义

| 场景 | 部分加入 | 理由 |
| --- | --- | --- |
| 拾取（地面/尸体/箱子） | **允许** | "只能装 3 个"是自然体验；剩余留在地上 |
| 交易 / 购买 / 邮件领取 | **不允许** | 部分成功会产生对账歧义，是 bug 温床 |
| 容器间移动 / 整理 | **不允许** | 部分移动会让玩家看到中间态 |

不允许部分的场景，`policy` 必须声明 `allOrNothing=true`，由规则层在**一次事务内**判定整体可行性，不做"先加一半再回滚"。

### 6.3 堆叠

堆叠键 = `(defId, bind==未绑定, expireAt==0 或相同批次)`。按 D5：

- 不同 `defId` 不可堆。
- 已绑定与未绑定的同 def **不可堆**。
- 有 `expireAt` 的实例只与**同一到期批次**堆叠。

**待裁决（见 §9）**：耐久与词条是否参与堆叠键。若参与，需引入 `stackKey` 字段把判定集中到一处，禁止在业务代码里散写比较。

## 7. 权威与写入分流

### 7.1 写操作分类

| 操作类型 | 例子 | 权威 | 事务边界 |
| --- | --- | --- | --- |
| 产生 / 销毁物品 | 拾取、购买、丢弃、消耗 | 服务器 | 单命令事务 + `operationId` 幂等 |
| 重排物品 | 拖拽、排序、切换页签、查看 | 客户端视图态 | 无（不上行） |
| 改变装备 | 装备/卸下 | 服务器 + `Loadout` 锁定 | 与进局流程串行 |

判据一句话：**凡可能改变"物品总量或归属"的操作必须过服务器事务；只改变"显示顺序"的操作不下行。**

### 7.2 战斗投影

背包与判定的唯一接口是一条**定长投影**：

```text
SimProjection {
    弹匣 / 备弹 / 当前武器槽
    快捷消耗品可用数量（4 格计数）
}
```

- 投影字段全部定长、可进快照与 checksum。
- 负重（D6）、词条、耐久、绑定状态**一律不进投影**。
- 对局内消耗一瓶药：投影计数 −1 + 发一条命令 → 权威侧结算 `ItemInstance`，不回写投影（避免二次扣减）。
- 投影的存在意义是"让 Sim 只看见战斗需要的最小事实"，不是"背包的副本"。

## 8. 持久化与膨胀治理

### 8.1 写入模型

- **容器级脏标记**：只有内容或状态变化的容器进入待写集合。
- **批量 upsert**：一次提交期内合并同类写入，按 `containerId` 排序提交，避免随机写。
- **事务边界**：一次玩家命令内的所有容器改动要么全提交、要么全回滚；跨玩家交易走两阶段（预留 → 提交/释放）。
- **写入不等于生效**：先落库后回包；回包失败不回滚已落库事实，由客户端按 `revision` 重拉对齐。

### 8.2 可刷新容器状态机

```text
Ready --(玩家开箱)--> Opened --(到期)--> Refilling --(服务器时间到)--> Ready
```

- 刷新**只认服务器时间**，客户端时间不参与。
- `nextRefreshAt` 随容器持久化，重启后按墙钟重算，不重置为"立即刷新"——否则重启即刷箱。
- 开箱本身不产生物品；**产生物品的动作才落库**，避免空开也写库。

### 8.3 尸体与世界容器收缩

D3 的"全量持久化"不等于无限增长。收缩是唯一例外，必须写进设计而不是默默执行：

| 容器 | 收缩判据 | 处置 |
| --- | --- | --- |
| `Corpse` | 区域 × 时间 × 数量三重上限 | 超限时：未拾取物合并进"残骸容器"或销毁，**留审计记录** |
| `WorldChest` | 配置的刷新周期 | 到期刷新内容，不删除容器本体 |
| 玩家容器 | 不收缩 | 由玩家自行整理 |

收缩必须可观测：每次收缩产出"容器 id / 回收物品摘要 / 触发判据"的审计条目，禁止静默丢弃。

### 8.4 产出溯源

`ItemInstance.origin` 记录产出源头（掉落表 id / 容器 id / 交易方），用于：

- 刷物品排查（同一来源异常高频产出）；
- 经济审计（某类物品的注入总量）；
- 客服回滚（按 `itemUid` 定位全链路）。
