# 工具链域形态基线专项设计

> **版本**：0.1（2026-10-22）
> **定位**：裁决“开发工具链的每个域内部该长什么样”——把清单 `categories` 当作域，为 9 个域各定 5 条形态基线，并把其中可机械判定的三条落成 `toolchain.py check` 的域规则。
> **不做的事**：不裁决跨域的形态统一（实现语言与目录位置由运行时边界决定，见[平台专项](开发工具链平台专项设计.md) §1/§9）；不裁决具体工具的算法、交互与视觉；不登记收敛批次与状态（归 `Docs/施工进度/`）。
> **冲突裁决**：入口、清单、写盘契约以[《开发工具链平台专项设计》](开发工具链平台专项设计.md)与[《工具执行与写盘契约专项设计》](工具执行与写盘契约专项设计.md)为准；本文只裁决“域内形态”。
> **关联**：[平台专项](开发工具链平台专项设计.md)、[写盘契约](工具执行与写盘契约专项设计.md)、[生成器工具箱](生成器工具箱专项设计.md)、[GM 分层](GM与调试工具分层专项设计.md)、[修改指南](../../修改指南.md)。

## 1. 定位与判据

**统一的粒度是“域”，不是整条链，也不是单个工具。** 理由三条：

1. 消费者按域找工具（“我要烘焙”“我要跑门禁”），不按运行时找；
2. 域是 CI、计划任务、维护人的自然单位，域内不一致的成本由同一批人反复承担；
3. 清单的 9 个 category 中有 7 个天生混合 kind（C# 页件 + Python CLI + 门禁/内容），跨 kind 拉平不成立，域内统一接缝才是可执行的那一层。

**判据：换工具不换心智。** 只统一“调用方需要重新学习”的部分——入口、命名、结果、写面、文档指向。能写进清单并被 `check` 判出来的才进基线；判不出来的（抽象层次、交互流程、代码风格）不写。

## 2. 域与形态边界

| 域 | plane 组成 | purpose 组成 | kind 组成 | 域内形态基调 |
|---|---|---|---|---|
| baking | 6 editor | 6 dev | 5 action + 1 window | 全 C#：一个窗口承载多种烘焙 |
| ui | 10 editor | 10 dev | 7 action + 3 window | 全 C#：窗口 + 上下文入口并存 |
| debug | 6 runtime + 2 external | 8 debug | 6 page + 1 cli + 1 hud | 页件 + 一个日志 CLI + 一个运行内 HUD |
| codegen | 5 external + 1 editor + 2 runtime + 2 none | 8 dev + 2 debug | 5 cli + 3 action + 2 docs | Python 生成器 + 编辑器内生成器 |
| deploy | 4 external | 4 delivery | 4 cli | 纯 Python 运维 |
| quality | 7 external + 2 editor | 7 delivery + 2 dev | 6 gate + 2 action + 1 cli | 门禁编排 + 纪律动作 |
| build | 2 external | 2 delivery | 2 build | 出包与冒烟 |
| content | 3 external + 3 editor | 3 dev + 3 delivery | 3 action + 3 content | 内容候选、CDN 与 Bundle |
| env | 5 external + 2 none | 4 delivery + 2 dev + 1 debug | 3 cli + 2 gate + 2 docs | 环境恢复、夜间、索引 |

**`plane` 是生效面轴、`purpose` 是能力线轴、`kind` 是宿主形态轴**：域内三者都可混（gm 同时有运行态页件与外部进程条目，codegen 同时服务开发与调试），但同一 kind 在域内仍只有一种形态：

- `page / window / action`：只经 Hub 适配，入口、报告区、确认方式由 Hub 壳统一；
- `cli / gate / build / content`：命令行入口 + 输出前缀 + 退出码 + 声明的 `args`；
- `hud`：运行内自创建载体，域内不提供 Hub 执行面，只在索引与 Hub 里说明前置；
- `docs`：只做说明，不提供执行入口。

平面语义与六条判定规则见[平台专项 §3.2.1](开发工具链平台专项设计.md#321-平面与前置)；用途（三条能力线）语义见[平台专项 §3.2.2](开发工具链平台专项设计.md#322-用途能力线)。

## 3. 九份域基线

每份五条：**入口 / 命名 / 结果 / 写盘 / 文档**。

### 3.1 baking（内容烘焙）

1. **入口**：唯一窗口 `baking.toolbox` 承载全部烘焙动作；五个 action 只从该窗口或 Hub 触发，不新增菜单与快捷键。
2. **命名**：id 为 `baking.<对象>`；产物按“目标资产 + 烘焙类型”命名，不另造缩写。
3. **结果**：每次烘焙输出 `[baking/<对象>]` 摘要（成功/跳过/失败计数）；单资产失败不中断整批，但必须逐条列出。
4. **写盘**：只写声明的 `outputs`（目标资产或生成数据）；覆盖前确认，不写 BuildHash 闭包。
5. **文档**：唯一权威《烘焙工具箱专项设计》；新增烘焙类型先在该文登记，再进清单。

### 3.2 ui（UI 工具）

1. **入口**：窗口（绑定标记/编排/回写）从 Hub 打开；BindRoot Inspector、资源右键等上下文入口保留原形态，只以 `docs` 条目说明，不做成“没有选择对象也能点”的 Hub 按钮。
2. **命名**：id 为 `ui.<对象>`；生成物 `*.g.cs`、绑定指纹、样式档各自的命名只有一个出处。
3. **结果**：动作输出 `[ui/<工具>]` + 变更/失败计数；窗口关闭给出本次变更摘要与可回滚项。
4. **写盘**：资产写盘只走 Unity 序列化管线与 `ToolInteractionSession`，禁止裸文件写与无确认保存场景。
5. **文档**：唯一权威《UI 编辑器工具专项设计》；上下文入口为何不进 Hub 写在该文。

### 3.3 debug（调试与诊断）

1. **入口**：调试页统一实现 `IEditorToolPage`，生命周期由 Hub 驱动；运行态页件声明 `plane=runtime` + `requires=[play]`，`debug.local-chain` 声明 `plane=external`（被投影物是本地部署环境，不要求对局在跑），其编辑态自管心跳是唯一显式例外。
2. **命名**：id 为 `debug.<页>`；页与 CLI 对同一动作使用同一动作名（`start` / `abort` / `kick` / `rules` / `settle-flush`）。
3. **结果**：页内操作给结果行；CLI 输出与页内使用同一字段名（`room` / `player` / `action`）。
4. **写盘**：GM 只改运行态，不写工程资产；破坏性动作必须确认。
5. **文档**：唯一权威《GM 与调试工具分层专项设计》；操作手册（07/13）只作查表。

### 3.4 codegen（代码生成）

1. **入口**：CLI 统一走 `python scripts/codegen/toolbox.py <tool>`，单脚本直调只保留既有消费面；编辑器内生成器（SimTrig / Bind / Lua 辅助）只从 Hub 或上下文入口进。
2. **命名**：Python 生成器 `gen_<对象>.py`（snake_case）；编排入口 kebab（`refresh-hash.py`）；id 为 `codegen.<工具>`。
3. **结果**：统一 `[codegen/<tool>]` + 一行 `FAILED` + exit 1；校验/对账类 mismatch 即非 0。
4. **写盘**：生成物必须幂等（未变源重跑 diff 为零），只发布变更文件；生成物不手改。
5. **文档**：唯一权威《生成器工具箱专项设计》；工具箱外的生成器在该文 §5 登记。

### 3.5 deploy（部署与云运维）

1. **入口**：全部为 `cli`，经清单 `command` 执行；不提供编辑器入口。
2. **命名**：id 为 `deploy.<对象>`；预览参数统一 `--dry-run`，`--what-if` 只作已登记别名。
3. **结果**：`[deploy/<对象>]` 输出；破坏性动作先 plan 再执行，结束回读真实状态，不停在“已发送”。
4. **写盘**：只写远端与 `deploy/logs/`；密钥只从环境或 `LocalNotes/` 读，不回显、不入库。
5. **文档**：唯一权威《10-Windows云主机部署》；速查只作命令索引。

### 3.6 quality（质量门禁）

1. **入口**：门禁统一 `python scripts/gate/test.py --suite <L0|L1|L2|L3|Doc>`，L2 可由 `l2-unity-gate.py` 单独执行；同一门禁可被 CI、夜间、人三条路径调用。
2. **命名**：lane 名固定；id 为 `quality.*`；门禁脚本与 lane 的映射只在 `test.py` 一处。
3. **结果**：每次门禁产出一份机器可读摘要（lane/status/total/failed/artifacts），人读输出是它的投影。
4. **写盘**：只写 `TestResults/`；门禁不修代码、不写 `Assets/`。
5. **文档**：唯一权威《05-验证与门禁》；纪律规则变更同步《修改指南》。

### 3.7 build（构建）

1. **入口**：构建统一 `build-player.py` + `BuildProfiles/*.json`；冒烟统一 `player-smoke.py`；不新增菜单或第二入口。
2. **命名**：profile 名与产物名同源；工具 id 为 `build.<对象>`。
3. **结果**：出包结束给出 buildHash + 产物路径 + 冒烟结论；任一步失败非 0。
4. **写盘**：产物只进 `Builds/` / `Dist/`；不写源集。
5. **文档**：唯一权威《05-验证与门禁》。

### 3.8 content（内容发布）

1. **入口**：候选链固定 `gen-candidate`（签名信封）→ `publish-candidate`（CDN 布局）；本地起服 `serve-cdn`；Bundle/样例动作只从 Hub 进。
2. **命名**：id 为 `content.<对象>`；信封字段 `releaseId` / `revision` / `platform` / `expires` 域内同义同形。
3. **结果**：候选生成给出 releaseId + 签名结论 + 文件数；发布给出 CDN 根；失败非 0。
4. **写盘**：只写 CDN 根与 `Dist/`；不写源集；收集组变更按《资源收集目录专项设计》。
5. **文档**：唯一权威《资源收集目录专项设计》；信封/签名细节指向《热更与内容发布专项设计》。

### 3.9 env（环境与索引）

1. **入口**：环境类能力统一经 `toolchain.py` 子命令或已登记脚本；一次性运维脚本必须标 `@oneshot`。
2. **命名**：id 为 `env.<对象>`；计划任务名、脚本名、清单三处一致（`install-nightly-task` ↔ `env.nightly-install`）。
3. **结果**：统一 `[env/<对象>]` 前缀 + 一行失败；夜间编排把子进程输出原样落到 `TestResults/nightly/`。
4. **写盘**：只写 `LocalNotes/`、`TestResults/`、计划任务与本地环境；不改仓库源码。
5. **文档**：唯一权威《技术支持》；恢复步骤指向《环境恢复指南》。

## 4. 三条机械规则

三条都落在 `scripts/_toolchain_domains.py`，由 `toolchain.py check` 调用；发现即 `warning`，`--strict` 升为 `error`。

### R1 同义参数同名

同一域内，表达同一语义的参数只允许一个名字。同义组在此登记，`_toolchain_domains.SYNONYMS` 是它的执行副本，两边同批修改。

| 语义 | 规范名 | 允许的别名 | 说明 |
|---|---|---|---|
| 只预览不写盘 | `--dry-run` | `--what-if` | 别名必须在清单 `args.description` 里注明“别名”；新增别名先改本表 |

判据：域内若同时出现同组的两个名字，报一条域级告警并列出工具 id。

### R2 文档权威唯一

每个域声明两份数据：

- `categories[].docs`：域权威文档（该域的“正门”）；
- `categories[].allowDocs`：允许偏离权威的文档白名单（每项必须是仓库内存在的路径）。

判据：域内每个工具的 `docs` 必须命中 `{docs} ∪ allowDocs`；缺权威声明单独告警。新工具想指向新文档，必须在同一批把它加进 `allowDocs`，否则检查失败（`--strict` 下）。

### R3 一个域一个标签

命令类工具（`cli / gate / build / content`）必须在源码里给出稳定的输出前缀 `[<根>/<工具>]`：

- 同域所有命令入口的前缀**根**必须一致；
- 每个命令入口都必须能解析出前缀。

提取口径（按优先级）：`TOOL = '...'` 常量；`info|warn|fail('...')` 字面量；`print("[...")` 字面量。`toolbox.py <tool>` 经其 `TOOLS` 映射解析到真实脚本；非脚本入口（`dotnet`、外部 exe）不参与。

**为什么不是“前缀 = id”**：一条命令可以服务多条 id（`test.py` 同时是 `quality.l1/l3/doc`），前缀不可能同时等于三者；目录域与登记域也可以不同（`gate/` 承载 `quality.*` 与 `env.*`）。因此不变量取“**同域一个标签**”，收敛目标为该域 id。

## 5. 告警与例外

- 三条规则默认 `warning`：`check` 退出码不受影响，CI 不被历史漂移卡住。
- `--strict` 把 warning 升为 error；一个域收敛到 0 后，该域的规则应以 strict 运行（CI/夜间）。
- 显式例外只有三类：非脚本入口（R3）、多 id 脚本按域判（R3）、已登记别名（R1）。例外必须在本文件留字，不接受口头豁免。
- 新增同义组、新增域、扩展提取口径：同批修改本文件与 `_toolchain_domains.py`，并补一条规则单测。

## 6. 新增工具的动作

1. 选 kind：交互式进 `page/window`，一次性进 `action`，命令行进 `cli/gate/build/content`，运行内自创建进 `hud`，只说明进 `docs`。
2. 定 plane / purpose / requires：`plane` 按“生效时哪一侧必须活着”，`purpose` 按“服务哪条能力线”，`requires` 只写非空前置（语义见[平台专项 §3.2.1/§3.2.2](开发工具链平台专项设计.md#321-平面与前置)）。
3. id = `<category>.<对象>`，不得跨域。
4. `docs` 指向域权威或已在 `allowDocs` 中；否则同批加白名单。
5. `args` 复用域内规范名（R1），不新造同义词。
6. 命令入口打印 `[<域根>/<工具>]`（R3），并支持 `--help`。
7. **产物**：有产物就登记 `outputs`（`{path,kind}`，形态见[平台专项 §3.2.3](开发工具链平台专项设计.md#323-产物形态)）；非交互式写入者必填，交互式窗口靠 `writes` + `ToolInteractionSession`。
8. 新域：清单加 `category`（含 `docs`/`allowDocs`）+ 本文加一节 5 条基线 + 基线测试补一行。
9. 收尾：`toolchain.py docs` 重生成索引 → `check` → 脚本契约测试 → `--suite Doc` / `--suite L1`。
