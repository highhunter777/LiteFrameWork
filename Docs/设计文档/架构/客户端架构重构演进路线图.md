## 1. 目标与约束

**唯一主判据是单人认知负担。** 结构好坏不按代码量衡量——本路线图**不追求代码量下降**，也不以“少了几行”作为收敛成绩。判据只有一个：一个新上下文（人或 AI agent）只拿到目录结构与一条需求时，能否在**不追问**的情况下找到该改的那个文件。

五条约束：

1. **主判据**：单人认知负担。任何取舍先问“它让下一次改动更容易被找到，还是更难”。
2. **不砍现有功能**。可删切口只有一个——**删除后零可观察行为变化**（重复实现、死代码、只服务工具自身的制品）；行为有任何变化的，一律不算切口。
3. **一次只重写一层**。主干从第一天到合并当天必须始终**可编译、可跑一局**，禁止“先拆三个月再拼回来”。
4. **协作形态是单人 + AI agent 长期协作**。规则必须**能被一个上下文窗口读懂**：写不进一个窗口的规则等于没有规则，规则条数本身就是成本。
5. **热更沿用 HybridCLR**，`AOT | hot` 是**唯一硬边界**。HybridCLR 在此只作为**外部约束**引用——分界/身份/旧房/回滚的接入细节归 `Docs/施工进度/HybridCLR接入线.md` 与热更专项，本文不重复。

## 2. 边界

边界只有一条：**`AOT | hot`**。没有第二套“框架 / 产品”的编译期方向边界，也没有按技术层切的第三层边界——原来那些边界要么被这一条覆盖，要么不再需要。

### 2.1 分区归属

| 分区 | 归属 |
| --- | --- |
| **AOT（随包）** | `LiteFramework`（含原 `Core` / `Services` / `Adapters` / `Hosting` 目录与命名空间，合并为一个程序集；**目标吸收 `LiteCodeGen.Runtime`**）＋ `LiteNet` ＋ `LiteGame.Bootstrap`（即引导程序集） |
| **hot（内容包）** | `LiteGame`（产品；**目标吸收 `Luban.Tables`**）＋ `LiteSim` / `LiteSync` ＋ `Luban.Tables`（`Assets/GameData/Generated`；现役独立件；表值可热更，见 AGENTS 红线 1 现行口径） |
| **非玩家侧（不参与分区）** | `RoomServer*` / `MetaServer*` / `LiteTesting*` / `LiteCodeGen.Editor` / `DisciplineScanner*` / `ReplayTool` / 测试工程 / `Unity.Pipeline*` / `MCPForUnity*`——AR3 只检验 AOT → hot 一条边 |

判据只有一条：这一侧能否被换掉而不影响另一侧。能换的一侧是 hot，不换的一侧是 AOT。

**现役（阶段 4 前）**：`LiteCodeGen.Runtime` 与 `Luban.Tables` 仍是独立程序集——前者属 **AOT**（被 `LiteFramework.Services` 编译期引用；AOT 不能引 hot，故只能落 AOT），后者属 **hot**；两者在目标形态分别被 `LiteFramework`、`LiteGame` 吸收，故不算在 §2.2 的六件之内。

**编辑器程序件不计入运行时**：`LiteFramework.Editor` / `LiteGame.Editor` / `LiteCodeGen.Editor` 不打包、不计入运行时程序集数。

### 2.2 程序集收敛

hot 侧的**产品层**收敛为 1 个 `LiteGame`；共享内核 `LiteSim` / `LiteSync` 保持独立（它们与 RoomServer 双轨共编，不能并进去）——**不是 hot 侧只剩 1 个程序集**。产品层的模块归属不再由程序集表达，改由**目录 + 命名空间**表达；因此**产品层跨模块引用不再需要端口接口**——同一程序集内两个目录之间直接引用类型即可（接口的引入条件见 §3.3）。

目标程序集总数 **6 + `Dev`**：

| # | 程序集 | 侧 |
| --- | --- | --- |
| 1 | `LiteFramework` | AOT |
| 2 | `LiteNet` | AOT |
| 3 | `LiteGame.Bootstrap` | AOT |
| 4 | `LiteGame` | hot |
| 5 | `LiteSim` | hot |
| 6 | `LiteSync` | hot |
| — | `Dev`（开发面；不进发布包，不参与分区） | 不分区 |

表列**目标形态**；现役仍另有 `LiteCodeGen.Runtime`（AOT）与 `Luban.Tables`（hot）两件独立程序集（口径见 §2.1）；编辑器程序件不打包、不计入本表。

**时点在 HCLR P2 之后。** 该收敛依赖 HCLR P2 给出**真实**的 AOT/hot 集合——哪些文件真的落在哪一侧，只能由引用图算出，不能靠命名或目录约定声明。P2 之前的 AOT/hot 划分只是草稿，不足以支撑程序集合并。

### 2.3 边界明细不在本文

本文不列“哪些文件在 AOT 侧、哪些在 hot 侧”的清单。该明细由**引用图**与 HCLR 施工线给出：任何 AOT→hot 的编译边都意味着“该 AOT 件要么迁 hot，要么把类型/接口拆到 AOT 侧”。

文档不复制引用图——复制即分叉，分叉后的清单没人敢信（同一条理由见 §4.2）。

## 3. 粒度（本文核心）

本节回答“一个改动单元多大、边界画在哪”，其余章节都围绕它展开。

### 3.1 拆分轴

拆分轴是**改动单元**，不是技术层。

- 一个改动单元 ＝ **一个“能说出口的意图”** ＝ **一个目录** ＝ **一个命名空间**。
  - “能说出口”的口径：一句话讲完且不需要“和”——“结算发奖”是一个意图；“结算和发奖和邮件”是三个。
- **唯一分合判据**：两个改动**永远一起发生** → 同一单元；**从不一起发生** → 不同单元。
  - 这条判据优于任何外观相似性（“看起来像一类东西”“名字里都有 Battle”“都在 UI 目录下”）：它可被观测——看历史上它们是否总是同一个提交里一起改；“看着像”只能靠感觉。
- **产品侧改动单元不得按技术层拆**：`Abstractions/`、`SubModules/`、`Services/`、`Impl/` 这类目录名把同一个意图的声明与实现切开，读的人必须跨三个目录才能回答“这页逻辑在哪”。技术层不是拆分轴。

### 3.2 单元上限

一个改动单元的上限是**硬上限**，不是建议值：

| 项 | 上限 | 口径 |
| --- | --- | --- |
| 代码文件数 | **≤5** | 按[规范 02 §1.12](../../规范/02-代码与修改规范.md) 的计数口径 |
| 行数 | **≤600** | 按[规范 02 §1.12](../../规范/02-代码与修改规范.md) 的计数口径 |
| 入口文件 | **唯一，且与目录同名** | 想改这块的人先打开它 |

入口文件是本节的全部要点：**要回答“我该改哪个文件”，答案就是“打开跟目录同名的那个”**，不需要先读别的。

### 3.3 跨单元接口

**0 个跨单元接口。**

- 单元之间**直接引用类型**，不为“以后可能换实现”预留接口。
- 接口只在两种情况下引入，缺一即不引入：
  1. **实际跨 asmdef**——声明与实现真的不在同一程序集；
  2. **存在第二实现**——含测试替身。
- “为了解耦”“为了分层”“为了可扩展”都不是引入接口的理由；它们不满足上面两条。
- 推论：端口基线与 `port-lint` 一类“按端口记账”的守卫不再需要（§4.1）。

### 3.4 目录与命名空间

目录树只有一种形状：

```text
Assets/LiteGame/<域>/<单元>/
```

- **路径 = 命名空间，逐段相等，零例外。** `Assets/LiteGame/Battle/Settlement/` 的命名空间就是 `LiteGame.Battle.Settlement`；反过来说，命名空间有几段，目录就有几层。没有“多一段 `Internal`”“少一段 `Game`”的例外，也没有“目录对不上是历史原因”的豁免。
- **产品侧改动单元禁止**用 `Abstractions/`、`SubModules/`、`Impl/`、`Interfaces/`、`Services/`、`Common/`、`Utils/` 作目录名，**也不得新开** `Core/` 目录（存量 `Assets/LiteGame/Core/` 按守卫基线棘轮并回单元，本批不搬）；目录名必须能回答“这里装的是哪个意图”，回答不了的就不是目录名。
- **上述禁令不适用于三类另有权威的目录**：① 框架四件层目录 `Core/`/`Services/`/`Adapters/`/`Hosting/`（AOT 侧保留，见 §2.1）；② 内核与红线目录 `Packages/com.litegame.net/Core/`、`Packages/com.litegame.sim/`、`Assets/RoomServer/Core/`（R11）；③ `LiteGame.Core` 程序集（阶段 4 前仍存在）。

### 3.5 文件边界

**废除“一类一文件”。**

- 一个文件 ＝ **一个内聚职责**，允许 **2～4 个强相关类型**共存：值类型、枚举、其实现、其常量。
- **文件边界由变化原因决定，不由类型个数决定。** 为同一个需求永远一起改的类型 → 同一文件；改动原因不同 → 拆开。
- 只含 `interface` / `enum` / `struct` 的“纯声明文件”是上一轮形态的最大产物：它们存在只因为“一类一文件”，不因为职责。这类文件按 §5.1 的「声明件收敛」**并回实现文件**——并回，不是删除，内容不能丢。

## 4. 守卫

### 4.1 三条守卫

只保留 **3 条**：

| 编号 | 守卫 | 判据 | 违反时 |
| --- | --- | --- | --- |
| **AR1** | 路径 = 命名空间 | 文件所在目录逐段等于其命名空间 | 存量棘轮只减不增；新增即失败 |
| **AR2** | 改动单元上限 | 改动单元 ≤5 个代码文件、总行 ≤600、入口文件唯一且与目录同名（计数口径见[规范 02 §1.12](../../规范/02-代码与修改规范.md)） | 同上 |
| **AR3** | AOT 不引 hot | AOT 程序集不得出现对 hot 程序集的编译引用 | 失败即阻断 |

**其余架构守卫全部作废**：`port-lint`、`arch/zero-use-edges.json` 基线、旧路线图 §4.11 的十一条守卫，一律不再作为判据来源。作废的理由不是“它们守错了”，而是**规则条数本身是认知负担**——几十条规则没人记得住，三条记得住（§1 约束 4）。

作废**不等于**“那些边现在允许了”：AR3 覆盖程序集分区，AR1/AR2 覆盖单元粒度；被废除的守卫若守的是这两点，判据已由 AR1～AR3 承接；若守的是别的东西，则它裁决的关切本身已不在本文范围（见 §9）。

### 4.2 存量清单

存量清单**由守卫生成，不手写**：

- 每条守卫自带“当前违规清单”的生成能力（扫描即得）。清单不进仓库当手维护文件——手维护的基线文件会与真实仓库漂移，而且漂移不可见。
- 一律**棘轮语义**：只减不增。判定“是否新增”靠“与上次生成结果比较”，不靠“与手写白名单比较”。

## 5. 验收门槛

六条门槛，每条都是**可测的数**，不是“评审认为可以”。前两条是修正后的口径：它们量的是**一次改动的触碰面**，不是“代码变少了”。

### 5.1 六条门槛

| 门槛 | 判据 |
| --- | --- |
| 按钮改名的触碰面 | 改一个 UI 按钮的**处理器名**（含换处理器）触碰 **≤2 个文件**、生成器 **0 次**（现状 1 文件 + 0 次生成；改造前 4 文件 + 2 次生成） |
| 新表的登记面 | 新增一张表需 **0 个手维护清单文件**、`Luban/gen.bat` **1 次**（现状须改 `TableLayout.cs` 且触发 2 次 BuildHash） |
| 平铺命名空间 | `namespace LiteGame` 的文件数 **= 0**（现状 247） |
| 声明件收敛 | 纯声明文件（interface/enum/struct only）**≤60**（现状 306；实现方式是**并回实现文件**，不是删除） |
| 程序集收敛 | 玩家侧运行时 **6 + `Dev`**＝AOT `LiteFramework` / `LiteNet` / `LiteGame.Bootstrap` ＋ hot `LiteGame` / `LiteSim` / `LiteSync`（另 `Dev` 不进发布包；编辑器程序件不打包、不计入此数；现役两件独立件见 §2.1；现状 52；时点在 HCLR P2 之后） |
| 冷启动可发现性 | 全新上下文的子代理只给“域目录 + AR1/AR2 报错文本 + 一句需求”，**触碰 ≤2 文件且零反问** |

**「声明件收敛」的实现方式是“并回实现文件”，不是删除。** 只有 `enum` 的文件并回它唯一消费者的文件；只有 `interface` 的文件在没有第二实现时并回实现文件，并把该接口降为具体类型（§3.3）。

**「程序集收敛」的时点在 HCLR P2 之后**（§2.2）：真实 AOT/hot 集合未给出前，程序集合并无从判定。

### 5.2 冷启动可发现性：认知负担的可测代理

本条门槛名为「冷启动可发现性」——**冷启动**是它的**测量手段**，不是门槛名。

“认知负担低”不能靠感觉，用**冷启动子代理**当代理指标：

给一个**全新上下文**的子代理三样东西，**不给任何文档**——

1. 目标域的目录树；
2. AR1 / AR2 的报错文本；
3. 一句需求。

要求它**触碰 ≤2 个文件且零反问**。反问、翻文档、改到第三个文件，都算失败：失败说明目录名与入口文件名没有把意图说清楚（§3.1 / §3.2），不是“执行者不够聪明”。

这条门槛的价值在于它**不依赖人的经验**：同一测试换任何执行者结果都可复现，因此可以直接当回归判据用。

## 6. 顺序

### 6.1 规则先行

**先改规范与守卫，再动代码。** 本轮是**规则先行、代码服从文档**。

这是本仓库既有「文档与代码不一致以代码为准」的**显式例外**，且**只限本次架构收敛线**：

- 例外覆盖**架构类规则**（目录形状、单元粒度、接口引入条件、守卫集合），不覆盖红线类规则（BuildHash 源集、R11 房间内核纯度、R13 数值读口等仍以代码实测为准）。
- **裁决权落在规范层**：例外的操作面（适用范围、生效与失效时点、不得扩用的边界）以[规范 02 §1.15 例外裁决](../../规范/02-代码与修改规范.md) 为准，本节只给设计侧的理由。旧规范与新规则冲突时**以本文为准**，旧规范按本文回写；回写完成之前先按本文施工——否则规则永远改不动。
- 例外**不是长期的**：架构收敛线结束后“以代码为准”恢复；本文与其回写的规范一致后，这条例外不再被引用。

### 6.2 阶段划分

| 阶段 | 内容 | 侧 |
| --- | --- | --- |
| **0** | 规则：规范与守卫先改（AR1～AR3 落地、旧守卫下线） | hot |
| **1** | 去重：消除重复实现（纯减不增、行为不变），单独成批 | hot |
| **2** | UI 域竖向切：先切制品系统与生成链（§7.1），运行期目录不动（§6.3） | hot |
| **3** | 其余域逐域竖切 | hot |
| **4** | 收口：程序集合并与测试收敛——**押后至 HCLR P2** | 跨侧 |

- **阶段 0-3 全部在 hot 侧，不依赖 AOT 边界。** 这是顺序设计的关键：AOT/hot 的真实集合要等 HCLR P2，把阶段 0-3 建在它上面，整条线会被一个外部依赖卡住。
- **去重（阶段 1）先于逐域（阶段 2/3）**：重复实现意味着“两处都要改”；不先消掉，逐域竖切会切出两份仍然重复的单元。

### 6.3 逐域顺序

**每完成一个域即永久完成，不回改。** 顺序：

```text
UI → Meta → Battle → Dev
```

- **第一域是 UI**。理由：UI 是“改动单元”假设的第一个真实样本——边界最清楚、制品最多（§7.1）、重复实现最集中。
- **UI 域先切制品系统与生成链，不切运行期目录**（存量口径）：运行期 UI ＝ **10 个目录 / 17 个文件 / 1,452 行**，AR1 里 UI 域只占 **16 条**（全仓现状 1,114 条）——结构本来合理，重切它不产生收益。真正“粗”的是另外两处：**制品系统**（6 类制品互相耦合，改一处生成链要重跑全部产物与指纹，一个 sha 连累整条链）与**编辑器工具链**（`Editor.UITools` 原有 12,573 行）。阶段 2 的切口因此是“改一个按钮的处理器名只需 1 个文件、0 次生成”（§5.1），不是“把 UI 文件重新分堆”。
- **UI 运行期单元的命名空间对齐单独成批**（下一阶段起点）：单元重切前必须先让路径 ＝ 命名空间，而 UI 域现有 **14 条 ns 未对齐 + 1 个技术层目录 `Abstractions/`**；改 ns 会拉出跨程序集 `using` 涟漪——该批收益口径为 14 个文件改 ns + 22 条 `using` + 1 个目录平掉、AR1 1,114 → 1,099。混进制品批里做，任何一处 `using` 漏改都会让“改一个按钮”的触碰面重新涨回 3 个文件。
- **UI 域排除 `LiteGame.Editor.UITools`**。工具链在**运行时收敛之后**处理，判据只有一句：**它还有没有产物**。运行期不再需要 contract（§7.1），但 `#uiform` 表与 `UIPageManifest` 仍是工具链的输入——工具链若只剩空转就必须跟着收敛；若仍有产物，按“有产物”另行裁决，不在 UI 域里一起动。
- **Dev 最后**。开发面依赖全部产品面，先动它等于把依赖方向倒过来做。

## 7. 制品与半成品

### 7.1 UI 页面制品

一个 UI 页面只留 **2 类制品**（其余页面数据要么是表/清单登记，要么是生成物）：

| 制品 | 说明 |
| --- | --- |
| **prefab** | 页面的视觉与结构，也是控件（`BindNode`）、文案键（`LTextKeyRef`）、样式引用的读取面——生成链直读 prefab，不留第二份拷贝 |
| **logic** | 页面逻辑 C# 文件（与 prefab 同名，即 §3.2 的入口文件） |

**删除**：`*.contract.json` 一族（含 `UIPageContract.schema.json` 与生成/校验件）——页面制品类别由 **6 类收敛为 5 类**，少的就是 contract 这一类。

**不删**：`#uiform` 表（`id` / `prefab` / `layer` / `full_screen` / `cache_strategy`）——它是页面元数据的**唯一来源**，也是整条页面目录生成链的地基；删掉就没有第二处能回答“这个页面在哪一层、是否全屏、缓存策略是什么”。

**留待工具链批裁决**：`UIPageManifest.json`——工具维护的页面注册表（Owner / 状态 / 设计稿 / 设备档），不进运行时、不进包；退场判据落在工具链批（§6.3 的“它还有没有产物”），本文不预设它必删。

**改由表 + prefab 生成**：`toolbox.py ui-page` 读 `#uiform` 与页面 prefab（`scripts/codegen/_prefab_page_reader.py` 解析 YAML），产出 `UIPageCatalog.g.cs`（`PageDefinition`）与 `PageIds.g.cs`——**不带 sha256**。页面索引是“表 + prefab 里有什么”的投影，不是发布身份；发布身份只属于内容清单。

理由三条，缺一条都不足以删：

1. **contract 是源码的拷贝。** 它由 `UIPageLogicScanner.ScanEventWiring` **从源码扫出来**再落成 json——同一份绑定信息在源码与 json 各存一份，源码改了 json 不跟着改就是分叉；控件与事件绑定在 prefab（`BindNode`）与页源 C# 里本来就是真相，契约只是第三份。
2. **它没有运行时消费者，工具侧也不再需要。** 运行时代码被明令禁止读表与清单（`PageDefinitionGuardTests`）；控件/文案/样式改由 prefab 直读之后，工具侧最后一条消费也消失——留下的只有一份“运行时不读、只在工具里转”的私产。
3. **契约校验从未接入任何 script gate / CI。** 前两条靠的是“有人记得跑”，不是门禁——不具备裁决力。

### 7.2 StatusSystem 半成品

`StatusSystem`（`StatusSlotData` / `SimWorldState.Status` 固定 4 槽）是半成品：已进 checksum / diff / snapshot，但没有 driver。

**本次不动。** 它属**确定性面**——改槽位或序列化，checksum 与快照格式同时变，**拆掉的成本大于留着的成本**。Buff 作为独立功能另立项，不在本文讨论。

## 8. 风险

三条风险必须在动工前被承认；任一条爆发都**不允许就地硬掰代码**绕过。

1. **“废除一类一文件”的合法性只来自例外裁决。** 它与规范层“一类一文件”的默认表述正面冲突，本轮能成立的唯一依据是 §6.1 的规则先行（操作面见[规范 02 §1.15](../../规范/02-代码与修改规范.md)）。这个依据**有期限**：例外失效而规范层条文未同步时冲突重新成立，规则会以“按规范办事”的名义回涨——所以判定它是否仍然有效，只看规范层当前条文，不看本文措辞。
2. **程序集合并不可逆。** 6 + `Dev` 的合并会一次改掉 asmdef、csproj、测试工程引用、`link.xml`、扫描根与构建脚本；合错的回退成本是“重拆一遍”，不是“撤销一个 commit”。因此**押到最后**（阶段 4，且时点在 HCLR P2 之后）：前面各阶段都在同程序集内改目录、随时可回退，合并只做一次。
3. **≤5 文件 / ≤600 行 / 0 接口三条从未被真实域检验。** 这三个数从“一个上下文窗口能读完”推出来，没有任何真实域验证过。**UI 是第一个样本**（§6.3）：若 UI 域撞出例外（例如某单元天然要 7 个文件），**改规则，不硬掰代码**——硬掰的代价是下一代人看不懂这个单元为什么被切成这样，而那正是主判据（§1）要避免的。
