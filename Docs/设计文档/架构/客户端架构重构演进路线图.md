## 1. 基线：复杂度来自“多答案”，不是“代码多”

当前客户端并非没有分层，而是**同一类关切存在多套并存的答案**，且没有一条被声明为默认路径：

| 关切 | 当前多答案 | 直接后果 |
| --- | --- | --- |
| 取依赖 | `ClientContext.Require<T>`、`ServiceContainer.Resolve<T>`、`ClientHost.Product<T>`、静态 `Bridge` / `MetaBridge` / `RoomBridge` / `ProductSettings` | 模块依赖图无法静态校验；静态门面绕过所有权与声明图 |
| 管生命周期 | `ClientScope`、`ServiceContainer` 所有权、`IClientSegment.ShutdownAsync`、`IDisposable`、`DontDestroyOnLoad`、`LuaEnv.Dispose` | 初始化中途失败的模块、Unity 对象和 Lua 引用存在逃逸面 |
| 发通知 | 直接调用、C# event、`EventBus`、`CommandCenter`、`StageMachine.Request`、`StageSignal` | 选型无规则；事件中心与命令中心在正式玩法中缺少真实消费者 |
| UI 串行化 | `UINavigationController` 队列、`DialogService` 优先级/合并队列、`UITransitionRunner` 容量 1 队列、`UIService._openOps` 合并 | 四套队列/超时/取消/合并语义各自演化 |
| 对局状态 | `TestModeRuntime` 单例实例、`ILocalTestHooks` 开发宿主钩子、`MatchTestRules` 每局实例、`CombatConfig` 静态投影 | “当前局”是全局变量；作用域靠命名而非类型 |
| 表现层 | `Modules/Battle` 自持视图/表现/HUD（`Arena/SimView`、`Characters`、`Hud`）；HUD 经 `IBattleReadModel` 读公共事实 | 表现层绕过窄端口；HUD 与 Sim 内存布局耦合 |
| 页面模型 | prefab + Lua + `tbuiform` 行 + 绑定索引 + contract/manifest + 校验规则 + 文案/样式 | 一个页面 6～8 个制品；工具链因此长成 12.8k 行 |
| 构建边界 | `#if UNITY_EDITOR || DEVELOPMENT_BUILD || LITEFRAMEWORK_DEBUG`、asmdef | release 依赖图仍含 `LiteGame.Adapters.DevLocalServer` / `RoomServer.*` |
| 身份/版本 | `BuildHash`、`ConfigHash` / `CombatConfigDigest`、`RootMotionDigest`、`SourceHash`、`UIPageManifestHash`、`ReleaseManifest`、`PlayerCapabilities` | 多个身份概念并存；客户端五项能力全为 0/空，兼容检查处于半关闭 |

这些不是单点缺陷，而是**默认路径缺失**。本路线图只做一件事：把每类关切收敛为一条默认路径，并让“偏离默认路径”必须显式、昂贵、可被守卫拦住。

## 2. 设计原则

1. **一个关切一条默认路径**：同一类问题只保留一个首选机制；其他机制降级为明确的局部例外，不得并列扩散。
2. **所有权先于拆分**：先统一作用域、生命周期和状态所有者，再拆大类；否则拆出来的是更多互相引用的中等类。
3. **领域边界先于技术分层**：先回答“谁拥有这局对局、谁拥有这页 UI、谁拥有这个资源”，再按技术层拆程序集。
4. **先删后加**：没有生产消费者的机制先删除或冻结，再讨论新增抽象；禁止用新抽象掩盖旧抽象的空转。
5. **守卫先于口号**：每条“唯一路径”都必须能由架构测试或机械扫描发现偏离，否则只是注释。
6. **不改变 C0～C5 能力门槛**：本路线图不新增发布关口，也不降低现有门槛；只增加架构收敛的退出条件。

## 3. 最小目标设计（M0）

<a id="m0"></a>

### 3.1 目标

M0 是**结构止血**，不是重构终态：在不改变用户可见行为、不迁移全部代码、不重写 UI 工具链的前提下，建立六条不可逆的结构约束和六个后续重构必须依赖的接缝。M0 达标后，后续拆分不再需要先拆掉一套旧机制。

### 3.2 非目标

- 不重启已完成的 `BattleViewRig` / `UIBindIndex` 拆分；不在 M0 新开 `UIService` / `RoomClient` / `BattleContext` 拆分。
- 不重写 UI 页面制品与编辑器工具链。
- 不抽完整领域层，不改 Sim/网络/内容事务。
- 不删除仍被生产使用的框架机制。
- 不迁移全部静态读点（`TestModeRuntime` 现有读点进入 allowlist，新增读点才失败）。
- 不新增用户可见功能，不改变现有 UI、网络与内容接受/拒绝行为。

### 3.3 目标形态

```text
GameEntry
└─ ClientHost
   ├─ RootScope
   │  ├─ Content / Config / UI / Input / Presentation services
   │  └─ AccountScope
   │     └─ MatchScope
   │        └─ BattleSession
   │           ├─ MatchRules（显式参数）
   │           ├─ BattleContext（网络 + Sim）
   │           ├─ IBattleView（SimView 实现）
   │           ├─ IBattleReadModel（HUD/排行读口）
   │           └─ Diagnostics
   └─ DevModule（仅开发装配）
      ├─ IDevSession
      └─ ILocalTransportFactory → LiteGame.Adapters.Dev（本地服件）
```

M0 仍保留现有 `ClientHost` 的模块注册序与静态门面实现，但产品代码只通过上述接缝消费；旧入口在 M1/M2 逐步删除。

### 3.4 六条不变量

| 编号 | 不变量 | 判据 |
| --- | --- | --- |
| I1 | **唯一所有权**：跨帧、跨场景、跨对局对象必须登记到 Root/Account/Match/UI 之一；新增 public static 可变业务状态为零 | 静态字段 allowlist 只减不增；新对象构造点必须能回答“谁释放” |
| I2 | **唯一组合**：模块产物只写入同一 `ServiceContainer`，消费只经构造注入或 `Require<T>`；禁止新增 `Bridge` 式静态门面 | 新增静态门面失败；现有门面降级为 adapter，必须有 `Bind/Unbind` |
| I3 | **单向依赖**：框架（`LiteFramework.*` 与框架模块）不引用 `LiteGame.*`；`LiteGame.App` release 不引用 `LiteGame.Adapters.Dev` / `RoomServer.*`；`LiteGame.Modules.*` 不引用 `LiteGame.Adapters.*` | asmdef + 目录级架构测试 |
| I4 | **唯一 UI 操作原语**：导航、转场、弹窗、Loading 的排队/超时/取消/合并统一走 `IUIOperationQueue`；M0 先迁移导航与转场 | 新增私有队列失败；导航/转场共用同一队列 |
| I5 | **唯一对局状态所有者**：`BattleSession` 是 `MatchTestRules` 的唯一写者；`ILocalTestHooks` 由开发装配持有；`TestModeRuntime` 由 `IDevSession` 包装，现有直读进入 allowlist、新增直读失败 | grep/架构测试：无第二处写 `ActiveMatch`；新增 `TestModeRuntime` 直读失败 |
| I6 | **唯一身份入口**：`PlayerCapabilities` 来自单一来源（生成物或显式配置），且 M0 前后对现有清单的接受/拒绝结果不变；不得保留逐轴 0 与五轴检查并存的半实现 | 内容兼容对照测试；来源单一；现有清单结果不变 |

### 3.5 六个接缝

| 接缝 | 位置 | 契约 | 替代/收敛 | M0 验收 |
| --- | --- | --- | --- | --- |
| `IBattleView` | `Modules/Battle/Abstractions` | `Tick`、`OnRollback`、`OnReconcile`、`OnFrameEvents`、`AlignLocal`、`ResetInterpolation`、`RenderFrame` | `BattleContext` 只持端口；`SimView` 实现 | `Modules/Battle/SubModules/ArenaSubModule` 实现端口；`BattleContext` 无 `SimView` 字段 |
| `IBattleReadModel` | `LiteGame.Core` | 本地实体 HP/弹药/排名/存活等只读事实；快照式读口 | HUD、排行、击杀提示 | `BattleHudDriver` + `BattleRankboardDriver` 迁移；表现层新增代码不得直读 `SimWorldState` |
| `IUIOperationQueue` | `LiteFramework.Services`（Services/UI） | `Enqueue(IUiOperation, UiOperationPolicy)`；统一容量、超时、取消、合并、拒绝语义 | 导航队列、转场队列 | 导航与转场共用；现有 UI 队列/转场用例全绿 |
| `IBattleRun` / `BattleSession` | `Modules/Battle/Abstractions`、`Modules/Battle/SubModules/SessionSubModule/BattleSession.cs` | 持有 `MatchRules`、`BattleContext`、`IBattleViewGroup`、诊断；`WaitStartedOrEndedAsync/Tick/Dispose` | `ProcedureBattle` 直接持有 Context/Rig | `MatchTestRules` 唯一写者；Procedure 只消费 `IBattleRun`/`IBattleRunFactory` |
| `ILocalTransportFactory` | `Modules/Session/SubModules/TransportSubModule` | 不暴露 `RoomServer` 类型的本地传输创建口 | `ProcedureMatch` 直调 `LocalServerTransport` | App asmdef 无 `LiteGame.Adapters.Dev` / `RoomServer.*`；本地测试房路径可用 |
| `IDevSession` | `LiteGame.Core` | 测试模式开关、进入/退出/传送请求、一次性读清 | `TestModeRuntime` 静态 | 产品代码只依赖接口；静态实现只在 Dev 侧 |

### 3.6 M0 退出条件

1. 架构测试通过：无 `LiteFramework.* / 框架模块 -> LiteGame.*`、无 `LiteGame.Modules.* -> LiteGame.Adapters.* / LiteGame.Adapters.Dev`、无 `LiteGame.App -> LiteGame.Adapters.Dev / RoomServer.*`、无新增静态可变字段。
2. `IBattleView` / `IBattleReadModel` 就位；`BattleContext` 不再声明 `SimView` 字段；至少 2 个 HUD 驱动走读模型。
3. 导航与转场共用 `IUIOperationQueue`；现有 UI 导航、模态、转场、反馈用例全绿。
4. `BattleSession` 成为 `Battle` 阶段的唯一对局入口；`MatchTestRules` 只有 Session 写；新增代码只经 `IDevSession` 访问测试面，现有直读点进入 allowlist。
5. `ProcedureMatch` 经 `ILocalTransportFactory` 创建本地传输；App release 程序集图不含 `RoomServer.*`。
6. `PlayerCapabilities` 来源单一，且对现有发布清单的接受/拒绝结果与 M0 前一致（对照测试）；不存在“逐轴 0 但检查开启”的中间态。
7. `python scripts/gate/test.py --suite L1 --profile PullRequest`、相关 PlayMode UI 套件、`python scripts/gate/doc-lint.py` 通过；无用户可见行为变化。

### 3.7 M0 回退

M0 的六个接缝都以 adapter/wrapper 形式接入，旧调用链保留到 M1/M2 才删除。单个接缝回退只需恢复原构造点，不涉及数据迁移；唯一需要协调的是 `PlayerCapabilities` 的来源切换，必须与内容发布侧同一次发布回退。

## 4. 最终目标设计（M3）

<a id="m3"></a>

### 4.1 目标

M3 是**稳定目标**，不是一次性交付：每个关切只有一条默认路径；领域边界清晰；所有权、协调、身份和开发面都能被测试守卫。M3 达标前，C5 的通用包提取不得启动，否则会把当前多路径形态一起打包。

### 4.2 程序集与依赖


允许边之外的边一律禁止；其中以下五条是硬门禁：

- `LiteFramework.*` 与各框架模块不得引用 `LiteGame.*`；产品 → 框架的方向不可反。
- `LiteFramework.Services` 不得引用 `LiteFramework.Adapters`；`Core`/`Services`/`Adapters` 不得引用 `LiteFramework.Hosting`；适配器只实现服务 `Abstractions/`，装配在宿主与组合根完成。
- `LiteGame.Modules.*` 不得引用 `LiteGame.Adapters.*`/`LiteGame.Adapters.Dev`，也不得引用框架 `LiteFramework.Adapters`；适配器只实现模块端口，装配根注入（如 `IAnimationBackendFactory`、`IBattleViewGroupFactory`、`ILuaProductBridge`、`IRoomSessionBridge`）。无例外程序集。
- `LiteGame.Core` 只许引 `LiteSim`；不得引 `LiteFramework.*` / 其他 `LiteGame.*` / `RoomServer.*`。
- 表现/视图端口属于产品：`IBattleView`/`IBattleReadModel` 住 `Modules/Battle/Abstractions`，由同域表现件实现；框架只经产品注入的端口消费，不反向认识产品实现。

> 端口分层：模块自持接口（`Modules/<域>/Abstractions/`）是默认位置；产品跨模块的纯契约按归属落域；框架通用的输入端口留在 `LiteFramework.LiteGame/Modules/Input/Abstractions`。契约件与实现同属一侧，不维护中立契约程序集。
>
> 对局运行端口：`IBattleRun`/`IBattleRunFactory`/`IMatchSessionFactory`/`IRoomSessionFace`/`IBattleClient`/`IBattleClientFactory`/`IBattleDevDiagnostics` 住 `Modules/Battle/Abstractions`；会话运行时材料端口 `IAccountRuntime` 同住该处、由 `AccountSession` 实现（依赖倒置，避免 `Battle → LiteGame.Modules` 环）。
>
> 模块自持端口（实现侧在适配器，装配根注入）：`ILuaProductBridge`（`Modules/Procedure/Abstractions`）、`IRoomSessionBridge`（`Modules/Session/Abstractions`）、`ILuaRegistryFiller`（`Modules/Procedure/Abstractions`）、`IBattleViewGroup`/`IBattleViewGroupFactory`/`IBattleDevOverlay`（`Modules/Battle/Abstractions`）——`LiteGame.Modules` 不引用 `LiteGame.Adapters.LuaBridge`/`LiteGame.Adapters.Dev`。

`BattleSession` 是**对局运行聚合**，住 `Assets/LiteGame/Modules/Battle/SubModules/SessionSubModule/BattleSession.cs`，由 `BattleSegment` 装配，实现 `IBattleRun`：它持 `MatchSession`/`IBattleClient`/`BattleContext`、映射终局原因、驱动每帧；流程段只经 `Battle/Abstractions` 的 `IBattleRunFactory`/`IBattleRun` 消费。`LiteGame.Modules.Battle` 承担对局网络/预测/表现编排，不认识流程与页面。会话域只拥有 Account scope、连接与传输；Battle 取会话运行时材料经**依赖倒置端口** `IAccountRuntime`（住 `Battle/Abstractions`，由 `AccountSession` 实现），`Session` 不再构造 `BattleClient`/`BattleContext`（2026-11-01 裁决；施工记录见施工进度卷）。

### 4.3 模块与生命周期

`IClientSegment` 从“注册序即依赖序”升级为**显式依赖图**：

```csharp
public interface IClientSegment
{
    string Name { get; }
    IReadOnlyList<Type> DependsOn { get; }
    UniTask<IClientSegmentHandle> InitializeAsync(SegmentContext context, IModuleScope scope, CancellationToken ct);
}

public interface IClientSegmentHandle
{
    UniTask ShutdownAsync(CancellationToken ct);
}
```

- `ClientHost` 在启动前校验 DAG：缺失依赖、循环依赖、重复模块 fail-fast。
- 每个模块初始化前由 Host 建独立 `IModuleScope`；模块把本次初始化的资源/订阅/租约登记进 scope。任一模块失败时，Host 先释放该模块 scope，再释放已返回的 handle（若有），最后逆序释放此前模块。
- `ShutdownAsync` 的 `CancellationToken` 只约束等待上限，**不得跳过根作用域释放**；无论令牌是否取消，根 Scope、服务域和模块 handle 都必须进入释放路径。
- `SegmentContext` 是装配期登记面：模块只可在自己的 `InitializeAsync` 内 `Put<T>`；Host 在全部模块成功后 `Seal`，运行期不再新增注册。业务代码只读 `Require<T>`。
- `ClientHost.Product<T>` 仅保留给引导适配器与编辑器取件，不进入业务流程。

### 4.4 作用域与状态

| Scope | Owner | 允许持有 | 退出动作 |
| --- | --- | --- | --- |
| Root | 进程 | 内容、配置、平台设施、日志、全局 UI 服务 | 逆序 Shutdown、静态重置 |
| Account | 登录会话 | Token、Profile、Meta 会话、Account 服务域 | 撤销请求、清敏感缓存 |
| Match | 匹配到结算 | `BattleClient`、`BattleSession`、Match 服务域 | 断网、解绑、销毁对局态 |
| Battle | 开局到离场 | `Sim`、`IBattleView`、`IBattleReadModel`、输入桥、诊断 | 停视图、卸场景、释放租约 |
| UI | UI 根到关闭 | UI 实例、prefab 租约、展示子作用域 | 关闭清展示、销毁释放长期租约 |
| Scene | 加载到卸载 | 场景句柄、场景资源 | 卸载、归还租约 |

- `BattleSession` 是 Match/Battle 的唯一状态所有者；`MatchRules`、`TestMode`、诊断写入都必须经它。
- 删除 `SimTestRules.ActiveMatch` 的“当前局”语义；需要规则的地方由 `BattleSession` 显式传递。
- `CombatConfig` / `MovementConfig` / `WeaponConfig` 的静态投影从运行时删除，只保留编辑器/工具读口；运行时消费 `CombatValues` / `WeaponTable` 实例。
- `TestModeRuntime` 收敛为 `DevSession` 实例，由 Dev 模块注入；产品程序集不出现测试开关静态。

### 4.5 协同与操作

| 需要 | 唯一默认机制 |
| --- | --- |
| 同模块内同步协作 | 直接方法调用 |
| 跨模块事实、至少 2 个消费者 | `IEventBus` |
| 用户/GM 动作、需要审计或撤销 | `CommandCenter` |
| 跨帧长流程 | `StageMachine`（平面或层级） |
| 一次性等待 | `StageSignal` |
| UI 串行工作 | `IUIOperationQueue` |
| 游戏输入裁决 | `IInputService` 三门 |

- `EventBus` 与 `CommandCenter` 不再“先建机制等消费者”：没有真实产品消费者（探针/GM 演示不算）就删除或移入 `LiteGame.Adapters.Dev`；跨模块事实至少 2 个消费者才保留 `EventBus`。
- 删除 `PreemptiveStageMachine` / `PreemptiveHierarchicalStageMachine` / `PreemptionCore`，除非出现真实抢占需求并附测试。
- `UINavigationController`、`DialogService`、`UITransitionRunner` 降级为 `IUIOperationQueue` 的策略/适配器，不再各自持有队列、超时和取消状态。
- `UIService` 只保留打开/关闭管线与缓存记账；淘汰、换表、统计等拆到协作件。

### 4.6 对局领域与表现

- `BattleSession` 持有 `MatchRules`、`BattleContext`、`IBattleView`、`IBattleReadModel`、`IDiagnosticsSink`；`ProcedureBattle` 只做“取会话 → 等信令 → 驱动 → 收尾”。
- 客户端对局领域类型（`MatchRules`、`Loadout`、`SpawnPlan`、`DamageModel`）从 Procedure/Context 中抽出；Sim 侧领域系统保持现状。
- `IBattleReadModel` 是表现层唯一读口：HUD、排行、击杀提示、复活面板不再直接读 `SimWorldState` 数组；测试可注入替身。
- `BattleViewRig` 保持已拆形态：`BattleViewAssets`（取件/降级）、`BattleViewSceneAssembler`、`BattleHudAssembler`、`BattleFeedbackAssembler`、`BattleLookController`；Rig 只做组合与相位编排，目标不回涨超过 400 行。
- `RoomClient` 只留公共 API 与会话编排（相位门控/换房重置/重连流程）：入站解码分发（`RoomInbound`：重连响应裁决、快照帧水位）与出站打包发送（`RoomOutbound`：唯一 `PacketWriter`）各自成件，会话事实/重连凭据/输入窗口/质量探针各自成件（`RoomSession`/`ReconnectState`/`InputWindow`/`NetworkQualityProbe`）。（行数目标已按 2026-11-01 用户裁决删除——只保留结构目标：协议分发不在门面类。）
- `SimView` 保持通用表现（插值、静默门、实体视图），不引入游戏规则；游戏表现件只依赖 `IBattleView` / `IBattleReadModel`。

### 4.7 UI 与页面模型

- 一个页面收敛为 **`PageDefinition`**：`Id`、`Prefab`、`LuaPath`、`Layer`、`FullScreen`、绑定表、文案 key、样式引用。运行时只消费 `PageDefinition`，不读 contract/manifest/hash。
- `UIApiSpec` 作为唯一 API 源：由它生成 `UIBindIndex` API、`UIBindBase` 转发、Lua shim、dispatch、参考文档与测试；禁止四处手写同步。
- 运行期 UI 只保留 uGUI；UI Toolkit 只用于编辑器和开发工具；Lua 是页面逻辑层，不是第二套 UI 技术栈。
- 页面工具链只保留两类：`PageDefinition` 生成器与可机械判定、且有运行时后果的校验规则；contract/manifest/hash 若只服务工具自身，退回编辑器域，不进运行时。
- UI 领域细节（视觉、制作、控件、工作台）由《UI 系统总设计》吸收；本路线图只裁“运行时不得依赖编辑器契约、一个页面一个定义”的跨域约束，不另开 UI 路线。

### 4.8 开发面

- `LiteGame.Adapters.Dev` 是**唯一开发装配层**：`DevHud`、`DebugConsole`、`DebugPanel`、进程内 `LocalServerTransport` 及其 UI Toolkit host 都住本程序集（投影件在 `Dev/Projection`、本地服件在 `Dev/LocalServer`）。
- 产品 `LiteGame.App` 只依赖 `IDevSession` / `IDevOverlay` 端口；release 构建不出现 `DEVELOPMENT_BUILD` 分支，也不引用 `LiteGame.Adapters.Dev*` / `RoomServer.*`。
- 进程内本地服只由 `LiteGame.Adapters.Dev` 引用；本地测试传输通过 `ILocalTransportFactory` 注入产品流程。
- Dev 装配由场景/构建入口的 `DevBootstrap` 注入；产品 App 不通过编译引用认识 Dev。
- 新开发功能不得再用 `#if` 切产品文件；要么进 Dev 程序集，要么通过端口注入。

### 4.9 身份与版本

- 收敛为三层身份：`BuildIdentity`（构建哈希）、`ContentIdentity`（发布清单、配置摘要、根位移摘要）、`SchemaIdentity`（协议/配置/存档 schema）。
- `IdentityContext` 由组合根生成并传给握手、内容校验与诊断；禁止在业务代码里各自拼 `BuildHash` / `ConfigHash` / `SourceHash`。
- `PlayerCapabilities` 由 `BuildIdentity` 的生成物填充；兼容检查要么开启并有真实下限，要么 `CompatibilityMode.Off` 显式关闭，不允许逐轴 0 的半实现。
- `UIPageManifestHash`、`UIBindGenerationHash` 等工具身份只留在编辑器域，不进入运行时契约。

### 4.10 错误、异步与线程

- 统一错误分类：`ErrorKind`（Transient / Recoverable / Compatibility / Security / Fatal）+ 一个恢复策略入口；删除只做映射、没有执行器的 `ClientErrorRecovery`，或把它接进真实恢复链。
- 统一操作作用域：`OperationScope` 同时持有 `CancellationToken`、超时、合并键和所有者；UI 队列、内容下载、场景加载、会话重连共用同一套语义。
- `SafeCall` 只允许出现在外部边界（Lua 回调、Unity 消息、UI 逻辑回调）；业务路径不得用 catch-all 吞掉可恢复错误。现役边界清单（13 文件：Lua 回调 3、UI 逻辑/控件回调 7、调度器回调 2、表现降级 1）由 `TaskObservationGuardTests.SafeCall_只允许外部边界文件` 守卫，清单外即红。
- 明确线程亲和：Unity 服务、UI、表现、Sim 主线程；内容 IO/签名校验可后台，但结果必须显式切回主线程；`Log` 必须线程安全，或在后台路径禁止写。
- `.Forget()` 只允许带观测回调；禁止无观测的根任务。现役统一口：`TaskObservation.ForgetLogged(op)`（`Assets/LiteFramework/Runtime/Framework/Hosting/TaskObservation.cs`）；后台卸载白名单只有 `FileSystem` 的 JSON 段（`ThreadAffinityGuardTests`），`Log` 线程安全由 `LogRingConcurrencyTests` 覆盖。

### 4.11 架构守卫

以下守卫必须进 CI，失败即阻断合入：

1. 程序集边：`asmdef` 允许边表——未知边、反向边、跨层边失败；框架四件的方向（禁止 `Services → Adapters`、禁止 `Core/Services/Adapters → Hosting`）由 asmdef 边直接守，不再靠目录扫描。
2. `LiteFramework/Runtime/Core` 与 `LiteSim` 不得出现 `UnityEngine`，前者另禁第三方实现依赖。
3. `LiteFramework.*` 与各框架模块不得引用 `LiteGame.*`。
4. 框架（`LiteFramework.*`/框架模块）不得引用 `LiteGame.*`；`Runtime/Services` 不得引用 `Runtime/Adapters`；`LiteGame.Modules.*` 不得引用 `LiteGame.Adapters.*`。
5. `LiteGame.App` 不得引用 `LiteGame.Adapters.Dev` / `RoomServer.*`。
6. public static 可变字段 allowlist：新增失败，删除允许。
7. `DEVELOPMENT_BUILD` / `LITEFRAMEWORK_DEBUG` 只允许出现在 `LiteGame.Adapters.Dev*`。
8. `LiteGame.Modules.Battle` 的表现面不得出现 `SimWorldState` 直读（经 `IBattleReadModel`；测试除外）。
9. 结构守卫（不设行数阈值，2026-11-01 用户裁决）：装配段就地与命名、依赖边、UI 队列唯一实现、静态可变白名单等结构不变量；不按行数判定复杂度。
10. 单一 UI 队列：除 `IUIOperationQueue` 外，运行时代码不得声明 `Queue<...>` 作为 UI 调度器。
11. 身份入口：业务代码不得直接引用 `BuildHash` / `CombatConfigDigest` / `SourceHash`，只经 `IdentityContext`。

### 5.2 完成态：B5 之后每个问题只有一个答案

完成态不按“代码少了多少”衡量，而按“能不能用一句话回答”。下列每条都是一个可判定事实（守卫自动判，或评审按表核）。

**组织级**

- `Assets/` 顶层只剩 `LiteGame` / `ThirdParty` / `ShareResource` / `GameData` / `Scenes` / `Settings` / `StreamingAssets`；未登记顶层目录 = 0。
- 第三方只住 `ThirdParty/` 或 UPM；框架是 `Packages/com.litegame.framework` 可安装包；产品 asmdef 不直接引用第三方目录。
- 仓库根无构建产物，无指向已删 asmdef 的 csproj。

**热更级**

- 每个模块在模型里登记 `tier` 与收集组；“改 X 发什么包”由矩阵判定，不问人。
- 判定面（Sim/协议/房间内核）改动恒整包；页面/表/资源改动恒内容包；HUD 行为类例外逐条登记。
- `BridgeApiVersion` ＋能力集合、内容清单签名、`BuildHash` 三个身份各自单一来源，互不越界。

**架构级**

- asmdef 边 ⊆ 模型 `deps`，层号严格递增；`Core/Services/Adapters` 不引 `Hosting`；产品模块不引框架 `Adapters`；框架不引 `LiteGame.*`——违反即编译失败或守卫红。
- 框架四件可各自单独引用：只做 UI/设置的消费者不拖 YooAsset/xLua。

**模块级**

- 10 个模块（业务 4 + 服务 6）＋ 2 个沿用 `Modules.` 前缀的非模块件（Composition/Dev）＋ `LiteGame.Shared` 常量包 ＋ `LiteGame.Battle.Abstractions` 契约包；名与类型一一对应（04 §6.7）。
- 跨模块引用只指向 `Abstractions/` 里的类型；子包依赖是 DAG（叶子/共享/装配三档）。
- 新增模块 = 目录 + asmdef + `XxxSegment` + 模型登记 + 收集组；B5 后只改一处。

**代码级**

- `LiteClient`/`LiteView`/`Presentation` 残留 = 0；运行期 >400 行文件均有拆分方案或豁免登记（存量清单只减不增）。
- 命名空间跟目录；四个平铺命名空间的模块为存量登记，新增类型必须带模块前缀。
- public static 可变状态白名单只减不增；`TakeContainer` 消费清单封闭。
- 测试有明确模块归属（模型 `tests` 字段），可按模块筛选运行；是否拆测试 asmdef 按规模另评，不在 B5 承诺。

**完成态仍保留的边界**（是裁决，不是缺口）：C# 热更不在 B 批范围（分界与身份前置见 §5.3，接入另立 B6）；Battle 仍是最大模块（9 个子包，靠包图守卫）；Procedure 仍是业务模块；`LiteFramework.Async` 仍是 dotnet 侧切分；`Modules/*` 下零引擎文件仍走源链接共编。

### 5.3 C# 热更（HybridCLR）：允许内核热更后的分界

**结论**：允许 `LiteSim`、`LiteNet`、`LiteSync` 热更。代价不是给三个程序集打标志，而是把 **AOT/hot 的分界线从“框架 / 产品”改成“Unity 载体 / 纯 C#”**——一旦内核可换，任何 AOT 代码都不能再引用内核类型（`SimVector3`、`SimWorldState` 是结构体，藏不到接口后面）。

推导链：内核热 → 引用内核类型的产品代码必须热 → 引用产品模块的产品适配器必须热 → AOT 侧只剩框架与 Unity 壳。这与“框架不得引产品、产品不得引内核之外的反向边”是同一条边，只是从**编译期方向**升级为**构建期分区**。

#### 5.3.1 分界

| 侧 | 装什么 | 判据 |
| --- | --- | --- |
| **AOT（随包）** | `LiteFramework.{Core,Services,Adapters,Hosting}`、`LiteGame.Bootstrap`（B1.5 落地的薄引导：场景入口 + 致命错误面 + 入口装载）、Unity 载体（UI 控件、`AppLifetime`、相机 Rig 等 MonoBehaviour）、`LiteGame.Editor` | 被场景/prefab 序列化引用，或绑定引擎/平台 |
| **Hot（内容包）** | `LiteSim`、`LiteNet`、`LiteSync`、`LiteGame.Core`、`LiteGame.Shared`、`LiteGame.Modules.*`、`LiteGame.Battle.Abstractions`、`LiteGame.Adapters.*` 的纯 C# 部分 | 纯 C#、零 Unity 序列化载体、且被产品/判定面使用 |

精确的 hot 集合不进文档，**由引用图算出**：任何 AOT→hot 的编译边都意味着“该 AOT 件要么迁 hot，要么把类型/接口拆到 AOT 侧”。B6 开工时以编译器与构建脚本为准。

**迁移账（现在就能点清）**：

- `GameEntry` 拆成“AOT 引导（建 `ClientHost`、装载 hot、调入口）”+“hot 组合根（现 `AppComposition` 与 18 段）”。
- 引导期错误面（现 `ProcedureError.ShowBootstrapError`）必须留 AOT，不能随模块进 hot。
- Unity 载体与逻辑拆件：`BattleHudView`、`MapBoundsMarker`、`TpsCameraRigTuning` 留 AOT，逻辑经端口回 hot。
- `LiteGame.Adapters.{Unity,Luban,LuaBridge}` 与内核、模块一起进 hot（它们引用产品类型）。
- `Dev` 面（`LiteGame.Adapters.Dev`）不进发布包，不参与分区；开发期可不开热更。

#### 5.3.2 唯一值得加的接口

`IHotEntry`（AOT 定义、hot 实现）：`Initialize(IHostServices)` / `Shutdown()`。AOT 的引导只做“装载 + 调用”，不再认识任何模块类型。**它有真实消费者，不是预留空壳**；除此之外不需要任何业务层热更接口。

#### 5.3.3 身份与兼容（必须同批做，否则是互相骗）

1. `BuildHash` 从“AOT 编译期常量”改为“内核程序集自带的生成常量，运行时从已装载内核读取”；`BuildHash.g.cs` 生成进内核工程，两端同源。
2. 握手/Join 携带 `BaseHash`（AOT）+ `KernelHash`（hot 内核）；服务端准入要求 `KernelHash` 一致、`BaseHash` 满足 hot 包声明的 `requiredBase`。
3. `ReleaseCompatibility` / `PlayerCapabilities` 扩一档：hot 包声明 `requiredBaseHash`、`protocolVersion`、`simRulesVersion`；候选不兼容直接拒收（复用现有最低版本比较）。
4. `ContentIdentity` 增 hot-set 标识；`CombatConfigDigest` 的比对只在 `KernelHash` 相同时生效。

#### 5.3.4 五条规则（H1 已按“允许内核热更”改写）

| # | 规则 | 理由 |
| --- | --- | --- |
| H1 | **判定面可热更，但必须两端锁步**：`KernelHash` 不一致拒绝进房；校验和只在同版本间比较 | 确定性由“同源码”保证，改为“同版本 + Join 准入”保证；跨版本比较校验和没有意义 |
| H2 | **AOT 不引用 hot**，只认 `IHotEntry` 与框架端口 | 反向引用一换版本就断链；构建期 AOT 编译集不得包含 hot asmdef |
| H3 | **hot 程序集不含 Unity 序列化载体**（MonoBehaviour / ScriptableObject / 被场景或 prefab 引用） | 这些类型必须编译期存在；现役需拆的只有 3 个（见 5.3.1） |
| H4 | **hot→AOT 调用面单源 + 版本**：AOT API 清单（延续 `UIApiManifest` 机制）+ hot 包声明所需 base | 否则 AOT 一次重构打断线上内容；清单+版本+候选下限机制已跑通（Lua 面） |
| H5 | **裁剪与 AOT 泛型引用按职责分档**：`link.xml` 保留面 + 构建期生成 `AOTGenericReferences` | hot 代码用到的泛型实例化必须 AOT 侧生成过，否则运行期 `ExecutionEngineException` |

#### 5.3.5 三条现实风险（先量后上）

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 解释执行开销 | hot 程序集走 IL 解释器，判定 tick 可能是 AOT 的数倍 | 用 `SimReplayRunner`/`FramePump` 对真实对局（8 席 + bot）实测；不可接受则退回“数学 AOT + 规则 hot”，但那会重新引入出包需求——这是要用数据裁决的岔路 |
| AOT 泛型/反射 | 判定与 DI 都用泛型与构造反射（`ServiceContainer`）；hot 侧用到而未生成的实例化会炸 | H5 的生成器必须覆盖内核 + 模块的泛型面；`IeeeProbe` 继续守浮点语义 |
| 版本爆炸 | 每个 base 版本都要配套 hot 包；旧 hot 包在新 base 上必须被拒 | 5.3.3 的 `requiredBase` 比较；发布清单按 base 归档 |

#### 5.3.6 对交付节奏的影响

- 内核/判定修复不再需要商店过审：`改内核 → 发布服务端（publish+重启）→ 上传客户端 hot 包 → 客户端补丁 → Join`。
- **仍然两端锁步**：服务端不升级内核，客户端新 hot 包进不了房。hot 化买的是“免过审”，不是“跳过服务端发布”。
- 协议变更默认**不做多版本并存**：房间级强制同版本；需要灰度/回滚时再引入服务端双版本窗口（另立专项）。

#### 5.3.7 接入批（B6，现在不开工，前置清单已冻结）

1. 分区落地：`LiteGame.Bootstrap` + `IHotEntry` + 组合根与 18 段迁 hot + 3 个 Unity 载体留在 AOT；
2. 构建管线：hot asmdef 排除出包 → dotnet 编译 → dll + manifest 进内容包；
3. 装载：`IContentService` 取字节 → `LoadMetadataForAOTAssembly`（按需）→ `Assembly.Load` → 入口注册；失败回退上一代（激活事务已支持）；
4. 身份与兼容：5.3.3 的四项；
5. 守卫：AOT 不得引 hot（构建期）+ H3/H4/H5。

**触发条件**（满足任一启动）：内核/判定面修复频率 > 每月 1 次；或商店包审周期 > 2 周；或需要在不发版的情况下改变判定行为（不只是参数）。

**现在不做的**：空 `IHotUpdateModule`、多版本协议并存、为热更把框架改成纯逻辑、提前引包。

## 7. 禁止的重构方式

- 禁止在所有权、作用域和协调模型未统一前新开 `RoomClient` / `UIService` / `BattleContext` 拆分；已拆的 `BattleViewRig` / `UIBindIndex` 禁止回涨成新的大类。
- 禁止新增第二套静态门面、第二套 UI 队列、第二个“当前局”全局变量。
- 禁止用 `#if` 作为新增开发功能的边界；新开发功能只能进 `LiteGame.Adapters.Dev` 或经端口注入。
- 禁止把 contract/manifest/hash 等编辑器契约带入运行时；运行时只认 `PageDefinition` / `IdentityContext`。
- 禁止为单一实现新增接口；接口必须有真实替代、生命周期隔离或测试替身三种理由之一。
- 禁止在 M0/M1 改变用户可见行为；行为变化必须另立专项并补 UI/网络验收。
- 禁止在未查调用点前删除 `EventBus` / `CommandCenter` / `StageMachine` 变体；先删无消费者机制，再谈替换。
- 禁止把本路线图的阶段状态写进设计文档；进度只进 `Docs/施工进度/`。

## 8. 风险与回退

- **M0/M1 的接缝是 adapter**：单个接缝回退只需恢复原构造点，不涉及数据迁移；唯一需要同一次发布回退的是 `PlayerCapabilities` 来源切换与内容发布侧。
- **UI 队列迁移**：先让导航/转场共用队列，保持 `UINavigationController` / `UITransitionRunner` 公共 API 不变；用例全绿后再迁弹窗/Loading。
- **Dev 程序集搬迁**：目录移动按 `directory-move-sync` 同步 asmdef、测试、构建器与代码地图；若搬迁受阻，先冻结 `App -> Dev` 边，再分步。
- **页面单制品**：依赖《UI 系统总设计》吸收；若产品决定保留现有工具链，M3 至少做到“运行时不依赖编辑器契约”，不强行砍工具。
- **身份收敛**：与 BuildHash/内容摘要/发布清单强相关，不与会话或玩法行为同一次发布；能力生成物未就绪时只允许 `CompatibilityMode.Off` 显式关闭。

## 12. 定稿结论

- **最小目标以第 3 节为准**：M0 只做六条不变量与六个接缝，不改用户可见行为；M0 不达标不进入 M1。
- **最终目标以第 4 节为准**：M3 的“一条默认路径 + 领域聚合 + 单制品 + 单身份入口 + 架构守卫”是稳定目标；M3 不达标不启动 C5 通用包提取。
- **路线以第 5 节为准**：M0 → M1 → M2 → M3 顺序执行，阶段之间不并行改同一文件；每阶段以退出条件和架构守卫为准，不以“代码看起来变小”为准。
- **边界以第 1、2、7 节为准**：本路线图不替代 C0～C5，不重写 Sim/网络/内容，不新增第二套机制；上位文档按第 9 节吸收后再实施对应阶段。
- 一句话：**先统一，再拆分；先删，再加；先守卫，再宣称。**
