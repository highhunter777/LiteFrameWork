# 脚本形态统一专项设计

> **版本**：0.1（2026-10-21）
> **定位**：裁决 `scripts/` 下工程脚本的**角色分层、入口与登记、调用契约、文件与配置形态、语言边界与迁移顺序**；回答“新脚本该长什么样、现有脚本按什么规则收敛”。
> **不做的事**：不裁各工具的业务算法与产物语义；不重复清单 schema 与 `ToolWriteScope` 细则；不改 CI 车道、测试分层与发布流程；不要求所有脚本使用同一种语言；不把工程脚本放进 Unity 程序集。
> **冲突裁决**：入口/清单/CLI 形态以[开发工具链平台专项设计](开发工具链平台专项设计.md)为准；执行/写盘以[工具执行与写盘契约专项设计](工具执行与写盘契约专项设计.md)为准；生成器形态以[生成器工具箱专项设计](生成器工具箱专项设计.md)为准；L2-D 的 CLI 参数与 dry-run 批次以[开发工具链平台分层设计](开发工具链平台分层设计.md) §6 为准。本文只裁“脚本作者面”，不另立第二套清单或执行契约。
> **关联**：[scripts/README](../../../scripts/README.md)、[技术支持](../../工具链/技术支持.md)、[工具索引](../../工具链/工具索引.md)、[修改指南](../../修改指南.md)、[directory-move-sync](../../../.agents/skills/directory-move-sync/SKILL.md)。

## 1. 原则

脚本形态统一的目标不是“所有脚本写成一样”，而是让维护者与 Agent 在**任意一个脚本前**都能回答四个问题：

1. 它是不是入口？入口叫什么？
2. 它怎么被调用、怎么失败、失败码是什么？
3. 它由谁登记、被谁消费、移动后要同步哪些面？
4. 它该用 Python 还是 PowerShell？

四条原则：

| 原则 | 含义 |
|---|---|
| **单一 canonical 入口** | 每个用户面能力只有一个权威调用方式，写在清单 `command`；直调脚本保留兼容，但不得在文档里成为第二入口 |
| **按角色分层** | 全局入口、域入口、叶子工具、内部库、测试、一次性运维各有明确形态，禁止“既能直调又像库”的灰色地带 |
| **契约跨语言一致** | 参数、帮助、退出码、输出前缀、dry-run 的**语义**一致；语法保留各语言习惯，不强行把 PowerShell 写成 Python |
| **迁移按风险分批** | 先登记与契约，再文件形态，最后语言边界；不为了“统一”推倒 Windows 原生脚本 |

## 2. 现行形态（统一基线）

规模基线（v0.1 盘点）：`scripts/` 下 18 个 `.ps1`（约 2672 行）与 15 个 `.py`（约 2536 行）。当前同时存在以下差异：

| 面 | 现行形态 | 造成的实际后果 |
|---|---|---|
| 语言 | 生成器已全 Python；门禁/构建/部署/本地联测仍以 PowerShell 为主；内容发布为 PS | 新脚本没有默认语言，Agent 每次要猜 |
| 入口 | 存在“脚本直调 / `toolbox.py` / `toolchain.py`”三种路径；`gen-build-hash.py` 三者都可到达 | canonical 不唯一，文档与 CI 各写一套 |
| 登记 | 清单覆盖 18 条命令，但 `deploy/gm.ps1`、`deploy/deploy-room.ps1`、`deploy/wg-peer.ps1`、`local/local-chain.ps1` 等用户面脚本未登记；`toolchain_*.py`、`_codegen.py` 等内部模块与入口混放 | 用户找不到、注册面漏检、移动脚本后引用漂移 |
| 参数 | PS 用 `-Lane L1` 这类 PascalCase 参数；Python 混用 argparse、`sys.argv` 与位置参数 | 同一能力在 CLI 清单与脚本两处各写一份参数说明 |
| 帮助 | argparse 脚本有 `--help`；deploy 三件已有 comment-based help，gate/build/content/local 多数只有头注释或 `param()` | 不好发现用法，Agent 只能读源码 |
| 退出码 | 多数本地入口为 0/1；`local-chain`/`serve-cdn`/`nightly-gate` 会透传子进程任意退出码；argparse 返回 2；`toolchain.py` 另有 4/5。`wg-peer.ps1` 的 2/3/4 是**远端脚本**哨兵，不是本地退出码 | 调用方无法用统一规则判断“用法错误”还是“执行失败” |
| 输出 | 生成器 `[codegen/<tool>]`；CLI `[toolchain]`；内容脚本 `[FAIL]`；其余裸 `Write-Host` | 人读尚可，机器解析与日志检索困难 |
| 文件 | EOL 混用（部分 PS/Py 为 CRLF，其余 LF）；`l2-unity-gate.ps1` 带 BOM；多个 PS 含中文但无 BOM | PS 5.1 下中文误解析风险，diff 噪声 |
| 根路径 | PS 约 15 处重复 `$PSScriptRoot` 推导；Python 只有 codegen 收口到 `repo_root()` | 移动脚本时漏改一处即从错误 CWD 解析 |
| 配置 | 数据已是 JSON（`local-cdn.json`）；加载器必须是 `_` 前缀内部库，不得命名成 `*.config.ps1` 或可执行入口 | 容易被误当成可配置脚本直调 |

**结论**：差异集中在“作者面”，不是业务实现。统一应从登记与契约入手，语言只定边界，不做全量迁移。

## 3. 角色分层与入口

### 3.1 六类角色

| 角色 | 判据 | 命名 | 是否进清单 | 例子 |
|---|---|---|---|---|
| 全局入口 | 面向所有工具的发现/执行入口 | `toolchain.py` | 是 | `python scripts/toolchain.py` |
| 域入口 | 一个域一个稳定入口，负责分发子工具 | `<域>/<动词>-<对象>.ps1|py` 或既有工具箱名 | 是 | `codegen/toolbox.py`、`gate/nightly-gate.ps1`、`local/local-chain.ps1` |
| 叶子工具 | 单一职责、可独立执行 | 动词开头 kebab-case | 用户面/CI 面必进；仅被域入口注册的可豁免 | `gate/test.ps1`、`content/publish-candidate.ps1` |
| 内部库 | 被其他脚本 import / dot-source，不独立执行 | `_` 前缀 | 否 | `_codegen.py`、`_ssh-host.ps1` |
| 测试 | 脚本层契约测试 | `tests/test_*.py` | 否 | `tests/test_toolchain.py` |
| 一次性运维 | 历史补丁/一次性扫描，不进入日常流程 | 原目录保留，文件头 `@oneshot` | 否（仅告警） | `pipeline/patch_p1_plugin_metas.py` |

**生成器例外**：`codegen/` 继续遵守[生成器工具箱专项设计](生成器工具箱专项设计.md) §7——新生成器 `gen_<对象>.py`（snake_case）、全 Python、由 `toolbox.py` 注册。该域不与“kebab-case 入口”规则冲突，因为它的权威入口是工具箱，不是单脚本文件名。

### 3.2 入口规则

1. **canonical 入口 = 清单 `command`**。文档、CI、Agent 指令、计划任务都只写这一种；单脚本直调保留给既有消费面（`build-player.ps1` 门禁、`Luban/gen.bat`、`test.ps1` 内部调用），不在操作文档里作为首选。
2. **域入口只做转发**：解析子命令、校验参数、透传参数与子进程退出码；不承载业务算法，不复制叶子脚本的默认值。
3. **叶子工具不反向依赖域入口**；域入口可调用叶子脚本，叶子脚本不得调用域入口。
4. **内部库不可执行**：`_` 前缀文件不得包含 `main()` 或可独立运行的 `param()` 入口；只提供函数/类型。
5. **一次性运维脚本**：文件头第一行后加 `@oneshot` 标记与用途/执行日期；不要求清单登记，`toolchain.py check` 只告警不阻断。需要反复使用的，必须升级为叶子工具并登记。

### 3.3 登记判据（可机械检查）

一个可执行脚本（含 `main()` 或 `param()`）必须满足以下之一：

- 出现在清单某条 `command` 中；
- 被某个已登记入口的注册表引用（如 `codegen/toolbox.py` 的 `TOOLS`、`gate/nightly-gate.ps1` 的步骤表）；
- `_` 前缀内部库、`scripts/tests/` 下测试、或文件头带 `@oneshot`；
- 确属未登记的新入口 → 补清单，而不是加豁免。

`toolchain.py check` 增加“孤儿可执行脚本”检查：扫描 `scripts/**/*.{py,ps1}`，按上述判据归类；未覆盖项默认告警，`--strict` 升级为错误。检查只做静态路径/引用匹配，不执行脚本。

## 4. 调用契约

### 4.1 参数

- **清单 `args` 是跨语言参数 schema 的唯一来源**（字段与 `toolchain.py run` 的校验归 L2-D1）；脚本自身仍用原生解析，不要求所有脚本改 argparse。
- Python 入口用 `argparse`，长参数 kebab-case（`--project-path`、`--dry-run`）；只有域入口的子命令位置参数允许省略 `--`（如 `toolbox.py luban`）。
- PowerShell 入口用 `param()` + PascalCase（`-ProjectPath`、`-Lane`）；需要脚本级帮助时加 `[CmdletBinding()]` 与 comment-based help。
- 必填参数缺失、类型错误、枚举非法 → **调用前 fail-fast**，打印一行 usage，退出码 2；不得落到子进程才报错。
- 默认值只在一个地方声明：脚本参数或清单 `args.default` 二选一，清单声明后脚本不得再写一份不同的默认值。

### 4.2 帮助

- 每个入口必须支持原生帮助：Python `--help`；PowerShell `Get-Help` / `-?`（comment-based help）。
- `toolchain.py run <id> --help` 渲染清单 `args` 与默认值，不启动子进程（L2-D1）。
- 域入口无参时打印索引/用法并退出 0；未知子命令打印已知列表并退出 2。
- 帮助文本只描述当前行为，不复述业务规则；业务规则留在对应专项设计。

### 4.3 退出码

| 码 | 语义 | 适用范围 |
|---|---|---|
| `0` | 成功（允许零变更） | 所有脚本 |
| `1` | 预期失败（校验不过、对账不一致、执行失败） | 所有脚本 |
| `2` | 用法/参数错误 | 所有脚本 |
| `4` | 工具不存在 | 仅 `toolchain.py` |
| `5` | 编辑器未运行/不可达 | 仅 `toolchain.py` |

- 叶子脚本与域入口**本地**只使用 0/1/2；不得自造 3/4/7 等业务码。`wg-peer.ps1` 远端脚本里的 2/3/4 是哨兵，不构成本地契约；本地仍按 `throw`→1 或显式用法错误→2。
- 域入口对子进程的 2/3/4/7 等退出码归一为 1（原始码与摘要写 stderr）；`local-chain`/`serve-cdn`/`nightly-gate` 的透传面按此收口。
- PowerShell 的 `throw` 自然退出 1，可保留；需要 2 时显式 `exit 2`。
- 子进程退出码优先透传：域入口不得把子进程失败吞成 0。

### 4.4 输出

- 状态行统一前缀 `[<域>/<工具>]`（如 `[gate/l1]`、`[content/publish]`、`[toolchain]`）；一行摘要说明结果与关键计数。
- 正常状态/摘要写 stdout；错误与修复提示写 stderr。退出码是权威结果，不以“最后一行文本”判断成功。
- PowerShell 中机器相关输出用 `Write-Output`；`Write-Host` 只用于颜色/装饰，`--json` 模式禁用 `Write-Host`。
- `--json` 为**可选**能力：需要结构化消费的脚本可提供，启用时 stdout 必须是纯 JSON（诊断走 stderr）；本层不强制所有脚本实现。
- 热路径/批量循环不得逐行刷屏；进度输出按阶段汇总，失败时给出可复现命令。

### 4.5 dry-run 与 check

- **`--check` = 只校验，不写盘**（对账/门禁用）；**`--dry-run` = 预览将要发生的写盘**（动作工具用）。两者不得混用。
- 清单 `safety.dryRun=supported` 的工具，脚本必须提供对应的 `--dry-run`（或 L2-D 映射的既有 `--check`）；不支持的脚本必须明确拒绝，不得静默执行。
- dry-run/check 的退出码仍按 0/1/2；预览有变更但未写盘不等于失败（返回 0），除非该工具契约定义为对账失败（如 buildHash `--check`）。
- CLI 侧映射与 `run --dry-run` 的开放条件归 L2-D2；本文只要求脚本侧存在可调用的对应形态。

### 4.6 非交互与根路径

- CI、Agent、计划任务路径不得等待键盘输入；破坏性动作需要显式开关（如 `-Force`、`--yes`），不得用交互确认代替。
- 工程根一律由**脚本自身位置**推导，禁止依赖当前工作目录；允许显式 `--project-path` / `-ProjectPath` 覆盖。
- 同一语言只保留一个共享根推导实现：Python `scripts/_common.py` 的 `repo_root()`；PowerShell `scripts/_common.ps1` 的 `Get-RepoRoot`。叶子脚本不得再复制推导片段；`_codegen.py` 的 codegen 专用输出/执行面保留，根推导逐步委托 `_common`。

## 5. 文件与配置形态

### 5.1 编码与行尾

| 类型 | 规则 |
|---|---|
| Python | UTF-8 无 BOM；只允许 LF |
| PowerShell 新脚本 | **ASCII-only**；需要中文提示时优先改用 Python 或英文 |
| PowerShell 存量含中文 | 必须由 `pwsh`（PS 7+）启动；改动该文件时转为 UTF-8 **带 BOM**，或去中文。禁止新增“无 BOM 且含中文”的 PS |
| 所有 `scripts/**` 文本 | LF；在 `.gitattributes` 声明 `*.py text eol=lf`、`*.ps1 text eol=lf`，避免 `core.autocrlf` 造成工作区混用 |

行尾统一不改变任何逻辑；按文件触碰批次归一，不做一次性全仓格式化。编码/行尾由 `toolchain.py check` 扫描告警（无 BOM 的非 ASCII PS、BOM 的 Python、CRLF 文件），`--strict` 升级为错误。

### 5.2 命名

| 类型 | 规则 |
|---|---|
| 入口 | `<域>/<动词>-<对象>.py|ps1`（kebab-case），如 `publish-candidate.ps1`、`doc-lint.py` |
| 生成器 | `gen_<对象>.py`（snake_case，生成器专项例外） |
| 内部库 | `_<name>.py` / `_<name>.ps1` |
| 测试 | `tests/test_<主题>.py` |
| 配置数据 | `<name>.json`；加载器必须是内部库，不得命名为 `*.config.ps1` 或可执行入口 |
| 一次性运维 | 原目录 + 文件头 `@oneshot`；不新增 `ops/` 目录 |

### 5.3 文件头

入口脚本使用四段式头注释（生成器继续五段式）：

1. **用途**：它做什么、何时用；
2. **入口**：canonical 命令 + 直调兼容说明；
3. **契约**：退出码、输出前缀、是否 dry-run/check；
4. **消费点/重跑时机**：谁调用、改了什么之后必须跑。

内部库使用两段式：用途 + 公开函数/类型。头注释只写当前设计与约束，不写“已修复/已迁移”等状态。

### 5.4 配置与密钥

- 配置数据一律 JSON/YAML 等声明式格式；**禁止可执行配置**（`.ps1`/`.py` 配置只允许作为内部加载器）。
- 配置加载器命名为 `_local-cdn.ps1` 这类内部库；数据继续留在 `local-cdn.json`，加载器只做解析与默认值。
- 密钥、口令、测试者 `.conf` 继续按 AGENTS.md 红线与 `LocalNotes/` 管理；脚本不得内置密钥或在工作区打印明文。
- 配置路径与数据路径由脚本常量或 JSON 单源声明，不在多处硬编码同一路径。

## 6. 语言边界与迁移

### 6.1 新脚本默认 Python

新脚本默认 Python，理由与生成器裁决一致：可单测、UTF-8 语义稳定、与 `toolchain.py` 同解释器、避免 PS 5.1 的编码/行尾陷阱。

### 6.2 PowerShell 的合法保留面

只有满足以下之一才用 PowerShell：

- Windows 原生编排：计划任务（`schtasks`）、服务/进程宿主、`Start-Process` 生命周期、SSH/WireGuard 主机运维；
- Unity Pipeline/构建宿主：需要与 PowerShell 原生管道、现有构建脚本深度协作；
- 现有 PS 入口的**薄壳**：只做参数转发与进程编排，不改写业务算法。

**薄壳判据**：新增 PS 入口不超过约 150 行、不含数据转换/解析/生成逻辑；超过或含业务逻辑时，把逻辑放 Python，PS 只保留启动壳。`build-player.ps1`、`l2-unity-gate.ps1`、`local-chain.ps1` 等大型 Windows 绑定脚本**不在“为统一而重写”的范围**。

### 6.3 存量迁移规则

- **触碰迁移**：某个 PS 脚本因功能变更被改动，且满足“可迁 Python、无 Windows 原生依赖、逻辑占比高”时，在同一批评估迁移；不单独发起“语言统一”大迁移。
- **不迁移**：构建、门禁、部署、本地联测中与 Windows/Unity/计划任务强绑定的入口；它们的形态统一走 §4/§5，不改语言。
- **试点**：若启动语言迁移，先选一个低风险域（内容发布/扫描类）做试点，验收标准是行为等价、退出码等价、调用方零改动；试点报告进施工进度，不在本文记状态。

## 7. 批次与退出条件

| 批次 | 内容 | 依赖 | 退出条件 |
|---|---|---|---|
| S-A 角色与登记 | 用户面脚本补清单；内部库改 `_` 前缀或标 `@oneshot`；`toolchain.py check` 增加孤儿/编码/EOL 检查 | L1 | 清单覆盖全部用户面入口；孤儿检查绿（或仅剩 `@oneshot` 告警）；`scripts/README` 与工具索引同步 |
| S-B 调用契约 | 统一帮助、退出码 0/1/2、输出前缀、参数 fail-fast、`--check`/`--dry-run` 语义 | S-A；L2-D1 的 `args` schema | 所有登记入口有原生帮助；本地入口不再自造 3/4/7；dry-run 声明与脚本能力一致；契约测试通过 |
| S-C 文件与配置 | `.gitattributes` 统一 LF；PS 编码规则；四段式头注释；`_common` 根推导；配置加载器改名 | S-A | 新脚本检查通过；存量按触碰归一；移动脚本后根推导零重复；Doc/L1 绿 |
| S-D 语言边界 | 把“新脚本默认 Python / PS 薄壳判据”写进 `scripts/README` 与 `AGENTS.md` 常用命令；按需做一次试点迁移 | S-A、S-B | 规则有单一出处；新脚本抽查合规；无“为统一而重写”的大批 diff |

**并行性**：S-A 与 S-C 可并行；S-B 依赖 L2-D1 的清单 `args` 字段；S-D 只定规则与试点，不阻塞 S-A/S-B/S-C。每批独立可验收。

## 8. 风险与回滚

| 风险 | 处理 |
|---|---|
| 改名/移动脚本导致 CI、hook、计划任务、文档引用漂移 | 按 `directory-move-sync` 六面同步；`toolchain.py check` 的注册面检查必须绿；一次只搬一个域 |
| 行尾归一产生大 diff、掩盖逻辑改动 | EOL/编码批次只做字节级转换，不夹带逻辑；单独提交，评审看文件数而非内容 |
| 退出码变化破坏调用方 | 先 grep 消费面；对既有非 0/1 码保留一个批次的兼容映射，再收口；CI/Agent 只依赖 0/非 0 |
| 登记检查误报 | 孤儿检查先告警后严格；`@oneshot`/内部库/测试三类豁免明确；新增入口优先补登记而不是加豁免 |
| 语言迁移改变行为 | 只做低风险试点；验收要求退出码、stdout 关键行、产物字节等价；不做“顺手重构” |
| 与 L2-D 重复定义 | 清单 `args`/dry-run 映射只引用 L2-D，不在本文复制 schema；本文只要求脚本侧能力存在 |

**回滚**：清单/命名/入口可单文件回退；`.gitattributes` 可整体撤销（不涉及数据迁移）；脚本改名按 git rename 回退；退出码兼容映射保留到消费面确认后再删除。工程脚本不在 BuildHash 闭包内，本设计不触发共享源重生成。

## 9. 验收与检查面

- **结构**：`toolchain.py check` 覆盖清单、注册面、孤儿脚本、编码/EOL；`--strict` 全绿。
- **契约**：Python 契约测试覆盖帮助、退出码、未知子命令、参数缺失、输出前缀；PowerShell 至少覆盖一个代表性入口（如 `test.ps1`/`gm.ps1`）的 `Get-Help` 与退出码。
- **文档**：`scripts/README` 只保留目录职责与 canonical 入口，不复制每个工具的参数表；工具索引由清单生成。
- **门禁**：L1 + Doc；涉及 Unity Pipeline/计划任务的改名，按 `directory-move-sync` 核对六面，不额外触发 L2。
- **证据**：批次完成后由施工进度记录命令、输出与文件清单；本文不记完成状态。
