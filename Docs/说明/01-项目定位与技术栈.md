## 1. 两个身份

### 1.1 通用框架

仓库的第一重身份是一套**与玩法无关**的自研框架：客户端按 [客户端总设计](../设计文档/架构/商业级通用客户端框架总设计.md) 的 C0～C5 能力线，服务端按 [服务端总设计](../设计文档/架构/商业级通用服务端框架总设计.md) 的 R0～R4 能力线。它提供的能力面是：

- 宿主生命周期与装配（模块注册序、容器密封、失败回滚、优雅关闭）；
- 依赖注入与服务作用域（根 Scope／会话 Scope／租约与代次校验）；
- 分域时钟、事件总线、命令中心、分层状态机、对象池、日志门面；
- 内容服务与热更事务（候选包、签名、激活事务、反回退、健康探针）；
- UI 运行时（导航单写者、模态栈、绑定生成）与本地化；
- 验证基础设施（L0～L4 分层、纪律扫描、生成器工具箱）。

这些能力不依赖任何具体玩法，因此可以脱离 Demo 讨论。

### 1.2 确定性联机射击 Demo

第二重身份是一个**确定性联机的射击 Demo**：第三人称越肩画面，服务器权威步进 + 客户端预测回滚，判定逻辑两端共编。它以 [框架先行建设与业务接入专项设计](../设计文档/架构/框架先行建设与业务接入专项设计.md) 的 G0～G6 为推进口径，作用是给框架找到第一个真实消费者——证明框架"跑得动、验得过"，而不只是"接口齐全"。

### 1.3 两者互为约束

这不是拼盘，而是互相倒逼：

- **框架的能力边界由 Demo 的真实需求决定**：回滚与和解逼出跨运行时逐位一致的整数数学与双端共编；内容热更逼出租约、代次与激活事务；联机进房逼出票据、BuildHash 握手与重连恢复。
- **Demo 的每个机制都必须经框架落地**：装配、时钟、内容、UI、门禁都走框架提供的路径，业务侧不另起一套。

理解了这一层，才能理解仓库里一些"看起来过度设计"的结构（例如为什么房间内核要禁 IO/时钟/proto，为什么协议与判定只有一份源码）。代价与守卫的对应关系见 [02](02-架构总览与程序集分层.md) §6、§7。

### 3.3 关键第三方的取舍

- **UniTask**：框架唯一异步底座。因为它是第三方，`LiteFramework.Core` 保持零第三方零引擎，带 UniTask 的部分外提到 `LiteFramework.Async`（dotnet 双轨件）。
- **YooAsset**：提供内置包/离线包/联机候选三态与引用计数；项目在其上包一层租约与代次校验，避免把第三方 API 暴露给业务。
- **Luban**：一张表源同时产出两端读码与二进制，是"双端同读一份数据"的基础；表数值可热更，读码面进 BuildHash 闭包。
- **kcp2k + Protobuf**：快照走不可靠、信令走可靠；协议单源，杜绝两端各自拼包。
- **XLua**：只用于 UI 页面逻辑热更；脚本不得触碰判定与网络底层（白名单门面 + 沙箱）。

## 6. 现行边界

### 6.1 现行可跑通的面

- **启动与入口**：`Boot` → `GameEntry` 装配 13 个模块 → 流程机 `Launch/Patch/Preload/Main`；产品入口五页（登录/大厅/房间/结算/设置）经 Meta 真 HTTP 接线；开发入口＝F2 常用调试面板 + F3 开发控制台（`DevStartupConfig` 可直入），三者在 `UNITY_EDITOR || DEVELOPMENT_BUILD || LITEFRAMEWORK_DEBUG` 门禁内，正式包不含。
- **联机**：真 KCP 路径只接受 Meta 签发的票据；本地测试模式走进程内 `Room-Test`（`127.0.0.1:17777`，不建 Socket、不走票据）；云端测试房由编辑器 GM 页显式创建。
- **对局**：房间模板 `standard`/`four`/`eight`/`sandbox`；服务端 60Hz 权威步进 + 30Hz 快照（差分 + AOI + 背压分档）；客户端预测 + 回滚和解 + 回滚期事件静默门。
- **内容**：候选包、签名、激活事务、反回退、真实下载、Lua 沙箱、健康探针；配置表两端同读一份 `.bytes`。
- **门禁**：L0 依赖扫描、L1 纯逻辑、L2 Unity、L3 集成、Doc 各有脚本入口（`scripts/gate/`，`test.py` 提供 `L1/L2/L3/All/Doc` 套件）；纪律扫描 R1～R15 在 L1/L2 打红。
- **本地服**：开发档可在 Unity 进程内跑真 `RoomRuntime`（`LocalServerTransport`，自动补位开局），release 恒走真 KCP。

### 6.2 不在范围内的面

- **L4（真机/性能）** 尚未纳入统一门禁入口，基线由客户端总设计补齐。
- **发布侧**：真云 CDN、Android 真机矩阵（无设备，随 G4 登记）、断点续传与写盘中断矩阵未闭合。
- **正式业务面**：账号资产、库存、Loadout 仍缺，归 G3。
- **角色表现余部**：Hit/Death 等动作的帧事件接线、真对局动作对齐/打断/重连去重、8 人基线，归 G2 垂直切片。
- **观战/中途加入**：AOI 为它们留了模型空间，但未实现。
- **第三方素材**：按仓库政策不入 VCS；缺包克隆时该角色**没有视图**（工厂拒绝生成，不造占位替身），Console 有明确告警——对局可开、该角色不可见。

关口状态、证据与剩余面不在本章维护。

## 7. 工程化形态的四个特征

1. **双轨共编**：`LiteFramework` 的 Core/Async 两段、`LiteSim`、`LiteNet`、`RoomServer.Runtime/Application.Runtime`、`LiteTesting.Core`、`DisciplineScanner` 同时被 Unity asmdef 与 dotnet csproj 编译。收益是"同一份判定代码在客户端、服务端、dotnet 单测里逐位一致"；代价是 asmdef／csproj 两套引用与产物重定向（`.dotnet/`）必须同步。
2. **生成物单源**：协议来自 `.proto`，表来自 Luban，BuildHash 来自源集摘要，UI 绑定来自 prefab 扫描；生成器统一收在 `scripts/codegen/toolbox.py`，改源不重生成会被门禁或运行期摘要拦下。
3. **规范门禁化**：确定性（禁超越函数／FMA／float 等值比较）、房间内核纯化、适配器边界、数值读口、UI 视觉单一来源、平台特判收敛等，都不靠评审记忆，而由 `DisciplineScanner`（R1～R15）与专项扫描器在 L1/L2 打红。
4. **文档即基础设施**：说明回答"是什么/怎么跑"，规范裁"怎么做才合规"，设计文档裁目标架构，施工进度存证据；文档本身也有门禁（索引孤儿、链接与锚失效、设计与进度混写）。
