## 2. 仓库根

### 2.1 为什么根目录必然"多"

仓库根同时承担四个身份，是工程形态的物理约束：**Unity 工程根**（`Assets/`、`Library/`、`Temp/`、`obj/`、`Logs/`、`UserSettings/` 必须在根，且工程根＝仓库根）、**dotnet 方案根**（`global.json`、`obj/`、`TestResults/`）、**服务器进程 CWD**（本地跑 RoomServer 时工作目录是根，结算 journal `Outbox/` 随之落根）、**git 仓库根**。

治理目标不是"把根清空"，而是**每个条目可辨别、可登记**：新增根级目录必须同批登记本表与 `.gitignore`（带理由注释）。两处职责不同——本表是导航，`.gitignore` 是 git 规则，缺一处即门禁外漂移。

### 3.2 客户端框架

`Runtime/` 一个程序集，按"纯机制—服务—适配"三分：

- `Core/`：DI/Scope/Event/Command/Fsm/Pool/Clock/IO/Logging/Threading/Operations/Errors/Util/Module/Diagnostics/Serialization——零引擎零三方；套件同构 `<套件>/Abstractions/` 自持接口。
- `Services/<服务>/`：Content、Config（只留 `IConfigTableSource`/`ConfigSnapshotService`/`Setting` 等通用机制）、Animation（含播放后端契约/纯数学）、Vfx（通用特效服务内核）、Localization、Settings、Scene、UI、Audio、Entity——**接口由服务自持**；TPS/战斗输入/业务设置/游戏表层/表现已归产品侧，Camera/Input 的纯机制件同样归产品能力模块（`LiteGame/Modules/{Camera,Input}`）。
- `Framework/`：Hosting（+Recovery）、Identity、Diagnostics——宿主生命周期、身份上下文、诊断装配。
- `Adapters/<第三方>/`：Unity（含 `AnimationBackends`）、InputSystem（`PlatformKeyInput`）、Newtonsoft、YooAsset、XLua——实现模块接口，装配在组合根；Cinemachine/Luban 已随游戏扩展迁 LiteGame。
- UI 面关键件：`Modules/UI/UINavigationController.cs`（产品 UI 开关唯一写者）、`UIForm.cs`、`UIModalStack.cs`、`UIOperationQueue.cs`、`Bind/`（`UIBindIndex` 生成物）、`Widgets/`（31 个控件脚本，基类 `UIWidget`）。
- `Editor/`：UI 绑定生成器（`BindMenus.cs`、`EditorTools/BindGenerator.cs`、`Inspectors/`）。

`SimStep.Step` 的固定顺序即确定性契约：**复活 → 输入 → 移动 → 武器 → 射击 → 命令轮次/计分（最多 3 轮）→ 清理 → 帧推进 → 对局裁决**；输入先按 `EntityId` 升序稳定排序，"同帧多请求按玩家升序"由排序保证，不依赖数组原序。客户端预测路径 `resolveCombat=false`：武器消费与开火窗照常，但不产伤害/命中/死亡——那由权威快照与权威反馈面驱动。

## 4. 程序集与双轨

### 4.1 依赖图（箭头 = 依赖，左依赖右）

```
LiteSim（无程序集依赖，noEngineReferences）
  ├→ LiteNet                        协议/会话/传输，只引 LiteSim
  ├→ RoomServer.Runtime             内核（R11 纯化），只引 LiteSim
  │    └→ RoomServer.Application.Runtime   + LiteNet
  ├→ LiteGame.Core                  产品纯契约/纯计算，只引 LiteSim
  │    └→ LiteGame.Modules.Battle   + LiteFramework.{Core,Services,Hosting} + LiteNet + LiteSim + UniTask
  └→ LiteFramework.{Services,Adapters,Hosting} + LiteFramework.Core + LiteNet + LiteCodeGen.Runtime
        └→ LiteGame.Modules.{Composition,UI,Procedure,Meta,Session,Map,Dev}
             │                         （每域一个程序集；域间只经端口，引用集登记在 ClientAsmdefAllowlistTests）
            │                         （共享 8 域命名空间 LiteGame.Modules.<域>；★不引 Adapters.LuaBridge/Dev）
            ├→ LiteGame.Adapters.Unity   引擎后端（工厂注入，模块不反向引用）
```

并行支路：`LiteGame.Adapters.LuaBridge` 依赖各域程序集（实现其端口）+ `LiteFramework.{Core,Services,Adapters,Hosting}` + LiteNet + Luban + UniTask + xLua；`LiteCodeGen.Runtime` 零依赖；`DisciplineScanner` 零依赖。编辑器侧：`LiteFramework.Editor`、`LiteGame.Editor{,.Core,.UITools}`、`LiteSim.Editor`、`DisciplineScanner.Editor`，只在编辑器装配。

### 4.2 双轨规则

- `Assets/{LiteFramework,LiteTesting,RoomServer,Tools/DisciplineScanner}` 与 `Packages/com.litegame.{sim,net,sync}` 下 asmdef 与手写 csproj 编**同一份源码**：dotnet 侧供 `Tests.slnx`/宿主/CI，Unity 侧供编辑器与 Player。手写 csproj 共 **9 个**（`LiteFramework.Core`、`LiteFramework.Async`、`LiteTesting.Core`、`RoomServer.Runtime`、`RoomServer.Application.Runtime`、`DisciplineScanner`、`LiteSim`、`LiteNet`、`LiteSync`），全在 gitignore 白名单里。
- 产物重定向：模块内 `Directory.Build.props` 把 `BaseOutputPath`/`BaseIntermediateOutputPath` 指到 `.dotnet/`——**绝不许在 `Assets/` 下落 `bin/obj`**（Unity 会当插件导入，触发 CS1704）。
- 依赖红线：`LiteSim/LiteNet/RoomServer.*/LiteGame.Core` 的 `noEngineReferences` 为 true，不得引 UnityEngine；`LiteFramework.*` 不得引 `LiteGame.*`；`LiteGame.Modules.*` 不得引 `LiteGame.Adapters.*`、`LiteGame.Adapters.Dev` 与框架 `LiteFramework.Adapters`；框架内 `Services` 不得引 `Adapters`/`Hosting`，`Adapters` 不得引 `Hosting`；`Dev` 之外不得引用服务端程序集。
- 目录搬动同时打穿 asmdef/csproj/扫描目标/收集组/构建器/文档六面，按 `directory-move-sync` 执行。

## 5. 配置表链路

### 5.1 表源（唯一真相）

`Luban/Data/`：**11 张 `#` 前缀业务表**（`#combatnum`、`#movementconfig`、`#entityconfig`、`#itemconfig`、`#weapon`、`#uiform`、`#strategy`、`#contententry`、`#animationprofile`、`#crosshair`、`#ltext`）；**地图** `Map/*.json`（`map_arena01.json`、`map_training_ground.json`，一图一文件）；**3 张元表** `__tables__`/`__beans__`/`__enums__.xlsx`。

注册机制：`#` 前缀文件名自动注册（表名 = `Tb` + 词干）；非 `#` 源经 `Luban/Defines/*.xml` 的 `<table>` 注册（如 `map.xml` 的 `<table name="Tbmap" input="Map" mode="map" .../>`）；`__tables__.xlsx` 的行不参与注册；`Defines/builtin.xml` 提供 vector2/3/4 bean。

### 5.2 生成与产物

`Luban/gen.bat` 只是壳，实际入口 `scripts/codegen/toolbox.py luban`（等价 `python scripts/codegen/toolbox.py luban`）。一次生成四类：

| 产物 | 落点 | 用途 |
|---|---|---|
| C# 读码面 | `Assets/GameData/Generated/`（`Tables.cs`、`Tb*.cs`、行 bean） | 两端共编 |
| 二进制表 | `Assets/GameData/Config/<域>/*.bytes` | **两端同读这一份** |
| Lua 表 | `Assets/LiteGame/Lua/Cfg/` | 客户端脚本读表 |
| Lua 键常量 | `Assets/LiteGame/Modules/Shared/Generated/LuaKeys.g.cs` | `UI.Page_*` 六页常量（命名空间 `LiteGame.Modules.Shared`） |

`Luban/output/` 是遗留旧产物，勿用；`GameData/Config` 的 9 个域（Animation/Combat/Content/Entity/Item/Map/Movement/Strategy/UI）每域自成一 bundle，布局单源 `TableLayout.cs`。

### 5.3 判定面、摘要与闭包

- `Assets/LiteGame/Modules/Config/TableLayout.cs` 是"表清单/领域布局/取数键"单源；`JudgmentDomains = { Combat, Movement, Entity, Item, Map }`——这 5 域整表字节进运行期摘要 `CombatConfigDigest`（`LiteSim/Scripts/Config/`），随 `StartGame.ConfigHash` / `ReconnectResponse.ConfigHash` 下发，客户端复算不等即拒局。UI/Content/Strategy/Animation 属单端热更面，不进摘要。
- BuildHash 闭包（`scripts/codegen/toolbox.py build-hash`）= `Packages/com.litegame.sim/{Scripts,Systems}`、`Packages/com.litegame.net/Core/{Proto,Protocol,Transport/Security}`、`Assets/GameData/Generated`，外加两条源链接件 `SimConfigMapper.cs`、`TableLayout.cs`。**表数值 `.bytes` 不在闭包内**（守卫是运行期摘要）；但 `gen.bat` 会重写 `GameData/Generated`（在闭包内），故改表源后必须重跑 BuildHash。
- 第二目标 `Server/MetaServer/Host/BuildHash.g.cs`（Meta 构建身份）只进启动日志，不参与准入判定。
