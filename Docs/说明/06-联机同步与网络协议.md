## 1. 分层与单源

```text
battle.proto（单源，Assets/LiteNet/Core/Proto/）
  └─ Proto/Generated/Battle.cs（生成物，勿手改）
       └─ Protocol/：PacketCodec（信封）、InputPacker（输入位打包）、
            SnapshotDiffer/SnapshotCodec/SnapshotReassembler（差分/编解码/重组）、
            AoiFilter、CombatEventCodec、WireBudget（载荷预算）
              └─ Transport/：IClientTransport / IRoomTransport（窄端口）
                   └─ KcpTransportClient/Server + Adapters/kcp2k
                        └─ Transport/Security：SecureEnvelope*（预共享密钥信封）
```

- **协议单源**：`battle.proto` 是唯一 schema（protoc 与 Google.Protobuf 3.36.1 生成 `Battle.cs`，产物入库、勿手改）。服务端不可能另写一套消息结构——它引用同一个 `LiteNet` 工程。
- **信封**：线格式 `[1B PacketType][protobuf 载荷]`；`PacketCodec` 是纯函数、零 IO，坏包/未知类型/截断/解析失败一律返回 false，不抛异常。
- **传输**：业务只依赖 `IClientTransport` / `IRoomTransport` 两个窄端口；客户端传输由 `BattleClient` 持有并注入，`RoomClient.Dispose` 不释放传输。
- **BuildHash 覆盖**：`Core/Proto`、`Core/Protocol`、`Transport/Security` 均在闭包内；改线格式必然改哈希，Join 握手据此拒绝两端不一致的组合。

## 2. `PacketType` 全表与通道分工

| 值 | 类型 | 方向 | 通道 |
|---|---|---|---|
| 0 | `None` | —— | 不响应 0x00（过滤随机噪声） |
| 1 / 2 | `Join` / `JoinAck` | C→S / S→C | Reliable |
| 3 | `StartGame` | S→C | Reliable |
| 4 | `Input` | C→S | **Unreliable** |
| 5 | `StateSnapshot` | S→C | **Unreliable** |
| 6 | `MismatchReport` | C→S | **Unreliable** |
| 7 | 已退役 | —— | 保号不重用 |
| 8 | `Leave` | C→S | Reliable |
| 9 / 10 | `ReconnectRequest` / `ReconnectResponse` | C↔S | Reliable |
| 11 | `RestoreComplete` | C→S | Reliable |
| 12 | `MatchEnded` | S→C | Reliable |
| 13 / 14 | `StartMatchRequest` / `StartMatchResponse` | C→S / S→C | Reliable |
| 15 | `OwnerChanged` | S→C | Reliable |
| 16 | `Heartbeat` | 双向 | **Unreliable**（RTT/丢包观测，不参与保活） |
| 17 | `RoomSeats` | S→C | Reliable（房间页玩家列表） |
| 18 | `CombatEvents` | S→C | **Unreliable**（公共战斗事件独立包） |

**信令走可靠、状态与事件走不可靠**是硬分工：可靠通道上的重传会放大延迟，状态面宁可丢一帧也不能排队。连接保活由 kcp2k 内建 Ping/Timeout 承担，应用层 `Heartbeat` 只做观测。

**`CombatEvents` 为何独立成包**：命中/击杀/开火三个窗口曾随每份快照全量携带，实测把快照顶到 **1531B**，超过 KCP 不可靠上限 **1194B**，整份快照被 kcp2k 静默丢弃——现场表现是"打一会儿双方不同步"。独立后状态面尺寸只随实体数变，事件面有自己的预算与降级阶梯，互不挤占。

## 3. 上行输入：16 帧冗余 + 快照锚

客户端不是"每帧发一个输入包"，而是发送**未确认段的冗余窗口**：

- `InputPacker.MaxRedundancy = 16`：包内 `frames[0]` 是当前帧，`frames[i] = frame - i`；
- **窗口下界 = `LastSnapshotFrame + 1`**：只重发服务端可能还没见过的帧；
- **上界 = 环内连续可用帧数**：一旦跳帧就断开，不用陈旧帧冒充连续；
- `ack_snapshot` = 客户端已收的最新快照帧（未收到填 0）；
- `view_frame` = `SimView.RenderFrame`（jitter buffer 正在渲染的那一帧），服务器以它作为回溯补偿目标，并 clamp `[当前-16, 当前]`。

客户端每个渲染帧的驱动次序固定（`BattleContext.Tick`）：**网络泵 → 输入三件（采样入史、同份上行、沿用帧预发，必须先于本地服步进）→ 本地服步进 → 预测推进 → 追帧补发 → 表现视图**；上行提前 `InputLeadFrames = 3` 帧，追帧时多出的逻辑帧逐帧各发一包。

### 3.1 服务端输入闸门

- `ClientInputBatch.MaxFrames = 16`（L1 用例钉死与 `InputPacker.MaxRedundancy` 相等）；`FutureFrameTolerance = 8`；
- 预存用定容环 `PendingInputRing`：`Capacity = 32`（推导 8+16+1=25 ≤ 32），`MaxPlayerCapacity = 32`（单 uint 位图宽度）；
- 校验顺序：形状 → 帧号/按键/槽位 → 同帧去重 → `action_seq` → 数值边界 → 接受记账；接受记账只在全部通过时更新，非法包不烧帧槽/seq 槽；
- `EntityId` 由会话覆写（防伪）；`ack_snapshot` 越界只钳位计数、不丢输入；帧号 ≤ 服务端当前帧判 `StaleFrame` 整包拒绝；
- 同帧重复不再整条丢弃：未消费则后到生效（计数 `DuplicateFrame`）。

**字段映射单源**：`InputPacker.UnpackFrames` 是服务端 `ServerHost.HandleInput` 与离线本地服 `LocalServerTransport.HandleInput` 的唯一映射路径——两端曾各手抄一份逐字段拷贝，`AimPoint` 六字段真实漂移过一次（真服链路断点而本地服照常）。

## 4. 快照链：30Hz、差分、AOI、背压、预算

### 4.1 节拍与差分

- 30Hz 下发（`stride = TickRate/SnapshotHz = 2`）；`_broadcastOrdinal` 先自增再取模，`frame <= 0` 不广播，因此首个广播落在第 2 帧。
- 差分基线 = "最近一次广播出去的状态"，金标是轻量摘要 `EntitySnapshotEntry`（公共字段 + 开火窗 + 尸体期 + 主动作摘要 + 帧号位图），不含私有面/Globals/CustomData；float 按位比较。
- **全量帧触发**：`forceFull` ∪ 活体位图变化 ∪ 60 帧到期 ∪ 某席位 ack 落后 30 帧 ∪ Globals/CustomData/Rng 脏。全量触发是**整帧属性**：本帧对所有客户端都是全量，换来差分基线一义性。
- **关键状态粘滞**：掉血/击杀/死亡/复活/保护/尸体窗变化后 1s（60 帧）内重复下发，抗不可靠快照的丢包。
- **每广播帧算一次差分、每客户端各取一次**：`BeginFrame` 每帧一次（算变化集、判全量、推进基线），`BuildFor` 每客户端一次（纯读，按可见性过滤）。

### 4.2 AOI：只裁增量

- `radius <= 0` 关闭；默认格边 10m、半径 30m、栅格覆盖 ±640m（格数派生，不手写）。
- 邻域取视点格 ±`ceil(radius/cell)` 整格——**可以多发半格，永不漏发**（广播少一个实体 = 客户端静默分叉）。
- 网格外实体按 XZ 距离兜底并计 `OutsideCount`（>0 = 栅格未覆盖地图）；结果按槽位升序（确定性广播序）。
- **只裁增量帧**：全量帧是权威全貌，裁了会让客户端把视野外实体误判为死亡。

### 4.3 重组：持久镜像

`SnapshotReassembler` 的语义是**持久镜像**，不是每包新建：

- 全量帧清活体位图与全部运行态数组（缺席 = 死），增量只覆盖 `SlotDelta` 指到的槽位；
- 槽位应用同时写主动作摘要（`Actions[slot*4+0]`，属公共面）；
- 帧头与分配器版本先于私有面应用（否则 `TryResolve` 定位不到本人槽位，私有面静默不落地）；
- 比赛状态与本人私有面随每份快照应用——即使未触发和解，`OverlayPrivateAndMatch` 仍要刷新；
- 只接受严格新帧（`RoomInbound`：帧号 ≤ `LastSnapshotFrame` 直接丢弃），避免重连后旧包把状态拉回去。

### 4.4 背压与发送记账

| 档 | 动作 | 触发 |
|---|---|---|
| 1 | 抽帧（`ThrottledStride=2`） | 发送队列积压 |
| 2 | AOI 半径收到 15m | 继续积压 |
| 3 | 只保留最近 50% 实体（按视点距离升序） | 严重积压 |

队列上限 `4096B`；水位回落到 40% 以下且持稳 `2000ms` 才逐档恢复（防抖动）。降档只影响该客户端，其余席位不受拖累。

发送记账：`SnapshotLedger` 容量 128（30Hz 下约 4.3s，覆盖 30 帧判据窗口的 4 倍），每条记 `(帧号, 累计字节)`；`AckedBytes` 只能经**验证过的 ACK** 前推——ack 只能确认真实发过的帧，否则慢客户端可伪造 ack 清空水位。

### 4.5 载荷预算：1158B 的由来

`WireBudget` 把上限单源化，全部由真实常量推导：

```text
Mtu            = Kcp.MTU_DEF                     = 1200
UnreliableMax  = KcpPeer.UnreliableMaxMessageSize = 1194
EnvelopeBytes  = 数据头 19 + AEAD 标签 16        = 35
TypeBytes      = PacketCodec 类型字节             = 1
ProtoPayload   = 1194 − 35 − 1                    = 1158
```

快照发送前判 `snapshot.CalculateSize()`：

1. 超预算先裁最远一半实体（**仅增量帧**，全量帧的"缺席判死"不允许裁）；
2. 仍超则**诚实放弃**并计 `SnapshotDropped`——比发一个必被 kcp2k 丢弃的包诚实，也不虚增 `SnapshotSent`。

事件批按预算**留新弃旧**（`CombatEventCodec.PackBatch`），裁掉的条数计 `Trimmed`；单条就超预算的极端情形整批跳过并计 `Skipped`。事件批**不做 AOI**（公共事件全房可见，裁剪会让"视野外的击杀在进入视野时消失"），同一份 payload 发给所有可播席位。

## 5. 和解锚点（协议侧）

| 快照 | 比较 | 不一致时 |
|---|---|---|
| 全量 | `checksum`（公共全图口径） | 权威整帧覆盖 + 重放本地历史 |
| 增量 | `visible_checksum` + `match_checksum` 短路 | 逐槽 `SlotDelta.checksum` 定位，只写差异槽 |
| 超前/环外 | —— | 权威整帧覆盖续跑 |

重放终点截到 `MaxPredictionLead = 6`，保证本地帧号不越过输入冗余窗口。这正是 AOI 不会制造"每快照误和解"的原因：增量快照本就不含全图，不能用全图 checksum 比较。

## 6. KCP 与安全信封

- **KCP 全默认**：两处传输都是 `config ?? new KcpConfig()`，生产装配不覆盖。默认值 `DualMode=true`、收发缓冲各 7MiB、`Mtu=1200`、`NoDelay=true`、`Interval=10ms`、`FastResend=0`、`CongestionWindow=false`、窗口 `WND_SND=32`/`WND_RCV=128`、`Timeout=10s`、`MaxRetransmits=20`。
- **安全信封**（`Transport/Security`）：6B 头 = magic `"LSE1"` + `Version=1` + `kind`；ClientHello 38B、ServerHello 102B（双 nonce + 32B proof）、ClientFinish 38B；数据帧 = 19B 头 + 密文 + 16B tag，序号从 1 起，19B 头进 AAD；可靠位是 1 字节通道号。
- **密钥**：PSK 强制 32B（AES-256-GCM），可从环境变量 `LITENET_SECURE_ENVELOPE_KEY`（base64）读；信封载荷上限缺省 64KiB，可配 1B..1MiB。信封源集在 BuildHash 闭包内——改密文帧形状或握手版本即两端 wire 不兼容。

## 7. BuildHash 与玩法数据摘要

| 项 | 内容 |
|---|---|
| 覆盖 | `LiteSim/{Scripts,Systems}`、`LiteNet/{Proto,Protocol,Transport/Security}`、`GameData/Generated`（Luban 读码面）、共享源链接件 `SimConfigMapper.cs`/`TableLayout.cs` |
| 算法 | 相对路径 Ordinal 排序 → `路径\0内容`（CRLF/CR 归一为 LF）→ SHA-256 → 前 16 个十六进制字符 |
| 当前值 | `48fa22580c3a03c4`（`Assets/LiteNet/Core/Protocol/BuildHash.g.cs`，`--check-shared` 复算 109 个文件通过） |
| 生成 | `python scripts/codegen/gen-build-hash.py`（一次写共享源集与 Meta 构建身份两个常量） |
| 守卫 | 出包门禁 `--check-shared`；发布 Meta 前 `--check` |
| 握手 | `JoinRequest.build_hash` 不等则拒绝进房 |

**表数值已移出闭包**：`Assets/GameData/Config/*.bytes` 的数值改动不触发 BuildHash，而由运行期摘要 `CombatConfigDigest` 守——客户端装载后复算 `StartGame.config_hash`，不等拒局。这样表值可两端热更不出包，而"两端跑着同一份代码、数据却不同源"由数据面守卫兜住。

## 8. 重连与会话状态

`RoomClient` 状态机：`Idle → Connected → SuspectedLost → Reconnecting → Restoring → Connected`；拒绝/版本不符/超时进 `Failed`，**不自动重试**（应用层决策：重 Join 或退出版本提示）。

重连流程：

1. `BeginReconnect` 凭 `JoinAck.reconnect_token` 重拨传输，连接建立后自动发 `ReconnectRequest`（Reliable）；等待预算 `RoomClient.ReconnectTimeoutMs = 10s`；
2. 收到 `ReconnectResponse`（`ok` + 权威快照 + 输入历史 + `seed`/`config_hash`/`build_hash`）后进入 `Restoring`；
3. 版本确认比对 `seed`/`config_hash`/`build_hash`，不一致即 `Failed`；
4. 客户端应用快照与历史后发 `RestoreComplete`（Reliable），服务端放行 `Restoring → Active`；在此之前服务端**抑制该席位的增量广播**，恢复完成时 `RequestFullSnapshot` 把整帧重锚，避免留 `(N_r, B]` 陈旧缝。

票据（服务端 `ReconnectService`）：**一次性**消费即作废、绑 `(playerId, roomId)`；TTL 缺省 5 分钟（`host_tuning.reconnect_ticket_ttl_ms`，范围 1s..24h）、容量 256（`reconnect_capacity`，超限淘汰最老）；票据是 CSPRNG 16B 熵的 base64url 不透明串；客户端在 `MatchEnded` 时清空票据（重连窗口关闭）。`JoinTicketFormat` 与 `JoinFieldLimits` 另管准入票据（HMAC + kid 验签、房间/版本/时效/重放校验）。

## 9. 边界与当前形态

1. **proto 注释滞后**：`InputMessage.frames` 注释仍写"最近 ≤4 帧"，实际冗余 16（以 `InputPacker.MaxRedundancy` 为准）。
2. **KCP 全默认**：没有针对弱网/移动端调参；`FastResend=0`、拥塞窗口关闭，丢包恢复主要靠输入冗余、快照增量与 1s 全量兜底，弱网表现仍是待验证面。
3. **预算只记账不裁决**：实体很多或全量帧超预算时 `SnapshotDropped` 会计数，但不会自动改变房间容量或策略。
4. **无自定义 MTU/分片策略**：MTU 走 kcp2k 默认 1200，分片/重组由 KCP 负责；大快照靠差分、AOI 与预算规避。
5. **事件面不做 AOI**：全房可见且全量重发（30Hz 自带丢包收敛），客户端按 `(kind,a,b,frame)` 去重。
6. **瞄准字段已收敛**：`InputFrame` 的 `aim_x/aim_z/aim_y`（字段 4/5/10）已 `reserved` 不重用，瞄准走 `aim_point`（11-13）单口径。
7. **字段级全表**在 [07 联机全栈参考](07-联机全栈参考.md)；本章只讲结构与机制。

## 10. 本章要点

- 联机层的核心不是"发得快"，而是**把不可靠做得可恢复**：输入冗余、快照差分、全量兜底、AOI 只裁增量、预算超限诚实丢弃。
- 两条锚点必须分清：**全量快照用全图 checksum，增量快照用 visible/match + 逐槽 checksum**；混用会造成每帧误和解。
- 事件面与状态面必须解耦预算：一次字段膨胀就能让整条状态流被静默丢弃。
- BuildHash 守"两端同一份判定代码"，`CombatConfigDigest` 守"两端同一份表数据"，两者分工不要混。
