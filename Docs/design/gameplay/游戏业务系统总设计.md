# 游戏业务系统总设计

> 状态：现行总设计
> 版本：1.2
> 更新日期：2026-09-23
> 适用范围：UnityLib-LiteGame 的战斗、武器、技能、聊天、公会与背包系统
> 维护责任：游戏业务架构
>
> 定位：在现有 `LiteSim.Core + LiteNet + RoomServer + Luban + LiteGame UI` 基础上，给出可直接拆分任务的业务总设计。

## 0. 先定结论

施工顺序采用[框架先行建设与业务接入专项设计](../architecture/框架先行建设与业务接入专项设计.md)：先完成底座、必要通用服务/宿主及五个最小样例，框架准入通过后集中开发本文正式业务。此前可分析业务契约、复用已有灰盒和构建技术原型；不以样例替代武器/技能/库存/结算等真实语义验收。

首版采用 **3D 俯视角、8 人竞技、服务器权威状态同步**：

- 逻辑帧 60Hz，快照 30Hz；继续使用现有 KCP 双通道、protobuf、预测/和解、AOI、服务器回溯命中。
- 战斗、武器运行态、技能/动作运行态、状态效果、局内背包全部属于 `RoomServer/LiteSim`；不写 Mongo，不交给客户端决定。
- 局外背包、装备、货币、结算属于 `ProfileService`；客户端 `FileSys` 只能做缓存。
- 聊天属于 `ChatService`，公会属于 `GuildService`（MVP 可先与 Lobby/Chat 同进程）；两者不进入 Sim、不进入回滚。
- 技能系统在实现层命名为 **`ActionSystem`**：技能是 `category=skill` 的动作，和冲刺、交互共用单主动作槽；不另造一套万能技能框架。
- 跨边界只允许两个业务 DTO：
  1. `MatchStartSnapshot`：Profile/Guild → RoomServer，锁定本局装备、技能、公会加成。
  2. `RewardDelta`：RoomServer → ProfileService，结算奖励一次性回写。

## 1. 现有工程基线与必须先修的前置

### 已有、直接复用

- `LiteSim.Core`：60Hz `SimStep`、固定槽位 `SimWorldState`、`SnapshotRing`、回滚、命令缓冲、帧事件缓冲、hitscan、死亡/伤害基础链路。
- `RoomServer`：权威循环、输入闸门、快照广播、AOI、lag compensation、重连骨架、Ops 指标。
- `LiteNet`：KCP 双通道、protobuf 单源、`RoomClient`、快照差分/重组。
- `Luban`：客户端 binary、服务端 JSON、Lua 生成物和 build hash 链路。
- `LiteGame`：Lua UI 注册、Bridge、UI 控件库、对象池、VFX/Audio 服务。

### 当前缺口

当前没有可直接使用的武器、动作/技能、局内背包、局外库存、聊天、公会业务实现；`demo_tbitem` 只是表链路示例，不应直接当生产库存模型。

### P0 阻塞项：快照平面状态协议必须补齐

> **状态：已交付（Sync-P0，2026-09-22）**——下述四条改造与公共/私有分层编码已全部落地（代码 `3839dac`；[施工记录](../../施工进度/同步契约P0.md)）：定型 WeaponRuntime[2]/ActionRuntime[4]/StatusSlot[4]/MatchBag[12]/MatchState/资源数组、SlotDelta 12..18 公共战斗面、MatchStateDelta/PrivateStateDelta 私有家族、InputFrame 7..9（只增字段号）。原契约保留为验收口径；六大系统的正式业务实现（本文件 §4～§9）仍未开始。

原缺口（历史记录，现已修复）：`SimWorldState.CustomData/Globals` 会参与差分与全量清空，但 `StateSnapshot/SlotDelta` 没有完整承载它们。武器/技能状态若直接塞进 `CustomData`，重连/全量和解会出现“服务端有、客户端被清零”的分叉。因此先做以下改造，再接六大系统：

1. 需要预测、回滚、重连或 HUD 展示的字段，进入明确的定长运行态数组/`SlotDelta`，不能放引用对象或 `Dictionary`。
2. 所有新字段同步修改 `CopyTo`、`SimChecksum`、`SnapshotDiffer`、`SnapshotReassembler`、反射布局测试。
3. `CustomData` 仅保留版本化的状态效果/模组扩展；若它需要跨端恢复，必须增加完整序列化字段。
4. 协议只增字段号，不重编号；迁移前保留 buildHash 严格拒绝混房，目标增加 Protocol/Sim/Gameplay 兼容身份，按热更专项完成双端准入与旧客户端路由后切换。

公共和私有状态分开编码：公共 `SlotDelta` 只发可见实体的姿态、HP、动作摘要；比分/回合放 `MatchStateSnapshot`；弹药、技能 CD、本人局内背包放入 `PrivateStateSnapshot`，只发给对应玩家。重连顺序为“公共全量快照 → 比赛状态 → 本人私有状态 → 输入历史”，避免泄漏其他玩家的库存，也避免依赖当前未承载 `CustomData` 的全量路径。

## 2. 总体拓扑和权威边界

```text
客户端 UI/Lua
   │ 只调用门面，不直接发业务包
   ├─ BattleService ── LiteNet(KCP/protobuf) ──► RoomServer + LiteSim.Core
   │                                             └─ 60Hz Sim / 30Hz Snapshot
   ├─ HTTPS/JSON ──► Gateway(JWT) ──► ProfileService / Lobby / Guild / Chat
   └─ WebSocket ◄──────────────────── Chat/Guild/好友/系统推送

Profile/Guild ── MatchStartSnapshot ──► RoomServer
RoomServer ── RewardDelta ──► ProfileService.Apply（Mongo 事务、幂等）
```

| 领域 | 唯一权威 | 客户端能做什么 | 通道 | 持久化 |
|---|---|---|---|---|
| 位置、血量、伤害、比分、冷却、弹药、局内物品 | RoomServer AuthSim | 提交输入/意图 | KCP + 快照 | 终局归档/被标记时存输入 |
| 武器/动作定义 | Luban 构建产物 | 只读 | build hash | 不进业务库 |
| 局外物品、装备、货币 | ProfileService | 发 UseCase | HTTPS | Mongo + ledger |
| 聊天消息/好友 | ChatService | 发消息、拉历史 | HTTPS + WebSocket | Mongo；在线状态 Redis |
| 公会成员/职位/科技 | GuildService | 按权限发命令 | HTTPS + WebSocket | Mongo + guildLog |
| 表现和 UI | 客户端 View/Lua | 读取快照/事件 | 本地 | 本地缓存 |

严格禁止：客户端上传伤害、弹药、冷却、物品数量、奖励、公会角色；客户端上传的只是输入或请求。

## 3. 统一数据和协议约定

### 3.1 Sim 固定布局

建议新增以下固定布局（具体数组可按现有容量常量实现）：

```text
WeaponRuntime[entity, 2]   = weaponDefId, magAmmo, reserveAmmo,
                             nextFireFrame, reloadEndFrame, state, shotSeq
ActionRuntime[entity, 4]   = actionId, startFrame, phase, castToken,
                             cooldownEnd, charges
StatusSlot[entity, 4]      = effectId, endFrame, param
MatchBag[entity, 12]       = itemDefId, count, quickSlot
MatchState                 = phase, team, score, timer, winner
```

`ActionState` 沿用现有动作设计：`None/Windup/Active/Recovery` 四阶段，单实体一个主动作槽；技能槽的冷却/充能另放固定数组。

### 3.2 输入位和边沿

建议统一 `SimInputFrame.Buttons`：

| 位 | 意图 |
|---:|---|
| 0 | Fire |
| 1 | Reload |
| 2 | SwitchWeapon |
| 3 | Skill1 |
| 4 | Skill2 |
| 5 | Skill3 |
| 6 | Interact/Pickup |
| 7 | UseItem |
| 8 | Dodge/保留 |

`InputFrame` 追加 `selected_weapon_slot`、`target_entity_id`、`action_seq`；服务器按会话重写 `EntityId`，按 `(playerId, frame, action_seq)` 去重。渲染帧只更新待消费意图，逻辑帧只消费一次。

### 3.3 通道选择

- `Move/Aim/Fire/Skill`：继续走不可靠输入包，保留最近 4 帧冗余；结果由服务器可靠事件确认。
- `Pickup/Use/Drop/Reload/Equip`：一次性命令走可靠通道，必须带 `requestId/commandId`。
- `Chat/Guild/Inventory`：HTTPS 请求 + WebSocket 事实推送，不混进 `battle.proto`。
- 服务器事实与客户端请求分开命名：`Command`（请求）、`DomainEvent`（成功事实）、`Snapshot/Push`（同步载荷）。

### 3.4 版本和幂等

- 版本契约遵循[热更与内容发布专项设计](../client/content/热更与内容发布专项设计.md)：现有 buildHash 保留作迁移期严格门禁，目标分离代码/协议/Sim 兼容、玩法数据摘要与表现内容；所有战斗表和 Action 指令进入 GameplayDigest，不能只用编译期常量证明运行时新数据。
- 已有 schema/指令集内的数据允许双端发布，仅新房间采用；每局固定配置快照，重连/回放/归档使用原版本，不靠全局可变 CombatConfig 切换。
- 所有非战斗写操作带 `requestId`；库存带 `expectedRevision`，公会带 `expectedVersion`。
- 所有时间字段用 UTC；错误统一 `{code, messageKey, args}`。

## 4. 战斗系统方案

### 4.1 玩法范围

- 8 人房，单张俯视角地图，3 分钟或击杀目标先到结束。
- 移动、瞄准、射击、命中、伤害、死亡、延迟复活、KDA、比分、重连。
- 首版先做死亡竞赛；团队模式只替换 `Team/ScoreRule`，不改底层系统。

### 4.2 固定系统顺序

```text
Input/边沿
→ Movement + Aim
→ CharacterState/Action 仲裁
→ Weapon 装备/冷却/弹药
→ Action/Skill 请求与阶段推进
→ Hitscan/Projectile 命中
→ Status Tick
→ Damage/Heal/Resource/Inventory 命令轮次
→ Death/Respawn/Score/Loot
→ Cleanup
```

同帧多个请求按 `EntityId` 升序处理；不使用自动扫描、动态事件订阅或不稳定容器遍历。

### 4.3 状态优先级

`死亡 > 状态效果 > 主动作槽 > 移动/瞄准 > 表现过渡`。

当前死亡若直接 `Despawn`，会丢失复活、击杀结算和观战信息；改为 `Dead` 状态保留槽位，记录 `RespawnFrame`，到时在固定出生点复活并加短暂无敌。

### 4.4 客户端预测边界

- 预测：移动、朝向、镜头跟随。
- 不预测：命中、伤害、开火结果、技能判定、拾取、奖励。
- 本地可立即播枪口火焰/按钮反馈，但命中、掉血、击杀必须等服务器事实。

### 4.5 战斗模块落点

```text
Assets/LiteSim/Core/Systems/CharacterStateSystem.cs
Assets/LiteSim/Core/Systems/WeaponSystem.cs
Assets/LiteSim/Core/Systems/ActionSystem.cs
Assets/LiteSim/Core/Systems/StatusSystem.cs
Assets/LiteSim/Core/Systems/MatchInventorySystem.cs
Assets/LiteSim/Core/Systems/RespawnSystem.cs
RoomServer/Match/CombatFacade.cs
RoomServer/Match/SettlementBuilder.cs
```

## 5. 武器系统方案

### 5.1 首版武器

首版只做两把 hitscan 武器，验证完整的射速、弹药、换弹、切枪和多弹丸链路：

| 武器 | 射击模式 | 弹匣 | 射速/伤害初值 | 备注 |
|---|---|---:|---|---|
| 突击步枪 | 自动单弹丸 | 30 | 600 RPM / 20 | 稳定中距离 |
| 霰弹枪 | 单次 8 弹丸 | 8 | 75 RPM / 8×弹丸 | 验证多 pellet/spread |

数值只是首轮可调值，最终以 Luban 表为准；投射物、近战、附件、耐久、词条后置。

### 5.2 Luban 表和运行态

`tb_weapon`：

```text
weapon_id, archetype, slot, fire_mode, damage, rpm, magazine_size,
reload_frames, range, spread, pellets, ammo_type, projectile_def_id,
switch_frames, vfx, sfx
```

`WeaponRuntime`：

```text
weaponDefId, slot, magAmmo, reserveAmmo,
nextFireFrame, reloadEndFrame, equipEndFrame, state, shotSeq
```

所有射速/换弹时间统一转换为整数帧：`fireInterval = ceil(60 / rpm)`；禁止用浮点倒计时。

### 5.3 处理流程

1. `InputSystem` 检测 Fire/Reload/Switch 边沿。
2. `WeaponSystem` 校验当前槽位、动作槽、冷却、弹药、换弹状态。
3. 合法 Fire 生成 `Fire` 命令；扣弹、推进 `nextFireFrame`，服务器执行回溯 hitscan。
4. 命中生成 `Damage` 命令；结果进入 `FrameEvent` 和可靠 `CombatEvent`。
5. Reload 只在服务器确认后进入 `Reloading`；死亡、受击打断规则写入表。

### 5.4 安全和验收

- 服务器拒绝超频、负弹药、伪造武器槽、重复 `action_seq`、越界射程和非法目标。
- 同 seed 重放，射击结果、弹药和伤害完全一致。
- 150ms 延迟下命中使用现有 `LagCompensator`，回溯窗口由 `SimConfig.LagCompHistory` 控制。
- 重复 Fire 包不得造成重复伤害；换弹中途取消、死亡边界各有测试。

## 6. 技能系统方案（实现名：ActionSystem）

### 6.1 设计原则

- 技能、冲刺、交互读条共用 `ActionState`；移动、瞄准、连发射击不进入动作时序，只通过占槽仲裁。
- 一个实体同时只有一个主动作；中断规则、优先级、可否移动由表驱动。
- Sim 只执行有界效果指令，不执行任意 Lua、Timeline 脚本或 MonoBehaviour。
- 技能请求不预测；确认后 View 按 `FrameEvent/ActionState` 播放表现。

### 6.2 数据链路

- `tb_action`：动作类别、时间轴导出物、判定轨、表现轨、动画轨、事件轨、中断掩码、优先级。
- `tb_action_num`：前摇/生效/后摇、冷却、资源消耗、伤害、半径、持续时间、位移距离、护盾值。
- Unity Timeline 是编辑入口；导出时 `frame = round(seconds * 60)`，误差必须 `< 1e-4`；对局中禁止热重载。
- 导出器还要校验帧单调且非负、判定轨引用的 effect 存在、半径/射程合法、中断规则无自环、资源消耗非负，并写入 `contentHash`。

### 6.3 首版三个技能

| 技能 | 初始建议值 | 判定 |
|---|---|---|
| 冲刺 Dash | 12 帧位移，4m，冷却 180 帧，前 12 帧无敌 | 位移/碰撞由 Sim 执行，可被死亡打断 |
| 范围爆破 AOE | 前摇 30 帧，半径 4m，伤害 40，冷却 300 帧 | 生效帧生成 Area/Damage 命令 |
| 能量护盾 Shield | 前摇 12 帧，护盾 60，持续 180 帧，冷却 360 帧 | StatusSlot 记录结束帧和剩余护盾 |

### 6.4 动作仲裁

`ActionSlots.TryOccupy(entity, actionId)` 统一处理：冲刺是否打断射击、交互移动是否取消、受击是否打断技能。同帧多个请求按优先级再按 `EntityId` 决定，结果进入 `ActionAccepted/ActionRejected`。

连发射击仍由 `WeaponSystem` 每帧处理，不占用主动作槽；若换弹/切枪需要前后摇，则以 `category=reload/equip` 的动作进入同一仲裁，避免把高频 Fire 变成动作系统的重负担。

### 6.5 验收

- 三技能的前摇、判定、持续、冷却、消耗两端一致。
- 回滚/重连不会重复伤害、重复消耗或重复播放关键表现。
- CD UI 与服务器快照误差不超过 1 逻辑帧。

## 7. 背包系统方案：局内和局外完全分离

### 7.1 局内背包（MatchBag）

**目标**：服务一局内的弹药、拾取物和临时消耗品，不污染账号库存。

- 固定 12 格，4 个快捷栏；每个槽位 `itemDefId + count`，不放对象引用。
- 首版物品：轻/重弹药、治疗包、护盾电池、临时增益；不做交易、掉落表编辑器和复杂随机词条。
- `Pickup/Use/Drop` 是服务器可靠命令，校验距离、归属、数量、冷却和使用条件后写入 `SimCommand`。
- 私有背包内容只发给本人；地图上的可见拾取实体按 AOI 广播。
- 状态随快照、回滚、重连恢复；对局结束只生成 `RewardDelta`，不逐帧写库。

建议接口：

```text
RequestPickup(requestId, pickupEntityId)
RequestUseItem(requestId, quickSlot)
RequestDrop(requestId, slot, count)
```

### 7.2 局外背包（Profile Inventory）

静态定义使用 `tb_item`：`id/type/stack_max/use_type/equip_slot/rarity/value/icon`。

Mongo 文档：

```text
inventory {
  playerId,
  revision,
  slots: [{slot, itemUid, defId, qty, durability, bind, expireAt}],
  currency: {gold, premium}
}

loadout {
  playerId,
  revision,
  weaponUids[2],
  actionIds[3],
  consumableUids[4]
}
```

首版 40 格；支持堆叠、移动、拆分、使用、装备、卸下、丢弃。所有写入走一个 UseCase：

```text
POST /inventory/command
{ operationId, expectedRevision, command, clientNonce }
```

服务端 Mongo 事务内校验数量/绑定/槽位，成功后返回新 `revision + delta`；版本冲突返回稳定错误码，客户端重新拉取，禁止客户端自行合并。

### 7.3 进局和结算

1. ProfileService 读取库存/装备，生成不可变 `LoadoutSnapshot`。
2. ProfileService 可先创建带过期时间的 `MatchLoadoutReservation`，锁定本局会消耗的物品；RoomServer 校验 profileRevision 与房间版本契约（迁移期含 buildHash，目标含 Protocol/Sim/Gameplay 身份），由快照初始化 `WeaponRuntime/ActionRuntime/MatchBag`。
3. 对局中任何变化只存在 AuthSim。
4. 结束后生成 `RewardDelta{settlementId, matchId, playerId, exp, currency, items, consumptionDelta}`。
5. `POST /internal/profile/apply` 以 `(playerId, matchId)` 唯一 ledger 幂等写入；请求带 `serverInstanceId/finalChecksum/resultHash`，仅接受 RoomServer 服务凭证；重复请求返回原结果，不重复发奖；未使用的预留物品按结算策略释放/退回。

## 8. 聊天系统方案

### 8.1 频道

统一支持 `World / Room / Team / Guild / Whisper / System`；首版开放 `Room + Team + Guild + System`，世界频道和私聊在限流、举报链路完成后开启。

聊天永不进入 Sim、快照或回滚；战斗快捷语若需要低延迟，只做 `InputFrame` 中的枚举/位，不复用聊天文本通道。

### 8.2 服务和数据

`ChatService`（MVP 可与 Lobby 同进程）：

```text
chatMessage {
  messageId, channelType, channelId, serverSeq,
  senderId, nicknameSnapshot, text, createdAtUtc,
  moderationFlags
}
```

- HTTP：发送、历史分页、拉取未读。
- WebSocket：实时推送、系统公告、好友/公会变化。
- 服务端生成 sender/nickname/time/seq，客户端不能自报。
- 文本先做 Unicode 规范化，再按 UTF-8 字节数限制 ≤ 200；默认 5 条/10 秒；敏感词、禁言、黑名单、频道 ACL 均在服务端执行。
- 客户端重连携带 `lastSeq`，服务端按频道补推，保证不丢序、不重复显示。

ChatService 只依赖带 TTL 的 `IGuildChannelAuthorizer` 缓存，不反向依赖 GuildService；公会成员变化通过 `GuildMemberChanged` 使频道权限缓存失效。

### 8.3 客户端落点

新增 `Bridge.chat` 门面，Lua 负责频道页、消息列表和输入框；C# 负责连接、序号、重连和脏位更新。复用 `VirtualList/SimpleList/InputField/Toast`，不让 UI 直接拿 `INetworkService`。

## 9. 公会系统方案

### 9.1 MVP 能力

创建、搜索、申请、邀请、审批、拒绝、成员列表、退出、踢人、任命官员、会长转让、公告、公会频道；默认上限 50 人。

科技树、捐献、商店、跨服战后置。若加入科技，科技效果只在下一局生成 `GuildBonusSnapshot`，不允许在对局中动态改属性。

### 9.2 数据模型

```text
guild       {guildId, name, icon, notice, level, capacity, leaderId, version}
guildMember {guildId, playerId, role, contribution, joinedAt, lastSeen}
guildApply  {guildId, playerId, message, status, createdAt}
guildInvite {guildId, playerId, inviterId, expireAt}
guildLog    {guildId, seq, operatorId, op, targetId, createdAt, payload}
```

角色：`Leader / Officer / Member`。每次写操作带 `requestId + expectedGuildVersion`，使用 Mongo CAS/事务；同时写不可变 `guildLog`。并发审批、踢人、转让时版本不匹配直接失败，不静默覆盖。

### 9.3 接口

```text
POST /guilds
POST /guilds/{id}/apply
POST /guilds/{id}/approve
POST /guilds/{id}/invite
POST /guilds/{id}/leave|kick|role|transfer
GET  /guilds/{id}
GET  /guilds/{id}/log
```

GuildService 只向房间提供 `guildId/role/bonusSnapshot`；不把完整成员列表或公会文档塞进战斗快照。

## 10. 客户端 UI 和 Bridge 约定

新增四个玩法门面：

```text
Bridge.battle   // 快照、事件、请求开火/技能/拾取
Bridge.bag      // 局内/局外背包 ViewModel 和 UseCase
Bridge.chat     // 频道、发送、历史、重连补推
Bridge.guild    // 公会视图、命令、版本冲突
```

- C# 规则和网络门面；Lua 只做内容编排和界面逻辑。
- UI 只读 `ViewModel`，不直接改 Sim、Mongo 或网络包。
- 战斗 HUD：HP、弹药、换弹进度、技能冷却、护盾、击杀提示、延迟/丢包。
- 背包：`VirtualList + TabGroup + StateButton + Dialog`。
- 聊天：`InputField + VirtualList + Toast`。
- 公会：`VirtualList + TabGroup + Dialog + RedDot`。

8 人 HUD 的弹药、技能 CD、血条和击杀提示由 C# `HudModel` 聚合脏位后直驱控件；Lua 不做逐帧调用。背包、聊天、公会列表采用批量刷新，避免监听累积和高频跨语言 payload。

## 11. 里程碑和工期

按“两名客户端 + 两名服务端”估算；单人执行约 6–8 周。

| 阶段 | 日历 | 交付和闸门 |
|---|---:|---|
| S0 契约冻结 | 2 天 | 表 schema、协议字段、错误码、事件名、幂等约定；修复快照平面状态缺口 |
| P1 战斗 + 武器 | 5 天 | 2–4 人灰盒，步枪/霰弹、弹药、换弹、死亡复活、回溯命中 |
| P2 Action/技能 | 5 天 | Timeline 导出、冲刺/AOE/护盾、单主动作槽、冷却/中断 |
| P3 局内背包 | 3 天 | 12 格、拾取/使用/丢弃、重连恢复、RewardDelta |
| P4 Profile/局外背包 | 5 天 | 游客登录、40 格库存、Loadout、Mongo 事务和结算幂等 |
| P5 Lobby/房间 | 3 天 | 房间创建/加入、token、8 人房、房间状态 |
| P6 公会 | 4 天 | CRUD、申请审批、角色、公告、CAS、guild chat |
| P7 聊天 | 4 天 | WS、房间/队伍/公会/系统频道、过滤、限频、补推 |
| P8 集成压测 | 5 天 | 8 人 5 分钟、150ms/10% 丢包、重连、重复请求、监控/审计 |

依赖关系：`P1 → P2/P3 → P4 → P5`；`P6/P7` 在 P4 身份和 WS 契约完成后可并行。

## 12. 验收标准

### 规则和联机

- 8 人完整对局 3 分钟无 tick stall、死锁或状态泄漏。
- 10% 丢包、150ms RTT 下最终收敛，和解率目标 ≥99%；重连能在 5 秒内恢复权威快照、动作、弹药和局内背包。
- 客户端篡改伤害/冷却/物品/公会角色无效；服务器下一快照可纠正客户端。
- 服务器/客户端规则测试覆盖 Fire cadence、弹药、换弹、Action 帧、冷却、中断、复活。
- 拾取/使用/掉落回滚后 checksum 一致；同一库存 `requestId` 重试 100 次只执行一次；重复 Fire 不重复伤害。

### 数据和社交

- 库存移动/拆分/装备并发 100 次无丢失更新；重复 `operationId` 不重复扣除或发奖。
- 结算 ledger 唯一键 `(playerId, matchId)` 生效，Profile 超时可安全重试。
- Chat p95 推送目标 < 500ms（同区）；过滤、限频、权限和 `lastSeq` 补推可验证。
- 公会所有写操作通过角色矩阵和 version CAS；每次变更可在 `guildLog` 追溯。

### 工程质量

- Luban 双端玩法语义与 Gameplay 身份一致，文件各自通过完整性验证；迁移期 buildHash 仍严格检查。Timeline 非整数帧导出失败。
- L1 纯规则测试、RoomServer 无头测试、协议 round-trip、Mongo 集成测试、Unity L2 UI 测试全部纳入 CI。
- 关键 Ops：tick、快照大小/频率、丢包、和解率、回溯、发送队列、Profile 幂等命中、Chat 限流、公会权限拒绝。

## 13. 明确后置项

首版不做：语音、交易/拍卖、装备随机词条、武器附件/耐久、复杂投射物/近战、技能树、跨服战、公会商店、世界频道运营活动、自动匹配 MMR、复杂大世界 AOI。

这些功能保留表字段和服务接口扩展位，但不进入当前 Sim、协议和验收范围，避免把首版战斗闭环拖成“大一统系统”。
