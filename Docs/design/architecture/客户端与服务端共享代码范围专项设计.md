## 0. 文档地位与冲突规则

### 0.1 本文裁决什么

**共享范围**：哪些源码允许被客户端与服务端共同编译；每一档共享各自的**同源义务**是什么；依赖方向规则；新代码划入共享范围的判据与准入流程。

### 0.2 本文不裁决什么

| 主题 | 归属 |
|---|---|
| 哪些计算必须两端逐位一致（确定性纪律） | 《状态同步专项设计》 |
| 服务端内部分层与纯化禁令的**动机** | 《商业级通用服务端框架总设计》§7/§8 |

| **在哪改、改完跑什么** | 《开发导航/修改指南》《开发导航/代码地图》 |

本文与上述文档冲突时，**裁定范围归本文，其余主题归原文档**。本文不复制它们的第二份定义。

### 0.3 为什么现在需要这份文档

**Current（2026-10-01 实测）**：共享范围是施工长出来的，不是裁出来的。

- "共享"在仓库里同时指三件不同的事——"能编译"、"必须逐位一致"、"谁可以依赖谁"——三者**互不相等**，且差集从未被裁决；
- 《框架先行建设与业务接入专项设计》与《客户端总设计》全文 **"同构" 0 次命中、"两端共用" 0 次命中**；"双端"仅 4 处，**全部指玩法数据的发布维度，不指代码**；
- 《服务端总设计》《Meta 专项》《状态同步》《帧同步备选》《联机同步策略选型》五篇中 **"双轨""同一份源码"词面 0 次命中**；
- 唯一点名共享的条文是《服务端总设计》§7："`LiteSim.Core` 和 protobuf 生成链不随 Host 重构迁移"——**只点名两项**，不含已共编的 `RoomServer.Runtime` 与 `LiteFramework.Core`；
- "双轨共编"这个说法目前只活在 `Docs/开发导航/代码地图.md`（导航层，按《项目说明/06》§2 定义**只答"在哪、去哪改"，不写设计动机**，不是目标形态的权威）。

**结果**：共享集合的准入靠人工纪律，已产生 10 处越界与漂移（§7）；其中两处红字级后果（Player 构建含服务端程序集、S0 源集守卫半失效）与其余结构性问题**已于 2026-10-01 批①～批④ 全部收口**——§8.1 的 G1–G5 五条守卫全部落成可执行用例。

## 1. 三个判据必须分开问

这是本文立论的基础。仓库长期用"双轨共编"一个词覆盖三件事，于是三个问题被当成一个：

| 判据 | 问的是 | 决定 | 守不守得住 |
|---|---|---|---|
| **① 能编译吗** | 零引擎依赖？第三方依赖两端可对齐？ | 文件放哪、哪个程序集 | **编译器守** |
| **② 错了会被抓住吗** | 两端行为分叉时，多久暴露？ | 能不能改坏 | **握手守 / 用例守 / 没守** |
| **③ 谁可以依赖谁** | ProjectReference / asmdef references | 谁能认识谁 | **编译器守** |

判据 ①②③ 各自独立。当前仓库的事实是：

- 满足 ① 的集合（**177 个 .cs**）远大于满足 ② 中"硬守"的集合（**47 个 .cs + 玩法表**）——中间 130 个文件曾长期**无守卫共享**（批③ G4 已为其中真会静默漂移的两类点补上契约用例）；
- 判据 ③ 的守卫在编译期是硬的，但**方向本身从未被裁决**，于是出现一条进 Player 的客户端→服务端引用（§7-1，已修）。

**本文据此把"共享"拆成五档。**

## 3. 方向规则

> **规则 D1（服务端产线）**：`RoomServer.exe` / `MetaServer.exe` **只准**依赖 S0 / S1 / S2。不得依赖 S3 / S4。
>
> **规则 D2（客户端）**：客户端**可以**依赖 S0–S3，但对 **S1** 的依赖必须在装配处分档声明——它是「**调试宿主**」关系，不是对等共享。
>
> **规则 D3（同源方向）**：S0 内**禁止**任何方向的分叉实现（"不引入第二套消息定义"已由《联机同步策略选型》§2 规定，此处承接）。

**D1 的实测依据**：`RoomServer.csproj` 与 `MetaServer.csproj` 均**零** `LiteFramework` / `LiteGame` 引用（grep 为空）——规则 D1 是**已被遵守的既成事实**，本文只是把它写成规则。

**D2 的实测依据**：`LocalServerTransport` 让客户端在**进程内**跑真 `RoomRuntime` + `SnapshotPipeline` 做离线开发——这是 S1 的正确用法。2026-10-01 批② 起，该依赖**只出现在具名程序集** `LiteGame.DevLocalServer`（D2 登记表唯一成员），由 L1 用例 `纪律_D2_…` 把守；业务程序集（`LiteClient.Runtime`/`LiteGame.App`）不再引服务端程序集。

### 4.3 准入流程（新代码要划入共享范围时）

```
问 ① 零引擎依赖吗？
  ├─ 否 → S4（客户端专属），结束
  └─ 是 ↓
问 ② 错了会被握手抓住吗？（两端行为必须逐位一致）
  ├─ 是 → S0：进 gen-build-hash.py 的 TARGETS；改后必跑生成器
  └─ 否 ↓
问 ③ 两端都要"跑"这套机制吗？
  ├─ 是 → S1：asmdef noEngineReferences + 第三方两端同版本
  └─ 否 ↓
问 ④ 只有形状共享（接口/DTO），两端各自实现吗？
  ├─ 是 → S2：零第三方实现依赖；实现由组合根显式接线
  └─ 否 → S3（只服务验证）或 S4
```

**配套动作（三件，缺一不可）**——这是 2026-10-01 诊断域批实测出的教训：

1. **asmdef**：`noEngineReferences: true`（新增目录时）
2. **csproj**：`<Compile Include="新目录/**/*.cs" />`（`LiteNet.csproj` 是逐目录列举，不是整树 glob）
3. **`.gitignore` 白名单**：`!Assets/<模块>/<新目录>/*.csproj`（若新目录自带 csproj）
4. 若新目录有 dotnet 产物 → **同目录 `Directory.Build.props`**（重定向到 `.dotnet/`）

> **仓库无根级 `Directory.Build.props`**——重定向是**逐目录**的，新增共享目录必须自带，否则 `obj/` 里的生成 `.cs` 会被 Unity 当源码导入（CS1704/CS0579）。

## 5. 同源义务（共享不成立的两条路）

### 5.1 路径参与身份

多份产物的**路径**进哈希（Luban 表路径改动即 hash 变，2026-09-26 已实测）。共享方向的路径挪动必须同步：`ScanTargets.cs`、YooAsset 收集组、`Tests.slnx`/csproj、`.gitignore` 白名单、构建器路径、`gen-build-hash.py`。

### 5.2 第三方依赖"同版本异构"

同一份源码，两端依赖来源不同——这是共享最脆的一环：

| 依赖 | Unity 侧 | dotnet 侧 | 对齐方式 |
|---|---|---|---|
| Google.Protobuf | `Assets/LiteNet/Vendor/Google.Protobuf`（DLL） | NuGet `3.36.1` | **人工对齐版本号**（注释明写"同一版本号"） |
| UniTask | `Assets/Plugins/UniTask` 2.5.11（源码） | NuGet `UniTask` 2.5.11 | 人工对齐 |
| kcp2k | `Vendor/kcp2k`（源码） | 同左（源码） | 无差异 |

**规则**：任一版本号变动，必须同批核对两端；**S0 的第三方依赖变动另须重跑 BuildHash**。

## 6. 口径边界（防止误用）

| 说法 | 边界 |
|---|---|
| "R 是共享的" | 指**能编译**（S1），**不**指结果必须逐位一致。`RoomServer.Runtime` 的改动**不**触发 BuildHash |
| "S0 以外都不保证同源" | 没错，但**不等于可以随意分叉**——S1/S2 仍受所属纯度红线与用例管辖（R11 等） |
| "S1 共编所以不会分叉" | **错**。两端依赖注入、线程模型、时钟来源都不同；S1 只保证**代码**相同 |
| "共编 = 同一个 DLL" | **错**。两端各编一份（Unity 侧 asmdef / dotnet 侧 csproj），**依赖解释不同**。BuildHash 常量的同值是"同目录双编"的副产品，证明的是源码相同，不是二进制相同 |
