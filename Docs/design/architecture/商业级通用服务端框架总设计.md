## 2. 目标、范围与非目标

### 2.1 目标

重构后的框架应满足：

1. **正确**：60Hz 时间轴、多人输入、快照 ACK、重连和结算具有唯一且可测试的语义。
2. **安全**：所有外部数据均不可信；身份、长度、频率、数值、权限和重放窗口在边界校验。
3. **通用**：生命周期、会话、安全、房间调度、可观测、持久化契约和测试夹具可跨玩法复用。
4. **可扩展**：单进程可承载多个房间，并能通过增加实例水平扩展。
5. **可运营**：可配置、可观测、可排空、可灰度、可回滚、可归档、可审计。
6. **可验证**：单元、契约、集成、网络损伤、长稳、容量和发布验证形成固定门禁。

### 2.2 通用框架负责什么

以下能力属于通用服务端框架：

- Generic Host、配置和依赖装配。
- Transport 适配、连接信息、包限额和安全信封。
- Join Ticket、Session、Reconnect、Rate Limit、Replay Window。
- Match 生命周期、Room Registry、Worker 调度和排空。
- 结构化日志、Metrics、Tracing、健康检查和故障上下文。
- Match Archive、Settlement Outbox、幂等和服务间调用契约。
- 测试时钟、假传输、网络损伤、进程夹具和容量基准。

以下能力保持项目/玩法特定，不强行做成万能插件：

- 武器、技能、状态、伤害、复活、地图和掉落规则。
- Sim 固定布局、系统执行顺序和玩法 checksum。
- 具体快照字段、AOI 规则和奖励计算。
- UI、Lua、表现、VFX 和客户端输入采集。

通用化目标是稳定边界和运行机制，不是建立运行时动态插件市场。首版采用编译期装配和显式接口。

### 2.3 非目标

- 不在第一阶段全面拆微服务。
- 不把每个房间绑定一条独立线程。
- 不让 RoomRuntime 直接访问 Mongo、Redis、HTTP、Console 或系统墙钟。
- 不以 Redis/MQ/Kubernetes 的数量衡量商业化程度。
- 不在正确性问题未解决前扩展武器、技能、聊天或公会功能。

## 3. 已有资产与保留决策

以下基础保留并继续演进，不做推倒重写：

- `LiteSim.Core` 保持纯 C#、固定布局、固定系统顺序和确定性边界。
- `LiteNet` 保持 protobuf 协议单源和 Transport 适配层。
- Room 内权威 Sim 保持单线程执行，AOI 只影响广播，不影响判定。
- 客户端预测、服务器权威、快照和解、远端插值和服务器回溯命中继续作为默认同步范式。
- Profile/Guild 向 RoomServer 提供不可变 `MatchStartSnapshot`；RoomServer 只输出 `RewardDelta`，不在对局中查询永久数据。
- Meta 服务先采用模块化单体；只有容量、故障域或团队所有权提供证据时才拆分。
- 测试继续沿用 L0～L4 分层和 `scripts/test.ps1` 统一入口。

## 5. 上线前 P0 正确性与安全项

### P0-1 精确逻辑时间轴

当前 `ServerLoop.TickPeriodMs = 1000 / 60` 实际形成 16ms 周期，即 62.5Hz。追赶逻辑只处理执行落后，不能补偿错误的目标时间轴。

目标实现：

- Deadline 使用 `Stopwatch.GetTimestamp()` 与 `Stopwatch.Frequency` 计算。
- 第 n 帧目标时间使用整数有理数：`start + floor(n * frequency / tickRate)`。
- 把 `IMonotonicClock`、`IDelayStrategy` 注入调度器，L1 使用虚拟时钟，无真实 Sleep。
- 追赶设置每轮最大步数；超过预算记录 dropped debt，并触发过载指标。
- `RoomRuntime.Step()` 始终使用固定 `dt=1/60`，不接收 wall-clock delta。

验收：虚拟时间 10 分钟恰好调度 36,000 帧；30/60/120Hz 参数化测试均无累计漂移。

### P0-2 多玩家同帧输入隔离

当前 `InputGate` 的 pending 表只以 frame 为键，第二名玩家会覆盖第一名玩家。

目标实现：

- 使用 `PendingInputRing`，容量覆盖未来容忍窗、冗余窗和安全余量。
- 每个 ring slot 保存 `frameNumber`、`SimInputFrame[playerCapacity]` 和 valid bitset。
- 去重状态按 player 维护，消费按 `(frame, playerId)` 读取并清位。
- slot 被新 frame 复用时必须完整清理，禁止陈旧输入泄漏。
- playerId、frame、actionSeq 全部先验证后索引。

验收：2～8 名玩家同帧提交不同 Move/Fire，所有输入各自只消费一次，不串位、不覆盖。

### P0-3 数值和协议边界

目标实现：

- `MoveX/MoveZ/AimX/AimZ` 必须为有限值。
- Move 分量与长度遵循配置上限；Aim 必须非零并规范化或按协议规定量化。
- 所有字符串限制 UTF-8 字节数；repeated 字段限制元素数；包体在 protobuf 解析前限制长度。
- 未知 packet type、截断、超长、非法枚举、非法按钮和越界 seq 统一拒绝并计数。
- 拒绝日志不回显 token、完整 payload 或个人数据。

验收：NaN、正负 Infinity、超大数、超长 token、超大 repeated 和随机字节模糊测试均不能污染 Sim、分配无界内存或终止进程。

### P0-4 ACK 与背压可信化

目标实现：

- 每 Session 维护 `LastSentSnapshotSeq/Frame`、`LastAcceptedAckSeq` 和有界发送 ledger。
- 只接受 `lastAck <= ack <= lastSent` 的单调 ACK；未来、回退和不存在的 ACK 计数并忽略。
- ACK 到达只释放 ledger 中已确认序号之前的累计字节，不能直接令 `AckedBytes=SendQueueBytes`。
- 优先从 Transport 暴露真实 pending bytes；应用 ledger 作为协议层补充，不伪装成 KCP 内部队列真相。
- `SnapshotDiffer.NeedsFull` 只读取经过验证的快照 ACK。

### P0-5 稳定版本和配置摘要

协议中明确区分：

| 字段 | 语义 |
| --- | --- |
| `protocolVersion` | protobuf/信封兼容版本 |
| `simVersion` | Sim 布局和系统语义版本 |
| `buildHash` | 代码和协议构建摘要 |
| `configHash` | 规范化战斗配置摘要 |
| `contentVersion` | 可热更内容版本 |

上表是目标语义，不表示现有协议已包含全部字段；当前 buildHash 仍覆盖表产物，configHash 已有规范化但为截短值。迁移与版本发布统一遵循[热更与内容发布专项设计](../client/content/热更与内容发布专项设计.md)：先补字段/协商、Join/重连/归档与双端测试，再开放代码、玩法数据和表现内容的独立发布，不能直接放宽旧检查。

文件完整性对原始字节计算完整 SHA-256，binary 不做换行归一化；客户端 binary 与服务端 JSON 的玩法一致性对规范化解析数据计算，规则固定 schema、类型、排序、编码和浮点表示。不得用 GetHashCode、随机种子或目录自然顺序。

房间创建时固定不可变玩法配置，替代进程全局可变 CombatConfig；已有 schema/指令集内的数据发布只供新房间采用，旧房间、重连与回放继续旧快照。服务端部署、客户端可用内容、版本准入与旧房间排空按热更专项协调。

### P0-6 身份、票据与重放保护

- Client 先通过 HTTPS 登录和 Lobby 获取短期 Join Ticket。
- Join Ticket 至少绑定 `playerId/accountId`、`roomId/matchId`、过期时间、nonce、build/sim 版本和 audience。
- RoomServer 使用本地公钥或共享验证器验签；对局热路径不查询 Profile 数据库。
- Reconnect Ticket 使用密码学安全随机数生成、一次性消费、短期有效并绑定 Match/Player。
- KCP cookie 只解决连接探测问题，不等同于业务身份、加密或完整性保护。
- 公网部署必须采用成熟的安全传输或安全信封，提供机密性、完整性、序号和重放窗口；不得自创密码算法。

## 6. 目标总体架构

```text
Client
├─ HTTPS/WebSocket ──► Gateway / MetaServer
│                      ├─ Auth
│                      ├─ Lobby
│                      ├─ Profile + Ledger
│                      └─ 后置：Chat / Guild
│
└─ Secure KCP/UDP ───► RoomServer.Host
                       ├─ Transport Adapter
                       ├─ Connection Security / Rate Limit
                       ├─ Session Gateway / Ack Tracker / Reconnect
                       ├─ Match Coordinator / Room Registry
                       ├─ Room Worker Pool
                       │  └─ RoomActor
                       │     └─ RoomRuntime + LiteSim.Core
                       ├─ Settlement Outbox / Match Archive
                       └─ Logging / Metrics / Health / Tracing
```

核心数据流：

```text
Socket
→ 长度与信封校验
→ 身份/频率/重放校验
→ Session 解析
→ 按 roomId 路由到有界 Worker Mailbox
→ RoomActor 单线程处理
→ RoomRuntime.Step
→ OutboundMessage
→ 每 Session 编码/背压
→ Transport Send
```

数据库、HTTP、归档写入和日志输出不得阻塞 Room Worker。需要持久化的结果先写入有界 Outbox，再由后台服务重试发送。

## 7. 模块边界与建议工程结构

最终建议结构：

```text
Server/
├─ GameServer.Contracts/              协议版本、错误码、服务间 DTO
├─ RoomServer.Runtime/                纯 RoomRuntime、输入环、快照与生命周期内核
├─ RoomServer.Application/            MatchCoordinator、Session 用例、Worker 路由
├─ RoomServer.Transport.Abstractions/ Transport 端口、连接元数据、队列指标
├─ RoomServer.Transport.Kcp/          kcp2k 适配与安全接入
├─ RoomServer.Infrastructure/         日志、指标、归档、Outbox 实现
├─ RoomServer.Host/                   Generic Host、配置、健康检查、装配
└─ MetaServer.Host/                   Auth/Lobby/Profile 模块化单体
```

不要直接进行目录大搬迁。过渡顺序为：

1. 先在现有 `RoomServer` 工程内按 namespace 和文件夹建立边界。
2. 用 characterization tests 固定行为，消除静态单例、系统时钟和直接发送委托。
3. 当依赖方向稳定后再拆 csproj；每次只拆一个边界。
4. `LiteSim.Core` 和 protobuf 生成链不随 Host 重构迁移。

建议最小接口：

```csharp
public interface IMonotonicClock { long Timestamp { get; } long Frequency { get; } }
public interface IJoinTicketValidator { JoinPrincipal Validate(string ticket, JoinContext context); }
public interface IRoomTransport { /* send/pump + endpoint/queue metadata */ }
public interface IMatchArchiveWriter { ValueTask AppendAsync(MatchArchive archive, CancellationToken ct); }
public interface ISettlementOutbox { ValueTask EnqueueAsync(SettlementEnvelope item, CancellationToken ct); }
```

只在存在两个真实实现或能显著隔离 IO/时间/安全边界时引入接口；不要为每个类机械创建接口。

## 8. RoomRuntime 与线程模型

### 8.1 RoomRuntime 纯化

`RoomRuntime` 只持有房间内确定性状态，输入为命令，输出为事件：

```text
RoomCommand
├─ AuthenticatedJoin
├─ ClientInput
├─ Disconnect/Rebind
├─ Tick
└─ Shutdown

RoomOutput
├─ SendTo/Broadcast
├─ MatchStateChanged
├─ ArchiveChunk
├─ SettlementReady
└─ CloseConnection
```

禁止项：

- 直接调用 Transport。
- 直接读取 `DateTime.Now`、`Environment.TickCount64` 或随机全局状态。
- 直接打印 Console。
- 直接访问 Mongo/Redis/HTTP/File IO。
- 从其他线程修改成员、Sim 或输入缓冲。

### 8.2 Worker Pool

- Host 启动固定数量 Worker，默认依据物理核和压测配置，不按连接数动态创建线程。
- `hash(roomId) % workerCount` 决定房间归属；房间生命周期内不跨 Worker，除非实现显式迁移协议。
- 一个 Worker 顺序驱动多个 RoomActor；每个 RoomActor 仍是单线程。
- Mailbox 必须有界，并对输入、控制消息和出站消息设置不同优先级/配额。
- 单房间持续超预算时降级广播并触发隔离/关闭策略，不能拖垮同 Worker 的全部房间。

首版不实现运行中房间跨进程迁移。水平扩容通过 Lobby 将新 Match 分配到有容量的 RoomServer 实例完成。

## 9. Match、Room 与 Session 生命周期

### 9.1 Match 状态机

```text
Created
→ WaitingForPlayers
→ Starting
→ Running
→ Finishing
→ Settling
→ Closed

任意阶段 ──不可恢复错误/运维终止──► Aborted
```

每次迁移必须：

- 由单一命令触发并验证当前状态。
- 记录原因、时间、matchId、版本和责任实例。
- 具备超时策略和幂等保护。
- 产生结构化事件，驱动归档、结算和 Lobby 状态。

`Running` 期间不读取永久角色数据。`Finishing` 冻结结果，`Settling` 只负责提交已冻结的结算信封，不能重新计算奖励。

### 9.2 Connection 与 PlayerSession 分离

- `Connection` 表示一次传输连接，可随断线立即移除。
- `PlayerSession/PlayerLease` 表示 Match 内席位，在重连窗口内保留。
- 重连成功后把新 Connection 原子绑定到旧 PlayerSession，旧连接立即失效。
- SessionManager、票据表、发送 ledger、限流桶必须有容量上限和周期清理。
- connectionId 复用不能复活旧身份或旧 ACK 状态。

### 9.3 重连闭环

客户端和服务端都必须实现完整状态机：

```text
Connected → SuspectedLost → Reconnecting → Restoring → Connected
                                      └──超时/拒绝──► Failed
```

恢复顺序固定为：

1. 验证一次性票据并重绑席位。
2. 下发协议/Sim/配置版本确认。
3. 下发公共全量快照。
4. 下发 Match 状态和本人私有状态。
5. 下发必要输入历史与事件去重水位。
6. 客户端恢复完成 ACK 后再进入正常增量广播。

## 10. 同步、快照与可靠命令

保留《状态同步专项设计》的四个数据面：

- `PublicStateSnapshot`：公开可见战斗状态。
- `MatchStateSnapshot`：阶段、时间、比分和结果。
- `PrivateStateSnapshot`：仅本人可见的弹药、CD、资源和局内包。
- `CombatEvent`：按 `frame + eventSeq` 去重的事实事件。

可靠命令用于 Pickup/Use/Drop 等一次性行为，必须携带 `commandId/actionSeq`。服务端维护有界幂等窗口；重复 100 次只允许生效一次。

任何新增 Sim 字段必须同时修改：

1. 固定布局和 `CopyTo`。
2. checksum。
3. 全量快照与增量差分。
4. Snapshot 重组。
5. 回滚与重连。
6. 归档/回放。
7. .NET/Unity 跨运行时基线测试。

## 11. Meta 服务与持久化

### 11.1 首版模块化单体

```text
MetaServer.Host
├─ Auth Module       登录、账号绑定、访问令牌
├─ Lobby Module      RoomServer 注册、容量、匹配与 Join Ticket
├─ Profile Module    进度、库存、Loadout、Reservation、Settlement Ledger
└─ Shared Infra      Mongo、鉴权、Outbox/Inbox、HTTP、Metrics
```

Chat/Guild 在战斗服稳定后加入，可先与 Meta 同进程，但保持独立模块和数据所有权。

### 11.2 数据原则

- MongoDB 使用副本集模式，事务只围绕必须原子化的 Ledger/Inventory 更新。
- 所有外部写操作带 `requestId/operationId`，数据库唯一键是最终幂等裁判。
- 库存使用 revision CAS；公会使用 guildVersion CAS。
- Redis 只用于可丢失或可重建的在线状态、限流桶、注册表和短期 TTL，不作为永久事实来源。
- RoomServer 不保存永久库存，不接受客户端上报奖励数量。

### 11.3 结算 Outbox

结算流程：

```text
RoomRuntime 冻结 MatchResult
→ SettlementBuilder 生成签名 SettlementEnvelope
→ 本地持久 Outbox
→ 后台提交 Profile.Apply
→ Profile 事务内写唯一 Ledger + 更新库存/进度
→ 返回原结果或首次结果
→ Outbox 标记完成
```

推荐唯一键：`operationId` 和 `(playerId, matchId, settlementType)`。Profile 超时、RoomServer 重启或网络重试不得重复发奖。

## 12. 配置、启动与关闭

RoomServer.Host 使用 .NET Generic Host：

- Options 绑定并在启动阶段 ValidateOnStart。
- 配置来源为版本化文件、环境变量和 Secret Provider；命令行只用于本地覆盖。
- 端口、Worker 数、房间容量、tick/snapshot 频率、队列上限和安全策略均有范围校验。
- 启动失败必须返回非零退出码，不能带默认错配置继续运行。

优雅关闭：

1. Readiness 置 false，Lobby 不再分配新 Match。
2. 停止接受新 Join，现有房间进入 drain。
3. 在配置时限内完成对局；超时则归档 Aborted 原因并安全关闭。
4. 刷新 Outbox/Archive 到持久介质。
5. 停止 Worker、Transport 和 Host。

## 13. 可观测性与 SLO

### 13.1 日志

使用结构化日志，公共字段包括：

`service/version/instanceId/matchId/roomId/playerIdHash/connectionId/event/errorCode/durationMs`。

token、重连票据、聊天原文、IP 全量值和 protobuf payload 禁止写日志。高频逐帧日志默认关闭，只在采样诊断中开启。

### 13.2 Metrics

最低指标集：

- `room_active`、`match_state_transition_total`、`session_active`。
- `tick_duration_seconds`、`tick_deadline_miss_total`、`tick_debt_seconds`。
- `input_accept/drop_total{reason}`、`packet_reject_total{reason}`。
- `snapshot_bytes`、`snapshot_full_total`、`send_queue_bytes`、`backpressure_tier`。
- `reconnect_attempt/success/failure_total`、`reconnect_restore_seconds`。
- `settlement_outbox_pending`、`settlement_retry_total`、`settlement_idempotent_hit_total`。
- 进程 CPU、GC、堆、线程、Socket 和异常计数。

Metrics 标签禁止使用 matchId、playerId、connectionId 等高基数字段；这些信息只进入日志和 Trace。

### 13.3 Health

- `/live`：进程事件循环仍能响应。
- `/ready`：配置、Transport、Worker、必要依赖正常且实例未处于 drain。
- `/metrics`：Prometheus/OpenTelemetry 指标出口。

对每帧 Sim 不创建 Trace Span。Trace 用于 Join、Match 分配、重连、归档和结算等低频跨服务流程。

## 14. 部署与安全运营

必须补齐：

- 多阶段 Dockerfile、非 root 用户、只读根文件系统和显式端口。
- 开发/测试/预发布/生产配置分离；Secret 不入库。
- 容器资源 request/limit、优雅终止时限和 readiness gate。
- RoomServer 实例注册、容量上报和 Lobby 分配策略。
- 滚动发布先 drain 再停止；不把运行中的新 Match 分给旧版本实例。
- Mongo 备份恢复演练、索引迁移、Outbox 堆积恢复和回滚手册。
- 依赖漏洞、Secret、许可证、SAST 和容器镜像扫描。

协议和 Sim 不兼容发布采用版本并存：旧 Match 继续由旧实例完成，新 Match 只进入新实例。不得在运行中热替换 Sim 规则。

## 15. 测试框架与商业门禁

继续沿用《测试开发框架总设计》的 L0～L4，并增加服务端专项目标。

### L0 静态门禁

- 预发布滚动升级、drain、旧新版本并存和回滚演练。

CI 仍以 `scripts/test.ps1` 为唯一测试入口。PR 跑快速 L0/L1/L3；Nightly 跑网络损伤与中长跑；Release 跑 24 小时长稳、容量和部署演练。

## 20. 完成定义

每个服务端重构项只有同时满足以下条件才算完成：

1. Current/Target 文档状态已更新，没有把设计写成已实现。
2. 正常、边界、恶意输入、失败恢复和幂等路径有对应测试。
3. 指标、日志和错误码可定位失败，不依赖临时 Console 文本。
4. 队列、缓存、Session、Ticket 和历史环均有显式容量与清理策略。
5. 协议兼容、配置摘要、快照、重连和归档同步更新。
6. PR 对应 L0/L1/L3 全绿；需要 Unity 客户端配合的变更同时通过 L2。
7. 部署配置、回滚方式和运维影响已记录。
