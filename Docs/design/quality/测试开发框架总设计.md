> 状态：现行总设计
> 版本：1.5（补 L2 PlayMode 段落地）
> 更新日期：2026-09-25
> 适用范围：Unity 客户端、UI 界面与自动化、UI 性能、纯 C# 框架、帧同步、网络协议、RoomServer 与发布验收。
> 维护责任：质量工程
> 唯一执行入口：`scripts/test.ps1`。Unity 交互遵循根目录 `UNITY-GUIDE.md`。
> 客户端 Player、真机、故障注入、资源泄漏、升级回滚和商业发布硬门禁由《商业级通用客户端框架总设计》第 16～18 节补足；发生客户端范围冲突时以该文档为准。

## 1. 目标

这套方案不是“增加一些测试”，而是建立可迁移、可重复、可审计的测试开发框架。框架必须满足：

- **确定性**：同一代码、数据、种子和平台产生同一结果；失败必须能用种子复现。
- **隔离性**：测试不依赖执行顺序，不污染进程、磁盘、场景、资源或网络端口。
- **可观察性**：失败报告包含测试层级、种子、最后状态、日志和可下载产物。
- **分层反馈**：快速逻辑、Unity 资源、网络联机和真机性能分别执行、分别归因。
- **通用性**：公共框架不依赖 LiteGame 业务类型，业务夹具留在各自测试工程。
- **门禁化**：不能依赖开发者“记得运行”；PR、夜间和发布使用固定执行契约。

不把肉眼观感、复杂美术质量、第三方账号和线上运营策略伪装成单元测试。此类内容进入 L4 验收，并保留人工结论和证据。

## 2. 总体架构

| L1 逻辑测试 | 纯 C# 规则、Sim、协议编解码、确定性、框架契约 | xUnit / `dotnet test` | PR 5 分钟 | Windows + Linux |

## 3. 分类与元数据

测试类型和运行时长必须分开标记。`Category` 描述**测试类型**（Lane 另由测试工程决定，见下），`Duration` 决定“什么时候跑”。

| 维度 | 值 | 用途 |
| --- | --- | --- |
| `Category` | `Unit` / `Contract` | 无进程外依赖；多在 L1 |
| `Category` | `Integration` | 真实文件、Socket、数据库或多组件装配；多在 L3 |
| `Category` | `Asset` / `Smoke` | 资源与 Unity 装配；多在 L2 |
| `Category` | `EndToEnd` | 跨进程或完整用户路径；多在 L3/L4 |
| `Category` | `Performance` | 夜间/发布；不能进入普通功能门禁 |
| `Category` | `Quarantine` | 临时隔离；默认所有门禁排除 |
| `Duration` | `Fast` / `Medium` / `LongRunning` | PR 排除 `LongRunning`，夜间执行 |
| `Priority` | `P0` / `P1` / `P2` / `P3` | 发布风险与排障顺序 |
| `Owner` | 稳定团队名 | 失败路由，不写个人昵称 |

**Lane 与 `Category` 的关系（2026-09-22 澄清）**：Lane 由**测试工程**决定，不由 `Category` 决定——`Tests/**/*.Tests.csproj`（dotnet）进 L1/L3，Unity 测试程序集（`Assets/Tests/**`，经 `run_tests --mode editor`）进 L2。`Category` 只描述**测试类型**，所以**同一 Lane 可以出现多个类型**：`Unit` / `Contract` 不限于 L1；L2 的 Unity EditMode 用例照测试性质打标——资源/内容完整性 → `Asset`，行为或跨运行时契约 → `Contract`，纯逻辑无外部依赖 → `Unit`，装配冒烟 → `Smoke`。表内“多在 Lx”是**典型归属**，不是判据。

UI 测试不新增并行分类：界面契约按 `Asset` / `Contract` / `Smoke`，用户路径自动化按 `EndToEnd` 或 `Integration`，性能基线按 `Performance`。UI 用例另用 `UIType` 扩展属性标记 `Surface`、`Automation` 或 `Performance` 测试形态；目录、语义定位、PlayMode 接入、性能采样和设备门禁统一见 [UI 测试开发专项设计](UI测试开发专项设计.md)。

约束：

- 新测试必须标记 `Category`；存量无标签测试在迁移期间默认进入 L1，防止静默漏测。
- `Quarantine` 必须关联缺陷、责任团队和不超过 7 天的到期日；禁止用重试掩盖不稳定。
- P0 覆盖启动、登录、存档/库存、支付相关状态、战斗主循环、协议兼容和热更入口。
- 测试名描述“条件、行为、结果”，不要只写方法名或缺陷编号。

## 4. 测试编写契约

每个测试遵循 Arrange / Act / Assert，并满足以下硬约束：

1. 一个用例只验证一个业务行为；多个断言可以共同描述同一结果。
2. 不读取真实当前时间，不直接 `new Random()`，不依赖字典枚举或文件系统自然顺序。
3. 异步等待使用 `Eventually`，必须有超时和最后状态说明；禁止无界循环和固定长 `Sleep`。
4. 外部状态由 `TestScope` 或专用夹具拥有，按注册逆序释放；清理失败也算测试失败。
5. 共享静态状态必须进入禁并行 Collection，或改造成实例依赖；不能靠测试顺序维持通过。
6. 网络测试不得使用公共固定端口；必须租用端口，或在单 Collection 内串行管理固定端口。
7. 测试不得访问生产凭据、线上服务和真实用户数据；密钥只来自 CI 的测试环境。
8. 失败后保留最小充分证据，不默认保存成功用例的高体积日志。
9. 构建与测试并行度必须显式封顶；不得按宿主机全部逻辑核无界创建 worker。

### xUnit 模板

```csharp
using LiteTesting;
using Xunit;

public sealed class InventoryContractTests : System.IDisposable
{
    private readonly TestScope _scope = new TestScope(nameof(InventoryContractTests));

    [Fact]
    [Trait(TestTrait.Category, TestCategory.Contract)]
    [Trait(TestTrait.Priority, TestPriority.P1)]
    public void DuplicateCommand_IsAppliedOnce()
    {
        int quantity = _scope.Random.NextInt(1, 10);
        // Arrange / Act / Assert
    }

    public void Dispose() => _scope.Dispose();
}
```

### Unity EditMode 模板

```csharp
using LiteTesting;
using LiteTesting.Unity;
using NUnit.Framework;

public sealed class WidgetAssetTests : UnityTestBase
{
    [Test]
    [Category(TestCategory.Asset)]
    public void Widget_HasNoMissingComponents()
    {
        var probe = Scope.CreateGameObject("Probe");
        Assert.NotNull(probe);
    }
}
```

Unity 测试只通过 `UnityTestScope` 或 `AssetDatabase` 创建临时对象/资源，并由 Scope 删除。不得手工创建、编辑或删除 `.meta`。

## 5. 确定性与数据治理

### 随机数据

- 全局种子来自 `LITETEST_SEED`，默认值固定；每个测试按完整测试 ID 派生独立种子。
- 失败报告必须打印全局种子与测试 ID；复现时设置同一环境变量。
- 使用 `DeterministicRandom`，不依赖不同 .NET/Mono 版本可能变化的 `System.Random` 序列。

### 基线文件

- 基线是裁判，不是方便更新的快照。内容必须可由版本化工具重新生成。
- `Tests/**/Baselines/**` 变更必须带 `[baseline]` 说明，并由非作者复核。
- 基线记录生成器版本、输入版本和平台；禁止在断言失败时自动覆盖。

### 测试数据

- Builder 只提供合法最小对象；边界值在测试中显式覆盖，避免“万能 Fixture”隐藏前置条件。
- 敏感数据必须合成或脱敏。产物中不得出现 Token、账号、设备标识和聊天原文。

## 6. 分层范围

### L1 必测

- DI 注册/解析/循环依赖/Seal，事件注销，池化双归还，时钟分域，FileSys 原子写。
- Sim 固定布局、深拷贝、checksum、输入排序、回滚、快照差分/重组。
- 协议 round-trip、未知字段兼容、长度/频率边界、重复命令幂等。
- 武器、Action、背包、库存、聊天、公会等纯规则与权限矩阵。

### L2 必测

- Unity 全量编译无新增错误，EditMode 测试数不得为 0。
- `.meta` GUID、丢失脚本、Prefab/UI 模板、自定义 Inspector 与资源引用完整性。
- UI PlayMode 使用真实 UIService、Lua 页面与实例化链路，覆盖首开/关闭/复用、初始化失败、并发与取消、Covered/Paused 清理、模态/焦点、列表滚动/重绑、语言切换、DevReload/Shutdown。仅验证转场 Runner 或模板结构不能替代此项。
- UI 具体用例、所有权计数与目标设备预算以 [UI框架总设计第 12 节](../client/ui/UI框架总设计.md#12-验收预算与观测) 为唯一细化来源；这些新增覆盖为待补足项，执行能力按现有 scripts/test.ps1 契约接入。
- UI 界面测试、语义自动化测试和 UI 性能测试按 [UI 测试开发专项设计](UI测试开发专项设计.md) 归档：界面契约进入 L2，P0 自动化进入 L2 PlayMode，性能趋势进入 Nightly，目标设备性能进入 L4 Release。
- UI 自动化必须使用稳定 `ui-id`/语义角色和可观察等待；UI 性能必须记录构建、设备、分辨率、数据规模、种子及 p50/p95/p99，不能用坐标点击或 Editor 数字代替发布证据。
- Unity/Mono 与 .NET 的 IEEE/checksum 基线逐位一致。
- 场景或 Prefab 测试不得保存、覆盖用户已有的未保存内容。

### L3 必测

- RoomServer + 2 至 8 个无头客户端，真实协议和传输适配器。
- 150ms RTT、10% 丢包/乱序、断线重连、重复包、过期输入、伪造实体与超频请求。
- 可靠命令重试 100 次只生效一次；重连恢复公共、本人私有和输入历史状态。
- 长跑记录 tick stall、和解率、积压、内存趋势和首个分歧帧。

### L4 必测

- 目标机型启动、热更、切后台、低存储、弱网、安装/升级和崩溃恢复。热更的分层矩阵、故障持久点、候选 Lua/配置与回退覆盖遵循[热更与内容发布专项设计](../client/content/热更与内容发布专项设计.md)。
- 热更正常成功用例必须到达定义的业务健康入口；BootstrapError 可达仅能通过对应恢复用例，不能替代新内容激活成功。L3 验证双端数据/协议，真 LuaEnv/YooAsset 与文件系统中断恢复须由 L2/Player 验证。
- CPU/GPU 帧时、GC、峰值内存、包体、加载时延和功耗按版本基线做回归。
- UI 使用目标加载模式与实际资源包验证：活跃/缓存实例依赖不被提前卸载，Scope 退出和低内存清理不持续增长；中英/伪本地化、安全区、输入和减少动效按产品配置验收。
- 发布候选版本使用与生产一致的构建参数；结论和 Profiler/日志作为发布产物保存。

## 7. 执行 Profile

| Profile | L1 | L2 | L3 | L4 |
| --- | --- | --- | --- | --- |
| PullRequest | 快速、双平台 | 自托管 Editor | Integration/E2E，排除 LongRunning | 不执行 |
| Nightly | 全量 | 全量 | 含 5 分钟长跑和网络损伤 | 可选设备冒烟 |
| Release | 全量、冻结依赖 | 指定 Unity 版本 | 完整长稳 | 必须，人工审批 |

本地命令：

```powershell
powershell -NoProfile -File scripts/test.ps1 -Lane L1 -Profile PullRequest
powershell -NoProfile -File scripts/test.ps1 -Lane L3 -Profile PullRequest
powershell -NoProfile -File scripts/test.ps1 -Lane L2 -Profile PullRequest
powershell -NoProfile -File scripts/test.ps1 -Lane All -Profile Nightly
```

`L2` 必须通过 Unity Pipeline 执行。后台运行前启用 `set_autotick`，异步编译和测试必须轮询终态；存在多个实例时显式指定工程或实例。

## 8. 门禁与报告

硬门禁：

- 退出码非 0、编译错误、测试数为 0、超时、清理失败、非法 GUID 都判失败。
- PR 不自动重试失败测试。确认框架/基础设施故障后，由维护者重新触发整个 Lane。
- L1/L3 在 Windows 与 Linux 分别报告；一个平台失败不能取消另一个平台的诊断。
- TRX、失败日志、种子和测试产物由 CI 上传；L1/L3 分开命名，保留失败归因。
- UI 测试若程序集未编入、测试数为 0、Console 有新增 Error、语义定位不唯一、页面关闭后仍有订阅/租约/异步写入，或性能样本缺少设备/构建/数据规模，均判相关 UI Lane 失败；视觉截图差异必须带参考图、阈值和批准记录。

质量指标采用“只升不降”的基线治理：

- P0/P1 需求覆盖率、变更行覆盖率、分支覆盖率按模块记录；没有可信基线前不伪造统一百分比。
- 首轮目标：核心纯逻辑变更行覆盖率不低于 80%，关键协议/幂等/权限分支必须 100% 场景覆盖。
- 统计不稳定率、平均反馈时间、超时率和隔离测试数量；`Quarantine` 数量不得长期增长。
- 覆盖率是风险信号，不替代断言质量、变异测试和故障注入。

## 9. 新功能完成定义

功能只有同时满足以下条件才算完成：

- 正常、边界、非法输入、失败恢复和幂等路径均有对应层级测试。
- 新增状态字段同步更新快照、CopyTo、checksum、差分/重组、重连和布局测试。
- 测试可独立重复运行，失败能用固定种子复现，所有资源可清理。
- PR 所属 Lane 全绿；涉及 Unity 资源必须 L2 全绿；涉及联机必须 L3 全绿。
- 涉及 UI 的功能必须同时具备资产/结构契约、真实生命周期或用户路径用例；涉及发布表现的 UI 变更必须提供 Player/目标设备性能样本和可下载证据，不能以手工点通替代自动化门禁。
- 测试与生产代码由同一变更提交，文档只记录长期契约，不记录一次性施工过程。
