# 非作者机恢复与验证记录（2026-10-12）

> **这份文档回答什么**：在一台**不是项目作者机**的机器上打开本工程，要把工程恢复到「能编译、能跑测试」需要做什么、哪些问题属于**项目本身**、哪些只是**本机缺东西**。
>
> **它不做什么**：不修改项目台账。[待办总览](待办总览.md) 与[代码质量审计](代码质量审计-客户端.md) 的状态**不因本文改变**——下面 §2 的环境事实在作者机上大多**不是问题**，写进去会污染真相源。要不要把 §1 的条目登记进台账，由 Owner 另行裁决。

## 0. 为什么会有这份文档

本仓库按设计**不入库**美术/字体/角色包/第三方付费包/URP 管线资产/部分场景（`.gitignore` 多处 + [环境恢复指南](环境恢复指南.md) §3）。因此**任何非作者机克隆下来，场景与 prefab 都会带着一批解析不了的引用**——这不是仓库损坏，是既定策略的必然结果。

本记录把那批"看起来像故障"的东西逐条定性，省下下一台机器重复排查。

## 1. 真项目缺陷（与本机无关，可直接修）

### 1.1 `GmSceneCommands.cs.meta` 漏提交

| 项 | 事实 |
| --- | --- |
| 现象 | `Assets/LiteGame/App/Commands/GmSceneCommands.cs` **已入库**，其 `.meta` **当时未入库**（同目录其他 `.cs` 均成对） |
| 核验 | 修复前 `git ls-files Assets/LiteGame/App/Commands/` → 有 `.cs` 无 `.cs.meta` |
| 后果 | 任何机器首次打开时 Unity 会**生成随机 GUID**；该 GUID 与作者机不一致，跨机引用不可复现 |
| 处置 | **本次提交已 `git add` 入库**（guid `be1a99ec97b31594dad69ebd63177ad8`）——本条已修复，登记在此仅为留档 |
| 建议 | 加门禁：`.cs` 与 `.cs.meta` 成对存在才算通过。Unity 侧无法靠脚本保证——这是入库纪律缺口 |

### 1.2 每次打开工程必脏两个文件（结构性矛盾）

两处都不是人工改动，是**编辑器一开就自动重写**：

**(a) `ProjectSettings/GraphicsSettings.asset`**

```
serializedVersion: 14 → 15
删除 m_LegacyDeferred
新增 m_BrgStripping、m_LightProbeOutsideHullStrategy、m_CameraRelativeLightCulling
m_SRPDefaultSettings 的 URP 资产 guid 改写
```

`m_BrgStripping` / `m_LightProbeOutsideHullStrategy` 是 **Unity 6 字段**，2022.3 不该有。根因：本机 `E:\Unity\2022.3.55f1c1` 虽报 `2022.3.55f1c1`，但 `Editor.log` 自述 `Built from '2022.3/china_unity/release'`——**是 Unity 中国版构建**，序列化行为与社区版有别。

值得单独指出的是：`scripts/gate/toolchain.json` **已经声明了** `"edition": "Unity China"` + `source: unity.cn/download`，但 `restore-check.ps1` **从不读这个字段**（全文无 `edition`/`revision` 匹配），只比对 `ProjectVersion.txt` 的 `m_EditorVersion` 字符串是否等于 `2022.3.55f1c1`。**声明与校验脱节**——换一支同版本号的社区版构建，门禁照样放行。

**(b) `Assets/Plugins/Demigiant/DOTween/DOTween.dll.mdb.meta` 与 `Editor/DOTweenEditor.dll.mdb.meta`**

根因是 `.gitignore` 有 `*.mdb`（调试符号实体不入库），但这两个 `.meta` 在 `c3e1082`（"放开 ProjectSettings 与 DOTween 入库"）被一并提交。**实体永远缺失 ⇒ meta 永远是孤儿** ⇒ Unity 一开就删它，并刷警告：

```
A meta data file (.meta) exists but its asset
'Assets/Plugins/Demigiant/DOTween/DOTween.dll.mdb' cannot be found
```

**建议**：(b) 二选一——要么 `*.mdb` 出 gitignore 并入库，要么把这两个 `.meta` 从入库移除；选后者更省体积且与"调试符号不入库"一致。(a) 让 `restore-check` 真的去读 `toolchain.json` 里已有的 `edition`/`revision`——字段已经在了，只是没人校验。

### 1.3 `restore-check.ps1` 的场景检查项陈旧

`scripts/gate/restore-check.ps1:121` 检查：

```powershell
if ((Test-Path '...\Assets\Scenes\Boot.unity') -or (Test-Path '...\Assets\Scenes\Test.unity'))
```

但仓库实际入库的是 `TrainingGround.unity` / `UiWorkbench.unity`（`.gitignore:151-157` 于 2026-10-11 收窄后只放行这两个），`Test.unity` 已在 `58fbfd3` 删除、`Boot.unity` 从不入库。

**后果**：任何非作者机跑 `restore-check` 都会拿到一条**误导性**的 `Assets/Scenes missing - cannot run directly`。

**建议**：改为扫 `Assets/Scenes/*.unity`（存在即 OK），或直接查 `TrainingGround`/`UiWorkbench`。

### 1.4 `restore-check` 的唯一 blocking 项：Odin Inspector

`Assets/Plugins/Sirenix`（按席位付费、不可再分发）缺失时 `restore-check` 退出码为 1。

**现状澄清**：本次实测 **它不阻断编译**——`LiteGame.Editor.dll` 在无 Odin 的情况下正常产出。`restore-check` 把它列为 blocking 是**保守设定**，与实测不符。若确认编辑器侧功能不依赖 Odin，可降级为 WARN（需 Owner 裁决，本记录不改门禁行为）。

## 3. 验证结果（2026-10-12 实测）

### 3.1 编译

`Unity.exe -batchmode -nographics -quit`：**`error CS` 0**。5 个 `Unity.Pipeline*` 程序集全部产出。

> **踩坑留档**：首轮自制的补丁 1 脚本用 `- .*\n` 抓 `defineConstraints`，要求列表项的 `-` 在第 0 列；而 Unity 自己写的 meta 里列表项**缩进两格**。正则落空走了兜底分支，产出 `defineConstraints:` 后跟一行裸 `  []`，Unity 解析器报 `Parser Failure at line 10`，**5 个 Roslyn DLL 根本没加载**——正是该补丁要修的问题本身。
> 教训：**"编译 0 错误"不等于"资源被正确加载"**，插件 meta 的解析失败不进 `error CS`。已修，见 `scripts/pipeline/patch_p1_plugin_metas.py`。
