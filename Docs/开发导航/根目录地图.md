# 根目录地图

> **定位**：回答"仓库根每个条目是什么身份、入不入库、为什么在根"——一张表看懂根目录为什么"多"。乱与不乱的判据在这里一眼可辨：结构性必然（Unity 固件、四位一体）还是真乱点（见文末登记）。
> **不做的事**：不答"代码/文件在哪、谁改它"（归 [代码地图](代码地图.md) 的"谁改它"视图）；不答"怎么改怎么验"（归 [修改指南](../修改指南.md)）；不承载 git 规则本身——入库判定的权威是根 `.gitignore`（其分段注释即登记理由），本表是它的导航视图。
> **冲突裁决**：本表与 `.gitignore` 不一致时以 `.gitignore` 为准，顺手改本表；条目身份与设计裁决冲突时以设计文档为准。
> **维护纪律**：**新增根级目录必须同批登记本表 + `.gitignore`（带理由注释）**。两处职责不同——本表＝导航，`.gitignore`＝git 规则——缺任何一处即门禁外漂移。

## 为什么根目录必然"多"

仓库根同时承担四个身份，这是工程形态的物理约束而非规划失误：

1. **Unity 工程根**——Unity 强制 `Assets/Library/Temp/obj/Logs/UserSettings` 在根，且 Unity 工程根必须等于仓库根；
2. **dotnet 方案根**——`global.json/obj/TestResults` 随方案与测试落在根；
3. **服务器进程 CWD**——本地跑服务器时工作目录是仓库根，运行落盘（结算 journal 等）随之落根；
4. **git 仓库根**——源码域、文档、工具链的宿主。

其中 1 无法改变，2/3/4 只能跟着挤。因此"目录多"是常态，治理目标是**每个条目可辨别、可登记**，而非把根清空。
