### 施工记录

#### 2026-09-25 · 端到端装配批（#12 收口——装配面完整，候选仍 fail-closed）

**背景**（框架先行落地审查发现的收口项）：#12"端到端装配"的缺口是 `GameModules` 装配
`verifier: null` + 空健康聚合——件已全交付但装配面断开。本批把**信任锚解析、探针族、
验签器按 KeyId 每候选解析**三面接通，装配面从"断开"变为"完整但当前零锚点"。

**① 信任锚**（`ContentTrustAnchors.cs` 新）：编译期内置锚表（`IEnumerable<Anchor>`——
当前**零条目**）。根信任编入应用本体（随应用签名分发），**不放可写存储**——否则攻击者
加入自己的公钥 + 自签候选即绕过整条验签链。锚点 provisioning = 发布流程生成密钥对 →
公钥条目加入锚表 → 重新编译。

**② 验签器按 KeyId 每候选解析**（`PatchRunner`）：原 `ISignatureVerifier verifier` 单验签器
改为 `Func<string, ISignatureVerifier> verifierResolver`——按 `offer.Manifest.KeyId` 从
受信公钥库解析（§6"签名公钥标识（对应 TrustedKeyRing）"）；未登记/已撤销 → null →
校验器按 UnknownOrRevokedKey 拒（fail-closed 语义不变）。

**③ 探针族接入编排健康确认**（`GameModules` Content 模块）：
`CompositeHealthCheck` 从空聚合改为接入候选配置（`config/` 前缀）与候选 Lua（`lua/` 前缀 →
模块名 → `CandidateLuaValidator` 受控沙箱）两个探针——发布约定经 `ReleaseLayout` 单源。
入口资源可加载性探针（`AssetsHealthProbe`）查当前代次入口，须在资源包初始化后才有意义
（Patch 先于初始化，时序不可能）——归 Preload 后接缝（待办总览 §2.1 边界登记）。

**④ `ReleaseLayout`**（`Shell/Resource/`，新）：发布布局约定单源——`config/` 前缀 = 配置、
`lua/` 前缀 = 热更脚本、模块名派生（剥 `lua/` 与 `.lua`、`'/'` 保留与 LuaPreloader 同规则）。
探针装配与发布流水线共用。

**测试**：EditMode +7——`ReleaseLayoutEditModeTests` 5 例（config 挑选、Lua 模块派生与
LuaPreloader 同规则、空清单、零锚点 ApplyTo 返回 0、登记/撤销 Resolve 语义）+
`UiNavModalEditModeTests` 2 例修复回归。

**验证（本批实测）**：L1 **778/778**（LiteFramework 496 + LiteNet 160 + LiteSim 97 + LiteTesting 7 + Meta 18）；L2 门禁通过（12070 meta、编译零错误、EditMode **222/222** + PlayMode 12/12）。

**边界登记**：当前零内置锚点 → 候选仍一律被拒（fail-closed 保持——装配面完整但"接受候选"
需发布流程 provisioning 真实密钥对）。CDN 通道（`HttpCandidateFetcher`）随部署配置接入。（后注：锚点已于 2026-09-26 provisioning、CDN 通道 2026-10-02 接入、真实资产包段 2026-10-03 达成——“零内置锚点”边界已消解。）

#### 2026-09-25 · 候选校验内核交付（H3-a）

**背景**：热更批(一)(二)交付的发布身份/签名校验/激活事务在**生产代码中零消费者**
（全仓引用只有定义文件与测试）；设计 §7 的"下载/校验"执行侧一行未落。
本批补上其中**可纯规则交付**的部分——填平"信任侧已备好、执行侧为零"的缺口。

**① 候选文件与空间端口**（`Assets/LiteFramework/Scripts/Core/Content/CandidateFileSource.cs`）

- `ICandidateFile` / `ICandidateFileSource`：候选文件读句柄与访问端口。只暴露长度与完整字节——
  设计 §5 要求摘要对**原始字节**计算完整 SHA-256，`ContentHash.Hasher` 需整块输入；
  逐文件整体读入有界（`ReleaseBudget.MaxFileBytes` 默认 512MB）。**流式分块属大包优化，
  在有真实包规模数据前不预先引入**（§15"没有目标包规模与设备数据时不虚构"）。
- `IDiskSpaceProbe`：磁盘余量端口。**单独成端口**而非并入文件端口——平台可能能读文件却拿不到配额，
  且预检失败必须有明确结果而不是静默跳过。
- `SpacePrecheck` / `SpaceCheckRequest` / `SpaceCheckResult`：§7"计入候选、临时/解压峰值、保留版本及余量"。
  **溢出安全**：各分项 long 累加用显式判定，溢出即判"不足"——回绕会让"空间不够"变成"空间充足"。
  可用空间不可知（-1）同样按**不足**拒绝。

**② 失败分类**（`Assets/LiteFramework/Scripts/Core/Content/DownloadFailure.cs`）

`DownloadFailureKind` 按 §12 错误类别表分类，并带 `IsTransient` 判定：
暂态（网络超时/源不可用）可重试换源；确定性（缺失/长度不符/摘要不符/读取错误/空间不足/
清单外文件/重复文件）**重试无效**——§12"不通过反复重试或忽略验证绕过"。
分类决定动作，不是一个笼统的"失败"。

**③ 候选内容校验**（`Assets/LiteFramework/Scripts/Core/Content/CandidateContentVerifier.cs`）

**本批核心**：`ReleaseManifestValidator` 只校验描述**字段形态**（路径合法、长度非负、摘要形状），
**从不读文件字节**；本类把清单与**落盘内容**对上：

- 逐文件**复算摘要**（§7"文件通过完整性校验后才进入资源/Lua 解析与执行"）；
- 长度先于摘要：廉价且能立刻拒掉截断/超长，避免为大文件白算摘要；
- 端口自报长度与实读不符时以实读为准再核一次；
- **双向差异**的"多"一侧：清单外杂散文件检出（防多源拼接/残留污染）；
- 大小写按 `OrdinalIgnoreCase` 比较——Windows 文件系统不区分大小写，
  清单声明的 `a.lua` 与落盘的 `A.lua` 在真实平台无法区分，必须同一口径；
- `TryFindDuplicatePath` 补上 `ReleaseManifestValidator` 精确重复检查之外的**平台归一化口径**；
- 批量复用单个 `ContentHash.Hasher`（该类注释的设计意图"对成百上千个候选文件循环校验"，
  此前生产零调用）。

**④ 下载计划**（`Assets/LiteFramework/Scripts/Core/Content/DownloadPlan.cs`）

§7"YooAsset 负责下载实现，项目负责可信发布描述、事务代次与激活决策"的**决策侧**——
纯决策不做 IO，与"下载怎么做"完全分离，使 L1 能覆盖全部分支：

- 来源按优先级稳定排序（同优先级保持声明顺序，避免平台排序不稳定导致行为漂移）；
- **每次重试轮转到下一个来源**，优先级只决定首次用哪个源；
- 有界重试（`MaxAttemptsPerFile`）、指数退避**只计算不等待**（Sleep 属 IO 层，Core 不引入等待语义）；
- `AllDownloaded` 按清单逐项核对（大小写不敏感）。

**设计取舍**：初版设了 `MaxSourceSwitches` 与 `MaxAttemptsPerFile` 两个旋钮，实测发现二者职责重叠——
源数 ≤ 尝试上限时轮转自然覆盖全部源。已删除前者（无独立消费者，§22 精神）。


#### 2026-09-25 · 补丁编排、健康聚合、Lua 静态身份交付（H3-c / H3-e 聚合面 / H3-d 静态面）

**⑤ 补丁编排**（`Assets/LiteFramework/Scripts/Core/Content/PatchCoordinator.cs` + `ContentOrchestrationPorts.cs`）

**这是热更链的第一个生产消费者**——把此前零散且无调用方的 `ReleaseManifestValidator`（描述层）、
`DownloadPlan`（获取决策）、`CandidateContentVerifier`（内容执行侧）、`ActivationTransactionStore`
（持久事务）**串成一条可测编排**。

顺序（§8 + §4 mermaid，每步持久化以便中断恢复）：
启动恢复 → **依赖检查** → 空间预检 → 获取 → 校验 → 标记待激活 → 激活 → 健康 → 确认。

- **依赖检查**（§6"本发布生效前必须已确认的版本"）：未确认则拒绝候选。判据为"已确认**或**本次在途"。
- **中止点顺序**：`MarkPendingActivation` 持久化**早于**激活——顺序颠倒会让进程在激活后中断时无从恢复（§8 表行 2）。
- **失败一律保留允许版本**（§8"从允许的 Confirmed 版本重建，不使用半成品"）：留档失败 → 重建已确认代次 →
  代次提示回已确认。**留档先于重建**，即便重建抛错失败原因已持久化。
- 未进入激活链路时**不调用**重建——已确认内容本就在运行，重建是多余的清缓存。
- 端口分离：`ICandidateFetcher`（网络 IO 特性）独立于 `ICandidateFileSource`——
  R11 纯化纪律禁止核心逻辑引用 HTTP/传输，端口分离让编排保持纯逻辑可 L1 覆盖。
- `IGenerationSink` 补上设计 §9 的缺口：`YooAssetContentService._generation` 此前无 setter、
  代次从未切换，健康确认后必须推进否则新内容永远不被加载。

**⑥ 健康确认聚合**（`Assets/LiteFramework/Scripts/Core/Content/CompositeHealthCheck.cs`）

§8"健康确认至少覆盖候选 ConfigSnapshot、Lua/main、全部必需注册表、关键 UI/入口及其资源"。
**一项一个探针**（合并成"全都检查"会让失败无法定位到具体项）；聚合**不短路**——
一次报告全部不健康项（与 `MetaConfig.Validate` 同款纪律）；探针抛异常按**不健康**处理，
不中断链路也不被当作健康。**无探针 = 判为不健康**（未确认任何覆盖项就声称健康，等于放弃 §8 要求）。

**⑦ Lua 候选静态身份**（`Assets/LiteFramework/Scripts/Core/Content/CandidateScriptSet.cs`）

### 4. 守卫机制（预埋清单 + 签名快照）——设计要点

### 4.7 风险、回滚与边界

- **最大风险：混快照**。config/ 全量 + LoadAsync 单次构造是硬约束；不要为“只发一张表”做 partial overlay，否则 cfg.Tables 跨表不一致。
- **判定面 ≠ 纯客户端热更**：D6 是设计事实；演练 A7 要能解释“拒局正确”，不要把拒局当回归。
- **Lua 的 require 缓存**：首版是启动期整套脚本；运行中重载归 H5。LuaPreloader 重复 key 显性拒绝，不要静默覆盖。
- **激活/回滚**：坏候选必须在健康检查阶段失败；失败后 activation.json 保持旧 Confirmed，下次启动仍可用。
- **包名/入口文件**：若把 CandidateEntryFilesHealthProbe 退役，删除类时同步设计 §2.1/§8；若保留，先把包名单源注入，禁止在探针里写死 DefaultPackage。
- **构建门禁**：build-player.py 的 L0 仍可能因自研 vendored 包缺 LICENSE 红；演练可用 --skip-restore-check 绕过，但正常出包前要补/裁决（见 B3 章 41.3）。
