> **批次**：服务端审计 P1（四项）　**日期**：2026-10-11　**状态**：已完成（附验证证据；未提交）
> **来源**：《[代码质量审计：服务端](../代码质量审计-服务端.md)》§修复优先级 2——"HTTP 成功判定改 2xx 区间；实例密钥按注册/结算分权；`/auth/guest` JSON 异常面统一；BuildHash 接真或显式门禁挡版本准入"。
> **口径**：正确性补强（不改架构）。**两处对外行为变化**（部署面 + 契约面）在 §2 与 §4 显式标注：结算凭据必须独立提供（fail-closed）；Meta 构建身份改为生成物。

## 1. HTTP 成功判定改 2xx 区间（①）

| 位置 | 改前 | 改后 |
|---|---|---|
| `LobbyRegistrationClient.TrySendOnce`（注册/心跳） | `(int)response.StatusCode != 200` → 记失败 | `!response.IsSuccessStatusCode` → 记失败 |
| `SettlementSubmitService.TrySubmitNext`（结算提交） | `(int)response.StatusCode == 200` → 标记完成 | `response.IsSuccessStatusCode` → 标记完成 |

同批改正 `SettlementSubmitStep.Submitted`/`Failed` 与类注释里的 "200" 口径（文档随代码）。

**同批登记的相邻缺陷（本次未修，见 §5）**：非 2xx 里包含 409（Meta 台账冲突）与 400（载荷非法）这类**确定性**拒绝——现策略是"保持待提交 + 指数退避重投"，对确定性拒绝**永不收敛**，且因 `TrySubmitNext` 只取 `ListPending()[0]` 会**头阻塞**后续所有条目。修它要动重试拓扑（跳过集/终态处置），超出本批"判定区间"的范围，故登记为待办。

## 2. 实例密钥按注册/结算分权（②）

**现场**：`/matches/result`（写结算账本）与 `/lobby/instances/register`（注册实例）共用同一份实例密钥（Meta `LobbyInstanceKeyBase64` ≡ 房间端 `--lobby-instance-key`）。`InstanceKeyAuth` 注释自认"日后若需分权再拆独立密钥"——即两条权限面从未分离：**能注册实例的凭据即可写账本**，任何一处凭据分发泄露同时放大到资金面。

**修法（两条权限面各一份凭据，缺则 fail-closed）**：

| 面 | Meta 配置 | 房间端注入 | 校验点 |
|---|---|---|---|
| Lobby 实例注册 | `LobbyInstanceKeyBase64`（不变） | `--lobby-instance-key` / `LITENET_LOBBY_INSTANCE_KEY`（不变） | `/lobby/instances/register`、`/lobby/rooms` |
| 结算提交 | **新增 `SettlementInstanceKeyBase64`**（空 = 该端点 503 功能关闭） | **新增 `--settlement-instance-key` / `LITENET_SETTLEMENT_INSTANCE_KEY`**（缺则**启动即拒**） | `/matches/result` |

- `MetaConfigValidator`：给了结算凭据就必须合法（Base64 ≥32 字节，原值不回显）；**不给不报错**（与 Lobby 同款"空即关闭"）。
- 房间端**不做回退**：结算管道启用而缺结算凭据 → 抛（提示新 CLI/env），不静默复用 `--lobby-instance-key`（那等于把分权又抹平）。
- `InstanceKeyAuth` 类注释改为"凭据按权限面分离，由调用方传入对应面的期望值"。
- `Config/roomserver.json` 注释同步（结算凭据不在文件、与注册分权、缺则拒启）。

**验证覆盖（如实）**：配置面由 L1 `MetaConfigTests`（新增 2 例：非法值拒绝/原值不回显 + "两个独立字段互不推导"）；端点面由 L3 `SettlementL3Tests`（改用分离密钥 + 新增"Lobby 凭据写账本必 401"正证）——**L3 本机跳过**（`MongoFixture` 不可用，4 例 skipped，与 P0 批同款环境限制）。**残余缺口**：L1 面上没有"端点确实读结算凭据"的可执行断言——端点序是"功能门 → 凭据 → 存储"，而存储装配需要真 Mongo（启动迁移 `MigrationStartupService` fail-closed），故无 Mongo 时到不了凭据分支（这是“功能门先于鉴权”这条**有意**规则的代价，不为测试改序）。

## 3. `/auth/guest` 请求体解析异常面统一（③）

`AuthEndpoints` 原来只 `catch (JsonException)`——`ReadFromJsonAsync` 对**非 JSON content-type** 抛的是 `InvalidOperationException`，于是 `POST /auth/guest` 带 `text/plain` 会**未处理异常 500**，而同形状请求在 Lobby/Settlement 得 400。改为与另两处同形：

```csharp
catch (OperationCanceledException) { throw; }   // 请求中止随管道传播
catch (Exception) { command = null; }           // 坏 JSON / 非 JSON content-type / 形状失败 → 400
```

（顺带移除随之无用的 `using System.Text.Json;`。）端点层"反序列化收口块 4 份近似拷贝"的**收敛**（审计 §二[中]）属 P2，不在本批。

## 4. Meta BuildHash 接真（④）

**先更正审计的前提（以代码为准）**：审计写"Lobby 版本准入与票据盖章消费的就是这个假哈希"——**不成立**。唯一消费点是 `MetaHost.BuildIdentity → Program.cs` 启动日志的 `build=`；Lobby 的版本准入（`InstanceRegistry.TryAllocate(requiredBuildHash)`）与票据盖章（`LobbyTicketSigner.Issue(..., chosen.BuildHash, ...)`）消费的是**房间实例上报的** buildHash，其值为 `LiteNet.BuildHash.Value`（真值，且受 `--check` 门禁把守）。故"门禁挡版本准入"这条在本代码上无对象可挂。

**实际缺陷**：手写占位 `BuildHash.Value = "meta-0.0.0-unwired"` 是"看起来像版本号却没有来源"的假身份（还带 `0.0.0` 让人误读为语义化版本）。

**修法（接真）**：`scripts/codegen/gen-build-hash.py` 扩为**两个目标**（同一生成器、同一复算规则）：

| 目标 | 源集 | 输出 | 用途 |
|---|---|---|---|
| shared | `SHARED_TARGETS`（Sim/协议/安全信封）+ 表数据 | `Assets/LiteNet/Protocol/BuildHash.g.cs` | **两端握手红线**（Join 校验） |
| meta（新） | `META_TARGETS`（`Server/MetaServer/**`）+ 源链接件 `Assets/RoomServer/Application/JoinTicketFormat.cs` | `Server/MetaServer/Host/BuildHash.g.cs` | Meta 构建身份（启动日志） |

- 手写 `Server/MetaServer/Host/BuildHash.cs` **删除**（生成物取代）；`MetaHost.BuildIdentity` 注释写明"生成物 + 与握手红线不是一回事"。
- 校验口径：`--check` 复算**两个**常量；**`--check-shared` 只查共享源集那个**，`build-player.ps1` 出包门禁改用后者——**Meta 是独立产物，其常量陈旧不该拦客户端出包**（把守点 = 发布 Meta 前跑 `--check`）。
- 编排/提醒同步：`refresh_hash.py` 步骤文案、`scripts/hooks/shared-source-reminder.ps1`（新增 `server\metaserver\*` 提醒分支）、`AGENTS.md` 红线 1、`修改指南`（必跑表 ×2、出包前行）、`项目说明 04` 的 buildHash 节。
- **残留风险（如实登记）**：Meta 常量没有**构建期**门（无 Meta 发布脚本可挂，也不该挂到客户端出包门禁）——若改了 Meta 源而不重跑生成器，日志会报旧身份。缓解：生成器一次写两个常量 + hook 提醒 + `--check` 人工/CI 复算。

## 6. 顺带登记的新条目（审计未列）

**确定性拒绝的头阻塞**：`SettlementSubmitService.TrySubmitNext` 只取 `ListPending()[0]`，而非 2xx 一律"保持待提交重投"——Meta 返回 409（台账冲突）/400（载荷非法）时该条目**永不收敛**且**阻塞其后全部条目**（外加上限内退避重投属无效流量）。修法方向：区分"可重试"（5xx/超时/401）与"确定性拒绝"（除 401/408/429 外的 4xx），后者让位（跳过集 + 计数 + 告警）或按裁决终态处置，保留条目供人工恢复。**本批只登记**（改重试拓扑需设计裁决，且与 §2 设计文档"失败保持待提交"的原文冲突，须先改设计再改代码）。
