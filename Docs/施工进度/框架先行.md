## 5. 结论与下一步

**当前判定：框架准入仍未达成**（五包在"进行中"或"未开始"，五个样例无一成链）。但主动作已变了三次：**PlayMode 执行能力**从"不存在"到"已接入 L2 门禁"（样例验证取代接口存在性验收的执行层）；**服务端从单房间变成真正的多房间**（§116"任意 roomId 指向同一 Room"已不成立）；**热更端到端装配面已完整**（候选仍 fail-closed，缺的只是锚点 provisioning 这个运维动作，不是框架能力）。

剩余缺口**收窄为一条未交付前置件 + 两块覆盖度**：

**未交付前置件**——没有替代物，不补则对应准入项永远拿不到证据：

1. **§5-5 存储与幂等未开始**（依赖 Meta M0-c）——阻塞准入项「持久化契约有效」与样例⑤。

**覆盖度 / 运维动作**——载体、接口与装配面均已在：

2. **包④ 真实客户端全链路联合记录**——隔离、排空（第 2–3 步）、跨房间过载隔离**均已达成**；仍差"两个真实客户端过真实传输跑完整对局到结算"。设计侧固定 Worker Pool 与有界 Mailbox 属 R2；排空第 4–5 步依赖 M0-c 与 Worker 池。
3. **包③余部**——样例②余部（导航 Go/Back/Replace 真资源段、列表段、DevReload 环境重建段、输入锁恢复），准入项「资源与缓存稳定」「可诊断」「可扩展」缺的循环计数、端到端诊断与扩展点样例。
4. **包②收尾**——装配面已完整、链路可跑，但**零内置锚点**使候选一律被拒。补齐 ＝ 发布流程生成密钥对 → 公钥入 `ContentTrustAnchors` → 重新生成 → 随包发布（**运维 provisioning，非代码缺口**）。完成后解锁准入项「可构建与真实启动」「更新与配置可靠」与样例① 的验签/下载段。

**已消解**：~~§5-4 票据验证接口未交付~~（M0-d 2026-09-26）；~~包②端到端装配断链~~（2026-09-25 装配批）。

**下一步**：
- **包② 锚点 provisioning**——链路已通，只差密钥对生成与锚表重生成；这是解锁两个准入项的最短路径。
- 包③余部（见上第 3 条）——样例②/③的覆盖度段，可在客户端侧独立推进。
- 包④ 全链路联合记录——真实传输已有骨架（`MultiRoomTransportTests`），补"跑到结算"一段。
- 包⑤需等待持久化，且依赖 Meta 的 M0-c。

**三条实测教训**（均与"测试要测的就是它声称测的那件事"有关）：

1. **在途窗口必须由测试自己制造**：`LoadRealPrefabAsync` 原先直接 await 真实 IO，加载若同帧完成，

2. **取消的终态必须显式观测**：`ShowAsync` 的取消交付为 faulted task，未观测时 UniTask 记 unhandled
   异常并打 error 日志——**会踩 UI 门禁"Console 新增 Error 即判失败"**。用例须 `Assert.Throws` 取用。
3. **诊断用例先写再删**：先用 `CancelDiagnosticPlayModeTests` 打点确认取消路径本身正确
   （`open.Status=Faulted` / `IsOpen=False`），再改断言——避免"改测试迁就实现"掩盖真缺陷。
