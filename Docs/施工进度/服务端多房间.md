**会话路由键**：`Session.RoomId`（`RoomServer/Application/Session.cs`）——输入/断线/重连/离场先按它
找房间，再按 `PlayerId` 找席位。与 `PlayerId` 同为 App 层**路由缓存**，不构成身份（身份在 `Principal`）。

**端口归属澄清**：端口是**宿主级**参数（`RoomServerConfig.Port`），不是每房间一份。
此前 `RoomConfig.Port` 与配置端口并存，多房间下语义含混；已改为宿主从配置取端口，
`RoomConfig.Port` 仅在单房间兼容形态下使用。

## 3. 关键裁决与实测踩坑

### 3.1 玩法数值：进程级共享，配置层**显式拒绝**按房间覆盖（用户裁决 2026-09-26）

Sim 系统**静态读** `CombatConfig`：

| 位置 | 读取 |
| --- | --- |
| `InputSystem.cs:19-20` | `CombatConfig.MoveSpeed` |
| `MovementSystem.cs:23` | `CombatConfig.Gravity` |
| `ShootingSystem.cs:28,31,41,50,73` | `HitscanHeight` / `HitscanRange` / `HitscanRadius` / `BaseDamage` / `DamageSpread` |

`RoomRuntime.FixedConfig` 只快照 `Digest`，**不快照参与计算的值**——`FixedCombatConfig` 类注释自述
"单房间形态下两者一致，多房间差异在 R2 前不会出现"。

**因此**：若允许配置按房间写不同玩法数值，客户端拿到的 `ConfigHash` 与实际计算值会不符——分叉且不可见。
本批**显式拒绝**该形态（`rooms` 分区不得含名为 `combat` 的模板），并在类注释写明"每房间参数化依赖
Sim 侧迁移（G1/热更批）"。**这是把风险挡在门外，不是解决它**——Sim 参数化本身仍未做。

### 3.2 票据验证必须**先于**建房

动态建房下若先建房再验票，任何人拿垃圾 token 打不同 roomId 就能把房间表撑到容量上限 = 拒绝服务。
故 `HandleJoin` 顺序为：字段边界 → token 非空 → buildHash 红线 → **票据验签（含 roomId 绑定）** → 建房。
用例 `票据先于建房_垃圾票据打不同房号不会撑大房间表` 钉住该顺序。

### 3.3 会话表容量必须按**全服潜在连接数**算（实测缺陷）

原实现 `new SessionManager(4 * 首房间.ExpectedPlayers)`。多房间下这是错的：配置 2 人房、容量 8 房时，
会话表只有 8 格，**第二个房间的连接会被会话上限拒掉**（`OnTransportConnected` 超限即断开）。
实测表现为多房间用例大面积 NRE（席位表空）。

改为 `4 × MaxRooms × MaxExpectedPlayers`（`RoomServerConfig.MaxExpectedPlayers` 在装载期算好）。
单房间兼容形态仍沿用原口径。

### 3.4 配置驱动形态**不预置房间**

`ServerHost` 原构造即建一个预置房间。动态建房下预置会白占一格容量，且"该预置哪个 roomId"没有依据。
现：给 `config` → 预置该房间（单房间兼容）；给 `roomServerConfig` 而不给 `config` → **不预置**，
所有房间首次进房时按模板创建。冒烟实测 `房间数=0`。

### 3.5 `combat` 配置分区形状与 Luban 产物一致

`combat` 取数组形状 `[{...}]`（同 `tbcombatnum.json`），而非对象。这样配置既可直接内联，
也可由部署把表产物整段嵌入——**两条路产出的字节形状相同**，不会因形状不同多出一套解析分支。

### 3.6 设计文档 §1 成熟度表已同步（2026-09-26）

设计 §116 原记"当前任意 roomId 指向同一 Room"——该陈述在本批后已不成立。按用户指示，
设计侧 §1 成熟度表「多房间与扩缩容」行、§4 冲突裁定「多房间」「MVP 单循环」两行、
以及「身份与传输安全」行（M0-d 票据）已同步为当前状态并回链施工记录；版本 1.2 → 1.3。

同步遵循该文档 §0 的既有约定：**Current 只记已有代码/测试/运行产物证明的能力**，
未达项显式保留为 Target 并写明归属（固定 Worker Pool 与有界 Mailbox、房间销毁后清理、
drain 与过载隔离 → R2）。后续本文件状态变化时，该表需一并复核。

**样例④"至少两个独立房间验证隔离"的判据**（`MultiRoomIsolationTests`，11 例）：

- 两 roomId → 两个不同 `RoomRuntime` 实例（`NotSame`），席位各自从 0 起、互不可见；
- A 房满员开局不带动 B 房（B 房未进人 → **不存在**）；
- 同房号重复进房复用既有房间（非每连接一房）；
- 达容量上限拒绝新建房且既有房间不受影响；
- 断线只影响本房间，另一房间席位保持 Active；
- 每房间各自推帧：未开局的房间帧号不动；
- 票据绑定房间与所进房间不符 → 拒绝且**不留房间**；
- 垃圾票据打不同房号 → 房间表零增长（先验票后建房）。

### 2026-09-26 · 排空与跨房间过载隔离（框架先行准入项「联机宿主闭环」剩余缺口）

**目标**：把准入项「联机宿主闭环」推到达标——该条要求"入房、同步、重连、离场、**两房间隔离**和
**关闭排空**通过"。隔离已于同日达成，本批补后者，并把样例④的"真实客户端/真实传输"一半补齐。

**一、排空（设计 §12 优雅关闭五步）**

设计给的是**固定五步**，逐条对照实现（未覆盖的两步在代码注释与用例里显式标注，不留含糊）：

| 步骤 | 状态 | 落点 |
| --- | --- | --- |
| 1. Readiness 置 false，Lobby 不再分配 | **无此面** | 本服务不接 Lobby（实例注册/容量上报归 R2）；等价语义由 `ServerHost.Draining` 承担 |
| 2. 停止接受新 Join，现有房间进入 drain | **已实现** | `BeginDrain` → `HandleJoin` 一律拒绝（含已在册房间）；既有对局的输入/重连不受影响 |
| 3. 限时完成对局；超时归档 Aborted | **已实现** | 房间级 `DrainDeadlineMs`；到点仍未终态由 `Pump` 发 `ShutdownReason.DrainTimeout` |
| 4. 刷新 Outbox/Archive 到持久介质 | **未实现** | 无 Outbox，依赖 M0-c |
| 5. 停止 Worker/Transport/Host | **未实现** | 由调用方 `Dispose` 承担 |

- `ServerHost.BeginDrain(deadlineMs)` / `Draining` / `DrainComplete` / `CurrentMs`；
  幂等且**排空期限只可前移**（后一次调用不能延后已定期限）。
- 新增 `ShutdownReason.DrainTimeout`：与 `Operator` 的区别在**语义而非机制**——归档/日志据此区分
  "正常排空"与"排空超时被强停"。该枚举**不在 proto 内**（已核），加值不改协议。
- 常态入口接上：`Program.cs` 常驻形态改用 `Console.CancelKeyPress` 触发排空，不再直接杀进程。

**二、跨房间过载隔离（§514 / §593 / §560）**

`CrossRoomOverloadTests` 4 例。与既有 `RoomBroadcastTests`「背压超限_该客户端降档抽帧_其余客户端
不受拖累」的分工是**房间内 vs 跨房间**：那条靠 per-Session 记账隔开，本组靠 per-Room 管线 +
逐房间推帧隔开——**失效模式不同**，所以两组都要在。覆盖：整房被压时另一房的广播频率/推帧/管线水位
互不受影响；过载恢复只影响本房间。

**三、真实传输段（样例④"两个真实客户端"）**

`MultiRoomTransportTests` 5 例，真 KCP + 真客户端（127.0.0.1 回环）。与 `MultiRoomIsolationTests`
（假传输、纯命令面）的分工：那条钉路由与状态隔离的**逻辑**，本组钉隔离在**真实传输下**同样成立
（UDP 回环、编解码、连接与房间的绑定都是假件抹掉的）。覆盖：两客户端进两房各自满员开局、
A 房满员不带动 B 房、两房快照各不串房间、断线只影响本房、排空后新进房被拒而既有对局不停。

**两处实测踩坑（均是用例假象，非产品缺陷）**：

1. **`PumpNowMs` 不存在**——我凭印象写了这个 API，编译才红。改用 `ServerHost.CurrentMs`
   （与 `Pump` 的 `_nowMs`、`BeginDrain` 的截止时刻同一时钟源）。
2. **"不 ack"等价于"慢客户端"**——`StepPair` 首版没有 ack 语义，导致 B 房那个我从没 ack 的
   席位自己积压降档，断言 `BackpressureThrottled == 0` 失败（实际 72）。这不是背压缺陷：
   **水位只经验证过的 ACK 释放**，用例必须显式表达"谁在正常反馈"。改成 `ackA`/`ackB` 参数
   显式声明，并在注释里写明"没写 ack ＝ 这一房全员慢客户端"，避免后来者再踩。

**未验证（须如实标注）**：`Program.cs` 的 Ctrl+C → 排空路径**未做端到端验证**——本环境用
`Stop-Process` 只能硬杀，不触发 `Console.CancelKeyPress`。第 2–3 步的状态迁移由 13 例排空用例
（`DrainTests`）在宿主层覆盖，但"信号 → 排空 → 退出"这条进程级链路仍待在真实终端里手验一次。
