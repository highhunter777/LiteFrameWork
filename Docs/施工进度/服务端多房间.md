## 3. 关键裁决与实测踩坑

### 3.1 玩法数值：进程级共享，配置层**显式拒绝**按房间覆盖（用户裁决 2026-09-26）

Sim 系统**静态读** `CombatConfig`：

| 位置 | 读取 |
| --- | --- |
| `InputSystem.cs:19-20` | `CombatConfig.MoveSpeed` |
| `MovementSystem.cs:23` | `CombatConfig.Gravity` |
| `ShootingSystem.cs:28,31,41,50,73` | `HitscanHeight` / `HitscanRange` / `HitscanRadius` / `BaseDamage` / `DamageSpread` |

`RoomRuntime.FixedConfig` 只快照 `Digest`，**不快照参与计算的值**——`FixedCombatConfig` 类注释自述
"单房间形态下两者一致，多房间差异在 R2 前不会出现"。

**因此**：若允许配置按房间写不同玩法数值，客户端拿到的 `ConfigHash` 与实际计算值会不符——分叉且不可见。
本批**显式拒绝**该形态（`rooms` 分区不得含名为 `combat` 的模板），并在类注释写明"每房间参数化依赖
Sim 侧迁移（G1/热更批）"。**这是把风险挡在门外，不是解决它**——Sim 参数化本身仍未做。

### 3.2 票据验证必须**先于**建房

动态建房下若先建房再验票，任何人拿垃圾 token 打不同 roomId 就能把房间表撑到容量上限 = 拒绝服务。
故 `HandleJoin` 顺序为：字段边界 → token 非空 → buildHash 红线 → **票据验签（含 roomId 绑定）** → 建房。
用例 `票据先于建房_垃圾票据打不同房号不会撑大房间表` 钉住该顺序。

### 3.3 会话表容量必须按**全服潜在连接数**算（实测缺陷）

原实现 `new SessionManager(4 * 首房间.ExpectedPlayers)`。多房间下这是错的：配置 2 人房、容量 8 房时，
会话表只有 8 格，**第二个房间的连接会被会话上限拒掉**（`OnTransportConnected` 超限即断开）。
实测表现为多房间用例大面积 NRE（席位表空）。

改为 `4 × MaxRooms × MaxExpectedPlayers`（`RoomServerConfig.MaxExpectedPlayers` 在装载期算好）。
单房间兼容形态仍沿用原口径。

### 3.4 配置驱动形态**不预置房间**

`ServerHost` 原构造即建一个预置房间。动态建房下预置会白占一格容量，且"该预置哪个 roomId"没有依据。
现：给 `config` → 预置该房间（单房间兼容）；给 `roomServerConfig` 而不给 `config` → **不预置**，
所有房间首次进房时按模板创建。冒烟实测 `房间数=0`。

### 3.5 `combat` 配置分区形状与 Luban 产物一致

`combat` 取数组形状 `[{...}]`（同 `tbcombatnum.json`），而非对象。这样配置既可直接内联，
也可由部署把表产物整段嵌入——**两条路产出的字节形状相同**，不会因形状不同多出一套解析分支。

### 3.6 设计文档 §1 成熟度表已同步（2026-09-26）

设计 §116 原记"当前任意 roomId 指向同一 Room"——该陈述在本批后已不成立。按用户指示，
设计侧 §1 成熟度表「多房间与扩缩容」行、§4 冲突裁定「多房间」「MVP 单循环」两行、
以及「身份与传输安全」行（M0-d 票据）已同步为当前状态并回链施工记录；版本 1.2 → 1.3。

同步遵循该文档 §0 的既有约定：**Current 只记已有代码/测试/运行产物证明的能力**，
未达项显式保留为 Target 并写明归属（Worker Pool 运行时消息路由、房间销毁后清理 → R2）。
排空与跨房间过载隔离已有独立证据；后续本文件状态变化时，该表需一并复核。

**样例④"至少两个独立房间验证隔离"的判据**（`MultiRoomIsolationTests`，11 例）：

- 两 roomId → 两个不同 `RoomRuntime` 实例（`NotSame`），席位各自从 0 起、互不可见；
- A 房满员开局不带动 B 房（B 房未进人 → **不存在**）；
- 同房号重复进房复用既有房间（非每连接一房）；
- 达容量上限拒绝新建房且既有房间不受影响；
- 断线只影响本房间，另一房间席位保持 Active；
- 每房间各自推帧：未开局的房间帧号不动；
- 票据绑定房间与所进房间不符 → 拒绝且**不留房间**；
- 垃圾票据打不同房号 → 房间表零增长（先验票后建房）；
- **Worker 执行形态**（`WorkerExecutionContextTests` 2 例，真 KCP）：Join/StartGame/快照经 Outbound 回传到达客户端；两 Worker 两房并行互不串；全员离场由 Worker 收尾并销毁房间。

### 2026-10-04 · 排空第 5 步"信号→排空→退出"进程级手验（联机宿主闭环末项收口）

**需求**：「联机宿主闭环」最后一项——排空第 2–4 步已交付，但 `Program.cs` 常驻形态的
"信号 → 排空 → 退出"从未在真实进程上端到端验证（本环境 `Stop-Process` 只能硬杀、不触发
`Console.CancelKeyPress`——2026-09-26 段的原判仍成立，本次改用**控制台事件注入**完成手验）。

**方法**（Windows 控制台信号仅有的两种可控投递形态）：

- **构建**：`git worktree --detach` 干净 HEAD 源（`e306617`，不混并行线工作区 WIP）→
  `dotnet build Server/RoomServer -c Release`（**0 错误**；8 警告均为 kcp2k vendored SYSLIB0023
  与 Luban 生成代码 CS8981 既有项）。
- **运行形态**：生产入口（常驻、`workerExecution:true`、多房间懒创建），CWD=仓库根
  （`Config/roomserver.json` 与 `Outbox/settlements.journal` 按生产相对路径解析）；
  `--port 17997..17999 --allow-insecure-local`（本机联调裸 KCP——手验对象是关闭链路，与安全面无关；
  票据为原型形态未配 `--ticket-key`，对关闭链路同样无影响）。
- **注入**（外置 harness，仓库外临时件）：A/B 用 `CreateProcessW(CREATE_NEW_PROCESS_GROUP)` +
  `GenerateConsoleCtrlEvent(CTRL_BREAK_EVENT, pgid)` **定向**投递（Windows 不允许向独立进程组定向
  投递 CTRL_C_EVENT，Ctrl+Break 是唯一定向注入法）；C 先给 harness 独占分配**私有控制台**、
  子进程普通继承，再 `GenerateConsoleCtrlEvent(CTRL_C_EVENT, 0)` 广播**字面 Ctrl+C**
  （harness 以原生 handler 吞掉本进程信号，控制台内仅子进程收到——父 shell 不共享该控制台，绝无误伤）。
  .NET `Console.CancelKeyPress` 对 Ctrl+C/Ctrl+Break **同入口**派发、`Program.cs` 不分支
  `SpecialKey`——两种信号走同一条排空代码路径。
- **客户端**（B）：harness 内置真 KCP 无头客户端（`KcpTransportClient` + `PacketCodec`，
  `Token="test"`、`BuildHash=BuildHash.Value`，同 `MultiRoomTransportTests` 形态），全部调用
  封送至 10ms 泵线程（同 Unity 主线程使用形态）。

### 2026-10-03 · 结算 Outbox 完成语义与压实（架构审查 P1 修复——容量改按待提交计）

**缺陷**（2026-10-03 架构审查登记）：`FileSettlementOutbox` 无"标记完成"原语——待提交数恒等于历史累计数，容量按其判；长跑服务器累计到 `settlement_outbox_capacity`（默认 1 万）后**永久 `RejectedFull`**，新结算只计数不落盘。总设计 §11.3 的"Outbox 标记完成"在存储侧无承载。

**修复（§11.3 的存储半步；提交管道归 R3）**：

- `ISettlementOutbox` 增 `TryMarkCompleted(matchId)`：追加完成标记行（write-through，**标记行写先行**——崩溃窗口内"盘有标记、内存未及"自愈于重启重放；写失败内存不动可重试），条目退出待提交面；未知/已完成/写失败 → false（幂等）。
- **容量改按待提交数计**（`_entries.Count`）——标记即释放，长跑不再涨满；`Count`/`ListPending` 语义同步收窄为"待提交"（宿主 `SettlementOutboxPending` 标注本就是"待提交"，零改动）。
- **压实**：`Flush` 收口时（有未压实标记）或连续标记达 1024（自动，防判重集合随长跑无界增长）重写日志为仅含待提交行（temp 写全 + `File.Replace` 原子替换）；判重集合收敛为待提交——此后同 matchId 重入盒作为新待提交接受，重复提交不重复发奖由 Meta 台账唯一索引兜底（§11.2）。压实失败不抛：计 `CompactionFailures`、内存语义不变、下次收口重试，最坏回退 = 不压实（正确性不受影响）。
- 线格式**追加** `Kind` 字段（s=结算行 / c=完成标记行；缺省 = 结算行）——既有日志零迁移可重放；`RoomServerConfig`/`ServerHost`/`Program` 零改动（四态枚举与接线不变）。

**边界登记**：完成标记的**消费方**（拿到 Meta 幂等确认后调用的后台提交服务）归 R3——本批交付的是存储侧原语与有界性根治；压实会移除已完成行的判重记忆，"提交方在压实窗口内重发"依赖 Meta 台账幂等（设计内行为，已在用例钉住）。

### 2026-10-02 · R2 Worker 执行形态（Runtime 迁 Worker + Outbound 回传 + 房间 Owner 切换）

**交付**：`ServerHost` 新增 `workerExecution` 形态（生产入口 `Program.cs` 显式开启；嵌入式/历史用例保持默认
宿主 owner 直驱，语义零变化）：

- **Runtime 执行迁 Worker**：房间命令（Join/Input/Disconnect/Rebind/RestoreAck/Tick/Shutdown）与快照广播
  在 `hash(roomId)%workerCount` 归属的 Worker 线程执行（§8.2"一个 Worker 顺序驱动多个 RoomActor、
  每个 RoomActor 仍是单线程"）。宿主只做 Transport IO、准入、会话映射与回传应用。
- **Outbound 回传**：Worker 产出经每房间 Mailbox 的 Outbound lane 回传，限定三类事实——`RoomOutput`
  （纯输出）、`RoomSendItem`（发送意图：快照/重连响应，宿主编码并经 Transport 发送）、
  `RoomSeatReboundItem`（重连落定：宿主更新会话映射）。回传有界（lane 容量），入盒被拒显式计数。
- **房间 Owner 切换**：房间由宿主在 admission 时创建（验票/预留），随后交给归属 Worker 驱动直至终态；
  生命周期内不跨 Worker（hash 稳定；同房号重建后仍归同一 Worker）。交接的静默边界：销毁以
  "Worker 无在途驱动、无待驱动、三 lane 全空"为前提。

**线程边界（共享面）**：

- Worker 独占：RoomRuntime、SnapshotPipeline、房间广播记账、Mailbox 的 Control/Input 消费。
- 宿主独占：Transport、Session（连接/路由字段）、会话表、房间表、出站回传消费、Ops 汇总。
- 跨界全部经 Mailbox（不可变信封 + 值语义载荷）；发送目标在宿主侧按"会话存在 + 代次一致 + 未断开"复核。
- 宿主 owner 形态的会话级广播记账收进 `BroadcastAccount`（`Session` 转发成员保持历史调用面），
  Worker 形态用房间本地 `RoomBroadcastSeat`（连接号/相位取自 Runtime 席位，代次取自命令信封；换绑重置记账）。

**关键语义与实测踩坑**：

- Tick **合并节流**（至多一条在途）：Worker 落后时 Tick 堆积会把后续输入按"服务器已推进帧"整批判过期。
- 排空超时 Shutdown **只投递一次**（`DrainTimeoutIssued`）：否则每 Pump 重复入盒既放大超时计数又挤占控制 lane。
- **终态销毁等 Worker 静默**：Worker 执行 Shutdown 与宿主观察到 Closed 之间存在回传窗口，不静默就丢弃会把
  仍在路上的结算输出一并丢掉。
- **连接号是传输层原值**（kcp2k 用随机 int，**可为负**）——"无连接"哨兵必须用**相等比较**
  （`RoomOutboundEnvelope.NoConnectionId`）；旧式"`< 0` 即无连接"会把真实负连接号误判成无连接。真实传输用例
  实测踩中；同批修正宿主侧 `IsCurrentEnvelope`/`ResolveEnvelopeSession`/重连旧连接判定等同类写法。
- 迟到 Join（座位已占但发起连接已不在）：补发 Disconnect 释放孤儿席位；动态预留由
  `StaleJoinRollbackPending` 复检回收（保守的 JoinPending 全局扫描防误删在途房间）。

**未覆盖（如实）**：

- 房间**跨 Worker 迁移协议**未实现（§8.2"除非实现显式迁移协议"——首版不做；水平扩容仍走 Lobby 分配新实例）。
- `worker_count > 1` 的并行由 hash 路由天然提供，但**无负载再平衡**；房间数超过 Worker 数时同 Worker 顺序驱动。
- Worker 形态下输入/ACK 类 Ops 计数由多线程累加（Interlocked；周期行为近似读值），观测行定位不变。
- 宿主 owner 形态仍为嵌入式默认；两形态语义等价性由两组测试分别钉住（非逐条同跑）。
