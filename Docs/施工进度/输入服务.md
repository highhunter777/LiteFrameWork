## 定位与范围

设计文档里没有叫"输入服务"的模块——"输入"散在三处且各有归属：**玩法侧的采集与三个门**
（《角色状态与动作专项设计》§3）、**UI 侧的输入仲裁/焦点**（《UI 框架总设计》§6.2）、
**服务端的输入闸门**（`RoomServer/Runtime/InputGate`，本批不动）。本批做的是**第一处**：
把它从"C2 批② 落在 `LiteSim.View` 的采集类 + 流程里的一个裸委托"提升为一个有名字、有所有权、
可登记拦截源、可 L1 验证的框架服务；UI 侧的模态结论作为**一个具名拦截源**接入，不改
U1-③ 已交付的输入锁语义。

## 施工记录

### 2026-09-26 · 输入服务批：三个门收进框架服务

**为什么动**（原形态的三处问题，都是"看起来能用、验收时才暴露"的类型）：

1. **无所有权**：`PlayerController` 由 `ProcedureBattle` 每次进对局 `new` 一个；而它持有的
   "上下文门"查询（`Func<bool> isUiBlocking`）来自装配根。同一条链的裁决权拆在两处，
   服务关服/离场时没有统一的清空面（静态清零语义的实例版不存在）。
2. **拦下时静默改变玩法**：原实现门关时返回**全零意图**——UI 关掉后的那一帧，"一直按住"的键
   凭空断一次（**未实测**：该行为由代码路径直接推出——`Collect` 在门关时返回 `default`，
   而消费者每逻辑帧取值，故解拦后必有一帧零输入；本批按此推断修正，若真机上观感无误可回退）。
3. **三件（设备源/上下文门/帧边界门）只有两件有归属**：设备源与上下文门在 View/流程，
   帧边界门靠 `RollbackSim.PrepareNext` 的幂等性隐式成立——没有断言能钉住"追帧不产生额外输入"。

**代码位置（框架侧，`LiteGame.Runtime/Input/`，全部 `namespace LiteGame`）**：

- `IIntentSource.cs`（新）——设备抽象：键鼠与触屏输出同一份 Move/Aim/Buttons；**不自缓存位置**
  （瞄准换算的参照原点由调用方逐帧给出，避免设备侧留一份与裁决不同帧的陈旧原点）。
- `IntentGate.cs`（新）——拦截源注册表与**唯一裁决多项式**：任一源成立即拦下，
  先登记者优先报出理由（登记序即优先级）。零引擎依赖、零分配（`Evaluate` 每渲染帧跑，
  用索引 for + 原地压缩，不用 foreach 装箱枚举器）。容量 16，超出抛错（容量不足显性失败）。
- `InputService.cs`（新，`IInputService` 实现）——协调者：
  - **上下文门**：每渲染帧求值一次；拦下 → 本帧采样结论作废（`SampleDiposedByGate` 计数），
    待用意图保持上一次放行值；
  - **采样与上行**：`TryTakeForSend` 只在"本帧采到新输入"时报 true，与预测消费的是同一份；
  - **帧边界门**：`TryTakeForPrediction(frame, …)` 同帧第二次返回 false，未采样过也返回 false。
- `IInputService.cs`（新）——接口与三件契约文档；`KeyboardMouseIntentSource.cs`（新）——
  键鼠设备源（键位 + 鼠标地面射线），从 `LiteSim.View/Input/PlayerController.cs` 平移并**职责收窄**：
  不再自带上下文门/帧边界门，只回答"按键现在是什么"。

**代码位置（接线侧）**：

- `App/GameModules.cs`（改）——`InputModule` 模块（注册序在 `UiShell` 之后、`Container` 之前，
  Root 级、跨对局复用；`Shutdown` 走 `ResetAll`）；装配根登记唯一产品级拦截源
  `ui.modal`（`() => uiService.IsModalOpen`，经委托——流程仍不认识 UI 运行时，§5.1）。
  **模块类名是 `InputModule` 而不是 `Input`**：本文件 `using UnityEngine`，同名嵌套类会让
  `Input.GetKey` 这类既有引用解析到我们的类型（CS0117），属隐蔽破坏，已实测确认后改名。
- `App/Procedure/ProcedureBattle.cs`（改）——构造参数 `Func<bool> isUiBlocking` 换成 `IInputService`；
  `AttachView` 时注入本局设备源与相机（相机是局内对象，故设备源归阶段所有，离场 `SetSource(null)`）；
  `OnUpdate` 增加第 ① 步渲染帧采样（`SampleOnRenderFrame(_context.LocalPosition)`，位置取自 **Sim 预测态**
  ——不读视图 Transform，避免把平滑误差回灌进输入）。
- `Runtime/Battle/BattleContext.cs`（改）——`AttachInput` 收 `IInputService`；`Tick` 里把输入拆成两步：
  ① 第 `Frame+1` 帧的输入**先入本地预测史**（`RollbackSim.OnRealInput`，早到即入史），
  ② 同一份输入上行。顺序不可换——否则"发了但没预测"会让下一份权威快照判定不符，自造回滚。
- `Assets/LiteSim/View/Input/PlayerController.cs` + 目录（**删除**）——`LiteSim.View` 从此不持有输入；
  对应 asmdef 依赖未变（`LiteSim.View` 本就引 `LiteFramework.Core`，删类不收依赖）。

**实施口径偏离与登记**：

1. **服务放 `LiteClient.Runtime` 而非 `LiteSim.View`**：设备源要 `UnityEngine.Camera/mouse`，
   `View → Runtime` 会与既有 `Runtime → View`（`BattleContext` 用 `SimView`）成环。
   裁决：**Sim 输入行的生产者是客户端服务，不是表现层**——`BattleContext` 在 Runtime，
   它上行给服务器的是输入而非表现；`LiteSim.View` 保留 Sim/表现数学等消费者面。
   `SimInputFrame.cs`（Sim 侧契约）的注释同步从 `M11 PlayerController` 改为 `M11 输入服务`。
2. **上下文门语义：作废 + 保持，而非"输出全零"**。设计 §3 第 2 件字面是"UI/菜单打开时输出零战斗意图"，
   本实现把它落成**效果等价**的形态：拦下期间生效的意图恒为"最后一次放行时的意图"，UI 关闭后
   按住的键照常生效；差别在于**不再凭空插入一帧全零**（原实现会——见上"为什么动"第 2 条）。
   同时作废让 `TryTakeForSend` 不把最后一次意图反复重传。若验收要求严格零值语义，改回是
   `SampleOnRenderFrame` 里一行（`_pending = default` 而非 return）。
3. **不按会话相位拦**（曾拟登记 `session.reconnecting`）：断线但未出提示 UI 时（`SuspectedLost` →

   由 `ui.modal` 覆盖。此口径与 `ProcedureBattle` 原 `IsUiBlocking` 一致，不是新裁决。
4. **离散意图未实现**：Reload/Switch/Skill/Pickup/UseItem 需要按键沿检测 + 逐玩家单调递增的

   消费者是武器/Action 系统（归 G2）。本批设备源只产出 Move/Aim/Fire 三个连续意图，**不伪造 seq**。
5. **测试面**：`LiteSim.Core.Tests` 的 `RollbackSimTests` 与 Nightly L1 全套（含 `M10_LONGRUN`）

### 2026-10-02 · 输入分叉修复①②：拦下改空意图照发 + 追帧沿用帧补发

**为什么动**（用户审查发现的两处"本地预测输入 ≠ 服务器实际所得"分叉，同一根因两张面孔：

1. **① 上行门与预测门的新鲜度不对称**：被拦截源拦下（或设备未返回采样）的渲染帧里，预测侧
   沿用上一份意图推进（`TryTakeForPrediction` 只要 `_hasPending` 就返回旧值），上行门却因
   "本帧没采到"拒发（`TryTakeForSend`）——该帧输入永不发出。服务器对缺席帧的唯一读法是
   空输入兜底（`RoomRuntime.StepFrame`：`TryConsume ? stored : default`，`InputGate` 无
   "沿用上一份"路径）。移动中按住方向键时弹模态 → "本地继续走、权威已停"，每份快照和解回拉；
   持续拦截期间分歧持续累积（本地史还把这些帧 `OnRealInput` 成"已确认真实"，和解重放沿旧意图
   再走一遍）。附带伤害：拦下静默 >1s（`FullResendAckLagFrames`=30）会触发 `NeedsFull` 把
   **整帧**持续强制成全量（全房陪付带宽，`SnapshotDiffer`/`SnapshotPipeline.BroadcastIfDue`）。
2. **② 追帧突发的未上行预测帧**：`BattleContext.Tick` 每渲染帧只按 `State.Frame+1` 上行一帧；
   某渲染帧跑 ≥2 个逻辑帧（dt 尖峰/低帧率）时，多出的帧用"沿用上一帧"推进
   （`RollbackSim.PrepareNext`）且**永不发出**（帧号已翻页、冗余窗只含发过的帧）。服务器对
   这些帧按空输入执行 → 移动中每漏一帧分叉一个帧位移；~30fps 渲染时每渲染帧欠约一帧，
   成快照频率（30Hz）的持续橡皮筋，偶发抖动则单次回拉。

**代码位置与修复口径**：

- `Assets/LiteClient/Runtime/Input/InputService.cs`（①）——`SampleOnRenderFrame` 被拦与
  设备未返回两条路径统一改为：**写空意图 + 置"已采样"**（`_pending = default; _hasPending = true;
  _sampledThisRenderFrame = true`）。语义=「本帧没有战斗输入」三处同读：本地零意图预测、
  上行零意图包、服务器空输入兜底，逐位一致 → 不分叉。解拦后首个采样帧即恢复实时按键
  （`ProcedureBattle.OnUpdate` 采样 L298 先于 `Tick` L300，无凭空零帧）。
- `Assets/LiteSim/Core/Scripts/RollbackSim.cs`（②）——新增 `TryGetExecutedInput(frame,
  playerIndex, out input)`：读**已执行帧**的实际输入（含 PrepareNext 沿用帧；沿用帧 Buttons 已
  被 `PredictedButtons` 掩码，正是本地实际执行的那份）。帧号 ≤ 已执行帧、越界槽位拒绝。
- `Assets/LiteClient/Runtime/Battle/BattleContext.cs`（②）——`Tick` 在 `_sim.Tick` 之后把本
  渲染帧多执行的帧（`inputFrame+1..State.Frame`）逐帧经 `TryGetExecutedInput` 取回并
  `SendInput` 补发；每帧各自发包（`InputGate.Store` 每包只取 serverFrame+1 一帧，追几帧发
  几包），最近帧窗口自动携带更早帧兜丢包。断线（`!_battle.Connected`）不补发——那段空跑由
  重连全量快照和解收口。
- **对 2026-09-26 偏离登记 2 的推翻**：「作废+保持 ≈ 输出全零，效果等价」的论证只算了本地
  预测面，漏了上行/权威面（见①机制）；且"拦下期间生效的意图恒为最后一次放行值"连本地侧也
  违反《角色状态与动作专项设计》§6 验收"UI 打开时角色不动"（模态开着人继续走、开火位也在
  沿用）。本批恢复设计 §3 第 2 件的字面语义（零战斗意图），登记 2 的"解拦后凭空断一帧"顾虑
  在现架构下不成立（采样先于预测）。若产品后续要求"某类 UI 拦下期间保持移动"，应另行登记
  **非拦截**语义的来源（或服务器侧"沿用最后已知输入"），不得回到"本地沿用+上行静默"的组合。
- `Assets/LiteClient/Runtime/Input/IInputService.cs`——接口文档同步（上下文门条目、`Pending`、
  `TryTakeForSend`、`SampleWithNoSource` 口径）。
