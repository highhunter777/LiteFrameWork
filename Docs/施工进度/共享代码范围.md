## 批①（2026-10-01）

### 起因

专项盘查共享面时实测出 10 处越界与漂移，其中三条与"源集清单 / 双编件"直接相关：

1. **S0 源集清单跨语言各写一份，且已漂移**——`scripts/gen-build-hash.py` 的
   `DATA_TARGETS` 只有 `Assets/GameData/Config`、`DATA_EXTS = ('.bytes',)`；
   而 `Tests/LiteNet.Tests/BuildHashTests.cs` 是同一份清单**再写一遍**，且多出
   `RoomServer/Data` 与 `.json`。**该目录 2026-09-28 已随"服务端改读 .bytes"删除**，
   用例对不存在目录静默跳过 → **守卫对源集的复算有一半走空，且不报错**。
2. **`LiteNet/Diagnostics/` 的双编件不完整**——`LiteNet.csproj` 的 `Compile Include`
   是**逐目录列举**，新目录必须记得手工补（漏了 = dotnet 侧静默不编，Unity 侧 asmdef
   却会自动收）；`.gitignore` 白名单亦无该路径。
3. **`Luban.Tables.asmdef` 的 `noEngineReferences` 为 false**——它是"两端同代码同数据"
   的 S1 候选，却不满足 S1 义务 ①。

### 落地形态

```text

  ├─ TARGETS / DATA_TARGETS / DATA_EXTS
  ├─ DATA_EXCLUDE_NAMES / SKIP_DIRS / SELF_NAMES
  ├─→ Assets/LiteNet/Protocol/BuildHash.g.cs            常量（原有）
  └─→ Assets/LiteNet/Protocol/BuildHashSourceSet.g.cs   清单（本批新增，单源）

Tests/LiteNet.Tests/BuildHashTests.cs           读 BuildHashSourceSet，不再复写清单
Assets/LiteNet/LiteNet.csproj                   补 <Compile Include="Diagnostics/**/*.cs" />
Assets/LiteNet/Diagnostics/Directory.Build.props 新增（产物重定向）
.gitignore                                      补 !Assets/LiteNet/Diagnostics/*.csproj
Assets/GameData/Generated/Luban.Tables.asmdef   noEngineReferences false → true
```

### 过程中被守卫抓到的一处（G1 的第一个真实用例）

`BuildHashSourceSet.g.cs` 落在 `Assets/LiteNet/Protocol/`——**那正是 hash 源集目录**，
而收集规则是 `*.cs` 全收。首次跑 L1 当场红（`BuildHash_与当前源码复算一致_未忘记重跑生成器` FAIL）。
危害不止"自指"，而是**不收敛**：文件内容含 hash → hash 变 → 文件内容变 → hash 再变……
根因与既有的 `BuildHash.g.cs` 完全同类，故按同样办法处理：生成器与测试**同步排除 `SelfNames`**
（由单源清单下发，不再各写一份）。修后连跑两次 hash 稳定。

## 批②（2026-10-01）· 方向反转收口

### 起因（§7-1，🔴）

`LiteClient.Runtime.asmdef` **无条件**引用 `RoomServer.Runtime` + `RoomServer.Application.Runtime`；
唯一消费者是 `Assets/LiteGame/Runtime/Net/LocalServerTransport.cs`（离线隔离开发）。
`ProcedureMatch.cs:116-126` 有 `#if UNITY_EDITOR || DEVELOPMENT_BUILD || LITEFRAMEWORK_DEBUG`
**但 asmdef 引用是程序集级的，`#if` 只挡调用点、挡不住引用** → 两个服务端程序集进**所有**
Player 构建，并被 `LiteClient.Runtime` 的全部引用方传递性带上（含测试）。

### 三条路逐一收窄（实测，非推断）

| 路 | 判定 | 依据 |
|---|---|---|
| (a) 独立程序集 + 构建配置排除 | **否** | `DevHUD.cs` 记录的真实回归：「**Player 里的剥离由三宏负责，不需要也不应该靠程序集边界**」——DevHUD 曾用 asmdef 边界替代宏、结果 HUD 静默消失；且 `DevHUD` 的 asmdef 用 `autoReferenced:false` 也没挡住出包。asmdef 的真正"排除"手段只有 `includePlatforms:[Editor]`（会让 play 模式失效）或 `defineConstraints` |
| (b) 在装配处分档声明 | **采纳** | 设计 §3 D2 原文"必须在装配处分档声明——它是**调试宿主**关系"。且实测 `LocalServerTransport` **零依赖 `LiteClient.Runtime` 其它件**（只用 LiteNet/LiteSim/RoomServer），同程序集纯属偶然 → 可机械落地、无环 |
| (c) 条件剥离（`#if` + 宏） | 部分 | 调用点已有三宏门禁；但其**载重开关**实测不在 asmdef 可达范围内 |

**关于 (c) 的实测**：`LITEFRAMEWORK_DEBUG` **只在 dotnet 侧定义**
（`Assets/LiteFramework/LiteFramework.Core.csproj` 的 `DefineConstants`），
`ProjectSettings/ProjectSettings.asset` 的 `scriptingDefineSymbols` 与任何 asmdef
都**不含**它 → Unity 里本地服的实权开关是 `UNITY_EDITOR || DEVELOPMENT_BUILD`。

## 批④（2026-10-01）· `LiteFramework/Core` 收窄

### 起因（§7-4，🟠）

`LiteFramework.Core` 是 **S2 契约共享**档位，义务是"零引擎 + **零第三方实现依赖**"（S2 与 S1 的分界线）。
但它声明 `references: ["UniTask"]`——服务端若要用它的契约，会被迫拖进一个**实现级**第三方依赖。
且实测**零个服务端工程引用它** → "名为共享、实无消费者"。

### 关键实测：哪些是真依赖

| 文件 | grep 命中 | 判定 |
|---|---|---|
| `Fsm/ProcedureStage.cs` | 1 | ❌ **注释**（"Core 引不了 UniTask"）——非依赖 |
| `IO/FileSys.cs` | 1 | ❌ **注释**；异步签名本就是 BCL `Task`（"Core 零依赖纪律"） |
| `Hosting/{ClientHost,ClientModule,SharedLoadCoordinator}` | 12/2/7 | ✅ 真依赖 |
| `Config/ConfigSnapshotService`、`Content/{ContentOrchestrationPorts,CompositeHealthCheck,PatchCoordinator}` | 2/6/2/2 | ✅ 真依赖 |

**唯一硬反向依赖**：`ActivationTransactionStore`（留 Core）用 `ContentGeneration`（原在 `ContentContracts.cs`）
→ 故 `ContentContracts.cs` 必须**拆**：`ContentGeneration`/`AssetLease<T>` 留 Core，`IContentService` 进 Async。

### 过程中踩到并修正的两处

1. **csproj 与源码不同目录 → obj 目录打架**：最初把 Async 的 csproj 放在 `Assets/LiteFramework/`（与 Core 同目录），
   两个工程共用 `.dotnet/obj/` → `project.assets.json` 互相覆盖、**包静默不还原**（编译报 `CS0246 未能找到 Cysharp`）。
   **仓库既有惯例是每个 csproj 独占目录**（`LiteSim/Core/`、`RoomServer/Runtime/` 都这样）。已把 csproj 移进 `Scripts/Async/` 并配自带 `Directory.Build.props`。
2. **`ProjectReference` 相对深度算错**：csproj 移到 `Scripts/Async/` 后，`..\LiteFramework.Core.csproj` 会解析到
   `Assets/LiteFramework/Scripts/`（少一层），用 `dotnet msbuild -getItem:ProjectReference` 求值才定位到；已改 `..\..\`。
