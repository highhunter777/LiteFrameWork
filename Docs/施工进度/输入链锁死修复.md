## 缺陷（真缺陷，非设计意图）

**锁死主链**（每一环均有代码事实与 [Diag] 哨位实测）：

1. 客户端 `RoomClient.SendInput` 冗余窗＝**固定"最近 ≤4 帧"**（`_recentCount` 只看环内连续可用段）；
2. 预测领先（本地帧 − 权威帧）在本形态是**常态**——领先 >4 后，服务器要消费的 `serverFrame+1` 永远不在窗内；
3. 服务端 `InputGate.Store` 旧口径主帧取"窗内最大 ≤ serverFrame+1"——取不到即整包按越界丢弃（`DroppedOutOfRange` 按包增长、`AcceptedCount` 冻结）；且包内未来帧（> serverFrame+1）一律不预存；
4. 权威收不到输入 → 本地预测每份快照失配 → **按快照频率持续和解回滚**（橡皮筋/锁死，不可自愈）。

**伴生缺陷三处**（同批根治）：

- **多步渲染帧空输入分叉**：一渲染帧走 2+ 逻辑帧时，进程内权威与客户端共用累加器且**先**步进——客户端输入三件在 `TickOutgoing` 之后才做，多出的帧被权威按空输入兜底执行，与本地沿用逐位分叉 → 每份受影响快照都和解（低帧率下成快照频率橡皮筋）。
- **追帧补发按下标读错行**：`TryGetExecutedInput(frame, playerIndex)` 按数组下标读回，但历史数组由 SimStep **就地按 EntityId 排序**、远端槽位常携带零身份（排在最前挤位）——下标口径会取到别人的输入发出。
- **和解重放终点无上限**：卡顿帧"同步采纳 + 本地步进"逐次把领先顶高——越过输入冗余覆盖范围后服务器再也找不到所需帧号，锁死形态不可自愈。
