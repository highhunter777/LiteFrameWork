# 模块拆分施工进度：GameModules 按件拆到 App/Bootstrap

> 依据：《客户端总设计》§5.1（"只在隔离外部 IO、平台 API、所有权或存在真实替代实现时增加接口；
> 禁止为每个类机械创建接口"同一段的**启动模块命名**约定——本次新增）、§6.1（按依赖顺序初始化、
> 失败只关已成功者、关闭逆序）、§5.1 逻辑边界（流程不认识 UI/适配器运行时）。
> 本文件只记录施工状态与证据；目标与验收以设计为准，不在此重复定义。

## 起因

`App/GameModules.cs` 515 行，11 个 `IClientModule` 实现全嵌在一个 `internal static class GameModules` 里。
**它不是被设计成这样的，是搬家的落点**：`c74e78b`（第三刀）把 `GameEntry` 与 `GameModules` 从
`Main/` 整体迁进 `App/`，当时目的是量"Runtime 里除装配根还有没有适配器依赖"（用编译器量，
只报 2 个错、全在两行 `new`）。之后该文件只被改过 5 次，没人回头拆。

体量分布：9 个叶子模块 15–73 行，`Container` 160 行（占 31%），外层壳 2 行。

## 裁决（2026-09-26）

用户裁决**全拆**（不是只拆 Container）。拆出后新增一条**命名约定并写入设计**（§5.1）：

> 装配根注册的 `IClientModule` 实现一律 `<能力>Module`，一件一文件、顶层类，住 `App/Bootstrap/`。

**为什么必须有后缀**（这不是风格偏好，是可裁决的技术约束）：模块类名取自领域通用词——
`Content`/`Config`/`Settings`/`Input`/`Clocks`/`Container`。放顶层会与**既有类型或引擎 API 争名**：
本批实测，`Input` 作为顶层类会劫持 `using UnityEngine` 文件里 `Input.GetKey` 的解析（CS0117）。
加 `<能力>Module` 后缀，才使"每件一文件 + 顶层类"这条路成立。

`GameModules.cs` 删除；装配序列移入 `GameEntry.RegisterModules(host)` —— **调用序即依赖图**
（`ClientHost` 不推断，§6.1），并在每个 `AddModule` 后标注该模块的依赖来源。

**为什么不引入 `namespace LiteGame.Bootstrap`**：本仓命名空间是**每程序集一个**
（`LiteGame` / `LiteGame.UI` / `LiteSim.View`……），顶层类合既有做法；用命名空间分隔还要先改
命名约定，收益不足。类名后缀已解决争名问题。

**过程中被编译器抓到的一处**：`RegisterModules` 初写成 `static`——`LuaHostModule(gameObject)` 需要
实例的 `Component.gameObject`，CS0120 当场红。保留**实例方法**是正确形态（`GameEntry` 是
MonoBehaviour，宿主对象即引导件自身）。

**边界与未做**：

1. **`App/Bootstrap/` 目录不进 `ScanTargets.LiteGameTopLevelDirs`**——该表管 `Assets/LiteGame/*`
   顶层；`Bootstrap` 在 `App/` 之下，由 R8/R12 的 `Assets/LiteGame` 全域扫描覆盖（该扫描排除
   `Editor/`，但 `Bootstrap/` 是要被扫的运行时装配代码）。
2. **模块仍是 `internal`**：装配根与模块同程序集，不对外暴露；跨程序集引用者（DevHUD 已并入
   Editor 程序集）如需观测，走既有的 `IModuleStats` 面而非直接引用模块类。
