> **批次**：服务端审计 P0（三条急件）　**日期**：2026-10-11　**状态**：已完成（附验证证据；未提交）
> **来源**：《[代码质量审计：服务端](../审计/代码质量审计-服务端.md)》§P0 急件——① `SettlementOutbox` 跨线程数据竞争；② `ServerLoop` 60Hz 权威循环无异常吸收 + `expected_players` 与内核容量失配；③ proto→`SimInputFrame` 双手抄（已真实漂移一次）。
> **口径**：修法照审计给的方向（"加锁 / 包 try-catch + 对齐校验 / 抽共享 mapper"），**不改对外行为契约**（除 §2 明确的两处加固：异常不再杀死循环线程、越界配置装载期即拒）。

### 1. P0-1 `SettlementOutbox` 跨线程数据竞争

**现场（三条线程汇合，全类零同步）**：

| 入口 | 线程 | 出处 |
|---|---|---|
| `Enqueue` | ServerLoop 权威循环（60Hz） | `ServerHost.ApplyOutput` 的 `SettlementReadyOutput` 分支 |
| `ListPending` / `TryMarkCompleted` / `Count` | `SettlementSubmitService` 后台线程（`Thread "SettlementSubmit"`） | `SettlementSubmitService.TrySubmitNext` / `PendingCount` |
| `Flush` | 排空收尾路径（主线程） | `Program → host.FlushSettlementOutbox()` |
| `Count`（Ops 行） | 权威循环（打印时） | `ServerHost` Ops 行读 `SettlementOutboxPending` |

`_entries`（`List<PendingSettlement>`）/`_seen`/`_completed`（`HashSet<string>`）/`_marksSinceCompaction`/`_stream` 全裸并发——`List<T>.Add` 与 `ToArray` 并发即"枚举中改动"或目标数组长度不足，`HashSet` 并发写可静默损坏，`FileStream` 并发追加可写坏日志行（重启装载即报坏行）。

**修法（单临界区；审计"加锁或单线程编排，小"）**：`FileSettlementOutbox` 新增 `_gate`，`Count`/`Enqueue`/`TryMarkCompleted`/`ListPending`/`Flush`/`Dispose` 全部入锁；`Compact()` 显式声明"调用方须持锁"。
- **锁内只做内存 + 单行追加写**（write-through 本就是同步落盘，量级 KB）；
- **HTTP 不在锁内**：提交方先 `ListPending()` 取快照 → 锁外 POST → 按 matchId `TryMarkCompleted`（接口语义天然支持分步：标记按 id 幂等，不依赖先前快照）；
- 接口 `ISettlementOutbox` 补**线程契约**注释（三条线程 + "实现必须并发安全"+ HTTP 不得进实现内部），类注释补"跨线程安全"条目。
- **残留代价（如实登记）**：后台线程触发压实（重写全日志）时，权威循环的 `Enqueue` 会等锁——压实每 1024 条完成标记才发生一次，量级毫秒。若将来成为抖动源，改法应是"压实出临界区"，本批**不做**（那会把原子性问题换成一致性问题）。

**验证**：新增 `SettlementOutboxFileTests.并发入盒与标记_无结构损坏_账目自洽_日志无坏行`——2 个入盒线程 + 2 个提交线程（全程与入盒重叠：快照/标记/Flush/诊断读），断言 ①无异常 ②400 条全部 `Appended` ③排空后待提交面归零 ④**重开日志 `SkippedCorruptLines == 0`**（并发追加若无线程纪律会留交错半行）。
**反向对照（去锁即红）**：`git stash push -- Server/RoomServer/SettlementOutbox.cs` → 同用例 **FAIL**；`git stash pop` → **PASS**（同一用例、同一机器，正反对照闭环）。

### 2. P0-2 权威循环异常吸收 + 席位容量两侧对齐

**现场**：`ServerLoop.LoopBody` 的 `_pump()` 无 try/catch——线程是 `IsBackground`，抛异常即死：进程既不推进对局也不退出（僵尸），且**无任何日志**。对照 `RoomWorkerPool` 的 worker 隔离，同系统两种纪律。**触发源现成**：配置 `expected_players` 允许 1..64，内核 `PendingInputRing` 硬限 1..32；33+ 席位让 `RoomRuntime` 构造抛异常，而 `OpenRoom` 的 try 只包了 `BuildRoomConfig`，异常一路窜上循环线程。

**修法（三件）**：
1. **吸收 + 计数 + 节流上报**：新增 `ServerLoop.PumpOnce()`（`Run`/`LoopBody`/`StepCatchUp` 三处帧体调用统一走它）——异常一律吞下，计 `LoopStats.PumpFailures`、记 `LoopStats.LastPumpError`；上报节流"首败必报 + 其后每 100 次一次"（坏配置"每帧必抛"不得刷屏，但也不得静默）；上报口 `Action<Exception> onPumpError` 由宿主注入（Shell 层才允许 Console）。
2. **上界单源**：内核新增 `PendingInputRing.MaxPlayerCapacity = 32`（构造校验改用之），宿主 `RoomServerConfig` 的 `expected_players` 上界改引同一常量——两侧各写死过一次的漂移面消除，越界配置**装载期**即拒。
3. **建房 try 包住内核构造**：`ServerHost.OpenRoom` 的 try 覆盖 `AddRoom`（构造失败 → `RoomsRejectedBadConfig++` + 日志 + 拒绝该房号），不依赖上游校验的兜底。

**观测面**：`LoopStats.PumpFailures` → `Ops` 行新增 `loop: pumpFail=`（>0 = 权威帧体在抛且已被吸收）；`Program` 跑满时长行新增 `泵失败=`（附最近一次异常描述）。

**验证**：`ServerLoopTests` 新增 2 例——`帧体持续抛异常_循环不中断_计数与首败加每百次上报`（虚拟 2s=120 帧每帧必抛：`pumped==120`、`Ticks==120`、`PumpFailures==120`、上报恰 2 次）；`帧体抛异常_无上报口_仅计数不中断`。`RoomServerConfigTests` 新增 `单房间人数超内核容量_装载期拒绝_边界值合法`（33 拒 / 32 收）。

### 3. P0-3 proto→`SimInputFrame` 单一映射（双手抄）

**现场**：`ServerHost.HandleInput` 与 `LocalServerTransport.HandleInput` 各手抄一份"逐字段拷贝 + 冗余窗截断"，注释自述 **AimPoint 六字段已真实漂移过一次**（真服断点而本地服照常——本地绿掩盖真服红）。无共享 mapper。

**修法**：**共享 mapper 早已存在但未被使用**——`LiteNet.Protocol.InputPacker.FromProto`（`LiteNet.csproj` 注释明写"输入/槽位与 Sim 结构体的 proto 映射是协议层职责（协议单源）"，两个宿主程序集均已引用 `LiteNet`）。本批在 `InputPacker` 补 `UnpackFrames(msg, into)` = "整批解包进复用数组，返回**原始条数**"（截断上界取打包侧 `MaxRedundancy`，与 `ClientInputBatch.MaxFrames` 由 L1 契约用例钉死同值），两个宿主站点改为一行调用——**漂移面结构性消除**（含 Count/Frame/AckSnapshot/ViewFrame 的装配序原样保留）。

**验证**：`InputPackerTests` 新增 2 例——`映射_全字段面逐项钉住_十字段无一漏`（把 **10 个字段**全部填成可区分值逐项断言；原用例只钉 6 面，`SelectedWeaponSlot`/`TargetEntityId`/`ActionSeq` 此前无护栏）与 `解包整批_与单帧映射同源_超窗不越界写`（含"包内条数被人为撑过窗口时不越界写、原始条数如实返回"的防御面）。

### 1. HTTP 成功判定改 2xx 区间（①）

| 位置 | 改前 | 改后 |
|---|---|---|
| `LobbyRegistrationClient.TrySendOnce`（注册/心跳） | `(int)response.StatusCode != 200` → 记失败 | `!response.IsSuccessStatusCode` → 记失败 |
| `SettlementSubmitService.TrySubmitNext`（结算提交） | `(int)response.StatusCode == 200` → 标记完成 | `response.IsSuccessStatusCode` → 标记完成 |

同批改正 `SettlementSubmitStep.Submitted`/`Failed` 与类注释里的 "200" 口径（文档随代码）。

**同批登记的相邻缺陷（本次未修，见 §5）**：非 2xx 里包含 409（Meta 台账冲突）与 400（载荷非法）这类**确定性**拒绝——现策略是"保持待提交 + 指数退避重投"，对确定性拒绝**永不收敛**，且因 `TrySubmitNext` 只取 `ListPending()[0]` 会**头阻塞**后续所有条目。修它要动重试拓扑（跳过集/终态处置），超出本批"判定区间"的范围，故登记为待办。

### 2. 实例密钥按注册/结算分权（②）

**现场**：`/matches/result`（写结算账本）与 `/lobby/instances/register`（注册实例）共用同一份实例密钥（Meta `LobbyInstanceKeyBase64` ≡ 房间端 `--lobby-instance-key`）。`InstanceKeyAuth` 注释自认"日后若需分权再拆独立密钥"——即两条权限面从未分离：**能注册实例的凭据即可写账本**，任何一处凭据分发泄露同时放大到资金面。

**修法（两条权限面各一份凭据，缺则 fail-closed）**：

| 面 | Meta 配置 | 房间端注入 | 校验点 |
|---|---|---|---|
| Lobby 实例注册 | `LobbyInstanceKeyBase64`（不变） | `--lobby-instance-key` / `LITENET_LOBBY_INSTANCE_KEY`（不变） | `/lobby/instances/register`、`/lobby/rooms` |
| 结算提交 | **新增 `SettlementInstanceKeyBase64`**（空 = 该端点 503 功能关闭） | **新增 `--settlement-instance-key` / `LITENET_SETTLEMENT_INSTANCE_KEY`**（缺则**启动即拒**） | `/matches/result` |

- `MetaConfigValidator`：给了结算凭据就必须合法（Base64 ≥32 字节，原值不回显）；**不给不报错**（与 Lobby 同款"空即关闭"）。
- 房间端**不做回退**：结算管道启用而缺结算凭据 → 抛（提示新 CLI/env），不静默复用 `--lobby-instance-key`（那等于把分权又抹平）。
- `InstanceKeyAuth` 类注释改为"凭据按权限面分离，由调用方传入对应面的期望值"。
- `Config/roomserver.json` 注释同步（结算凭据不在文件、与注册分权、缺则拒启）。

**验证覆盖（如实）**：配置面由 L1 `MetaConfigTests`（新增 2 例：非法值拒绝/原值不回显 + "两个独立字段互不推导"）；端点面由 L3 `SettlementL3Tests`（改用分离密钥 + 新增"Lobby 凭据写结算账本必 401"正证）——当时 **L3 本机跳过**（`MongoFixture` 不可用，4 例 skipped，与 P0 批同款环境限制）。
**已补验（2026-10-11）**：本机 `litegame-mongo`（单节点副本集 `mongo:8.0` @ `127.0.0.1:27017`）起后补跑 **L3 164/164 · 0 跳过**——结算闭环与分权正证**均已实证**，此处"未验证"结论**作废**。**残余缺口据此关闭**：L1 面"端点确实读结算凭据"确实做不出可执行断言（端点序"功能门 → 凭据 → 存储"，存储装配需真 Mongo 且启动迁移 fail-closed，无 Mongo 时到不了凭据分支——这是"功能门先于鉴权"这条**有意**规则的代价，不为测试改序），但该分支已由 L3 覆盖，**不再以"未验证"留档**；口径随之更新为"该面由 L3 把关"（见 `修改指南 §4 L3 前置`）。

### 3. `/auth/guest` 请求体解析异常面统一（③）

`AuthEndpoints` 原来只 `catch (JsonException)`——`ReadFromJsonAsync` 对**非 JSON content-type** 抛的是 `InvalidOperationException`，于是 `POST /auth/guest` 带 `text/plain` 会**未处理异常 500**，而同形状请求在 Lobby/Settlement 得 400。改为与另两处同形：

```csharp
catch (OperationCanceledException) { throw; }   // 请求中止随管道传播
catch (Exception) { command = null; }           // 坏 JSON / 非 JSON content-type / 形状失败 → 400
```

（顺带移除随之无用的 `using System.Text.Json;`。）端点层"反序列化收口块 4 份近似拷贝"的**收敛**（审计 §二[中]）属 P2，不在本批。

### 4. Meta BuildHash 接真（④）

**先更正审计的前提（以代码为准）**：审计写"Lobby 版本准入与票据盖章消费的就是这个假哈希"——**不成立**。唯一消费点是 `MetaHost.BuildIdentity → Program.cs` 启动日志的 `build=`；Lobby 的版本准入（`InstanceRegistry.TryAllocate(requiredBuildHash)`）与票据盖章（`LobbyTicketSigner.Issue(..., chosen.BuildHash, ...)`）消费的是**房间实例上报的** buildHash，其值为 `LiteNet.BuildHash.Value`（真值，且受 `--check` 门禁把守）。故"门禁挡版本准入"这条在本代码上无对象可挂。

**实际缺陷**：手写占位 `BuildHash.Value = "meta-0.0.0-unwired"` 是"看起来像版本号却没有来源"的假身份（还带 `0.0.0` 让人误读为语义化版本）。

**修法（接真）**：`scripts/codegen/gen-build-hash.py` 扩为**两个目标**（同一生成器、同一复算规则）：

| 目标 | 源集 | 输出 | 用途 |
|---|---|---|---|
| shared | `SHARED_TARGETS`（Sim/协议/安全信封）+ 表数据 | `Assets/LiteNet/Protocol/BuildHash.g.cs` | **两端握手红线**（Join 校验） |

| 存储未确认 503 | `{code:"store-unavailable", reason:"…内部原因…"}` | `{code:"profile.store-unconfirmed", messageKey:…}`（内部原因**不出响应体**） |

**协议级错误（请求未被受理）→ `{code,messageKey,args}`；领域结果（含 409 冲突）→ 领域 DTO；探针端点 → `text/plain`（编排器消费）。**

**过程更正（如实登记）**：本批初稿曾以"L3 本机不可执行，不在盲态下改对外契约"为由**裁决不改**；用户指出本机有 docker mongo 后复核——`litegame-mongo`（单节点副本集 `mongo:8.0`）可起，**L3 可跑**。前提失效即重做，没把"跑不了"当结论留着。断言同步钉死统一体（`503→code=profile.disabled`、`400→code=profile.invalid-request` + `messageKey` 在场、409 补钉 `expected`/`actual` **双数字**）。
**过程中的一次真红**：409 断言我先写成 `"expected":0`（实际是请求带来的 `9`）——L3 当场失败并指名用例，改回后全绿。这正是"能跑就必须跑"的价值：该断言在 L1 不可能暴露。

- **确定性拒绝**（**载荷级 4xx**：400 载荷非法 / 409 台账冲突 / 413 / 422）→ **不无限重投**：Outbox 追加**弃置标记行**（`Kind="x"`，含原因）退出待提交面并**让位**后续条目，计数 `Abandoned` + 警告日志；
- 弃置标记写介质失败 → 按可重试失败处理（事实不丢）。

### 2. 实现

| 层 | 改动 |
|---|---|
| `ISettlementOutbox` | 新增 `bool TryAbandon(string matchId, string reason)`（终态处置口；线程/幂等/介质失败口径同 `TryMarkCompleted`，注释写明） |
| `FileSettlementOutbox` | ①`TryAbandon`：**标记行写先行**（崩溃自愈口径同完成标记）→ 写失败内存不动（保持待提交）；②装载把 `Kind="x"` 与 `"c"` 同路处理（退出待提交面）并计数；③新 `Abandoned` 属性（装载重建 + 运行时累加）；④journal `JournalEntry` 追加 `Reason` 字段（追加字段，旧行兼容；线格式注释同步 `x`） |
| `SettlementSubmitService` | ①新步 `SettlementSubmitStep.Abandoned`（Loop `continue` = 立即让位）；②`IsDeterministicRejection` 判据（**400/409/413/422**；401/403/404/408/429/5xx **保持可重试**——判据与理由写进注释）；③失败分支：确定性 → `TryAbandon` 成功则计 `Abandoned` + 清 `_consecutiveFailures`（弃置≠端点不健康，不推退避）+ 警告日志；写失败回落可重试失败；④`Abandoned` 计数读口；⑤类注释与 §2 引文同步 |
