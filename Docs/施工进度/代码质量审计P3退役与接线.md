## 1. Meta Outbox：装配退役，端口/实现保留（附两处前提更正）

**现场**：`Contracts/Persistence/Outbox.cs`（端口 + 载荷/结果三态）、`MongoOutboxStore`、
`MetaHost` 的 `AddSingleton<IOutboxStore>`；生产零消费者；L1 内存替身（`FakeOutboxStore`）+ L3 真 Mongo
（7 例：入队序/唯一索引/容量拒/确认不复活/失败可重试/客户端重建/容器重启）均已实证。

**前提更正一（审计原文"当前每请求白挂一条存储依赖"）**：不成立。DI 是**惰性工厂**，`IOutboxStore`
在生产代码里从未被解析，注册本身不产生每请求成本。真正的问题是**误导信号**——一个注册了却没人解析的
服务，读图者会以为"Meta 外发 Outbox 功能已在跑"。

**前提更正二（审计原文"纯预置基础设施"）**：它是**设计交付物**，不是无主预置——Meta 专项 §3.1 把
`Outbox/Inbox` 列在 Shared Infra；§14-G1 明写"**只建接缝**：必要存储端口、迁移/事务/幂等约束、故障夹具"。
即：**端口与故障夹具正是 G1 要交付的东西**。

**裁决：退役"装配"，保留"接缝"。**

- **做**：删除 `MetaHost` 里的 `AddSingleton<IOutboxStore>`，原地改写为显式的"未接线（G3）"注释，
  并给出 **G3 接线清单**：① 此处补一行注册；② §10 优雅关闭第 3 步（刷新 Outbox）调用刷新；
  ③ `/ready` 增"Outbox 未超阈"判定。
- **不做①（不删端口/实现/用例）**：G1 交付物 + L1/L3 已实证，删掉等于把验证过的接缝再写一遍并丢回归覆盖；
  设计明确其归属，G3 只差一行注册。
- **不做②（不接线）**：**当前没有可接的消费者**——Meta 的结算路径是"事务内落账 + 重试由 RoomServer 侧
  Outbox 承担"（§8.2 的流程图即如此），Meta 自身没有外发写。为了"消灭死件"而临时造一个消费者，
  才是真错（凭空加一条无业务含义的存储写）。
- `MetaConfig.OutboxCapacity`：保留（§10 要求 Outbox 容量有范围校验），注释标注"当前无消费方（G3 启用）"。

**验证**：`OutboxPersistenceTests`（L1，内存替身）8 例、`MongoOutboxL3Tests`（L3）7 例均**直接构造实例、
不经 DI**，故装配退役不影响其覆盖；L1 1594/1594、L3 164/164 全绿。

## 2. 样例链路出生产构建（`MetaConfig.EnableSampleEndpoints`，缺省 false）

- **门控两处、同一个门**（都用 `boot` 门读，与既有 `MongoConnectionString`/`AuthSigningKeyBase64` 同款）：
  `SettlementSampleUseCase` 的注册 + `SampleEndpoints.Map(app)`。
- 默认（= 生产形态）：**路由根本不存在 → 404**。这一点是刻意的：如果只是"端点挂着但必然 503"，
  生产环境仍多暴露一个非业务面（攻击面与误用面都在），那是"退役了一半"。
- 显式开启 + 未配置存储 → 503（口径不变，错误体仍是 P2 批二收口的 `{code,messageKey,args}`）。
- **用例更新（L3）**：原 `未配置存储_样例端点503_拒绝相应功能` 重写为
  `样例链路_默认不挂载404_显式开启且无存储则503`——一个用例同时钉住"生产默认不存在"与"开启后功能门生效"；
  夹具 `StartHostAsync` 增 `EnableSampleEndpoints=true`（其余 4 例正是样例链路的验证面）。
- 判据：样例链路是《框架先行》样例⑤的验证载体（审计 §三：生产构建里没有消费者），不是业务面。

## 4. 结算 Delta：占位改**显式接缝**（不"补真"——设计未定义口径）

**为什么不能补真（证据链）**：

1. 设计规定了 RewardDelta 的**形状与归属**：《游戏业务系统总设计》§342
   `RewardDelta{settlementId,matchId,playerId,exp,currency,items,consumptionDelta}`；
   《Meta 服务专项设计》§3.1 分工表"奖励数值计算归 RoomServer，**Meta 只接受受验证 RewardDelta，不重算**"。
2. 设计**没有规定任何奖励口径**：全仓 grep（`Assets/GameData`、`CombatValues`、`WeaponTable`、各设计文档）
   无 reward/奖励字段、无"每杀多少经验/货币"的定义。
3. 项目自身的排期也把它放在**后面**：R3-Profile 记录与 `Meta服务专项设计 §8.2 实装口径`都写"真实
   RewardDelta 换算归 **P4**"；`待办总览` 亦列在 P4/P5。
4. 服务端总设计 §520/§600 红线：**不把估算值写死为事实**。凭空定一套"每杀 10 经验"会立刻成为对局经济的
   事实标准（客户端/运营/后续批次都会照着它走），比"暂时 0"更难收回。

**因此 P3 交付"唯一注入点 + 显式无经济实现"**：

- 新增 `Server/RoomServer/SettlementRewardPolicy.cs`：`ISettlementRewardPolicy`
  （`RewardDelta(playerId, kills, deaths)`，入参是本局**受验证的冻结事实**）+ `NoEconomyRewardPolicy`
  （delta 0 单例）；
- `SettlementSubmitService.Settings.RewardPolicy`（缺省 = 该单例）；`Program` 装配处**显式传入**（让接缝可见）；
- `BuildPayload` 是**唯一换算点**：`Delta = _rewardPolicy.RewardDelta(...)`，注释写死"别处不得自算 delta"。

**口径变化**：从"隐式 0 + 注释说归 P4"→"**显式无经济策略 + 可见注入点**"。P4 定口径时**只改装配一行**
（`RewardPolicy = new XxxRewardPolicy(...)`），提交管道、载荷形状、Meta 侧零改动。

**验证**：新增 2 例——`奖励换算_经注入策略取值_管道不自算`（注入每杀 10 → 载荷 `delta` 40/10）、
`奖励换算_未注入策略_缺省无经济即零`。
