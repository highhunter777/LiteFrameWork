### 排查结论（两条独立原因，缺任一条都解释不通）

| # | 原因 | 证据（改前） |
| --- | --- | --- |
| ① **决定性**：`Page_Lobby` 整场会话只查一次投影，且**没有任何刷新入口** | 查询只在 `OnShow`（`Page_Lobby.lua:37` 改前）；页面无 `OnUpdate`（无轮询）、prefab 无刷新钮；**从战绩页/设置页回大厅也不重查**——`Bridge.ui.Show` 走 `ui.Show`/`GoAsync` 后按 `Replace` 回大厅时目标是**已处于 Covered 的**同页，`UIService.ShowAsync` 对已打开页（Active/Covered/Paused）幂等返回且明确"不暗中再次 OnShow"（`UIService.cs:153-158`）；遮盖页关闭走 `OnReveal` 而非 `OnShow`（`UIForm.cs:201-205`） |
| ② **量级**：投影本身最长 10s 不变，且房间在"房主真正坐下"前不存在 | 房间明细随 RoomServer 心跳上报（`HostAssembly.cs:190` → `ServerHost.RoomSummaries()`），`Config/roomserver.json:15` 心跳 `heartbeat_interval_ms=10000`（Meta 侧存活时限 30s，`MetaConfig.cs:116`）；房间实体随**首入座者**物化（`ServerHost.cs:812-827` 的 `OpenRoom` 在 join 路径），而 `创建房间` 只出号＋出票 |

⇒ 结论：**调小心跳单独无效**（页面不重查照样看不见）；**页面自轮询单独也不够快**（仍受一跳心跳的窗口）。两条都要治。

本批只治①（客户端侧，改动面最小且决定性）；②的杠杆（心跳间隔／变更即上报）仍是配置面与后续批。

### 续批：把可见延迟压到 ≈3s（2026-10-18，同日）

**问题**：本批落地后最坏可见延迟仍是"节拍 3s ＋ 一跳心跳 ≤10s ＋ 首入座物化 ≈ 1s ≈ 13s"——两条独立旋钮，只调一个都不够（调心跳：页面不重查照样看不见；调节拍：仍受一跳心跳的窗口）。

**取舍（三个候选，选前两个）**：

| 候选 | 收益 | 成本/风险 | 结论 |
| --- | --- | --- | --- |
| A. 调小 `lobby.heartbeat_interval_ms`（配置面） | 窗口 10s→1s；**连带**drain 停止分配、`lastSeenAgeMs` 新鲜度同步变好 | 每实例 1 次 POST/s（载荷＝实例字段＋≤maxRooms 房明细行，~1KB）；内核允许下限 1000，Meta 存活时限 30s ⇒ 丢一跳无影响；零代码/零测试改动 | **取**（收益/风险比最高） |
| B. 客户端查询节拍（一个常量） | 把客户端侧的等待上限从 3s 压到 1s（**它是总延迟的地板**——服务端再快也要等下一次查询） | 空闲大厅页每秒一次 GET（Meta 内存投影、载荷 ~200B）；投影未变不重推 ⇒ 无条目重绑/滚动复位 | **取** |
| C. RoomServer「变更即上报」＋推送（服务端改动） | 与服务端心跳解耦（延迟只剩查询节拍），且随"变更数"而非"实例数"扩容——实例变多时是正解 | 要动 `LobbyRegistrationClient.Loop`（现为 `WaitStop(interval)` 单等待，须加唤醒句柄）＋ `ServerHost` 房间生命周期钩子＋去抖（开局 N 人进房会连发）＋ L1 用例；且**周期性心跳不能省**（Meta 的 TTL 与 drain 上报仍靠它），等于两套并存 | **不做**（相对 A+B 的边际收益 ≤1s，却引入服务端代码面与"漏报即不可见"的新失效模式） |

**落地**：`Config/roomserver.json` 与 `deploy/roomserver.container.json` 的 `lobby.heartbeat_interval_ms` 10000 → **1000**（容器形态原先缺该键、走缺省 10000，本批显式写明）；`Page_Lobby.lua` 的 `REFRESH_INTERVAL_SECONDS` 3 → **1**。**新口径**：最坏可见延迟 ≈ 1s（节拍）＋ 1s（心跳）＋ ~1s（首入座物化）≈ **3s**。

### 4. 边界与挂账（如实）

- **安全组（2026-10-17 补记：已放行并实测）**：用户已在控制台放行 `51820/udp`。**实测法（不装 WireGuard 也能验）**：读 `iptables -L ufw-user-input -v` 上 `dpt:51820` 规则的包计数 → 从开发机发 8 个 UDP 包 → 计数 **0 → 8 包 / 312 字节**，即数据包真的到了主机 ⇒ 安全组与 ufw 两层都通。`22` 目前仍对全部来源开放（含 root 登录），建议按 [09 手册 §1.1](../项目说明/09-上云联机测试.md) 收到管理 IP。
- **宝塔面板：用户裁决"隧道访问"，已落地并实测（2026-10-17）**：① ufw 改为 `8888/tcp on wg0`（**面向所有来源的那条已删**）＋ 清掉无监听的 `20/21/888`（FTP 系）三条陈旧放行；② 端口保持 **8888**（用户裁决，无需重启面板）；③ 面板实况（含**一次误判的更正**，留痕以免后人重走）——**HTTPS 专用**：`ssl.pl=True`，`http://` 探测得 000 是"用错协议"而非防火墙；**「访问 UA 验证」开着**（宝塔菜单项 30）：**无浏览器 UA 的 `curl` 一律 404**，我据此一度推断"面板没装 nginx/界面出不来"——**该推断不成立**：换浏览器 UA 后同一 URL 返回 **HTTP 200**（30579B 登录页，标题"阿里云 · 宝塔面板"），面板本体健康；根路径 `/` 404 属**安全入口**设计（入口路径见 `bt default`，本记录不回显）。**旁路入口（不依赖 WireGuard，已实测 200）**：`ssh -N -L 18888:127.0.0.1:8888 <host>` ＋ 浏览器开 `https://127.0.0.1:18888/<安全入口>` —— 隧道未起时这是进面板的最优路径，也是面板收敛后的破窗之一（比控制台 Web 终端更接近原生体验）。**提醒**：面板不再对公网开放，常规入口只有隧道内 `https://10.8.0.1:8888/<安全入口>`（待 peer 上线生效，届时 ufw 该规则计数开始增长）。**另发现未动**：`26372/tcp`、`39000:40000/tcp` 两条放行同样**无进程监听**（陈旧），提请用户裁决；`80/443` 亦无监听但宝塔后续建站可能要用，保留。
